# Chatwoot integration (dual identity)

fazer.ai agents talks to a Chatwoot account through **two token profiles over one HTTP client**, receives Agent Bot webhooks on a **dedicated receiver**, and obeys the rule **attribution = source of truth** (the bot acts only while no human owns the conversation). The agent runtime that decides replies lives in [`graph.md`](graph.md); this doc covers the transport, auth, provisioning, and gate.

Payload shapes, the HMAC scheme, the bot-token capabilities, and the ack/timeout behavior below were confirmed by reading Chatwoot's Agent Bot webhook source, not guessed: `lib/webhooks/trigger.rb`, `app/listeners/agent_bot_listener.rb`, `app/jobs/agent_bots/webhook_job.rb`, `app/presenters/conversations/event_data_presenter.rb`, `app/models/{message,attachment,contact}.rb`, `app/controllers/concerns/access_token_auth_helper.rb` (the `BOT_ACCESSIBLE_ENDPOINTS` allowlist).

## Client — two profiles (`src/modules/chatwoot/client.ts`)

`createChatwootClient(config, deps?)` validates the tenant-configured `baseUrl` once (anti-SSRF, https-only) and returns a `ChatwootClient`. Auth header is `api-access-token` (hyphenated so it survives reverse proxies that drop underscores — `CHATWOOT_AUTH_HEADER` in `constants.ts`); the conversation id in every path is the **display_id** (per-account, see below).

- **bot-token** — the whole gate loop: `sendMessage` (outgoing + `private:true` note), `sendPrivateNote`, `sendAudioMessage` (voice note), `sendTemplate` (HSM), `assignToAgent` (handoff), `toggleStatus`, `toggleTyping`, `setConversationCustomAttributes`. Chatwoot's `BOT_ACCESSIBLE_ENDPOINTS` (`conversations` → show / toggle_status / toggle_typing_status / toggle_priority / create / update / custom_attributes; `conversations/messages` → create; `conversations/assignments` → create) confirms the bot can do all of this; the upstream authorization issue #11985 does **not** apply to this build. NOTE: `show` is in that allowlist but only since **2026-06-05** (upstream #14655), so every conversation READ stays on the admin token — a bot-token read answers 401 on any older instance, and self-hosted Chatwoot versions are not ours to pick. NOTE: `toggle_typing_status` IS bot-accessible, so `toggleTyping` uses the bot token (the indicator is attributed to our bot, not the admin agent).
- **admin-token** — everything outside the bot allowlist: read history (`getConversation`, `getMessages`), the STT transcription write-back (`updateAttachmentMeta` — `attachments#update` is **not** in the bot allowlist), provisioning (`createAgentBot`, `setInboxAgentBot`), and labels — `assign_label` is scope-aware (`conversation | contact | task`), backed by `get/setConversationLabels`, `get/setContactLabels` (same `LabelConcern`, POST `{labels}` **replaces**, so the tool reads-then-appends), and `setKanbanTaskLabels` (PATCH `/kanban/tasks/{id}` `{task:{labels}}`, current set read from the kanban card snapshot) — plus contacts, agents, and the Kanban driver. Confirmed against Chatwoot's Kanban API: `GET …/labels → { payload: string[] }`, `POST …/labels { labels }` replaces the whole set (`LabelConcern#update_labels`).

**Handoff targeting** (`agent.settings.handoff`, read by `src/modules/handoff/settings.ts`): `route` (default — just `toggle_status open`, Chatwoot's inbox routing assigns whoever), `pinned` (assign a fixed agent/team after the open), or `agent_choice` (the model passes an `assignTo` NAME, resolved against the live lists at call time). `assignToAgent`/`assignTeam` reuse the bot-accessible `assignments` endpoint (`assignee_id` vs `team_id`); `listAgents`/`listTeams` (admin token) feed both the editor's picker (`GET /v1/chatwoot/agents-teams` → `listAgentsAndTeams`) and the `agent_choice` name match. Assignment is best-effort (a failure never breaks the turn — the handoff already happened). Confirmed against Chatwoot's API: `/agents` & `/teams` index render bare arrays of `{id,name,…}`; `POST …/assignments { team_id }` assigns the team (`AssignmentsController#set_team`).

`ChatwootApiError` carries `status` + `endpoint` and **never** the response body (it is customer PII / message content). On **401/403** it appends a reason, but only ever one drawn from a fixed allowlist of Chatwoot's own auth messages: parsing a body as JSON does not prove it came from Chatwoot (the base URL is tenant-configured, and anything in front of it can answer `{"error": …}`), so an unrecognized reason is reported as exactly that and the text is dropped. The allowlist exists because `render_unauthorized` answers `{error: message}` with **401** for both "Invalid Access Token" and "Access to this endpoint is not authorized for bots", so the status alone cannot tell a missing credential from a forbidden endpoint. A call made with an **empty** token never leaves the process: it raises `ChatwootMissingTokenError`, which says the client was built without that token instead of reporting Chatwoot's 401 for it. The base URL host is fixed per call; the DNS-rebinding caveat from `src/lib/ssrf.ts` applies (tracked).

## One Agent Bot per persona

The Chatwoot Agent Bot **is the message sender** shown in the conversation (its name + avatar), so each of **our** `Agent` personas gets its **own** bot: the model is **one `ChatwootAgentBot` per `(ChatwootInstance, Agent)`** (table `chatwoot_agent_bots`, unique on `(tenant, instance, agentId)`). Each bot carries its own `outgoing_url` (route token), HMAC `secret`, and `access_token` (used to post AS that persona). Chatwoot natively supports many agent bots per account, one per inbox (`AgentBot has_many :inboxes through :agent_bot_inboxes`; an inbox has at most one bot), so a persona serving N inboxes connects its single bot to all N.

Which persona handles a conversation is decided per inbox: the `Inbox` mirror row carries `agentId`. The receiver routes `inbox_id → Inbox.agentId → Agent`, and the runtime posts with **that persona's** bot token (resolved by `loadAgentBot`/`prepare.ts`). An event for an inbox we do not manage (`agentId` null) is a **no-op** on the wire: we ack 2xx and stay silent, never crash and never escalate. Silent to Chatwoot is not silent to the operator, though — the mirror creates that `Inbox` row for any inbox that sends traffic, so an inbox nobody bound accumulates real customer messages nothing will answer. A new incoming message that finds no agent therefore writes one `route` line (`{outcome: "no_agent", chatwootInboxId}`, level `warn`, `agentId` null and the mirrored `inboxId` naming what to repair) from either exit that reaches the state: the direct turn's `no-agent` outcome and the debounce flush's bail below its gate, both through `emitUnroutedMessage` (issue #318). See [`logs.md`](logs.md).

**Binding IS the wiring (no separate "provision" step).** Setting `Inbox.agentId` (the `PATCH /v1/chatwoot/inboxes/:id` → `bindInbox`) is the single operator action that wires an inbox end-to-end, and it keeps the Chatwoot side in sync: bind/switch (→ agent) lazily provisions **that persona's** bot (`ensureAgentBot`, named after the persona) and `setInboxAgentBot(inboxId, botId)` to connect it (Chatwoot's `set_agent_bot` replaces any prior bot on the inbox); unbind (agent→none) calls `setInboxAgentBot(inboxId, null)` to **disconnect** the bot (so Chatwoot stops delivering events that would otherwise strand new conversations as `pending` on a bot we ignore); rebinding the SAME agent is a no-op. The network side runs outside the tx; a Chatwoot/SSRF failure surfaces as a uniform 502 and we never persist the new `agentId`, so our state and Chatwoot stay consistent. One failure is not a desync: an **unbind whose inbox was deleted on Chatwoot** gets a 404 from `set_agent_bot`, and "no bot is connected to this inbox" is already true of an inbox that is gone, so the local binding clears instead of being stuck naming a persona for an inbox nobody can reach (#327). Renaming a persona propagates to its bot(s) via `renameAgentBots` (best-effort `updateAgentBot`; our row is the source of truth).

**Removing the mirror of a deleted inbox (`DELETE /v1/chatwoot/inboxes/:id` → `removeInbox`).** `syncInboxes` deliberately never prunes (a sync that cannot reach an inbox would otherwise delete a binding the operator configured), so an inbox deleted in Chatwoot leaves its row behind; this is the explicit action that trade-off assumes, and until #307 it did not exist. **The removal is fenced on Chatwoot answering that the inbox is gone**, and the fence is the feature rather than caution: the mirror recreates an `Inbox` row for any inbox that sends traffic (`upsertInbox`), so deleting the mirror of a LIVE inbox removes nothing — the next message rebuilds the row with no agent bound and the customer lands in `emitUnroutedMessage` with nobody to answer. So the row only goes when `getInbox` 404s (`remoteInboxIsGone`); a live inbox is refused with 409 and anything else with 502, because "we could not ask" must never read as "it is gone". A 403 in particular proves the inbox EXISTS: `fetch_inbox` runs `authorize @inbox, :show?` after the `find`. Nothing is written to Chatwoot and nothing needs to be — the inbox is gone, so no persona bot of ours is connected to it. Past conversations survive and stop naming an inbox (`Inbox.conversations` is `onDelete: SetNull`); `llm_usage.inbox_id` and `execution_logs.inbox_id` are bare columns with no foreign key, so past spend and past log lines survive with a dangling id and the dashboard renders them as an unnamed bucket. Whole-account cleanup remains `removeChatwootInstance`, which cascades the inboxes.

`display_id` is **account-scoped** (Postgres trigger `nextval('conv_dpid_seq_' || account_id)` + unique `(account_id, display_id)`), so it does not collide across inboxes within an account. The thread key `tenant:instance:display_id` is therefore collision-free without `inbox_id`.

## Webhook receiver (`src/modules/chatwoot/webhook.ts`)

Mounted at `CHATWOOT_WEBHOOK_MOUNT` = `/api/v1/chatwoot/webhook/:routeToken` (`src/api/v1/chatwoot.controller.ts`), JWT-less. The Agent Bot `outgoing_url` is derived from the **same constant** at provisioning time (`chatwootOutgoingUrl`), so the two can never drift — a 404 ack would make Chatwoot move the conversation `pending→open`. A unit test asserts the constant and a POST carve-out smoke proves the path reaches Elysia (never the SPA HTMLBundle).

Flow:

1. **Resolve** the per-persona Agent Bot by `routeToken` — a constant-time `SHA-256` probe on `ChatwootAgentBot.webhookRouteTokenHash` (cross-tenant ⇒ `asSuperAdmin`); the row yields tenant, instance, the persona's `chatwootAgentBotId` (the gate's "our bot"), and the HMAC `secret`. The instance's `disconnectedAt` comes back through the relation in the **same** query, not a second one. **Cached in process** (`route-token-cache.ts`, keyed by the hash, misses cached too), because this is the ack path: every query here is an interactive transaction competing for a pool shared with turns, ingest and compaction, and a slow ack costs the conversation (see below). The cache answers only what the process can still back up: fresh inside the 30s TTL; past it, served **and refreshed behind the ack** while the last lookup reached Postgres; past it with a *failed* lookup, a miss, so the ack blocks and fails honestly and Chatwoot's own retry ladder carries the event rather than a 2xx losing it (the payload is not stored, see Known limitations). Rule three is what keeps rule two truthful, and it costs nothing in the case rule two exists for: an idle instance on a healthy database. A request that arrives while a refresh is deciding waits on that one refresh instead of starting its own, and **inherits its outcome**: a refresh that could not reach Postgres fails all of them together, rather than resolving and sending each one down the blocking path to open its own transaction against the pool that just refused. Misses are held apart from hits and bounded, since an unknown token is what a prober loops on and this endpoint is public. Every writer that changes what a route token resolves to calls `invalidateRouteTokenCache()` **after its transaction commits** (provisioning/re-provisioning, connect, reconnect, soft-disconnect, instance removal, agent deletion, the last two because `ChatwootAgentBot` cascades), and a lookup that started before an invalidation is refused on write, so an in-flight read cannot resurrect what was just retired. The route token namespaces the bot, so multiple bots on one instance never collide. The plaintext lives only inside Chatwoot's stored `outgoing_url`; only its hash is in our DB, never logged.
2. **Authenticate after resolution**: verify the HMAC with the bot's decrypted `webhookSecret`. Scheme (verified against Chatwoot): `X-Chatwoot-Signature = "sha256=" + HMAC_SHA256(secret, "{ts}.{rawBody}")` in hex; `X-Chatwoot-Timestamp` = unix seconds (we enforce a ±300s anti-replay window); `X-Chatwoot-Delivery` = UUID. Unknown token and bad signature **all return the same uniform 401** (no oracle).
3. **Parse + normalize** the raw body (`normalizeChatwootEvent`, tolerant of both shapes: `message_created` nests the conversation under `.conversation`; `conversation_*` carries it at the top level). A non-event payload is `ignored` (still acked).
4. **Ack**, carrying the delivery id. **Nothing is written on this path** (see the ack budget below).
5. `recordAndProcessChatwootDelivery` runs **detached**: it writes the idempotency ledger row, then processes.

**The ack budget.** Chatwoot allows ~5s (`WEBHOOK_TIMEOUT`) and treats a slow or non-2xx ack as a bot failure. Since the bot only answers a `pending` conversation and `Message#reopen_conversation` never returns an `open` one to `pending`, an escalation there takes the bot off that conversation for as long as the customer keeps writing, while the turn itself may have completed correctly and had its reply discarded. That is why the resolution is cached and the ledger insert moved off this path: with both, a healthy ack needs **no** Postgres round-trip at all, so pressure anywhere else in the process cannot cost a conversation. Pinned by a test that hands the receiver a client which throws on `$transaction`.

**Idempotency ledger**: `ChatwootWebhookDelivery`, keyed by `(chatwoot_instance_id, delivery_id)`. A `delivery_id` is reused across the upstream's retries (transport dedup) but is fresh per distinct event. The ledger stores event name, status, two ids — the **conversation's display id** and the **inbound message id** — and one **shape** (`human_reply_shape`), but **not** the payload, which is PII; the normalized event is handed in-memory to the detached processor. The ids exist for one reason: they are what lets the stranded-delivery sweep tell a row that lost a customer's message from one that lost nothing. The shape answers the other half of that question, added by issue #439: whether the delivery owed a SIDE EFFECT — the human-reply takeover — which a row carrying no customer message can still have (see below).

A **redelivery is dispatched too**, and the CAS decides. The ledger row existing is not the same as the work having been done: the dispatch is detached and fires after the ack, so a process that dies in between strands the row on `PENDING` with nothing running, and Chatwoot, holding a 200, never sends that message again. Dropping redeliveries on the strength of the row would make that loss permanent. `processChatwootDelivery` opens with a CAS on `status: "PENDING"`, so a row already `PROCESSING`/`PROCESSED` matches nothing and returns `skipped`; nothing double-processes. (A crash *after* the CAS still strands the row on `PROCESSING`, and nothing on this path can close that window — the process is gone. What the **stranded-delivery sweep** below does is make sure it stops being silent.)

`processChatwootDelivery` does a CAS `PENDING→PROCESSING`, **mirrors the event metadata**, evaluates the gate, hands the normalized event to the runtime seam, then CAS `→PROCESSED`. Network/LLM work belongs **outside** the transaction (the runtime does it under `withEntityLock(threadId)` + a live re-read of the assignee before posting).

**Stranded-delivery sweep** (`delivery-sweep.ts`, issue #228): a per-tenant `DELIVERY_SWEEP` scheduler job, armed at boot and when a Chatwoot account is connected, self-rearming every 5 minutes, looks for rows still on `PENDING` or `PROCESSING` more than 30 minutes after the **current attempt** started.

The current attempt, not the receipt: tx1 stamps `claimed_at`, and the sweep measures a claimed row from that. A redelivery is deliberately allowed through to the CAS on a row stranded on `PENDING`, so a live attempt can begin long after the row arrived — dated to the receipt it looks abandoned the instant it starts, and the sweep would mark it `DEAD` and page an operator while the process answering it is still running.

Both non-terminal states strand, and for the same reason: the ack is spent before the ledger row is even written. A death between the insert and the CAS leaves `PENDING`, and #226's answer to that — a redelivery goes on to the CAS instead of being dropped — only helps when a redelivery actually arrives, which it usually does not, because Chatwoot holds a 200.

**The sweep does not answer the customer itself, and that is the design.** Recovering the turn means running one, and a turn run from a sweep is not the turn the delivery would have run: the flush machinery re-checks ownership and contact authorization itself, but the test-mode gate, the availability window and the redirect gate are applied by the delivery path and are gone with the process that died. A recovery that skips them replies out of hours, or on a conversation whose test mode was never activated.

**Delivery recovery** (`recover-delivery.ts`, issue #295): for each row it declares `DEAD`, the sweep arms one `DELIVERY_RECOVERY` job, and that job **re-runs the delivery path** — every gate runs where it already runs, because it is the same `processChatwootDelivery` a live delivery goes through. The body it needs was never stored (#228 keeps no payload at rest), so it is rebuilt from what survived: the **mirror** for two fields only, and **REST reads** for the rest — the message anchored `before: messageId + 1` so the page ends at it, and the newest page unanchored, because one page cannot hold both ends. `buildRecoveryPayload` shapes a webhook body and hands it to `normalizeChatwootEvent`, so exactly one place still knows how a Chatwoot payload becomes an event; the REST read's integer `message_type` is why `messageTypeOf` reads both spellings.

Re-firing the gates' side effects is safe, and the reason is **per gate** rather than one shared property. Availability posts behind a real CAS (`claimAwayMessage` claims the watermark before it posts, so a second invocation claims nothing). The test notice (`testNoticeSentAt`) and the redirect (`redirectSentAt`) are one-shot watermarks read before the act and written after it, which is weaker — they are safe for a recovery because a recovery is serialized against a live turn by the in-flight fence and against another recovery by the claim CAS, so its read is current. The residual window is a process that died *between* one of those acts and its watermark write: the recovery repeats it, which is a duplicate private note, or the fixed redirect link sent twice. Both are already reachable without a recovery, since the dispatch is detached and two live deliveries interleave the same way.

The claim is one statement: `processChatwootDelivery` takes `claimFrom: "DEAD"`, so the recovery's CAS is `DEAD → PROCESSING` with `attempts` incremented, and the winner owns the row — there is never a window where it sits `PROCESSING` with nothing holding it. `DEAD` is the sweep's verdict, reached by inference; a recovery that runs the turn is direct evidence, which outranks it (the same ordering a turn already uses when it runs over a `DEAD` row).

Bounded by four things. Two fences, both about the CONVERSATION rather than the row (a conversation with two stranded messages has two rows, so the row CAS says nothing about them): the **turn-in-flight fence**, asked of BOTH keys a turn claims — and the conversation key is then HELD to the handoff rather than merely probed, because a follow-up nudge needs no new customer message and reads exactly that key before it fires, so a probe would say nothing about one starting in the window between the answer and `runAgentTurn`'s own claim — the per-conversation one in this process's registry, and the per-contact-inbox GRAPH one in the thread's own row since #203 — so a recovery never runs beside a live turn, including one on another replica, and including a follow-up nudge, which claims only the graph key while posting into the conversation; built from the contact inbox the conversation is on at that moment rather than the one loaded before the REST reads; and a **per-conversation claim** taken with no await between the check and the add, so the two recoveries the scheduler claims in one tick do not both start a turn — `isTurnInFlight` cannot cover that, because a turn marks itself deep inside `runAgentTurn`, several awaits later. Then **`MAX_RECOVERY_ATTEMPTS` (3)**, because a recovery spends a model call and can call side-effecting tools; and **`MAX_RECOVERY_AGE_MS` (6h)**, measured from the ledger row's receipt, past which the reply stops being a late answer and becomes a stranger reopening a conversation that moved on — and which also keeps the free-form send well inside the WhatsApp 24h window the reactive path deliberately does not check. Finally, the job's two retrying outcomes take different roads because they wait on different things. A **busy** conversation (a live turn, or another recovery) **reschedules**, which clears the failure budget: a turn is deliberately unbounded — the sweep waits thirty minutes before calling one abandoned — while the scheduler's five backoffs are spent in about a minute, so failing here would burn a second stranded message's whole ladder while the first one's turn was still legitimately running. The rescheduling is still bounded, by the age ceiling. An **unreachable** account **fails**, so it backs off, dies at the scheduler's cap, and reaches the dead-letter line: that is a durable condition an operator has to fix, and it has to be given up on and said. **A reply WITHHELD does not close the loss either**: `superseded` is `shouldPost` standing down to a message the customer sent after this one, which for a live delivery means the newer message's own delivery carries the reply — a recovery cannot lean on that, because the newer delivery can have finished before this turn ingested the stranded text. It is the sliver the freshness check before the claim narrows and cannot close, so the row goes back to `DEAD` and the job completes: nothing is broken, the message lost its race, and the next pass refuses it at the freshness check. **A turn that THREW takes a different road**, and it is the one thing the delivery path cannot say in its return value: `"processed"` is about the ROW, and for a live delivery it is honest (the failure is recorded on the conversation and announced inside Chatwoot, and there is no retry to arm), while a recovery exists to answer — so it asks for the distinction explicitly (`onTurnFailure`, opt-in, so the live caller's contract is untouched), puts the row back to `DEAD`, and writes NO closing line. The attempt stays spent, because the claim stamped it. Measured before that: the model threw, nothing was sent, and the recovery still reported `recovered` with the row on `PROCESSED`. That backoff does not reach the dead-letter line, and it is worth knowing which cap wins: `MAX_RECOVERY_ATTEMPTS` (3) is lower than the scheduler's five, so a turn that keeps throwing exhausts the ROW first and the job then completes. The record is a `warn` line saying the recovery was given up on, plus the row itself, which stays `DEAD` on the page the sweep already opened. The dead-letter line is still the outcome for an **unreachable account**, which refuses before the claim and therefore spends no attempt at all.

One process death can strand a **burst** — two customer messages on one conversation are two `DEAD` rows. The newest row's recovery answers the conversation, ONCE; the older rows refuse on the newest-message check and stay `DEAD`, so the pages an operator already received about them stay open, and the refusal line says which case it is (a live delivery covers the newer message, or the newer message is stranded too). What is lost is the older messages' TEXT: a direct turn carries its own trigger text and nothing back-fills the channel from Chatwoot, so the model answers the last question and never reads the earlier ones. With coalescing on this does not arise, because the flush re-reads the conversation's messages and gathers the burst; gathering it here would be this module re-implementing the flush, which is the one thing its design refuses to do.

Three things are checked between the REST reads and the claim, all failing closed: the age again on the **message's own** `created_at` (the row's `receivedAt` is when *we* inserted it, so a webhook delayed by a Chatwoot retry can be hours older than it looks); that the rebuilt event is still `isNewIncomingMessage` (the ledger row proves it was one, so anything else means the REST read lost something — and handing that to the delivery path marks the row PROCESSED with no turn and closes the loss on a customer still waiting); and, if the delivery path *throws* after its claim, the row is put back to `DEAD` under a CAS guarded on `PROCESSING`, so the retry finds a row it can claim instead of one that reads as somebody else's.

**A control command is never replayed.** Re-running the delivery path assumes it did not complete, not that it did nothing: `/reset` performs its deletion before the tail settles the row, so a replay would delete the memory the conversation has accumulated since. Refused rather than made idempotent, because its author is an operator who is present and can retype it, and the row stays `DEAD` in the worklist so they see they have to. That is the one class of effect this refuses; the general property is **at least once** — a turn whose tools had already fired is re-run and fires them again, and nothing in the ledger records how far the dead process got.

A voice note the dead process had already transcribed costs nothing to recover: `Attachment#push_event_data` renders `transcribed_text` at the top level for `file_type: audio`, and the REST view calls that same method (MEASURED live), so the rebuilt body carries it exactly where the eager-STT pass reads it — and that pass reuses it rather than transcribing again.

The conversation's **state** comes from a live `GET /conversations/:id`, not from the mirror, and that is the one place a recovery cannot trust the mirror: the delivery that would have mirrored this message is the one that died. An incoming message on a `resolved` conversation reopens it (`Message#reopen_resolved_conversation`: `pending` on a bot inbox, `open` otherwise), so the mirror still says `resolved` while Chatwoot says otherwise — and copied into the body, that makes `shouldBotHandle` refuse a delivery that would have been answered. The snapshot goes through `reconcileMirrorFromLive`, so the mirror is **repaired** under the same ordering rule the webhook mirror uses (a webhook committed between the GET and the write still outranks it), and the body is built from the row that call returns. A snapshot `parseLiveConversation` cannot trust is a deferral, never a fallback to the mirror. Two fields still come from the mirror. `contactInboxId`, because the REST conversation renders no `contact_inbox`; and `redirect_origin_display_id`, because the fork renders it from `EventDataPresenter` only and the REST show does not carry it at all (MEASURED both ways). The second one has to travel: `processChatwootDelivery` arms the `REDIRECT_FOLLOWUP` ladder from the EVENT's `redirectOriginDisplayId`, so a body that omits it arms nothing — and a body that states no pairing *clears* one, on a row that already knew it. It travels **with its version** (`chatwootRedirectOriginAt`, sent as the body's `updated_at`), because on the wire the pairing and the `updated_at` that orders it are one fact: stated without a version, the old pairing outranks nothing and a widget re-entered from a second WhatsApp thread while the recovery was doing its REST reads would have its new episode overwritten by the old one.

**A recovery answers only while its message is still the newest thing the customer said**, and that bound is the delivery path's rather than this module's: `shouldPost` re-fetches immediately before posting, sees a newer incoming id and withholds the reply, so the turn comes back `superseded` while the row is settled all the same. For a live delivery that is right — the newer message's own delivery carries the reply. For a recovery the premise is gone: that delivery already ran, and a direct turn feeds the graph its OWN trigger text, so the stranded message was never seen by anything (its ingestion is the turn its delivery died before reaching). So the recovery asks the same predicate (`maxIncomingId`, on the unanchored page) **before the claim** and answers `unrecoverable` — no attempt, no model call, and the row stays `DEAD` in the worklist, which is the honest place for a message this design cannot answer. Only what the CUSTOMER said counts: an away message or an operator's note moves the conversation forward without answering anything. That page has to **reach back to the stranded message** to answer at all — one unanchored page is the newest twenty, so twenty outgoing or activity messages since the strand would push a newer customer message off it and the check would read as "nothing newer"; a page that never reaches back means the conversation moved more than a page since, and the row stays `DEAD`.

**A route whose agent has no `ChatwootAgentBot` is refused too**, and it is the one null this module must not pass on: `heldByAnotherParty` compares ids, so with `ourAgentBotId` null it cannot, the ownership gate goes loose, and a conversation another AgentBot holds reads as ours. A live delivery never reaches that — its `agentBotId` is the route token's bot, and the route exists because the bot does. Nothing could come of it anyway: the reply is posted with the persona's token and a client built without one refuses the call by name (#79). An inbox bound to NOBODY is a different state and still runs the path, because that is what writes the operator's `no_agent` line (#318).

The body carries the customer's own clock (`last_activity_at`, from the REST message's `created_at`), because `lastInboundAt` is advanced from it and the mirror falls back to `now` when the body says nothing — so a message the REST read returns WITHOUT a `created_at` is refused as a degraded read rather than replayed with no clock — a recovery would otherwise push the 24h window's anchor forward by however long the row sat stranded. That clock also puts the rebuilt body BEHIND a conversation whose activity moved on after the strand (an away message posted since), which is where the mirror's stale branch was dropping the watermark entirely: `lastInboundAt` is now **monotonic** rather than decided by that ordering, written whenever the payload is ahead of what is stored and never backwards, because what a stale delivery lost is the order of the conversation's STATE and the watermark is the time of a customer message. A successful recovery also writes its own **closing line** (`outcome: "recovered"`, `warn`, on the conversation): `retireCoveredDeliveries` corrects only rows it moves out of `DEAD` itself, and a recovered row left `DEAD` at the claim, so without this the row would leave the worklist while the page an operator already received stayed open. The **route** comes off the REST message (`inbox_id`, rendered on every message the index serializes), not off the mirror's `Conversation.inboxId` — and it is **written back onto that column** when the column is null, which is a repair rather than a convenience: only `runAgentTurn` reads the route off the EVENT, while `maybeConsumeCommandOrGate` resolves the agent from `Conversation.inboxId`, and with that column null it finds no agent and returns having run nothing — not the test-mode gate, not availability, not contact authorization — while the turn runs anyway. Measured: a test-mode agent on a never-activated conversation answered a real customer. The mirror's own write cannot be relied on for it, because that column moves only when the event WINS the ordering, and a rebuilt body is stale by construction whenever the conversation moved on after the strand: that column is nullable and stays null for a conversation whose mirrored events never named an inbox, and a body with no inbox makes `runAgentTurn` return `skipped` on its first line — no turn, row `PROCESSED`, loss reported closed. The mirror is the second reading, for an account that renders no such scalar; a rebuild that can name no inbox on either is a degraded read and stays `DEAD`. Which bot answers is then **derived** from that route — inbox → agent → `ChatwootAgentBot` — never stored: Chatwoot fans one message to up to two bot routes, so "the route it came from" is not "who should answer it now".

What the sweep does close is the other half of the harm, completely. Every stranded row becomes terminal, and **which** terminal state says what happened: `PROCESSED` when nothing was lost, `DEAD` when a customer message went unanswered.

**Takeover recovery** (`recover-takeover.ts`, issue #439): benign about the customer's message is not the same as "nothing was owed". Since issue #430, the delivery that carries a COLLEAGUE's reply — from the composer or the paired phone — is what steps the agent off the conversation, and that delivery carries no inbound message id, so the classifier read it as benign and the sweep closed it with no replay. The conversation then stayed `pending` and still the bot's, and the next customer message drove a full turn: the agent answering over the person, which is the defect #430 exists to close, surviving in the crash window. It self-healed only by repetition, when that person replied again.

Neither neighbouring verdict fits, in opposite directions, which is why it is a verdict of its own (`owed-takeover`). Closing the row replays nothing, and that was the defect. `lost` is wrong twice over: it marks the row `DEAD`, and that is a worklist for customers who wrote and were never answered, which a colleague's own reply has no place on; and `writeFlowEvent` DISPATCHES its alert as it writes, so it would page an operator about a message nobody lost, and it would arm a `DELIVERY_RECOVERY`, which spends a model turn answering a reply that was ours. So the row is closed `PROCESSED`, no line is written, and one `TAKEOVER_RECOVERY` is armed instead — a kind of its own because the four per-kind policies in `lanes.ts` answer differently for it, starting with the one that matters: it reaches no model.

What the ledger stores is the **shape** the payload had and not the route: `device` is also what an unmatched echo of our own reply looks like on a provider that does not reserve its send ids, and only the inbox row tells the two apart (`providerReservesEchoIds`). The recovery asks that half itself, against the inbox as it stands then, and re-reads the agent's mode and takeover switch the same way. It then runs the takeover through the SAME unit the live delivery runs (`human-takeover.ts`, extracted for exactly this reason) — the fence, the local claim, the toggle, the reconcile — rather than a second implementation of a fence whose every clause was paid for by a measurement. The delivery path is not re-run because it takes a webhook body, and the body of an outgoing message is the one thing that cannot be rebuilt: only a new INCOMING message's id is stored, so a synthetic body would drive the continuous ingestion with content nobody wrote.

**The changeover has a window, and it is one-sided.** The release before this one performs the takeover and writes neither new column, so a delivery it inserted and then lost to the very restart that deploys this one carries a conversation id and nothing else — the classifier reads it as the benign `no-message` it has always read and arms nothing. For those rows the behaviour during the changeover is the behaviour before the fix: no row is made worse, some are not yet made better. No backfill can close it, because the shape is a fact about the event body and the ledger deliberately stores none.

The ledger also carries **which bot route** the delivery arrived on. Chatwoot fans a message to up to two routes — the conversation's assignee bot and the inbox's — and only the route holding the conversation passes the gate, so a recovery that resolved the identity from the inbox would ask a stricter question than the delivery did and refuse the takeover on exactly the conversation another persona's bot holds. Rows written before that column fall back to the inbox persona, which is safe in one direction only and that is the direction it needs: a wrong identity can only make the fence answer "not ours".

**A toggle that threw is finished rather than refused.** The claim is written before the toggle deliberately, so an attempt whose call failed leaves the row `open` under a live claim while Chatwoot may still say `pending` — and the ownership fence, asked again, reads our own write as somebody else having moved the conversation on. The recovery therefore asks first whether the row carries its own unfinished claim (`open`, live deadline, `pending` as the status it replaced) and, if so, retries only what is left: the toggle and the reconcile, skipping the fence our claim would now fail and the claim that is already ours. Both directions are idempotent — a conversation Chatwoot really did leave `pending` moves, one it had already opened is set to the status it holds — and past the deadline the row means something else, so the fence is the right question again.

**It carries no version, and that is the one place it deliberately differs from the live path.** There the takeover compares the payload's `conversation.updated_at` against the row's status mark, so a hand-back committed after the reply outranks it — the two `pending`s are otherwise identical. Carried here, that check refuses nearly everything: `chatwoot_status_at` is a version, so it advances on every payload that DECLARES a status, the customer's own next message included, and a conversation the customer wrote on in between is precisely the conversation where the agent has been answering over a person. A version is not an identity, and a mark that advances on redeclaration cannot serve as one. What the recovery has instead is that it holds no frozen snapshot at all: it reads the state now and writes one statement later under a CAS on what it read, so "does the state now allow this" is the whole question. The cost, named: a hand-back that lands inside the sweep's window is undone and the operator clicks "Return to AI" once more — the same class of gap as issue #469, erring in the direction a fence must err in. There is also **no age ceiling**, unlike the delivery recovery: that one sends a reply, which goes stale; this one writes a status, and a conversation the agent is wrongly holding stays wrong however long the queue was.

Nothing was lost when the delivery could not have carried an inbound message, and that is asked of the **event name** first: Chatwoot sends an agent bot far more than messages, and `normalize.ts` reads a conversation id from nothing but the two shapes that are a conversation or a message (issue #257), so a contact being created reaches the ledger with both ids null. The event name is the one column every build has written, so it answers before any question about the ids does. Below it, nothing was lost when a message event carried no inbound message — read only on a row whose build was recording one. A row this build never touched is reported rather than closed, because its nulls are **unrecorded** and not "nothing was there" — during a rolling deploy the previous release keeps serving while the new one migrates, and it writes none of these columns. Two signatures, one per state, because each state promises a different column: tx1 stamps the claim on every row this build works, so a `PROCESSING` row without one came from an older build; nothing has claimed a `PENDING` row, so what speaks there is the conversation, written at insert for every event that reaches the ledger.

The backfill leaves rows younger than the same 30 minutes alone, for the same reason: it runs while the previous release is still serving, and a row that release inserted seconds ago is about to be claimed by it. Closed by the migration, that `PENDING → PROCESSING` CAS matches nothing and the upgrade itself discards a live customer message. Everything else that is still non-terminal at that age is terminal by rollout, and **which** terminal state is the same question the classifier asks first: `event` is not one of the columns the migration adds, so a conversation update, our own media write-back and a widget being triggered are closed rather than reported, and only a legacy `message_created` — ambiguous because neither id column is backfilled — lands `DEAD`. Measured against the local fork (4.16.0) by pointing a real Agent Bot at a capture endpoint: `AgentBotListener` dispatches exactly seven events (`conversation_resolved`, `conversation_opened`, `conversation_status_changed`, `conversation_updated`, `message_created`, `message_updated`, `webwidget_triggered`), and `webwidget_triggered` is the only one whose body is not a conversation — it carries a contact_inbox, so it is the only event a CURRENT build files with both ids null. There is **no watermark arithmetic left in the decision** — that is the design, arrived at by deleting three successive versions of it.

**The turn says what it covered, on the row.** When a flush answers a burst it retires the ledger rows of the messages that burst contained (`retireCoveredDeliveries`), the gate exits that consume a burst without a turn retire everything up to the id whose watermark they advance, and the receiver settles its own message the moment its fate is decided rather than waiting for tx2 (after advancing the watermark, never before: a death between those two writes must leave a false line in the loss list rather than a message that is terminal on the ledger and still below the watermark, which a later flush would answer) — on **every** outcome, where the flush holds two of them back. The same word means different things on the two paths: `superseded` on a flush hands the burst to a re-armed flush that will answer these same messages, while on the receiver the graph has already run over the message and it is the newer message's own delivery that carries the reply, so a row left open there is a lost-message alert every time the process dies in the tail after a deliberate supersede. `stale` arises on the receiver too, and settles like the rest: nothing queued that turn, so what calls it off is the EPISODE the message belongs to (`Conversation.resetAtMessageId`, see below) rather than a job, and leaving the row open would have the sweep replay the message into the conversation the command just cleared. This normally updates nothing: a delivery that completed already reached `PROCESSED` on its own. It matters in exactly the case that makes the sweep hard — a burst re-read from Chatwoot can contain a message whose own delivery died mid-processing, and rescuing those is what re-reading the thread buys. Retired there, a row still sitting non-terminal is one nothing covered, which is a fact about the row rather than an inference.

The write is keyed by **account, conversation and message** (display ids and message ids are numbered per Chatwoot account) and takes **`PROCESSING` and `DEAD`** — except where **another AgentBot** holds the conversation, and there it narrows. Chatwoot fans a message to up to two routes (`agent_bots_for` returns the conversation's assignee bot and the inbox's, each with its own delivery id), so the other bot's delivery for the same message may be `PROCESSING` right now, and retiring it would take a live loss out of the list: the receiver settles only its own row, and the flush's gate exits retire nothing at all, having no row of their own to name. A **human** holding the conversation is the opposite — they answer the message whichever route carried it — and keeps the wide key, as does any gate that consumed the message while the conversation was still ours. Every road that gives the row back writes it through one place, which RETRIES and reports three answers rather than two: restored, moved (something else took it, which is fine), or failed. The last one is never swallowed, and what it costs depends on the state left behind — `PROCESSING` is revisited by the sweep, while `PROCESSED` is looked at by nothing, so a failure there is said at `error` as a row needing an operator. Claiming from `DEAD` takes the LEDGER back and revokes nothing: a handler the sweep called abandoned holds no lock this side can take away. The overlap that matters — two invokes — is fenced all the same, because a handler already inside `runAgentTurn` holds the thread's durable claim (#203) and the recovery asks the row for it before handing over. `DEAD` is a correction rather than a contradiction: the sweep reaches its verdict by inference — nothing has moved this row — while a turn that ran over the message is direct evidence, and it wins. A row corrected that way leaves the worklist and gains a second `delivery` line next to the one that reported the loss, because the alert for it has already gone out and cannot be recalled — `answered_late` when a reply actually posted, `consumed_late` when the message was taken deliberately (a gate, an empty model reply, a human taking over mid-turn). Which one it is comes from the caller, since only the caller knows. The two writes are separate statements, the `DEAD` one returning what it moved, so the correction cannot be lost to a row turning `DEAD` mid-read nor written twice by concurrent retirees. Never `PENDING`. That last one is the state whose owner has not arrived yet, and a burst legitimately contains a message whose own delivery is sitting between its ledger insert and its opening CAS. Retiring that row would make the delivery's CAS match nothing and return `"skipped"`, so its mirror write never runs and `lastInboundAt`, the contact and the attribute bags stay behind — preempting a delivery rather than rescuing one. The case that leaves out is a delivery that died in the sliver between its insert and its CAS: it is reported as a loss even though a later burst answered it.

The three deleted versions all compared the stranded message against a mark on the conversation, and each failed differently: `>=` closed the crash window between the post gate's claim and the send; the handled watermark closed every message a later *deliberate skip* advanced past (a human takeover, a failed authorization), which is the most likely companion to a strand since a deploy causes both; and a dedicated "answered" high-water mark still closed a message a later burst **excluded**, because the skip had raised the burst's floor above it. The shared reason is that a watermark is a per-CONVERSATION high-water value and this is a per-MESSAGE question, so no scalar reading of it can be right.

`SELECT ... WHERE status = 'DEAD'` is the list of customers who are **still** unanswered, and each one also leaves an error-level `delivery` line on the conversation — what the Logs page renders and the alert channels dispatch. The row is retired **before** that line is written, deliberately: `writeFlowEvent` dispatches the alert as it writes and nothing can retract it, so a line written first pages an operator every time a redelivery claimed the row in between.

Two windows are known and left open. A turn that outlives the 30-minute threshold (nothing bounds a model call or a tool) has its row judged abandoned and its loss dispatched while the process is still working; the turn then completes and tx2 writes `PROCESSED` over the verdict **by id**, so the row ends up true and only the alert was wrong. And the legacy `message_created` rows the migration reports at rollout land in the DEAD list without a line or an alert, because both id columns are added by that same migration and nothing there knows what those rows carried — they are the ones matching `status = 'DEAD' AND conversation_id IS NULL`.

The ledger carries two ids and a timestamp for this and nothing else: the conversation, the message the delivery was about, and when the current attempt claimed the row. The second is written only for a **new incoming** message — the exact set that drives a turn — so a conversation update, the bot's own reply coming back as a `message_created`, and an incoming `message_updated` (usually our own media write-back coming around) all leave it null and none of them can put a row in the loss list.

**Losing the gate** is reported as two different things, because it is two different events: `handoff` with `outcome: "taken_over"` when a **human** holds the conversation, and `outcome: "ownership_lost"` with the observed status for anything else (most often Chatwoot auto-escalating `pending → open` after a slow ack, sometimes another party's bot). Both mean the bot stays silent, but only one of them means somebody took over. The reading is one unit, `describeClosedGate` (`src/modules/chatwoot/gate-close.ts`), because **three** gates close on that question and an operator filtering the log for one outcome has to get all three: the webhook on each event, the debounce flush before the turn, and the post-LLM recheck before posting. Which one a case reaches is a matter of timing, and the escalation reaches the first two rather than the last — it lands seconds after the ack, so no turn ever starts (issue #271). The webhook's line is deliberately narrower than its branch: one row per **new incoming customer message** on a closed gate, and none for a disabled agent, so the trail stays one line per message the bot did not answer instead of one per webhook event.

## Mirror sync (`src/modules/chatwoot/mirror.ts`)

`mirrorChatwootEvent` upserts conversation/inbox/contact **metadata** (no message body) into our DB, powering the UI conversation list + read API and giving the runtime fresh state to route on. It runs for every event (not only actionable ones), before the gate.

- **Contact** and **Inbox** upserts are atomic (`INSERT ... ON CONFLICT DO UPDATE`, safe under concurrency, never abort the tx). Contact keys on `(tenantId, chatwootContactId)` (the unique added by the `contact_chatwoot_unique` migration); Inbox on `(tenantId, instanceId, chatwootInboxId)`.
- **Conversation** is a read-modify-write serialized per conversation by `withEntityLock(threadId)` and guarded **monotonically**: an event whose `last_activity_at` predates the stored `lastEventAt` is skipped, so out-of-order deliveries (Chatwoot does not guarantee order) cannot regress status or assignee. `prevAssigneeId` is captured before the overwrite for the REENGAGE flow.
- **A reopen is ordered too** (#295): a brand-new incoming message is the one status transition a message reports faithfully, but faithfully AT ITS OWN INSTANT. Every payload is a snapshot of an earlier moment — Chatwoot freezes its own at enqueue, a delivery recovery rebuilds one from reads made a moment before — so a message serialized before an operator's resolve used to walk the status back to `pending` after it. `last_activity_at` is compared against the stored status mark at WHOLE SECONDS: the mark is `updated_at` and carries a fraction that is always a little ahead of the message it accompanies, so a raw comparison would refuse every same-second reopen (the burst below). And the **gate reads the status the mirror settled on**, not the one the payload proposed: a payload can be applied and still have its status refused, and acting on the proposal is how a conversation somebody had just closed got answered.
- **A recovery holds BOTH in-flight keys across the handoff** (#295). The conversation key is what a follow-up nudge and a second recovery read; `/reset` asks a different question (`threadBusyForResetOn`, which reads the GRAPH key and the durable claim) because it is about to delete the memory and the checkpoint, and it refuses while anyone is mid-write. Held only on the conversation key, the stretch between the mark and the turn's own claim was invisible to that question: a reset landing there saw an idle thread, cleared it, and the recovery then ran the turn that restored what the operator had just erased. The window holds the mirror write, the ownership gates, the contact-authorization call and the spend ceiling, and the last two reach the network. The two holds are taken as RESERVATIONS rather than as invokes: every writer asks `isTurnInFlight`, which counts both, while `markTurnOwning` asks `isTurnRunning`, which counts only invokes — it is deciding whether ANOTHER invoke was already reading the thread, and counting the recovery's own hold answered that about the caller itself, so a recovery starting a NEW conversation on a contact thread that already had one ran the model against the previous attendance with no divider between them and left the marker on the old conversation (measured). Both maps count rather than set, so the turn taking the same key a moment later is an increment. Both live in THIS process, though, and the claim that crosses replicas is not taken until `runAgentTurn` takes it — so a reset served by a second web replica reads neither, and the DIRECT path holds nothing at all there, on one replica as much as on many.
- **What that window actually costs is a turn that ACTS after the clear, not memory coming back** (#428, measured against the test database). The erasure holds: the reset's `SELECT … FOR UPDATE` on the thread row blocks `markTurnOwning` for the whole of its transaction, the checkpoint delete included, and the turn reads the channel only AFTER that claim (`READ AFTER THE CLAIM, never before it`), so it loads what the command left — measured, zero messages, zero summaries. The reply does not land either: `/reset` is itself an incoming message, so its own delivery advances the handled watermark past this turn's trigger and the supersede gate refuses the post. What nothing asks is the TOOLS. Measured with the command landing in the delivery path's own client build: the acknowledgement says the conversation was cleared, and the turn then calls `set_custom_attribute` and writes the attribute back onto it. So the fix is the call-off every other caller already has — a job retires theirs, and the direct turn has none — keyed on `Conversation.resetAtMessageId`: the Chatwoot message id the COMMAND carried, and the id of the message the turn is answering, compared in the source's own sequence (`src/graph/reset-episode.ts`). Not a moment of ours, and that took three review rounds to land: the turn's own config load, the mirror and the delivery ledger are each later than the last, and the ledger row is inserted on the detached path after the ack, so it does not even preserve the order two events arrived in. Written with `GREATEST`, because two `/reset` deliveries are not serialized either.
- **The fence above is asked BETWEEN steps, and a tool call happens inside one** (#449). The command landing once the model call is in flight is refused on its memory step by `threadBusyForResetOn`, says so in the acknowledgement, and clears everything else it can reach — and then the turn's tools write an attribute, a label and a kanban card back onto exactly that. The ask therefore also runs at the TOOL BOUNDARY: `runLoadedTurn` hands its fence to `buildAgentGraph`, which asks it once per tool-calling hop, before the node that every tool source passes through (native, HTTP, MCP, integrations, documents — a guard per tool would leave the tool added next week without one). A called-off hop answers each pending call with a refusal `ToolMessage` and ENDS the turn: routing away instead would leave an assistant turn whose `tool_calls` nothing answers, which the next turn replays to the provider and the thread stops working (see [`docs/graph.md`](graph.md)); answering back into the model would invite it to call the same tool again to the recursion limit. And an unreadable mark lets the tools run rather than throwing — measured against the real checkpointer, a throw from that node leaves the thread `[human, ai(tool_calls=…)]` with no answer, which is the broken sequence the refusal exists to avoid. The two windows this does not close are named in the issue: a conversation with no contact inbox skips the memory step, so nothing refuses and the acknowledgement claims a clean slate — the boundary is still written by the step before it, so the tools are still fenced — and the failure list names the memory step alone.
- **A turn that SETTLED the message closes the loss; one that answered nobody does not** (#295). The recovery asks a POSITIVE list — `posted` and `taken-over` — because the question is "is this customer still owed a reply" and the honest default for an outcome nobody has considered is yes. `empty` is the one that made the rule necessary: for a live delivery it is a complete outcome (the agent chose not to speak, the event is handled), but a recovered row exists BECAUSE the customer was left waiting, and an empty second attempt leaves them waiting with nothing on the way. `no-agent` and `agent-unavailable` join it — both write their own operator-facing line and both need an operator, and what they must not do is take the message off the worklist that operator reads. `taken-over` is the one non-`posted` close: a human holding the conversation will answer it, whichever route carried the message here. `blocked` is the third settling outcome and the line between it and `empty` is WHO decided: a guardrail tripping with `action: "silent"` is the operator's own policy saying this message must not be answered (the runtime calls that a consumed burst), and a re-run reproduces the same refusal, while `empty` is the model having run dry, which a second attempt could legitimately answer differently.
- **A rebuilt body carries no contact identity, and that is a position problem rather than an availability one** (#295). The live conversation DOES render `meta.sender` with `phone_number`, `email` and `identifier` (measured at the fork: `conversations#show` renders the full contact partial), so a recovery could state it. It may not: the mirror positions identity per field by the payload's `last_activity_at`, and a rebuilt body's is the stranded message's own clock, so an identity read now would be stamped with a clock from then. Measured — with the contact positioned at that same second by a sibling of the same burst and the live phone now different, the tie rule empties the field, and the contact reads as `no_identity` at the fail-closed gate that carrying it was meant to protect. One payload has one clock and it also orders status, assignee and the inbound watermark, so there is no second position to carry identity on. The exposure that remains is bounded by the next event on the conversation, which carries the identity at its own clock.
- **A live snapshot is applied immediately, never held across other calls** (#295). `reconcileMirrorFromLive` orders by the conversation's own version where both sides have one and falls back to `last_activity_at` where they do not — and that fallback cannot see a handoff or a resolve, because neither advances that field. So a snapshot held across two REST reads let a takeover committed inside them be written to the mirror and then walked back by the older bot-owned snapshot. The proactive nudge and the console's buttons already reconciled in the statement after their GET; the recovery was the one holding it, and it held it longest.
- **The gate believes whichever witness says the conversation is HELD** (#295, `effectiveAssignee` in `src/modules/chatwoot/normalize.ts`). Two assignee readings reach it: the payload's frozen snapshot and the mirror row as it stands after this event. Neither is uniformly newer, so the choice is made by which way a wrong answer fails. Believing "somebody holds it" can only cost silence, since the releasing event is conversation-level and applies when it lands; believing "nobody does" costs an answer posted over a human, and posted is the smaller half of it, because the runtime's ownership re-check runs AFTER the model call, so the turn has already run every tool it chose. The asymmetry is the mirror's own rule read from the gate's side: a message may never write the assignee at all, so a mirror reading human-owned under a bot-owned payload is the mirror doing its job. The gate used to prefer the payload wherever it spoke, and every payload speaks.
- **Same-second regression fence (status)**: the monotonic guard is second-granular and strict, so it cannot order events sharing one `last_activity_at` (a "reply + resolve" macro; a resolve never advances the field by itself). Message payloads are additionally **frozen at enqueue** by Chatwoot's `AgentBots::WebhookJob` — a delivery retry re-sends the pre-resolve snapshot. So only a BRAND-NEW incoming message (`message_created` + `incoming`, i.e. `isNewIncomingMessage`) may move a stored `resolved`/`snoozed` back to `pending`/`open`. Every other message event is fenced — an outgoing cannot reopen a conversation in Chatwoot, and a `message_updated` of an incoming message (our own STT/vision write-back) carries the same frozen snapshot. The fence also preserves the stored assignee fields. Legit reopens still apply: a new incoming message (ReopenService) and every `conversation_*` event. This staleness is what once made follow-ups fire on operator-resolved conversations.
- Field sources (verified against Chatwoot): contact ← `meta.sender`; inbox name ← message-event `inbox.name`; `channel` ← `EventDataPresenter` conversation `channel`; `last_activity_at` ← push_timestamps.
- **Resolution origin.** `Conversation.resolvedBy` records WHO closed a conversation, written by the four paths that close one themselves (`agent` for `resolve_conversation`, `followup_abandonment`, `redirect_closing`, `console`). Chatwoot never tells us: an operator resolving in its UI, an automation rule, and `auto_resolve_after` all arrive as a plain status change, so those stay NULL and the dashboard treats an unattributed close as not the agent's. Confirmed on 4.17.0: an operator's resolve leaves `meta.assignee_type: "AgentBot"`, i.e. no human, which is exactly what the old inference read as "the AI resolved it". Chatwoot also never reports a TRANSITION (`toggle_status` answers `{success, conversation_id, current_status, snoozed_until}`, and `success` is `save!`'s return), so the stamp carries `resolvedByAt`, the status version the closing caller observed, saying WHICH close it is about. When the stamp dies is one rule, `clearsResolutionOrigin`, asked by this mirror and by the live reconcile: the conversation left `resolved`, or a close of ours stated `resolved` and lost the ordering, or a brand-new incoming message reopened the episode — the last two guarded by that version floor so a retried delivery cannot erase a close made after it. The console is the exception and does not consult the ordering: an operator commanding a non-resolved status is a command, so it clears on both of its write paths. See `src/modules/conversations/resolution-origin.ts`.
- **Custom attribute bags** are mirrored too (`Conversation.customAttributes` / `Conversation.kanbanAttributes` / `Contact.customAttributes`) — see the attribute-context section below. Chatwoot ships the WHOLE jsonb on every event, so each is **assigned wholesale**, and only when the payload actually carried it (a degraded payload never wipes the stored snapshot). A stale event (monotonic guard) skips them like everything else. The conversation bags are covered by the conversation's own `lastEventAt` guard (they are written inside the per-conversation lock, past the stale check); the CONTACT bag cannot be, because the contact upsert runs before that lock (the conversation row needs the contact id) and one contact is shared by all its conversations — so it carries its own source watermark, `Contact.customAttributesAt`, and the write is a single compare-and-set `UPDATE … WHERE custom_attributes_at IS NULL OR custom_attributes_at <= $eventAt`. An explicit `{}` in the payload is a real "everything was cleared" and does clear the stored bag; an ABSENT bag does not.

## Attribute context: the agent READS what it wrote (`src/modules/chatwoot/attributes.ts`)

`set_custom_attribute` is the write side (conversation | contact | kanban card). The read side is a per-agent selection of attribute KEYS whose CURRENT values are rendered as an `<attribute_values>` block appended to the system prompt in `loadAgentConfig`, so the agent knows what has been collected and — via `filled="no"` on a selected-but-empty key — what is still missing. Without it the agent writes an attribute and is blind to it on the next turn (memory lives only in the checkpointer, which `/reset` wipes).

- **No API call.** Every Agent Bot payload already carries all three bags: `custom_attributes` (conversation), `meta.sender.custom_attributes` (`Contact#push_event_data`) and `kanban_task.custom_attributes` (the Pro fork's `FazerAi::Conversations::EventDataPresenter` + `Kanban::Task#common_event_data`). `normalize.ts` extracts them, the mirror persists them, and turn prep reads the columns it was already loading. This is why the mechanism works identically on the debounce flush and the proactive nudge, neither of which has a webhook payload in hand.
- **Config**: `agent.settings.attributeContext = { conversation: [], contact: [], task: [] }` (keys per scope, trimmed/deduped/capped at 20 keys of ≤64 chars by `readAttributeContextConfig`; see the prompt-injection bullet below for what happens to the VALUES). Empty everywhere ⇒ no block at all. Editor: Behavior tab → "Data in context", fed by `GET /v1/chatwoot/custom-attributes/:agentId` (definitions across the agent's instances, same best-effort contract as the label picker). Also on the `behavior-settings` surface, so REST v1 and MCP `agent_settings_get/set` project it.
- **Prompt-injection bound**: values are ultimately customer-authored, so each goes through `sanitizePromptValue` (control chars/newlines collapsed, then capped) and then XML escaping. One effective cap per call site: `ATTRIBUTE_VALUE_MAX = 400` **with a trailing `…`** for attribute values, the default `VALUE_MAX = 120` (no marker) for the `{{var}}` identity variables. The block is appended AFTER `{{var}}` interpolation, so a stored value containing `{{nome_contato}}` stays literal.
- **Freshness**: the mirror is refreshed by the very event that triggers the turn, so a reactive turn always reads current values. `set_custom_attribute` additionally write-throughs into the mirrored bag (`mirrorAttributeWrite`), which closes the only real gap: a nudge fired without a preceding inbound event, and the contact scope (Chatwoot does not deliver `contact_updated` to agent bots). That write-through is a single `jsonb || jsonb` UPDATE, not a read-modify-write: a turn's tool calls run concurrently, so two `set_custom_attribute` calls on the same scope would otherwise clobber each other's key. On the CONTACT scope the same statement also advances the watermark (`custom_attributes_at = GREATEST(custom_attributes_at, NOW())`), because Chatwoot accepted the key a moment ago and every event generated before that carries a pre-write snapshot: one of those, delivered late but still stamped after the last mirrored event, would otherwise pass the compare-and-set above and erase what was just written, with no `contact_updated` ever to put it back. Chatwoot remains the source of truth — the next event overwrites the bag.
- **Card caveat (`task` scope).** `Kanban::Task#dispatch_conversation_events` only re-dispatches `conversation_updated` when a card is LINKED or UNLINKED from a conversation; moving it between steps or editing its fields/attributes goes out over ActionCable (`kanban.task.updated`), which agent bots never receive. So the mirrored `kanbanAttributes` advance only when some conversation event arrives — in practice the next customer message, which is also what triggers the turn, so a reactive turn is still current. This is ALSO why `loadKanbanContext` still reads the card live instead of using the mirror: `kanban_move_card` must act on the step the operator sees right now, and a board-side drag leaves no trace in the webhook stream.

## Pre-turn gates in the receiver

Before a new incoming message reaches debounce/the runtime, `maybeConsumeCommandOrGate` evaluates
the operator-facing gates in a fixed order: redirect **cross-link** → **test-mode** (`/teste`,
`/reset`) → the WhatsApp→chat **redirect** ([`channel-redirect.md`](channel-redirect.md)) →
**availability** (business hours + away message) → **contact authorization**
([`contact-auth.md`](contact-auth.md), the external allowed/denied check). A gate that consumes the
delivery still advances the handled watermark, and the message is folded into the memory thread
like any other unanswered one.

**`/reset` leaves an audit row, and it is the only durable trace the command has** (#398,
[`api-and-fleet.md`](api-and-fleet.md)). The acknowledgement it posts is a chat message in a
conversation that can be deleted, and the flow log only ever gets a line when the command does NOT
run. `conversation.reset` names the steps that failed and the hand-back's outcome; the hand-back
itself is the service's own `conversation.return`. Both are `actorType: "system"`, because the
command is recognized only on an INCOMING message and the person who typed it is the contact, who
is no principal of this system.

## Attribution gate (`shouldBotHandle`)

The bot owns a conversation only while it is `pending` **and** no human is assigned. The gate is ours to enforce: Chatwoot delivers the event even when a human is assigned. With multiple bots, Chatwoot also delivers to a conversation's `assignee_agent_bot`, so we additionally require, when `ourAgentBotId` is known, that the conversation be unassigned or assigned to **our** bot — never to a different `AgentBot`:

```
act ⇔ status == "pending"
    ∧ assignee_type != "User"
    ∧ ¬(assignee_type == "AgentBot" ∧ assigneeId is known ∧ assigneeId != ourAgentBotId)
```

The third line is a **pair**, and passing half of it buys the first two lines only. `ourAgentBotId` without an `assigneeId` to compare against leaves the id unknown, so the clause cannot fire and every `AgentBot` reads as ours — silently, since the call still looks strict. Three scoped reads shipped that way (#210). Every caller that supplies `ourAgentBotId` therefore selects `assignee_id` too, and a test walks the source to hold that (`tests/modules/chatwoot-receiver.test.ts`); the other half, that the column reaches the literal, is a type error when the select omits it.

## Observer binding: watching an inbox somebody else answers (issue #476)

`bindInbox` is never neutral on the Chatwoot side: `set_agent_bot` makes every new conversation start `pending` and assigned to the bot, reopens a resolved one as `pending`, and hands the conversation to a human when a delivery's retries are gone. A monitoring agent could therefore only be attached by taking the inbox over. The fork's second binding (fazer-ai/chatwoot#453, `AgentBotObserver`) is what the **observer binding** uses: `observeInbox` provisions the persona's bot exactly like a bind (`ensureAgentBot`, own route token and secret) and attaches it through `POST /inboxes/:id/agent_bot_observers` instead of `set_agent_bot`, and records an `InboxObserver` row once Chatwoot agreed — `bindInbox`'s shape. The window between the fork's agreement and the row is the receiver's to read, not the row's: the fork delivers to a bot's route only because that bot is the inbox's responder or one of its observers, so `observerRuntimeForRoute` takes a delivery on a route whose agent is not the inbox's responder as an observer's when the agent is in monitoring (only a monitoring agent can be attached as one) or when the row exists (a production agent whose promotion slipped into the attach window still answers nothing) — but never when that bot HOLDS the conversation and the inbox has a responder to answer through — row or no row — since the fork delivers to the assignee bot too and an agent that used to answer this inbox keeps holding what it was assigned, after it becomes the watcher as well; that route is the assigned bot's, which the delivery path answers with the inbox's current responder (with NO responder there is nobody to hand it to, so the watcher keeps the conversations it holds — its memory is the only one the inbox has), and the payload says who holds it (a DEGRADED one, which carries no assignee metadata at all, is answered by the mirror rather than read as held by nobody — an explicit unassignment is an answer and stands); a production agent with no row on an inbox it does not answer is a mirror that drifted from Chatwoot and keeps the responder path it had. THE WINDOW IS NOT FULLY CLOSED, and the limit is the pair of signals it reads: an `updateAgent` promotion committing between the attach and the row leaves neither — no row yet, and no longer monitoring — so a delivery landing in that same instant is read as the responder's, and the mode recheck and the compensating detach cannot take back one already queued. Closing it needs a role the receiver can see BEFORE Chatwoot agrees (a pending row written ahead of the attach), which changes what the row means; it is named here rather than claimed away, and so are its four siblings: the role read from the binding as it stands now (an unobserve plus a promotion landing while a delivery is in transit), a null role read by the sweep as the responder's, the suppression that trusts the responder's current mode rather than what its sibling delivery did, and bot equality standing in for the role across a rebind. All five are the same missing fact — the delivery does not carry the binding generation it arrived under — and they are listed in `.codex-review-waived` and in the follow-up issue #540 that closes them together. An attach whose answer was lost is taken back on the way out, best-effort, for the reason every other compensation here exists: an attachment no row names observes past the mode and deletion refusals, and nothing here could name it afterwards — only what THIS call attached, though, so a re-submitted observe that fails leaves the binding it found, and only while nothing committed still needs it: two first-time observes of the same pair both read "not observing yet" and share ONE idempotent attachment upstream, so the row is re-read at compensation time and the detach is skipped when one stands (`alreadyObserving` answers about the start of the call; what authorizes the attachment is the state now). A read that fails there keeps the attachment: one nothing names is what `unobserveInbox` repairs on demand, while one a committed row depends on is a silent outage nothing repairs. That re-read is the strongest thing available without a shared ordering and it does not close the window — it can still land before the winner commits — which is the seventh entry in `.codex-review-waived` and the same pending row issue #540 carries; the repair is one call either way, since `unobserveInbox` asks the fork whether or not a row is there. A detach that fails leaves exactly what `unobserveInbox` repairs, and the retry asks Chatwoot again (idempotent) and writes the row. Where a bind and an observe of the same agent race past their checks, the responder binding wins from either side — the fork delivers once to a bot that is both, as the responder — so `bindInbox` retires the observer row under its lock (recorded as `inbox.unobserve`) and `observeInbox` writes no row for the inbox's responder; the observer attachment the race left on the fork is detached after the commit, best-effort, from either side — and that detach RE-READS the pair first, since it runs post-commit and outside every lock: bind, rebind and re-observe can all commit while it is in flight, and a stale DELETE would take away the new valid attachment, leaving a committed observer row that bot-status reports active while Chatwoot delivers it nothing. A read that fails there keeps the attachment, the same way every other compensation here decides. An agent deleted between an observe's checks and its row fails the row's insert on the agent's foreign key; the attach is then detached the same way and the observe answers not-found, since no retry could name that bot again. Every other throw from that transaction is the same shape: the row is unwritten, so the attachment upstream is the only trace of the call and is taken back — but only what THIS call attached, so a re-observe that found the binding already there leaves it, and a disconnect landing in the window does not strip an observer the disconnect itself keeps. An inbox takes ONE observer (`errors.inboxAlreadyObserved`, and the unique index says the same under a race): the graph's memory thread is keyed by contact-inbox and not by agent, so a second watcher would write the same thread — the duplicate this feature already refuses between an observer and a responder — and every question downstream (which route transcribes the audio, which one folds the message in) would become a coordination problem with no owner. Lifting that cap is a memory change first, not a binding one. Only a **monitoring** agent may observe — asked of a NEW observer, so a production agent that a race left with a row can still observe again, which is what repairs its bot — and asked TWICE: once before Chatwoot, and once more inside the transaction that writes the row, under the agent's own row lock (this module's one lock mode, which conflicts with the stronger one `updateAgent` takes, so the two serialize without blocking the child inserts the webhook mirror makes). The first read predates the Chatwoot calls and a promotion fits in the window; unasked again, the fork keeps an attachment for an agent that answers with no row naming it, and the receiver — finding neither a row nor a monitoring mode — reads that route as the responder's and folds the message in a second time. With the shared lock both orders end well: a promotion that commits first is seen here and the attachment goes back with the refusal, and a row that commits first is what `updateAgent` refuses against. Never the inbox's own responder, and `bindInbox` refuses an agent that already observes the inbox — the two bindings are exclusive per (inbox, agent). A monitoring agent may still be bound as the responder (that is #209's first rung), and `updateAgent` refuses to SAVE a non-monitoring mode on an agent that observes an inbox (asked of the target, not of the move, so a production observer a race left behind cannot be edited around), as `deleteAgent` refuses to delete one (`errors.agentObservesInboxes`): the route it holds answers nothing whatever the mode says, and the cascade of a deletion cannot make the Chatwoot call that detaches it. `unobserveInbox` is idempotent on both sides: it asks the fork to detach whenever a bot of the persona exists, row or no row (a 404 there means the inbox is gone or the bot was already detached, which is the state asked for), clears the row if one is there, and answers the inbox either way — which makes it the repair for every attachment no row names: an attach whose answer was lost, a redundant one a race left behind, an observe and an unobserve that overlapped on the network (no transaction of ours spans Chatwoot, so the pair can end with the fork and the row disagreeing, and whichever intent is asked again wins). A 404 to the attach is one of two things, and the inbox is asked before either is claimed: the inbox gone upstream while its mirror stayed (`errors.inboxGoneRemote`), or a Chatwoot older than that PR (`errors.chatwootObserverUnsupported`).

On the wire nothing changes: the observer receives the same seven events on its own route, and its media (STT, vision) resolves against the observer's own settings — the config lookups take the route's agent, since `Inbox.agentId` names the responder or, on an inbox a human team answers, nobody. The verdict call runs with the agent's own `modelFallback` behind it (issue #567), through the same `buildFallbackModel` the answer path uses and inside the same spend gate, with its own callbacks so the usage row names the model that actually answered: what an intermittent provider fault costs here is not a turn but a LABEL, and the tick would end with the conversation keeping its old classification and nothing on screen saying why. The fallback is resolved BEFORE the primary is built, because the primary's bounds depend on whether one exists (`maxRetries: 0` and a 45s timeout only when something is waiting behind it, the same rule the answer path follows); a fallback that cannot be built leaves a `warn` on the trail at build time rather than a server log; and the line naming the model that died when BOTH failed rides at `info` with `status: "error"`, since the stage owns the alarm and a second `observe`/`error` for one failure pages the operator twice. The pass follows the memory: beside a responder that remembers the message — or that analyses it on its answer path, which is a test responder in a conversation somebody activated — the observer's route runs no media pass of its own, because both routes receive the same audio and two passes are twice the provider bill and two writes racing into the same attachment's stash. In the receiver, `observerRuntimeForRoute` asks — in one query, on the same path `inboxAgentRuntime` runs — whether the route's bot observes the payload's inbox; when it does, `rt` is the observer's runtime and `observing` is true whatever `Inbox.agentId` says, so the delivery takes the monitoring path above. Three things differ from a monitoring responder: the handled watermark is advanced only when the inbox has **no** responder of ours (beside one, the responder's own delivery of the same message owns the mark, and an observer moving it would take the message out of that flush); the append to memory follows the mark (the thread is the contact-inbox's, shared with the responder, whose own route appends what it answers and folds in what it skips — an observer folding the same message in once more doubled every answered customer message in the checkpoint, so beside a responder the observer's route remembers nothing — while that responder's route will: switched off, or in test mode, the responder folds nothing in, so the observer remembers, and moves the watermark only beside a switched-off one, whose backlog is the past by the time the switch returns, never beside a test responder that may still answer an activated conversation; and "beside a responder" means one with a ROUTE, since a binding whose persona bot was deleted out-of-band on Chatwoot — the state the console shows as "missing", with a Reconnect beside it — receives no delivery of its own, and standing down for one that never comes would lose the message from memory entirely; and "beside a responder" also means one Chatwoot actually FANNED this message to, since it picks a message's recipients from the bindings standing when it emits the event — a responder bound afterwards gets no delivery for it, and standing down there omits the message from memory for good, nothing scanning a settled observer row again — so the binding carries its own age (`Inbox.responderBoundAt`, stamped only when the binding MOVES, cleared by an unbind, null on one made before the column and read as older than any delivery, which is the behaviour those inboxes already had): older than the moment the SOURCE emitted the event BY A MARGIN — the payload's own `last_activity_at`, read at the start of its second because the field is only ever epoch seconds and rounding early errs toward asking for evidence, with the receipt as the fallback for a payload carrying none — the binding stood when Chatwoot chose the recipients and the message is the responder's. The margin (five minutes) is what makes that comparison honest rather than removing it: `responderBoundAt` is stamped by US and `last_activity_at` by CHATWOOT, on a host whose clock is its own, so a Chatwoot running ahead would make a binding that came AFTER the event look older than it; outside the band the answer does not depend on which host is ahead, and inside it the ledger is asked instead — one extra read only for a binding made around the time of the event, which is the window the check exists for. Newer, or inside the band, the ledger is asked for a sibling delivery of this message on the responder's route — on the column that NAMES it, since a customer message is the row's `inboundMessageId` while a colleague's reply is outgoing and is named by `humanReplyMessageId`, so asking with the inbound column alone found no sibling for a reply ever and both routes appended it — and finding one is direct evidence the two routes merely raced — but only a sibling that can still SEE the binding counts, never claimed (it runs after this, with the binding committed) or claimed at or after the binding was made, since `bindInbox` calls Chatwoot before it commits `agentId` and a message arriving in that window reaches a responder route the mirror does not know yet, whose delivery resolves no runtime, answers nothing and settles: counting that one hands the message to a route that already declined it and neither route answers or remembers — and the claim NARROWS that window rather than closing it, which is another entry in `.codex-review-waived` and the same missing fact issue #540 carries: the route is resolved before the row is claimed, so a sibling that read the inbox before the commit and claimed after it satisfies this rule while the runtime it froze saw no responder. Closing it is a resolution stamp on the ledger, which is that issue's own change (the delivery carrying the binding generation it arrived under), and both read-only alternatives are worse: `routeObserved` is `false` for a route that resolved NOTHING exactly as it is for the responder's, and comparing the sibling's RECEIPT to the binding guts the check, since the sibling is a fan-out of the same message and straddles the binding exactly as this row does, so the observer would double-remember every message whose binding is newer than it. What the residual window costs is bounded: it needs an inbox with an observer and NO responder (with one already bound the sibling resolves the OUTGOING responder and the message is handled, not lost), a bind concurrent to the millisecond with an inbound message, and the two fanned deliveries straddling the commit in opposite directions — one observation tick, and a control command typed in that instant — and never THIS row, since one bot serves every role its agent holds and an observer unobserved and bound as the responder makes the responder's bot the one this delivery arrived on, whose recovery claim stamps a `claimedAt` after the binding: the row would prove itself covered by a delivery that never existed — while finding no such sibling means nothing is coming and the observer keeps the message. The question is asked ONCE, of the whole stand-down beside a responder, because the memory, the media pass and the control command all rest on the same premise; hung off the memory alone it left the other two standing down for a delivery that does not exist, the audio nobody transcribes and the `/reset` nobody consumes. The MARK, though, is not asked this question at all ON THE LIVE PATH — a REPLAY is the other case, and there the absence IS evidence, since the delivery reaches the receiver again only after the sweep gave up on it, so a sibling that was ever coming has long since arrived; held back there it would be withheld from a responder bound meanwhile, which would flush from a watermark predating the whole observed backlog: an absent sibling row is also what one still in transit looks like, and the emission clock is only second-granular, so moving the mark on that reading would put the message behind the watermark and the responder's own delivery, arriving a moment later, would answer nobody. The coverage answer may cost a duplicate line in memory; it may not cost an answer, so the mark stays the answering half's whenever one exists with a route (a read that fails keeps the stand-down: our own row being unreadable is not evidence the responder is missing anything, and doubling the shared thread is the worse error); a control command (`/teste`, `/reset`) beside a responder that will really handle it — in test mode, with a route, switched on or not, since a command is active on the mode alone — is not folded in either, since it is the responder's and this route reads it as ordinary text, and an ingestion racing the responder's `/reset` would append the command back after the reset emptied the memory; outside that, the same text is what somebody typed and the observer remembers it — and then it moves the INBOUND mark too, since suppressing `lastInboundAt` for a command nothing will consume leaves the follow-up episode gate and the 24h service window reading the previous inbound for a message the customer just sent); and the settlement is scoped to this delivery's row, never the responder's — the same scope another bot's route gets, and the exclusion runs the other way too: a WIDE settlement never closes an observer's row — the wide scope only, since a single-row settlement already names the row it may touch and the observer's own is exactly that shape. The wide scope exists because a human, a command or a gate answers the MESSAGE whichever route carried it, which is true of every route that could have answered and false of the one that never could; the observer owes the memory instead and pays it on its own schedule, and the throw that leaves its row for the sweep is worth nothing if the responder's copy already made the row terminal. A role not yet STATED is not a role of `false` either: the receiver writes it just after the claim, so an observer's row is briefly in progress having said nothing, and a row still being worked therefore settles only once it has said it is not an observer's (the `route_observed` migration stamped `false` on everything still on the worklist, so a null row being worked is a live delivery between its claim and its statement, whose own tx2 closes it a moment later). A TERMINAL row states nothing because nobody is left to state it, so the correction path is deliberately not narrowed by the role — leaving it open would keep a reported loss standing for a message a turn did handle. On an inbox nobody of ours answers, the resolve arms compaction under the observer, whose memory grows like a responder's — compaction only: the WhatsApp→chat redirect that hangs off the same resolve is the RESPONDER's, read off its runtime alone and skipped when there is none, because that branch ends in customer-facing text on the sibling conversation and an observer answers nothing whatever its mode says. A control command is decided against the RESPONDER on an observer's route: the command is the responder's, and reading the observer's mode there would call an active command inactive, moving the inbound watermark and writing a dropped-command line about a command nobody dropped. Surfaces: `POST/DELETE /v1/chatwoot/inboxes/:id/observers[/:agentId]`, the MCP tools `inbox_observe` / `inbox_unobserve`, and the Channels page — whose answering-agent picker drops this inbox's observers, since the two bindings are exclusive per (inbox, agent) and offering one is offering a request the apply is certain to reject. A colleague's reply the observer cannot remember is reported on the conversation rather than settled in silence, in both of its shapes: retries spent (`human_reply_not_remembered`) and a conversation naming no contact-inbox thread to hold it (`human_reply_no_thread`), the second being permanent — nothing to retry, and no later attempt that would find one. The mark block is inbound-only, so without this an outgoing reply settled PROCESSED with the reply in nobody's memory and no line anywhere. A switched-off observer marks nothing: its route is still the observer's, but ingestion refuses a disabled agent, so the message would sit behind the watermark with no memory holding it. Left unmarked, the message stays above the watermark, which is what says a stretch was never read (the flush after a flip to production reads above it) — it is not a replay, though: turning a monitoring agent back on arms nothing, so what arrived while it was off enters memory only on that flip. And a delivery the observer's ingestion left for the sweep is recovered ON ITS OWN ROUTE: the row carries the bot the delivery arrived on AND whether that route was an observer's, stated by the CLAIM itself in one statement — on EVERY delivery, both roles, and never a second write, since a separate one rejects inside a detached task long after the webhook answered 200 and leaves a row saying nothing, which the sweep moves to DEAD and the recovery refuses, so the retry never runs; claimed and stated together, a row that is PROCESSING has said what it is; the resolution that feeds it is RETRIED (the ingest arm's attempts and backoff), since standing before the claim it rejects with the row still PENDING and its role unsaid, with the webhook long since acknowledged and no caller left to ask again — because the column answers a three-state question and leaving the responder's row null collapsed two of them: `null` then meant "the responder's" and "nobody decided yet" at once, and a delivery that stranded between the claim and that statement was replayed as the responder. A delivery that cannot state its own role does not proceed under one nothing recorded; it fails there and comes back through the sweep. And bot equality is evidence about the role only while the binding is OLDER than the delivery: one bot serves every role its agent holds, so an observer unobserved and then bound as the responder carries the id it had as the watcher, and reading the route off a binding that postdates the message would replay a watched delivery as an answering one — a late reply to a customer rather than a silent loss. A null role against a younger binding is left DEAD too. Null now survives only on a row written before the column (its migration settles those still on the worklist) and on one stranded before the statement, and the recovery refuses to guess for either — asked only where the answer can differ, since a route that IS the inbox's responder bot is the responder's whatever the column says and refusing those would turn every ordinary strand into a dead row. The role is not derivable afterwards — the observer row follows Chatwoot's agreement, so a delivery inside the attach window has none, and a binding that moved since is about a different moment — so it is written, once, on the observer's own route; a row with no role recorded takes the inbox's own derivation, which is what keeps a rebind answering as the persona the inbox is bound to now. The role travels INTO the replay too, rather than being re-derived there: unbinding the watcher and promoting its agent between the strand and the recovery must not turn its delivery into an answering one — which is also what keeps a rebind answering as the persona the inbox is bound to now, since a route that is not an observer's falls through to the inbox's own derivation. Its control-command fence does not apply there: that fence is about a command the responder already executed, and an observer executes none — its ingestion is what stranded the row. The SWEEP reads the role too, for the one verdict it changes: a strand carrying a colleague's reply owes the human-reply takeover, and a takeover steps the RESPONDER off the conversation — an observer was never on it. So an observer's row of that shape owes none and arms none (the job would answer `not-owed` and report nothing, which is how the observer's own lost ingestion became invisible). It is terminal like its neighbour and counted apart, and what it lost is REPORTED rather than replayed, since the payload is never stored and the delivery recovery needs a customer message id to anchor on: the line says what is known and no more. Whether a sibling delivery covered it is a question about RECEIPT time and the sweep runs half an hour later, so the binding read there is evidence and not an answer — an inbox bound in between reads as covered when it was not — and it is asked of a responder with a ROUTE rather than of `Inbox.agentId` alone, since a binding whose persona bot was deleted upstream receives no delivery of its own. One level, `warn`: an `error` on that read alone would page an operator for the ordinary shared inbox, and an `info` would file the real gap where nobody looks. Checked against the bot rows first: a bot re-provisioned since carries a new id, so an observer's delivery naming one nothing carries any more is nameable by nothing and is left DEAD on the worklist rather than replayed into a runtime that would consume it. The live reconcile behind the Channels page reads each observer binding as well as each responder one (`${inboxId}:${agentId}` → active/missing): an observer's bot deleted out-of-band stops its deliveries exactly as the responder's does, and observing again is its Reconnect — and because the repair is the PERSONA's, the page marks ONLY the binding the call itself attached. It is tempting to mark every binding of that persona, since one bot serves them all and the repair travels to each — but that repair is best-effort per inbox (a failed sibling attachment is logged at `error` and the requested operation still succeeds), so marking them all clears the Reconnect from an inbox that is receiving nothing, and the reconcile does not catch it because it asks whether the BOT exists. Between an extra Reconnect that repairs nothing and a missing one that hides an outage, the rule this subsystem is built on picks the first. Closing it is the reconcile asking the ATTACHMENT per binding — the attach is idempotent and `ensureAgentBot` re-provisions a bot that is gone. ONE bot serves every inbox an agent is on (the row is one per instance and agent), so a deletion takes all of those bindings down together, and the repair travels with the REPLACEMENT rather than with whichever path happened to need it first: `ensureAgentBotAndReattach` wraps `ensureAgentBot` for all three callers — a bind, a reconnect and an observe, any of which can be the one that replaces the bot for all of them — and when the id actually changed it puts the new bot back on every inbox this agent observes AND on every inbox this agent answers. `reconnectInbox` does it whether the id changed or not, because gated on the change alone the repair is a ONE-SHOT: a per-inbox failure inside it would be unrepairable, the retry finding the row already carrying the new id and reattaching nothing, so the operator's second click would be a no-op on the very inbox the first one missed. ## Monitoring mode: bound, reading, never answering (issue #209)

`Agent.mode` has a third value next to `test` and `production`. A **monitoring** agent stays bound to its inboxes and receives every delivery, and never produces a customer-facing output: no reply, no typing, no follow-up or HSM template, no away or authorization message, and `/teste` never activates it (the command gate asks for `test` and nothing else). It is not `enabled: false`: a disabled agent is asked nothing, while a monitoring agent analyzes media before any gate and folds every message — the customer's and a human colleague's — into its memory exactly like a production agent does for the messages it does not answer. The predicates are `isMonitoring` and `ingestsContinuously` in `src/modules/agents/mode.ts`, and the mode is read through `normalizeAgentMode` everywhere, because the column is a plain string and the old `=== "test" ? … : "production"` ternary read a monitoring agent as a fully answering one.

"Never answers" is held at two seams and one fence rather than at every send:

- **The config load.** `loadAgentConfig` returns `null` for a monitoring agent, the way it does for a disabled one, and every caller that posts to the customer — the reactive turn, the debounce flush, the guardrail's replacement reply, the proactive nudges and their templates, the slow-tool ack — loads its config there first. The playground still loads it (`ignoreDisabled`: an operator talking to the agent in a fenced thread), and so does memory compaction (`ignoreMode`: a summary is not a reply).
- **The two sends that never load a config**, the generic follow-up (`isFollowUpLive`) and the redirect ladder (`isRedirectFollowUpLive`), carry an explicit arm.
- **The send fence.** A config is a model call old by the first send and several waits old by the last, and an agent flipped to monitoring (or switched off) inside a turn or a nudge must not see one more message go out. `agentStillSpeaks` (`src/modules/agents/speaks.ts`) re-reads the switch and the mode, and it rides the ask every customer-facing write already makes — `writeCalledOff` in the reactive turn, `stillWanted` in the nudge, `postPublicMessage` in the receiver's gate — so the input guardrail's template, the slow-tool ack, the output guardrail, the speech synthesis, each balloon of a split reply, and the gate's own away, redirect and authorization messages are fenced by the same reading. The graph is handed that same fence for its tool boundary, so a tool call the model asked for before the flip is refused rather than run. The turn stands down as `agent-unavailable` — not `stale`, whose bookkeeping is `/reset`'s — and the caller reads the agent again (`agentObservesNow`): the rolled-back turn left the message in nobody's memory, so an observer gets it through the same ingestion every watched message takes, with the watermark past it (the receiver's direct path and the debounce flush both do this, the direct path for a turn that threw after the flip as well, and for a test agent's gate that consumed the delivery under a flip, and the flush at each of its exits — the gate closed before the config loaded, the spend ceiling's, the authorization's, the turn's, and the throw that leaves ahead of the retry — since each sits behind its own wait); the burst is marked handled only once the observer's ingestion has it — the exits that mark on their way out ask first — so a hand-over that cannot read the burst leaves it unmarked and unsettled — a read that failed fails the flush, for the scheduler to retry it, since a monitoring agent arms no second flush and the next observed message would move the watermark past the burst — and so does a read of the agent itself that failed, at any exit, rather than passing for "not observing"; a bound reached or a missing thread stays a completed job, logged; a switched-off agent keeps the silence it asked for. The split reply asks before each balloon's typing indicator as well as before its send, and the slow-tool ack asks after its own send, before the typing indicator and before the tool runs. A nudge stands down the same way — `agent-unavailable`, which the reminder ladder retries as it does for an agent switched off before the nudge ran — where a run `/reset` retired stays `stale`. The spend ceiling's copy, note and handoff in the flush sit behind the same reading, asked after the client build and the ownership probe, last before each write. Fails open: an unreadable row is not a withdrawal.
- **A burst armed before the flip.** A `DEBOUNCE` job armed for a production agent expects the turn to cover its messages, so the receiver neither ingested them nor advanced the watermark. Flushed under a monitoring agent, the flush does what the observer would have done: hands each message of the burst to ingestion (idempotent by message id), reading above the handled watermark while it still sits below the armed burst and above the last reply once observed traffic has moved it past (the one mark no observed message moves), paging back past the newest page when what arrived after the flip pushed the burst off it, and advances the handled watermark past it, settling the deliveries it covered on the ledger (not when another bot holds the conversation: its own delivery of the same message may be in flight), only once the burst was in view (a walk that stops at its bound leaves the burst unmarked and fails the flush so the loss stays visible — the ordinary flush reads the newest page only and would advance the watermark past what the bound left out — and a conversation with no contact-inbox thread to fold it into leaves it unmarked too). A disabled agent's burst keeps waiting for the switch, as before.

In the receiver, `observing` (`rt.enabled && rt.mode === "monitoring"`; an agent that is also switched off takes the switched-off path, where nothing is marked) is read right after `act`. `act` keeps meaning what it means — the bot holds the conversation — and keeps its other readers, but holding it arms nothing: the gate, the commands, the debounce and the turn are skipped, no `handoff` trail line is written (nothing here would have answered), the handled watermark advances as it does for a human-owned conversation and the delivery settles as consumed — only once the observer's ingestion has the message: queued on a contact-inbox thread, from the payload or the mirrored row, or nothing to queue; with no thread anywhere it is left unmarked and unsettled, as the flush leaves such a burst, and an enqueue that failed — after the retries the ledger claim gets, since under an observer the append is the point — fails the delivery, whose row then stays on PROCESSING for the stranded-delivery sweep to recover and re-run, the receiver's counterpart of the flush's retry; a colleague's reply whose enqueue failed the same way has no recovery to wait for (an outgoing body cannot be rebuilt) and is reported as an error line on the conversation instead; every mark on an observed message waits for that answer, the human-held and consumed ones and the stand-down's own settlement included, and so does the delivery when whether the agent observes could not be read at all, or when the watermark itself could not be advanced (settled with the watermark below it, a watched message is one a flush after a flip back to production answers); a gate that consumed the message asks the observer fresh whatever mode the runtime was read with, and a test agent's consumed audio or image gets its eager media pass before the observer remembers it — and a reply on the widget conversation retires the pending redirect ladder rather than re-arming it — once the hand-over is known, so a delivery handed to the observer inside its gate or turn retires it too and its dispatch does not re-arm it; the flush's hand-over retires it the same way. Ingestion then receives `act: false`, because no turn ever covers a watched message. The takeover on a human reply stays production-only, as before. Flipping the mode to production re-arms the follow-up watermark (`promotedToProduction`), so the backlog observed is neither answered nor chased.

## Observation: what a watching agent does with what it reads (issue #477)

A monitoring agent's memory grows and nothing asks it anything, so the first thing it is asked is the cheapest thing a watcher can say: **what this conversation is about**, written as labels, kept current as it happens. Configured under `agent.settings.monitoring` (`observe/settings.ts`): `labelGroups` (each a name, `exclusive` or additive, and the label titles it may pick from — observation is ON while at least one group exists and OFF otherwise, so a monitoring agent with no group costs nothing; up to 5 groups of up to 40 values, and each name and title bounded in LENGTH as well, since both reach the model verbatim in the prompt's `<labels>` block and the verdict schema's enum and unbounded they make every tick fail on the provider's request limit — refused at the write boundary and DROPPED by the reader rather than clipped, because a label title is an identifier that has to match a row in Chatwoot and half of one matches nothing), `analysis` (`incremental`: a verdict per burst of customer messages plus a final one on resolve; `on_resolve`: the final one only), `window.messages` (how many of the newest messages the model reads, default 20), `debounce` (the burst window, default 20 s, at most 60 s), and `noteOnChange` (default on). - **The tick is stateless** (`runObserve`). The in-queue reading sits AFTER the label GET and before every POST, not once at the top: that GET is a Chatwoot round trip of its own, and a re-arm, a switch-off, a detach or a `/reset` served by another replica inside it reached the first write unseen — the scheduler's CAS notices a superseded run only after the handler returns, by which point the label, the note and whatever automation the label triggered have landed. What is left between the fence and the POST is the apply, which touches nothing outside the process. The in-queue reading is the one the verdict is applied against, so the fence and the apply cannot disagree. THE CONVERSATION ROW is read again for the two things that retire a verdict already computed — it REOPENED (the same question the load asked, over the seconds the model took) and the EPISODE ENDED (`/reset` retires the PENDING rows — up to the EPISODE BOUNDARY and not everything under the prefix, since that step runs late in the command and a customer message landing in the meantime arms a burst the operator wants classified; a row naming no message is a resolve verdict, which orders against nothing there and is stood down by the reopen fence instead — but a tick already CLAIMED is past every cancel and would put back the labels the operator was just told were cleared; the burst carries the message id it was armed on and is held to the same `resetAtMessageId` fence the direct turn is, in Chatwoot's own sequence) — both in one query, since the mirror is one row and two round trips would only widen the window they narrow, and on the same trip WHETHER THIS RUN IS STILL THE ONE: a message that lands while the model answers re-arms the same row, and the scheduler's own CAS catches that only after the handler returns, by which point the labels and the private note have landed (a label a later tick repairs, a note is permanent, and so is whatever a label-triggered automation did). Standing down cannot livelock, because standing down IS the successor being there. That whole read FAILS CLOSED: folded into `null` an unreadable row would say both "no reset happened" and "the conversation is gone", so the tick fails and the scheduler retries it, which the stateless tick can afford. The agent is read once more (`agentObservesNow`) and so is its binding: a verdict is seconds old, and an agent switched off, flipped to answering, or taken off the inbox in the meantime does not get a watcher's label under its name. Only a DEFINITE "no" stands the tick down there, and the same holds for the BINDING beside it — which is asked inside the label queue, against the `inboxId` the pre-write read returned rather than the load's snapshot, since a conversation moved to another inbox mid-call would otherwise be checked against an inbox it is no longer on; an unreadable answer fails the tick for a retry, which is what the helpers' three-valued answers exist for, and the MONITORING SETTINGS re-read is held to the same rule (it is the taxonomy the verdict is applied against, so keeping the snapshot writes labels from a taxonomy an operator may have just replaced). "Unreadable keeps the tick" is the right reading only at LOAD time, where nothing has been spent and refusing on a blip would silence observation; on the far side of the model call, keeping the tick means writing — and a model configuration that does not BUILD (a credential pending, rotated or deleted) fails for the same reason rather than being folded into "the agent stopped observing", which is neither true nor where an operator would look. THE LABELS ARE RE-READ TOO, from Chatwoot, immediately before the write: `setConversationLabels` replaces the whole set, so a POST built from the snapshot that fed the prompt silently deletes a label a colleague or an automation added during the model call — which is the one promise this feature makes. Only the set the verdict is applied ONTO is refreshed; the verdict is still the model's — except for a GROUP SOMEBODY ELSE MOVED while the model answered, or one whose DEFINITION changed under it, both of which are skipped entirely. The definition matters as much as the labels: a verdict answers "these values, accumulating or not", so an additive group flipped to exclusive mid-call would have `applyVerdict` sweep out a value the model was told could stand beside the one it chose. That one is detectable, unlike the write gap below: both readings are in hand, so the group's own slice of each is compared, and a person or automation that moved it is fresher information about that group than a transcript predating the move (the commonest verdict of all, "repeat the value you were shown", would otherwise revert the edit silently). Compared on the first pass only — the second reads a set our own write just changed, and its job is to repair that write, not to re-litigate it. The TAXONOMY is re-asked on both, though: the fence hands back the current configuration each time, and the repair is held to the groups the first pass ACTUALLY MOVED — its subject is that write and nothing else, so a group it left alone and a person edited between our POST and this read keeps the person's value, since that edit has now been SEEN and reverting it would undo a manual classification and fire whatever the label triggers — and to the groups it actually wrote — one replaced or redefined while the first POST was in flight is dropped from the repair, since writing a value from a group that no longer stands is precisely what the first pass refuses to do, and an empty slice writes nothing while the first pass's report stands. A re-read that FAILS never falls back to the stale set: the FIRST one failing FAILS the tick so the scheduler retries it, since nothing re-arms an `on_resolve` row and a transient timeout there is a conversation never classified (the retry spends the model call again, gated by the spend ceiling like any other); only the verification read after a successful write stays best-effort. The read-apply-write is SERIALIZED and then VERIFIED, because two classifiers now hold two rows and Chatwoot has no compare-and-set on that endpoint — the only endpoint for a conversation's labels replaces the set, so a label added by a Chatwoot automation, by a person in the UI, or by another replica INSIDE the round trip between our read and our write is erased by it, and nothing on this side can see that it was: the guarantee is "nothing outside the configured groups is touched by us", bounded by one round trip, and closing it needs an add/remove endpoint the fork does not have (`.codex-review-waived`): `withKeyedQueue` orders them inside a process — and the RETIREMENT FENCES ARE READ INSIDE THAT QUEUE, not before it, because `/reset`'s own clear runs in it too: read outside, the fence passes, the reset takes the queue first and clears, and the tick enters afterwards and restores exactly what the operator was told was gone. The private note is inside it as well, so it can never describe labels a reset removed between the write and the note. A second pass re-reads and re-applies the same verdict — our value still standing answers "nothing changed" and writes nothing, our value clobbered by the other classifier writes once more onto ITS set. The changes reported are the first pass's; the second is a repair — and THE RETIREMENT FENCES ARE ASKED AGAIN before that repair writes, because it is a second write authorised by a first pass's reading: a `/reset`, a detach or a switch-off landing between the two would have the repair restore exactly what the operator was just told was gone, which is the same hole reading the fences outside the queue opens, one pass later. A refusal there keeps the first pass's write and its report and stops. The write is `setConversationLabels` inside `withConversationLabels`, the client's ONE critical section for a conversation's labels — `assign_label`, the nudge's `assignLabels` merge and the reset's clear all run in it too, since the endpoint replaces the whole set and an unqueued read-then-POST anywhere erases what another writer added between the two, and a change is announced as a **private note** on the conversation — `🔎 <agent> · <group>: <from> → <to>` and the model's reason — so the person answering it sees why the label moved without opening the console; a note that fails to post does not undo the label, and a VERIFICATION read that fails no longer skips the note either: the write has landed by then, so what is owed is the sentence describing it.

## A person answering the customer ends the attendance (`takeover.onHumanReply`, issue #430)

The gate above reads status and assignee, and **nothing writes them when a colleague simply answers**. Measured on a live fork: a reply typed in the Chatwoot composer leaves the conversation `pending` with no assignee even with `enable_auto_assignment` on, and so does a reply typed on the phone paired to the number the inbox is connected to. Chatwoot's own `mark_pending_conversation_as_open_for_human_response` is guarded by `captain_pending_conversation?`, which the fork hard-returns `false`. So the next customer message drives a full turn and the agent speaks into a thread a person is already holding.

The receiver closes it: on a human reply it puts the conversation in the human queue (`toggle_status → open`), which is the transition the platform already spells "a human is on this", so the webhook gate, the debounce flush and the follow-up ladder all go quiet with no new state and no new predicate in any of them. Handing it back stays what it was: the console's "Return to AI" button, the REST endpoint behind it, or the MCP tool. Not `/reset`, which is a command only for a **test-mode** agent and ordinary customer text for any other.

**Two routes, one predicate** (`src/modules/chatwoot/normalize.ts`):

| route | how it looks on the wire |
| --- | --- |
| Chatwoot composer | `outgoing`, `sender.type == "user"` (`isHumanAgentMessage`) |
| the paired phone / another WhatsApp client | `outgoing`, `sender == null`, `content_attributes.external_sender_name == "WhatsApp"` (`isDeviceAttendantMessage`) |

The device row also requires the inbox's **provider** to be one whose send path reserves its WhatsApp id before the request (`baileys`, `native`, `uazapi`), read from the mirrored `Inbox.provider`. WhatsApp echoes back every message the session sends, our own replies included, and those echoes are matched to the row that produced them by `source_id` — written from the send RESPONSE. When that response is lost and the job retries, the echo carries an id Chatwoot never saw and is stored as a **new** sender-less outgoing message with the same marker; the fork's own comment names the shape, "rendered as if an agent had replied from the phone". The three providers above close it with a reservation, so an unmatched echo of our own reply cannot exist there. `zapi` writes the marker and matches on `source_id` alone, so the device leg is refused on it — acting there would have the agent take the conversation away from itself and file its own reply in the contact's memory as the attendant's. The composer leg is unaffected on every provider: it is sender-typed.

The second row **cannot** be spelled "outgoing with no sender", and that is measured rather than argued. Chatwoot itself produces three other sender-less outgoing shapes, all of which reach the bot as `message_created` on a `pending`, bot-owned conversation: an automation rule's `send_message` (`MessageBuilder.new(nil, …)`), a scheduled message whose author is not a `User`, and a CSAT survey. Only the device reply carries the marker, and every WhatsApp session path in the fork writes it (baileys, zapi, the session inbound writer, the reaction store). Private notes, reactions, templates, activities and `imported` rows are excluded; `imported` is unreachable through this event today (`Whatsapp::Session::SilentWrite` never reaches `AgentBotListener` during an import, probed) and is kept as a cross-repo fence, because the failure it prevents is an entire backlog opened and silenced at once on the day a phone is paired.

**Afterwards**, in the same delivery: the mirrored row is claimed `open` **before the toggle goes out**, in the same statement as the fence. Everything that decides whether the agent may still speak reads that row and never Chatwoot (the runtime's recheck after the model call, the debounce flush, the follow-up ladder's eligibility, the nudge's checks), so a turn already running when the person replied would otherwise reach its recheck inside the round trip, read `pending` and answer over them. The fence asks three things of one read: is the conversation still the bot's, is this decision still the most recent one about it (`chatwoot_status_at` ahead of the payload's version means a later answer already exists, and a hand-back writes `pending` too, so status alone cannot tell the two apart), and is the row still the one all of that was true of — the last as a compare-and-swap on status, status version **and assignee**, since status and assignee carry separate ordering marks and an assignment landing in that window leaves `pending` at the same version. The claim's 45 seconds start **inside** that swap, past the lock and the connection, because everything before it is queueing rather than fencing and a deadline stamped ahead of it reports a window it is no longer giving. That swap runs under the conversation's own advisory lock, the one `mirrorChatwootEvent` and the reconcile take: the predicate orders this write against one that has already committed, and the lock orders it against one that has already READ the row and has not written yet — which would otherwise commit its decision, taken on a row with no claim on it, straight over the `open` (issue #468, round 8). If the open then fails, the claim **stands**: a failed call is an unknown outcome, not a refusal, and rolling back on the unknown puts the agent back to answering into a conversation Chatwoot may have handed over. The next customer message settles it, through the reopen exception that already exists.

The claim carries **no version of its own** until that reconcile stamps one, and deliveries for a conversation are never serialized, so anything that commits in between decides against the state from before the claim: a customer message serialized before the toggle committed, a delayed `conversation_*` event carrying the same old `pending`, or any event at all on a deployment that sends no `updated_at`. Each of the three put the row back to `pending`, and a turn then passed its recheck and answered over the person (issue #436).

**So the write announces itself** (`status-claim.ts`). In the same statement that claims the row, it stamps a deadline and the status it is replacing, and while that claim stands the mirror refuses exactly that status — by name, in `decideConversationWrites`, where every other ordering question is decided. It cannot be done with a version: a customer message advances `conversation.updated_at` on its own account (`set_conversation_activity`), so a snapshot serialized just *before* the toggle carries a higher version than the state we decided on, exactly like one serialized after it. And it refuses one status rather than the field, because an operator resolving inside the claim produces one event we ack and Chatwoot never redelivers — a blanket fence would lose it for good. There are two exceptions, and neither of them is a guess about versions. The first is the version the source eventually gives our own transition: the live read that follows the toggle records it (`status_claim_stamped_at`), and from that instant the question is ordinary again — a payload strictly ahead of that version was committed after our write, so it is a hand-back and it lands, **whichever event carries it**. That last clause is load-bearing: when the hand-back's own `conversation_*` event is delayed or lost, the next thing carrying the new `pending` is the customer's own message, and refusing that on the stored status alone leaves the message acknowledged, the mirror closed to the bot, and nobody answering the customer (issue #468, round 7). The second is the source's own reopen on a row we believe is `resolved` or `snoozed`, which is the one route that can move a status with no version of its own and is therefore judged on what the row holds: on an `open` or `pending` row that same act does nothing, so a payload restating the replaced status there is a snapshot and nothing else.

What falls in the gap before the stamp is **deferred**, not dropped. We acknowledge those events and Chatwoot never redelivers them, so the newest version refused there is kept on the row (`status_claim_refused_at`) and the reconcile adjudicates it against the version it has just stamped: ahead of ours it was a colleague returning the conversation while the toggle was on the wire, and the status it restated is the one that stands; behind ours it was a snapshot frozen before our write, and it goes. When that adjudication moves the status, the reconcile **announces it itself** — the realtime broadcast and the durable `conversation.status_changed` — because nothing else will: the webhook that carried the transition was acknowledged with its status refused, so the mirror emitted nothing and every open console was last told `open` by the claim. A live read taken by anyone else in that window keeps its version on the same column and for the same reason: it may be the newer of two readings, and the owner's own GET would otherwise write its stale snapshot over what that one saw. No reading of the ordering MARKS can stand in for the stamp — a mark that moved says only that some write reached us, never whose or when — and three rounds of review broke three different readings of it (issue #468). A **failed** open keeps the claim, and keeps its deferred version unanswered: nothing stamps, so nothing adjudicates, and the fence is exactly what the deadline says. The same holds for a whole instance on a Chatwoot too old to send `updated_at`, where a hand-back made inside the window is refused and the mirror keeps the agent OUT of a conversation the platform returned to it until the deadline passes and some later payload restates `pending` — the safe side of a coin whose other face is issue #436 itself. And the deadline is what a crash cannot leave behind: past it the behaviour is the one this replaced. Then a live read reconciles the row with the version Chatwoot produced for the change (the toggle endpoint renders no `updated_at`, so there is none to write from the call itself); the claim is what makes a re-delivery a no-op through the gate, and the version is what keeps a delayed conversation event from walking the takeover back; the message is folded into the contact's memory as `human_agent` (issue #187's rule, applied to the route it did not cover); and one `handoff` flow-log line is written with `detail.via` naming the route, so the operator sees the cause at the moment it happened instead of an `ownership_lost` line on the next customer message.

A caller that writes to Chatwoot FIRST and mirrors afterwards cannot take one, and that is not an omission. The console's status buttons fall back to an **unversioned** write whenever their live read fails or carries no version (issue #77), which leaves the operator's hand-back with `chatwoot_status_at` exactly where the state a delayed human-reply delivery decided on left it — so the takeover's freshness check has nothing to compare and undoes the click. Giving that fallback a claim closes it and opens something worse: the fence would then skip a colleague who replied **after** the click, and the next customer message runs the agent over them. Both directions are measured.

**So that write is ordered by the source's message sequence instead** (`console-write-order.ts`, issue #469). The mark is the newest message Chatwoot knew about when the console applied the operator's action (`conversations.console_write_at_message_id`, stamped with `GREATEST` so an out-of-order click cannot move it back), and it is stamped on EVERY such write, the ones that reconcile with a real version included: the recovery below carries no version by construction, so a mark written only on the unversioned fallback would leave the deployments that HAVE versions with nothing to fence it, which is the one thing this got wrong on the first pass, and the takeover's fence refuses a human reply whose own message id is **at or below** it: that reply already existed when the operator clicked, so the click is the later decision. A reply above it was typed afterwards, is a genuine handover, and still takes the conversation over — which is the property a deadline could not offer and the reason the claim was the wrong instrument here. It needs no expiry, because the next message expires it. Same axis, same reasoning and the same boundary as `reset_at_message_id` (`src/graph/reset-episode.ts`): the source's own sequence is the order the operator and the customer lived, and any clock of ours dates the moment our code reached a line, an ack and a detached dispatch later. **The reading that produces the mark is taken BEFORE the action, by the caller**, and it has to be: the mirror runs after its caller's calls to Chatwoot, so a reading it took itself would already contain a colleague who replied during the round trip — and the mark would then cover that reply and have the fence skip the very handover it must honour, which is issue #430 reintroduced by the guard against this one. The mark is therefore a required argument of the mirror rather than something it derives, so each call site says whether it has a pre-write reading at all. And it is one of the terms the takeover's own compare-and-set swaps on, beside the assignee and for the same reason: a console write can move it while status, version and assignee all stay exactly as the delivery read them.

Available precisely where it is needed: `json.messages` has been in the REST show partial since 2020, and `updated_at.to_f` only since 2025 (4.0.2) — so the deployments for which the unversioned fallback is *every* path are the ones that render the sequence. **Where it does not reach**, and this is the remaining half of #469 rather than a closed one: a live read that FAILED outright names no message, so nothing is stamped and the fence has nothing to order. No watermark of ours can stand in, because the id it needs belongs to a message Chatwoot has and we have not seen. There the operator watches the conversation leave the agent again and clicks a second time. The console's plain status buttons take the same pre-write reading and stamp the same mark, because they reach the same defect by another button: pressing `pending` on a bot-owned conversation Chatwoot has as `open` is the operator giving it back to the agent, and with the version stripped it was measured going `open`, `pending`, and `open` again when a delivery frozen before the press landed. Handing a conversation to a PERSON stamps nothing, and needs nothing: the ownership check answers first and the fence is never reached.

The **recovery** (`recover-takeover.ts`) is fenced by the same mark, and it needs it more: it runs at least half an hour after the delivery it rebuilds, so a hand-back made in that stretch is the likely order of events rather than a race. The coordinate travels on the ledger row (`human_reply_message_id`), written at insert beside the shape, since the payload is never stored (issue #228) and `inbound_message_id` is null on a colleague's reply by construction. Its *finishing* branch does not ask the fence, and that is deliberate: a hand-back writes `pending` on the row, which takes the conversation out of the `open`-under-a-pending-claim shape that branch is selected by, so the case goes down the ordinary path and is asked there. A console mark on a row still in that shape means an operator who **opened** the conversation themselves, which is what finishing does.

The fence asks **Chatwoot first**, because the mirror can be behind it and the act being guarded is a write to Chatwoot: an attendant who answers and then immediately resolves or hands the conversation back does both before this detached delivery runs, and fenced on the row alone the toggle reopens what the operator just closed (the same shape `/reset` guards with its live refresh). It is a **gate only**, not a reconcile — writing that read onto the row would stamp it with a version newer than the message that decided the takeover, and the ordering check that lets a hand-back outrank us would then refuse every takeover there is. An unreadable read does not block: silence is not evidence that somebody took the conversation.

The claim is broadcast on the realtime tenant channel the moment it is written. The snapshot this delivery already published upstream still said `pending` — the claim had not been taken — so without it every open Conversations page keeps naming the bot as the owner; after a successful open Chatwoot's own conversation event corrects that a moment later, and after a failed one nothing ever does.

It runs on **production** agents regardless of the agent's own on/off switch, because a takeover is a fact about the conversation and the switch is a fact about the agent. Reading the switch here got it wrong twice: the runtime's post-model recheck asks about ownership and not about the switch, so a turn already running when the agent was switched off answers over the colleague anyway; and the conversation stays `pending`, so switching the agent back on hands it every conversation a person picked up meanwhile. A **test-mode** agent stays excluded: it lives in a conversation an operator activated with `/teste`, and an operator answering from the composer mid-test would silence the very agent they are testing.

The persona's bot row is required and checked before anything is claimed: without it every call goes out with an empty token (issue #79), so the open cannot succeed, and learning that from the exception would leave the row `open` on a conversation Chatwoot never moved. Keeping a claim is right for an *unknown* outcome; a missing bot is known.

`agent.settings.takeover.onHumanReply` switches it off, and it is **on by default** — see `src/modules/handoff/settings.ts` for why, and for why it is a block of its own rather than a field on `handoff` (the console's Tools tab replaces that one wholesale).

## Kanban driver + client loader

Chatwoot's Kanban owns the funnel/board/step/card model (the agents has **no** Funnel/Card tables). We drive it via admin-token methods on `ChatwootClient` — `listKanbanBoards`, `createKanbanBoard`, `updateKanbanBoard`, `listKanbanSteps`, `createKanbanStep`, `setBoardInboxes`, `setBoardAgents`, `listKanbanTasks`, `createKanbanTask`, `moveKanbanTask`, `updateKanbanTask` — against the Kanban routes `/kanban/{boards, boards/:id/steps, boards/:id/update_{inboxes,agents}, tasks, tasks/:id, tasks/:id/move}`. Create/update bodies wrap the Rails-required root key (`board`/`step`/ `task`); bind/move params (`inbox_ids`, `agent_ids`, `board_step_id`, `insert_before_task_id`) are confirmed against Chatwoot. `updateKanbanTask` PATCHes a partial `{ task: {...} }` (camel→snake: `startDate`→ `start_date`, `dueDate`→`due_date`) limited to the scalar fields `title`/`description`/`priority`/ `start_date`/`due_date` (the `update_kanban_task` native tool; `value`/`board_step_id`/`labels`/ `custom_attributes` keep their own paths). Permit list + `Task::PRIORITIES` (urgent|high|medium|low) + the `start ≤ due` validation confirmed against Chatwoot's Kanban API. The inner board/step/task shape is owned by the `/desenhar-funil` wizard.

The agent's **read** path is `loadKanbanContext` (`src/modules/chatwoot/kanban.ts`), resolved at turn prep when `kanban_move_card` is granted: `conversation.kanban_task_id` → `getKanbanTask` (board + current step + the **card snapshot**: `title`/`description`/`priority`/`status`/`value`/`startDate`/ `dueDate`/`custom_attributes`) → `listKanbanSteps` (board steps with the operator's per-step `description` + `cancelled` flag, cached 60s/board). `parseSteps` tolerates the `{ steps }` (current Chatwoot jbuilder), `{ payload }`, and bare-array shapes. This context is surfaced in the `kanban_move_card` description so the agent sees where the card is, the available steps (with their notes), and the card's data; the operator's funnel guide (`agent.settings.kanban.instructions`) is appended after it.

`loadChatwootClient(tenantId, instanceId, { botToken? })` (`src/modules/chatwoot/instance.ts`) is the single place that resolves an instance and decrypts the **admin** token into a ready `ChatwootClient`; the **bot** token is admin-only (`""`) by default and supplied by the posting paths via `botToken` (the persona token from `loadAgentBot`/`AgentConfig.agentBotToken`). The scoped instance read happens first; the SSRF-validated (DNS-resolving) client construction follows, outside the transaction.

## Provisioning (`src/modules/chatwoot/provisioning.ts`)

Provisioning is **lazy** and **per-persona** — there is no operator-facing "provision the bot" step. `ensureAgentBot(tenantId, instanceId, agentId, agentName, client, deps?)` runs the first time that persona is bound to an inbox of the instance (see `bindInbox`); the caller owns the admin-capable `ChatwootClient` and connecting the bot to specific inboxes.

1. Read the `(tenant, instance, agentId)` bot row (scoped). If present, **verify it still exists on Chatwoot** (`listAgentBots`) — an operator can delete the bot out-of-band. If alive → **return it** (idempotent), decrypting its access token. If **gone** → re-provision and refresh the row in place (so re-binding the inbox self-repairs; the dead id/token would otherwise 401 every reply).
2. **Outside any transaction**: generate the route token, derive `outgoing_url`, `createAgentBot` (name = the persona's name; returns `id` + `access_token` + `secret`).
3. **Persist** a `ChatwootAgentBot` row (`chatwootAgentBotId`, `accessToken`/`webhookSecret` encrypted, `webhookRouteTokenHash`, `name`). A `P2002` on the `(tenant, instance, agentId)` unique means a concurrent first-bind won the race: the freshly-created bot is orphaned on Chatwoot (rare — admin-only) and we adopt the winner's row (logged).

The bot's `secret` **is** the HMAC key the receiver verifies — provisioning and the receiver agree on it by construction (covered by a round-trip test). An explicit reset path (reaping orphaned/old bots on Chatwoot) is future work. Instance creation auto-runs `syncInboxes` (best-effort) so the inbox list is populated before any binding.

## Instance setup: account discovery (`listChatwootAccounts`)

The setup form takes **url + admin token** and discovers the `accountId` instead of making the operator hunt for the numeric id. `fetchChatwootProfile({ baseUrl, token })` (in `client.ts`) hits the **user-scoped** `GET /api/v1/profile` (NOT the account-scoped `/api/v1/accounts/:id/...`, which needs an id we don't have yet), and `parseChatwootAccounts` shapes `profile.accounts[]` into `{ id, name, role }[]`. `listChatwootAccounts` (management) is **stateless** — it does NOT persist the token (the operator supplies it again at create-time); any failure (bad token/URL, SSRF block, unreachable, or a token attached to zero accounts) surfaces as a uniform **502** (`errors.chatwootProfileFailed`, never echoing the URL/token) which the UI converts into a **manual-id fallback** field. Endpoint: `POST /v1/chatwoot/instances/list-accounts` (TENANT_ADMIN), a static sub-path with no overlap against the dynamic `/instances/:id` routes.

### Why the Chatwoot creds stay inline-encrypted (NOT in the vault)

The `ChatwootInstance.adminToken` plus the per-persona `ChatwootAgentBot.accessToken`/`webhookSecret` are **encrypted columns**, not `VaultEntry` rows, **by design** — and this is the answer to "should Chatwoot creds move to the vault?": **no.** The inbound webhook resolves the bot by `webhookRouteTokenHash` **before any tenant context exists** (the route token IS how we learn which tenant/instance/persona a delivery belongs to). A `VaultEntry` is tenant-scoped (RLS) and can only be read **after** `tenantId` is known, so sourcing the bot secret from the vault would be a resolution deadlock: we'd need the tenant to read the secret, but we need the secret (HMAC verify) to trust the request that tells us the tenant. Keeping the creds inline-encrypted on the row we resolve by hash sidesteps the chicken-and-egg, at the cost of a second secret-storage mechanism (accepted: it is a justified architectural decision, not debt). The vault remains the home for **agent-facing** creds (LLM keys, HTTP-tool credentials, STT/TTS providers) where a tenant context always exists at read time.

## Known limitations

- **A recovery only covers rows stranded from now on.** The sweep arms the `DELIVERY_RECOVERY` at the moment it declares a row `DEAD`, which is the only moment anything knows the row just became recoverable — its own query reads `PENDING` and `PROCESSING`, so a row already `DEAD` before this shipped is invisible to every later pass. Those rows stay in the `WHERE status = 'DEAD'` worklist, which is what they were before.
- **A recovery answers through the gates, so it may deliberately not answer.** A conversation a human or another bot has taken over is consumed rather than replied to, and that is the correct outcome, not a missed one.
- **Runtime tools that act ON Kanban from the graph** (move card on stage change): the driver methods exist now but nothing calls them automatically yet.
- **Payload shapes verified at source.** The agent-bot delivery body is exactly `payload.to_json` (no envelope), built by `EventDataPresenter#webhook_data` / `Message#webhook_data`. Field paths our code depends on, all verified: conversation `id` = **display_id**; `message_created`/`message_updated` nest the conversation under `.conversation`, `conversation_*` carry it at the top, and **every other event's body is a different subject** (a contact, a contact_inbox, an inbox, a kanban card, a message) rendering its own primary key under that same `id` key — so which id a body holds is knowable only from the event NAME, which is why `normalize.ts` allowlists the two conversation-bearing shapes and reads a conversation id from nothing else (issue #257); top-level `message_type` is the **enum string** ("incoming"…) while the nested `conversation.messages[].message_type` (and the REST messages API `_message.json.jbuilder`) is the **integer** `message_type_before_type_cast`; audio attachments expose `data_url` (inline_audio_url) + `file_type:"audio"` + `meta.transcribed_text`; contact is `meta.sender` with `phone_number`; `changed_attributes` is an array of single-key `{ key => { previous_value, current_value } }` hashes. `signing.ts`, `normalize.ts`, and `messages.ts` all match. NOTE: `attachments#update` runs `@attachment.update!(meta: …)`, which **replaces** the whole `meta` column — the STT write-back only sends `{ transcribed_text }` (n8n parity, acceptable) but it is not a merge.
- **A conversation never changes inbox** (measured at the fork, #295): `Conversation#inbox_id` is `not null`, set once by `ConversationBuilder` from the contact inbox, and nothing in `app/`, `enterprise/` or `lib/` updates it — `clone_inbox` creates new conversations on the destination rather than moving any. What Chatwoot transfers is the ASSIGNEE (agent or team), a different column. So a message's `inbox_id` and its conversation's cannot name different inboxes, and a delivery rebuilt from the message's route is not answering on a route the conversation left.
- **Wire-confirmed field paths.** The real `EventDataPresenter` / `Message#webhook_data` output confirms every field path above on the wire. `message_created` nests the conversation under `.conversation` (top-level `message_type:"incoming"` string; nested `conversation.messages[].message_type:0` int); `conversation_updated` carries `id` = **display_id** at the top; `meta.assignee_type` is `null` when unassigned; `meta.sender` carries `phone_number`/`email`/`identifier`; `channel:"Channel::Api"` for the WhatsApp-via-baileys inbox.
- **`unassign` does NOT set `pending`** (this corrects the plan's residual assumption "confirm unassign → pending"): a live probe showed clearing the assignee leaves `status` unchanged ("open" stays "open"), and `toggle_status → pending` does NOT clear the assignee (`conversations_controller#toggle_status` only saves the status). **The parenthetical that used to sit here, "it auto-assigns the acting agent solely on `open`", is wrong and was refuted by measurement on 4.17.0 (#398):** toggling a pending, unassigned conversation to `open` with the admin token left `assignee_id` null, on an inbox with `enable_auto_assignment: false` and on one with it `true`, with Sidekiq running and re-read after the round-robin job would have run. It matters because two review findings leaned on that sentence to ask for an assignee in the projections of `conversation.status` and of the untargeted handoff: there is none to carry. So returning a conversation to the bot requires BOTH an explicit unassign AND `status=pending`: `returnConversationToAgent` now calls `client.unassignConversation` (`assignee_id:0` → `AssignmentService` sets `assignee=nil`) **and** `toggleStatus("pending")`. Without the unassign, the gate (`assignee_type !== "User"`) would keep the bot silent on the next inbound message.
- **Both custom-attribute write endpoints ASSIGN; neither merges server-side.** `POST /conversations/{id}/custom_attributes` and `PUT /contacts/{id}` replace the whole bag with what they receive — the conversation action is `@conversation.custom_attributes = params.permit(custom_attributes: {})[…]` + `save!`, with no setter override on the model, and it is **byte-identical upstream** (not fork behaviour). Measured on the deployed fork inside a rolled-back `rails runner` transaction: writing `{produto:"A"}` then `{medida:"B"}` leaves `{medida:"B"}` — `produto` is gone; writing `{}` clears it. This is issue #112, and it mattered because two beliefs coexisted in this repo, one per caller: a comment in `client.ts` claimed the endpoint merged, while `/reset` depended on it NOT merging in order to clear. Our writers therefore read-merge-write against **Chatwoot**, never against the mirror (which lags and would erase an operator's UI edit), serialized per target with `withKeyedQueue`.
- **A number that "doesn't match" is usually our own PK.** `Conversation.id` here is a global autoincrement `BigInt`, also in the thousands, and it surfaces in `ExecutionLog.conversationId` and in the console — while every Chatwoot path takes the **display_id**. Looking that number up as a Chatwoot table id finds a row and closes a circular argument. Settle it with `SELECT id, chatwoot_conversation_id FROM conversations WHERE id = <N>;`. The types prevent the real bug (PK is `BigInt`, `chatwootConversationId` is `Int`, every client method takes `number`, so passing the PK does not compile) — the only escape is an explicit `Number(…)`. Chatwoot's own `id` is a **global** sequence and `display_id` is **per account** (`conv_dpid_seq_<account_id>`), so on a multi-account instance `id > display_id` is normal, not desynchronisation, and a 404 by table id is the correct behaviour. A proposal to make the API accept either id was closed `wontfix` for exactly this: the proposed `find_by(display_id:) || find_by!(id:)` fallback turns a safe 404 into the wrong conversation (a POST reaching the wrong contact) and makes the same URL change meaning once `conv_dpid_seq` reaches that number.
