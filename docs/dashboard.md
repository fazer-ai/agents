# Dashboard

The operator's dashboard (`src/client/pages/DashboardPage.tsx`, blocks under `src/client/pages/dashboard/`) is organised by the question an operator brings, not by the table the data lives in: is the agent doing its job, why does it hand over and what are people asking, what does it cost, is it healthy, and what else does it do on its own. This page maps every block to the query behind it, so the next change does not reintroduce a second source.

**Every figure comes from this app's own records.** Money is `llm_usage.cost_usd`, priced when the call was written and re-priceable after (`scripts/reprice-usage.ts`). No figure is read from Langfuse: it samples traces on the client, prices only at ingestion and delivers best-effort, so its sum is not a total. Langfuse appears only as the "Open in Langfuse" link (`DashboardCosts.langfuse`), and the page renders the same numbers with it unreachable.

## The one filter

Period, agent, inbox and source live in the URL (`?range=7d|30d|90d|12m|all|custom&from=&to=&agent=&inbox=&source=&audience=`, `src/client/pages/dashboard/filters.ts`). `audience` (`identified` | `anonymous`) refines the client source only: it is read, shown and sent under `source=client` and dropped under any other, and every block applies it (`audienceSql`, from the `anonymous` column each turn writes on its usage rows and flow lines). A value at its default is left out, a value that does not parse falls back to its default, and an agent or inbox id this account does not have is dropped from the URL rather than shown as an empty view. What the agent and inbox selects offer comes from `GET /v1/metrics/filter-options` (`src/modules/analytics/options.ts`): every agent and inbox, whole rather than paged, readable by anyone who can read the dashboard. An inbox whose name another inbox of the tenant also has (two connected Chatwoot accounts with a "SAC WhatsApp" each) carries `account: {id, name}`; this page's inbox select and the Dashboards panel editor's inbox filter read it as "SAC WhatsApp · <account>" ("Account 7" while the name has not synced, `inboxOptionLabel` in `src/client/lib/inboxOption.ts`), as the Dashboards panels' rows do. A link's ids are checked against that list only once it has arrived; an unreadable list keeps them. The window is half-open `[since, until)` in the browser's own days (`docs/ui.md`, "A day is defined by the viewer's browser timezone"), and the previous period is the same number of days before it. A window still running (a preset, or a custom range that reaches today) is read up to the instant the view was opened (the API query ends there; its days and drill-down links keep the whole window) and compared up to the same local time of day, N days back: the last 7 days at 10:00 against the 7 before them up to 10:00, never against whole days, which would read as a drop every morning and a rise late in the day. A window already over is compared with the whole days ending where it starts; "all" has none.

Every route takes the same query (`dashboardFilterQuery`, `src/api/v1/dashboard.controller.ts`) and every service builds on the fragments of `src/modules/analytics/filter.ts`:

| fragment | means |
|---|---|
| `cohortWhereSql` | **the view's conversations**: created in the window (`conversations.created_at`, when the conversation reached us), in the filtered inbox, and under an agent filter, the ones whose inbox is bound to that agent or that the agent ran on |
| `agentRanSql` | **the agent ran on it**: a real-traffic ledger row that is an agent turn (`node` null or not in `NON_AGENT_TURN_NODES`), by the filtered agent when there is one |
| `outcomeSql` | `classifyOutcome` in SQL (handoff, resolved by the agent, resolved before tracking, resolved by someone else, unresolved); fenced against the TypeScript rule by `tests/modules/analytics-outcome-sql.test.ts` |
| `usageWhereSql` | **the view's ledger rows**: billed in the window, in the source and audience, by the agent, in the inbox |
| `logWhereSql` | the same for `execution_logs`, which carries the same columns; under an inbox filter a line that names its conversation and no inbox (a takeover is logged from the webhook) is its conversation's inbox's. The Logs page reads the same rule (`inboxLogLineIds`, `src/modules/flowlog/read.ts`, bounded by the page size) |

**Every route reads through the metrics pool and answers within a bound** (`src/modules/analytics/budget.ts`, issue #1277). The reads, and the authentication of the `/api/v1/metrics` routes, run on a pool of their own (`METRICS_POOL_MAX`, default 3), so a page load queues there and never takes the connections turns need. Each request has one budget, `METRICS_TIMEOUT_MS` (default 15000), counted from its arrival and shared by the wait for a connection and the run of its reads; past it, or past the lock timeout, it answers 503 (`MetricsTooSlowError`, "try a shorter period, or again in a moment") and Postgres has already stopped the query. A block that gets that 503 says so in its slot, with its retry; any other failure keeps "Could not load metrics." The MCP `metrics_get` and `metrics_timeseries` return the same sentence. Sizes and the budget: `docs/deploy.md`, "Connection budget".

**What a page load costs the database.** The metrics pool runs with `jit=off` whatever the server says (`src/api/lib/pool-options.ts`): these reads are a few large aggregates, and compiling each one on every request cost more than it saved. The flow-log figures (handoffs by cause, silences, where the transfers went, follow-ups) reach their lines through the partial index `execution_logs_dashboard_lines_idx` on `(tenant_id, stage, created_at)`; a new figure over those lines writes a predicate that implies one of the index's arms, or it reads every line of the window, `generate` lines and their stored prompts included. A conversation's outcome and whether the agent ran on it are worked out once per conversation (`outcomeCountsSql`, the labels), not once per figure. The console sends each distinct request once per load ("How the console loads").

Conversation figures are real traffic by construction (a playground turn has no conversation). Ledger figures follow the source toggle.

## How the console loads

Every block asks its own route (`useMetricsBlock`, `src/client/pages/dashboard/useMetrics.ts`, issue #1732), with the page's query and, for the KPIs, the funnel trend and the costs, the previous period's too. Each route computes its figures from the records when asked, within the request's one `METRICS_TIMEOUT_MS`; nothing is kept between requests and nothing is computed ahead, so a late change to an old conversation (reopened, relabelled, repriced) is in the next request's figures with nothing to recompute. A block shows its own skeleton, in a `role="status"` region, until its answer arrives, and its figures are final when they show: there is no partial state. A fast block shows at once and a slow one holds only itself. A block whose route fails or is refused shows its failure and its retry in its own slot, and every tile that reads the same answer shows that failure with it, never a figure it did not get (the four cost tiles share one failure card; the KPI tiles and the funnel share one), and the retry asks that block's route again, and only it. Two blocks that read the same route with the same query (the cost block's cached input and the usage table's agent rows, the latency and problems blocks) share one request. A new view (a filter, a period, a new local day) is a new opening, at a new instant: every block asks again, the previous view's figures leave the screen at once, and its requests still running are aborted; on the server a metrics read whose caller is gone runs nothing (`runMetricsScoped`), so it does not hold a connection of the pool the new view needs. A block that compares against the previous period (the KPIs, the funnel trend, the costs) shows both or neither: it holds its skeleton until both answer, and when either request fails it shows its failure, and its retry asks again whichever of the two failed (`withComparison`). A block's retry belongs to its view. The flow-log blocks wait for the retention the filter options carry; options that cannot be read are asked again after one and four seconds, and past that those blocks show their failure and their retry, never "none in the period".

**When the database runs short of shared memory.** The heavier reads (costs, the breakdowns, health) run with parallel workers, which pass rows through dynamic shared memory, kept in `/dev/shm`. Docker gives a container 64 MB of it unless its compose sets `shm_size`, and three of those reads at once can fill it: Postgres refuses with 53100 ("could not resize shared memory segment"). `runMetricsScoped` then runs the same read again, inside the same budget, with `max_parallel_workers_per_gather = 0`, which takes no shared memory; the reads are pure, so running one twice changes nothing. Rows that tie keep one fixed order (`problemOrder` and `latencyOrder` in `src/modules/analytics/health.ts`), since Postgres hands tied groups back in whatever order its plan made them.

**The kept days' tables, for one release.** `dashboard_days`, `dashboard_dirty` and the `dashboard_dirty*` triggers that queue late changes stay in the database for the release that removed their reader: `migrate deploy` runs while the previous container still serves, and a rollback to it needs the triggers to keep invalidating its kept days. Nothing reads them now, so the daily `FLOWLOG_SWEEP` empties the tenant's kept days together with their queue (`src/modules/flowlog/retention.ts`), each batch in a transaction of its own after the log is pruned, the kept days before their queue, and no batch started past the pass's `SWEEP_PASS_MS` (the rest is taken by the next short pass): a rollback finds either everything it kept or nothing, and computes its days again, never a kept day whose invalidation was dropped. The release after drops the triggers, their functions and the tables.

**What "no data" means.** The flow log keeps `FLOWLOG_RETENTION_DAYS` (sent with the filter options as `flowLogRetentionDays`, with `firstRecordAt`, the tenant's first conversation or ledger row, where an all-time view starts). A day before the one the retention cutoff falls in is not read, even while the daily sweep has not yet emptied it (`flowLogFloor` in `src/modules/analytics/filter.ts`), so a figure does not change when the sweep runs; the handoffs, follow-ups and health routes take that floor once per request and answer it as `flowLogFrom`, and the console marks the days before it, so a view opened before midnight and read after it marks the day the read left out, and the blocks that read the flow log (handoffs, silences, follow-ups, problems) say so ("no data for N days", `flowLogCoverage`) rather than show it as zero: their charts draw those days under a dotted "no data" band (an all-time chart's axis starts at the first of them, `axisStart`), their tables leave them blank, and a block with nothing to show over a window with such days does not say there was none in the period (`hasNoData`). The day the cutoff falls in is read as the reader reads it, since the sweep is still emptying it.

**How the cost block reads the ledger.** `getDashboardCosts` makes two reads of the window's ledger rows. The first sums them per quarter hour of UTC, model and call type, then places each quarter in its local day: every zone's offset is a whole number of quarter hours, so a quarter falls in one local day and the zone's day is worked out once per quarter instead of once per row; one `GROUPING SETS` pass over those sums gives the period's total, the days, the models, and the days by model and by call type. The second takes the distinct conversations per quarter, then per local day, joined to their conversations once, for the conversation and resolved counts per day and for the period. The figures are the same as one read per figure, to the last digit.

## Log facts

The handoff, silence and follow-up figures read a few lines out of the busiest table of the database, and what each line counts as is decided by keys inside its `detail`. So those lines are also kept as **log facts** in `dashboard_log_facts` (issue #1731, migration `20261107220000_dashboard_log_facts`): one row per line that is a transfer (with its cause and, for a hand-over line, where it went), a `skip_reply` call that ran (with its reason) or a follow-up step that reached the customer, carrying the line's own time, conversation, agent, inbox, source and audience, so the filter reads them exactly as it reads the log (`logWhereSql`). Triggers on `execution_logs` write a line's fact when the line is written and remove it when the line is deleted, whatever deletes it (the retention sweep, a tenant's deletion, a test), rewrite it when the line is rewritten, and empty the facts on a `TRUNCATE`; the app never writes them. The figures over the facts are the figures over the log, filter by filter and to the last digit, and `tests/modules/analytics-log-facts.test.ts` reads both ways and asks for the same answer.

**One cause is decided when it is read.** Whether a `taken_over` line is a person taking the conversation depends on the conversation's other transfers and turns (the rule is in the table below), and those can be written after the line (a transaction that commits late, a line written with an earlier time) or swept before it. So the fact keeps `taken_over` as itself, and the reader decides it over the facts (`FACT_CAUSE_SQL` in `src/modules/analytics/activity.ts`), which hold every transfer of the conversation, looking up the agent's turns in the ledger as the log reader does. A transfer the retention sweep removes therefore changes the cause of a later takeover exactly as it does over the log.

**Lines from before the facts.** The migration writes no fact: it marks every tenant that existed as waiting (`dashboard_log_facts_state`), and the `DASHBOARD_LOG_FACTS_BACKFILL` job, armed at boot for each waiting tenant, fills its lines one hour of log per transaction, oldest first, for up to 30 seconds per run before it gives the lane back, and marks the tenant done when it reaches the present (`src/modules/analytics/log-facts.ts`). It locks the lines it fills (`FOR SHARE`) before writing their facts: a delete or rewrite still uncommitted when the batch reaches a line holds the batch, which then writes what the line has become (nothing, for a deleted one); one that comes later waits for the batch, and its trigger finds the fact. Until a tenant is done its figures are read from the log as before, and a SUPER_ADMIN's view of the whole fleet reads the log until every tenant is; a tenant created after the migration reads the facts from the start. A job that dies leaves the tenant reading the log, slower and still right, until the next boot arms it again.

## The blocks

The filter and the section index sit in one band across the top of the page, which stays on screen while the page scrolls (from the `lg` breakpoint). The index is a row, not a column beside the blocks: at a laptop's width a column took a quarter of the room the blocks need. Each section's title carries the icon its entry carries in the index.

The funnel's five tiles are laid out by the width the page has (a container query on their row, `KPI_GRID` in `PerformanceSection.tsx`), not by the window's, since the app's sidebar takes a share a window breakpoint cannot see: five across from 70rem, three and two below it, two by two below that with the last tile across the row. No width leaves a tile alone beside a gap.

Two windows coexist on purpose: conversation figures count conversations **created** in the window, ledger figures count calls **billed** in it. A conversation that started last week and was answered today is in today's cost and in last week's funnel.

## Series colours, order and the tooltip

A chart's series take the `--color-chart-1` to `--color-chart-8` tokens of `public/index.css`, never cycled: a categorical palette stepped per theme whose neighbours stay apart under colour-vision deficiency, and that does not borrow the theme's semantic tokens (accent, success, error), which can sit close in hue. Every colour clears 3:1 against the card surface in both themes (the light steps of aqua, yellow and magenta are darker than the dataviz reference for that). A series' colour follows the series, never its rank: the first render gives the kept series their slots in the caller's order, and from then on a series keeps its slot while it stays kept, so a colour does not move when another series joins or leaves the group or a new answer changes the ranking; a newcomer takes the free slot (`assignSlots` in `chart-series.ts`).

The series are ranked once per window by their total over it (`arrangeSeries` in `chart-series.ts`), never per day. Past eight, the smallest form one "Others (N)" group in the neutral muted ink, always last: a stacked chart sums them into one layer on top of the stack, a line chart draws them as thin neutral context lines, since rates do not add up. The legend under a chart reads that ranking left to right: on a stack, from the base (the largest series) to the top, then "Others (N)"; hovering, clicking or tapping "Others (N)" lists its members (the app's `Popover`, which a click, a tap or Enter opens): the eight largest over the window, then "and N more", so the list never outgrows its box and never needs a scroll the keyboard cannot reach; every series stays in the block's table and CSV, and in a stack's day detail. A chart hides only its drawing from a screen reader, which reads the block's table instead; the legend and the day detail stay reachable. Every vertical list reads the chart as drawn, top to bottom: a stack's tooltip and day detail start with "Others" and end with the base, a line chart's tooltip lists the day's values highest first, which is where the lines sit that day, with "Others" last.

The tooltip (`TooltipCard` in `charts.tsx`) is a summary: exactly the legend's series, each on a line of its own (a zero segment left out), and the legend's "Others (N)" group as one line with the legend's count, so the tooltip, the legend and the day detail show the same group; the day's total in the header on a stack; and on a stack a hint that a click shows everything. Clicking or tapping a day of a stacked chart (a segment names its day from its row, a transparent column per day behind the bars names it for the empty room and the loading bands), or pressing Enter or Space on it from the keyboard (one tab stop over the plot, the arrows move between days), opens its detail under the chart (`DayDetail`); the day never comes from the hover state: every series, the group's members under its line, each with its value and its share of the day, closed by its button, by Escape (heard anywhere on the page while it is open; the focus moves into it) or by clicking the same day again. A line chart's click stays the drill-down to the day's conversations, by the same rule: a point names its own day and line, a day's column (reaching past the plot's edges, so the outer half of a point at 0% or 100% counts) names the day alone, and a line between its points lets the click through. The table view and the CSV are built from the unfolded series, so they keep every one.

## Export and accessibility

Each block exports what it shows as CSV (`src/client/pages/dashboard/csv.ts`): raw numbers, a header row, the same rows the screen shows. A text cell that starts like a formula (`=`, `+`, `-`, `@`) is written behind an apostrophe, since agent, inbox and label names come from outside. A chart is hidden from the accessibility tree and a table with the same figures stands in its place (`Block`, `src/client/pages/dashboard/Block.tsx`); while a block's figures are loading it offers neither, since its table does not hold them yet; figures shown beside a chart that are not in its table (the handoff block's period totals and silences) go in the block's `footer`, which stays readable; the CSV and that table are built from one `BlockTable`, so they cannot disagree. Chart colors are read from the theme's CSS variables and re-read when the theme flips (`useChartPalette`).

Each block loads on its own (`useBlock`). A new filter takes the previous view's figures off the block at once, so nothing of the old view stays on screen or clickable while the new one loads; a refresh of the same view (the ceiling's poll, a retry) keeps them until the new ones arrive. A block whose request fails says so, with a retry, and offers no CSV: an empty result and a failed one never look alike.
