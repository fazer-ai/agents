# Occurrences

A monitor of why customers get in touch, grouped across conversations: any reason of contact, a request, a question or a failure, is grouped into a theme with the conversations that share it. A theme is flagged when it runs out of the usual, which is not the same as something going wrong: a new kind of request is flagged as well. No single conversation shows that, and the categories an observer applies per conversation are too broad to. Issue #314 describes the whole design; this document describes what is built.

## What is built so far

- **Readings.** The account declares the fields the monitor reads off each conversation and the inboxes it reads. Every round, the monitor reads the conversations of those inboxes that have new customer messages, by itself, and stores what it read in `conversation_readings`, one row per conversation and field. No agent is created, granted or pointed at it.
- **Canonical references.** When the account reads a reference, a model fits its free spellings to canonical names, and an alias dictionary remembers each decision.
- **Themes.** The model assigns each new reason sentence to an open theme or proposes a new one. Periodically, it merges, splits and renames the open themes.
- **Flags.** Every round counts each open theme exactly and flags it as new, above its usual, or concentrated on one reference.
- **Rounds.** Every few minutes a round runs those steps and leaves an `occurrence_runs` row with what it read, how long it took, how many model calls it made and what they cost.
- **Monitors.** An account has up to 10 monitors, each with its own name, inboxes, fields, model and cadence, and its own readings, themes, canonicals and rounds (see "Monitors").
- **Configuration**, through the console, REST and MCP. A monitor is off by default.
- **Dashboards.** A panel's `occurrences` source reads one monitor, the one picked in the panel editor (`monitorId`, pinned on save to the account's first when none is named), and shows its open themes now (an "occurrences now" panel, flagged first, on a TV as well) or the period's conversations by canonical reference (docs/dashboards.md).

## Monitors

Each monitor is a row of `occurrence_monitors` (`src/modules/occurrences/monitors.ts`): a `name`, unique in the account and up to 80 characters, a `position`, and its configuration in `config` (see "Configuration"). Every row the monitor writes carries its `monitor_id` (`conversation_readings`, `occurrence_conversation_reads`, `occurrence_runs`, `occurrence_themes`, `occurrence_theme_members`, `occurrence_theme_events`, `occurrence_canonicals`, `occurrence_aliases`), and the uniques are per monitor: one reading per monitor, conversation and field, one read mark and one theme membership per monitor and conversation, one canonical per monitor, field and name, one alias per monitor, field and spelling. So two monitors never share a theme, a canonical, a flag or a round.

- **The first monitor** is the one with the lowest `position` (then the lowest id). The paths from before there were several (`/v1/occurrences/config`, `/runs`, `/themes`, `/cost`, and the MCP tools without `monitor_id`) answer for it. An account with no monitor reads the defaults there, and its first save on one of them creates the first monitor, named "Ocorrências", in the same transaction as the save, so a save that is refused leaves the account without a monitor.
- **One inbox in two monitors** is allowed. Each monitor reads the conversation on its own: its own read mark, its own readings (two monitors with different fields or a different model read the same conversation differently) and its own cost. There is no deduplication.
- **The Chatwoot attribute** is the one thing two monitors cannot share: two monitors that copy a field with the same `key` to Chatwoot (`attribute: true`) on the same inbox would overwrite each other's value on every conversation they both read. A save that would leave that is a 422 naming the other monitor, the attribute and the inbox.
- **At most 10 monitors** per account (`MONITORS_MAX`): creating or duplicating past it is a 422.
- **Duplicating** copies the configuration only, off and with no inboxes, so a copy never reads the same conversations by accident; its themes, canonicals and rounds start empty. Without a name it takes the original's, numbered ("Ocorrências (2)").
- **Deleting** removes the monitor with every row it wrote, by cascade, and cancels its round under the round's own lock, so a reconcile in flight cannot arm it again. It answers how many open themes and rounds went with it.

Every write that reads the account's other monitors (the cap, a taken name, the attribute rule) takes the account's monitor lock first, so two saves at once are checked against what is there when each commits. The audit trail records `occurrence_monitor.created`, `occurrence_monitor.updated` (a rename, or the configuration before and after) and `occurrence_monitor.deleted`.

**The migration** `20261023120000_occurrence_monitors` turns each account's `occurrences` block of `tenant.settings` into its first monitor, "Ocorrências", with the block verbatim, and gives every row of the monitor that monitor's id. An account with rows of the monitor but no block (a block lost while its readings stayed) gets a monitor that is off, so nothing is lost; an account with neither gets none. A saved dashboard panel of the source names the monitor (`monitorId`), the account's round job is rekeyed to it, and the block leaves `tenant.settings` once the monitor holds it. It runs in one transaction and changes nothing the second time.

## Configuration

A monitor's `config` (`src/modules/occurrences/settings.ts`), validated on every save of that monitor.

- `enabled`: off by default, and also off for a block that no longer parses, so a damaged block never starts spending a model. A block that parses but can no longer run (one saved before the monitor named its inboxes and model, with `agentId`, or one still under the names the 20261022120000 migration renamed) reads as an off draft that keeps its fields.
- `inboxIds`: the inboxes whose conversations the monitor reads and counts, up to 50 (`Inbox` row ids as strings); `inboxIds` replaces the list on write. An inbox a write adds must be this account's (the refusal names it); one no agent receives is accepted and read through the Chatwoot API (see "Inboxes no agent receives"). Readings of any other inbox stay stored and count nowhere (see "The monitored inboxes").
- `fields`: the account's own fields, at most 10. Each has:
  - `key`: lowercase letters, digits and `_`, up to 64 characters, and never a name every object already has (`__proto__`, `constructor`);
  - `name` and `description` (what the monitor's reading is told to write), both without what the database refuses (a NUL or half of a character);
  - `attribute`: whether the value is also written to the conversation's Chatwoot custom attribute of the same key, so folders can filter by it.

  Nothing in the code or the console names a field. `fields` replaces the whole list on write. The console never asks for a key: a new field takes its key from its name (lowercase, accents dropped, anything else an underscore, a number added when another field holds it), and a saved field keeps its key when it is renamed, since its readings are stored under it. The key is shown only where it is the Chatwoot attribute's name, under a field written to the conversation.
- `reasonField`: the key of a declared field, required to switch the monitor on. The reason is why the customer got in touch, in one short sentence, of any kind; it is what themes are made of. A conversation whose reason is empty joins no theme.
- `referenceField`: optional, the key of another declared field, never the reason's. The reference is what the reason refers to, whatever the account deals with, and is what the canonical names and the concentration flag count by. Without it the monitor works the same, except that the concentration flag is never raised; the console says so where that threshold is.
- `cadenceMinutes`: minutes between rounds, 5 to 1440 (default 15).
- `consolidationMinutes`: minutes between consolidations, 15 to 10,080 (default 60).
- The flags' thresholds (see "Flags"):
  - `newMinConversations` (N): 1 to 10,000, default 5;
  - `windowMinutes`: the recent window, 15 to 1440, default 60;
  - `previousDays`: 1 to 30, default 7;
  - `aboveUsualRatio` (X): 1.1 to 100, default 3;
  - `concentrationShare`: 0.1 to 1, default 0.6.
- `model`: the one model every step runs on, `{ provider, model, credentialRef, baseURL }` or null, required to switch the monitor on. `credentialRef` is a `vault:<id>` of this account of a kind that holds an API key (the agent's model key's rule), required for every provider but `openai-compatible`, which needs a model id and an endpoint instead (its own `baseURL`, or the credential's: a model with neither, or on a credential with no base URL, is refused on save). With no credential it sends the placeholder key `no-key`, since the OpenAI SDK refuses an empty one before any request; a keyless server ignores it. `baseURL` is refused on a provider whose adapter drops it (`PROVIDERS_HONORING_BASE_URL`: only `openai-compatible` and `openrouter` take one), since the conversations would go to the vendor instead of the proxy; the same holds for an endpoint the model would inherit from its credential, and a model saved with either before does not run. A null or blank `model.model` is the provider's default. A write replaces `model` whole; one that leaves it out keeps it. The console lays it out as the agent's Model card (provider and model on one row, the API key below, and the base URL for `openai-compatible` only, as the agent's card shows it; an `openrouter` endpoint is set through REST or MCP, and the console keeps one it did not show), says under the field what keeps the model from saving (the model id or the base URL; a missing key is said by the key picker), drops the base URL when the provider changes, so a new provider's key never goes to the old server, and sends the model only when it changed, so a monitor whose saved model can no longer run can still be switched off. The credential shows in the vault's references as the occurrence monitor when any monitor uses it. The audit trail keeps the endpoint as its scheme and host only, since a URL can carry a key. Per-step models were dropped: the 20261022120000 migration keeps the reading's as the one model.
- `businessContext`: optional, up to 2,000 characters, without what the database refuses. Every step's prompt gets it after its fixed instructions, inside a `<business>` block, as context about the business; empty sends nothing. The fixed prompts are not editable through any transport.
- `recoverMedia`: off by default. On, the reading transcribes and describes again the voice notes and images upstream Chatwoot no longer holds (see "Voice notes and images on upstream Chatwoot" under "Readings"). The console shows it as "Old voice notes and images".

Switching the monitor on requires `inboxIds`, `model` and `reasonField`. A block that is off may be incomplete, so a draft saves. Any other invalid value is a 422, and so is a key the block does not have (in the block, in a field or in the model), which is refused rather than dropped; the block is left as it was. The names the block had before, `subjectField`, `problemField` and `models`, are such keys: REST and MCP refuse them.

**The migration** `20261022120000_occurrence_reason_reference_one_model` rewrites every stored block: `subjectField` becomes `referenceField`, `problemField` becomes `reasonField`, and `models.reading` becomes `model`; a value already under the new name wins, and the old keys are removed. It also renames the dashboard source view `subjects` to `references` on stored panels. It only touches blocks that still hold an old key, so applying it twice changes nothing. The column `occurrence_themes.flag_subject_id` keeps its name; the code calls it `flagReferenceId`.

## Readings

The reading is the round's first step (`src/modules/occurrences/reading.ts`). There is no tool for it: an earlier version had agents write readings through a native `record_reading` tool, which made what the monitor counted a side effect of which agent had the grant. It was removed before release; an allowlist that still names it gets nothing.

Which conversations a round reads:

- conversations of the monitored inboxes whose customer wrote after their last reading (`conversations.last_inbound_at` against `occurrence_conversation_reads.read_inbound_at`, and the newest customer message's Chatwoot id against `read_inbound_message_id` where the mirror has one, since two messages in the same second share a time);
- a conversation never read only when its newest customer message is inside the recent window (`windowMinutes`) of the round, so switching the monitor on reads what is happening now, never the whole history. Admitting it writes its row in `occurrence_conversation_reads`, so a conversation the per-round cap, the budget or the spend ceiling left for later stays due after the window moves past it;
- at most **200 per round** (`READINGS_PER_ROUND`), the ones waiting longest first; the rest wait for the next round, and the round's `detail.reading.pending` says how many;
- with at most half of the round's model budget: past it, no new read starts, a read still waiting for a permit or for its model is cut there, and what is left waits too, so the themes and the flags keep the other half.

What the model reads: the conversation's newest **30 messages** (`READING_MESSAGES`), customer and team, private notes, reactions and activity lines excluded, rendered as the observer renders them and capped at 20,000 characters from the newest back. As the observer, it overlays the transcriptions and image descriptions only this process holds (an upstream Chatwoot drops the attachment-meta write-back) and leaves out everything before the conversation's last `/reset`, before any quote is resolved, so the episode the reset ended is never read back. What the reading does with each customer message's media is one decision (`occurrences/media.ts`, `settleMedia`), and the reading never waits for it. A message's media is complete when every voice note has its words (or was transcribed to nothing) and its files have their content: the arrival pass's result held in this process (written once, when every file is through, including an email's inline images and a count of files it could not read), or a description or text on every file's own attachment. A message whose media is not complete and that is younger than **10 minutes** (`READING_MEDIA_GRACE_MS`, by the message's own time) leaves the conversation due for the next round, with no failure counted; older, or with no time, it is read with the renderer's marker (a voice note never transcribed, a file never described, or either gone from this process's memory on upstream Chatwoot, below). A customer message that arrives during the read is not part of it and keeps the conversation due; and the account's fields, each as `key (name): description`. The prompt carries **no list of values written before**. In the prototype, listing the recent values in the extraction prompt lowered folder precision from 96% to 91-93%, because the model forces a conversation into a name it was shown. The model extracts free text here, and similarity is judged later. It answers one JSON string per field; a conversation with no public message is read as saying nothing.

**Voice notes and images on upstream Chatwoot.** On the fazer.ai Chatwoot, a voice note's transcription and an image's description are saved on the attachment, and the monitor reads them at any age. On upstream Chatwoot they are not saved anywhere: this process holds them in memory for about 15 minutes, and a round can come later. With `recoverMedia` off (the default), a voice note or an image older than that reaches the monitor with the renderer's marker instead of its content, and the conversation is marked read. With it on, the reading recovers them first (`occurrences/recovery.ts`): each customer message the transcript renders (among its last 30 messages, and whole or cut within its character budget, counting what was recovered so far) whose media is not complete and that the conversation's last reading did not cover, the newest 5 of them, newest first (`RECOVERY_MAX_MESSAGES`), is transcribed again with the speech-to-text and described again with the vision of the agent that receives the inbox (the bound responder, else the first observer), with that agent's provider, key and model. Nothing is recovered when the monitor's own model does not resolve, since no reading could use it. An inbox whose agent is off, has neither switched on, or has a contact authorization gate recovers nothing and is read as before: the reading cannot ask that gate, and no refusal on record is not consent (a message from before the binding was never asked about). Each call asks the spend ceiling first, stops at half of the reading's remaining time (`RECOVERY_TIME_SHARE`, after the least time a model call needs), so the reading itself always keeps its own, keeps to the contact authorization's refusal marks (the conversation's and the one that agent left as a watcher), and is billed to the account with no agent, under its own node: `occurrence_transcription` ("Occurrences: voice note transcription") and `occurrence_vision` ("Occurrences: image reading"). Speech-to-text providers report no usage the price table can read, so a transcription's row carries no tokens and no cost, counted as a call with no price, written only when this call reached the provider (a voice note another pass transcribed, or was transcribing, is billed there), under the model that ran (the provider's default when the agent names none), even when the reading's time runs out during the write-back, and never repriced (`scripts/reprice-usage.ts` leaves `price_table = 'unmetered'` alone); an image's row is priced like any vision call. What was recovered is kept in this process's memory like the arrival pass's result, so a reading in the next 15 minutes does not pay for it again, and a message an earlier reading covered is never recovered, so each one is paid for once: when the customer writes again, the older voice note is read with its marker.

The transcript goes to the model escaped inside `<conversation>`, so a customer's own tag cannot close the block. A read that fails (Chatwoot could not be read, including a page it answered with a body or rows that do not parse, the provider erred, or the answer was unreadable) is counted against the customer message it was for, by its time and, where the mirror has one, its Chatwoot id (`failed_inbound_at` and `failed_inbound_message_id`), so a second message in the same second starts with no failures; after 3 (`READ_FAILURES_MAX`), that message is given up on until the customer writes again. A read the spend ceiling, the round's budget or the reading's share of it (also when it ran out while the call was out or waiting for a permit) or a step model that does not resolve refused is not a failure: the step stops there and the conversations stay pending. Four reads run at once, each as background work through the instance's model limit.

How a call is stored:

- Each value is trimmed, collapsed to single spaces and capped at 500 characters.
- An empty string is a value of its own: the conversation was read and said nothing. An empty reference is the no-reference bucket.
- A field the call did not name keeps whatever was stored for it.
- A call that names no field records nothing.

The Chatwoot write happens first, with the admin token. Only `attribute` fields with a non-empty value are written. If the round's budget ends inside the client's queue, or while the reading's write waits for a connection or a statement (which rolls it back), nothing is stored. Any other failure of that write is logged, and the reading is stored anyway: the reading is what the monitor counts, and the attribute is a copy for folders. Everything is fenced on the `/reset` mark that governed the transcript: a reset after it, while the model reads or by the time the copy's fence asks, means the values are the erased episode's, so the copy is called off and nothing is stored, and the conversation stays due for the new episode. A reset landing after that last check is caught under the conversation's row lock when the reading is stored, which leaves the reading with its canonical copy withdrawn. Right before it posts, the copy (the reading's, and the canonical's below) asks whether the monitor as saved now still copies that field on that inbox: a round reads its configuration once, at its start, and a save since may have let another monitor take the attribute there. A copy refused that way is skipped, and the reading is still stored and the conversation marked read; a monitor deleted mid-round starts no more readings.

`conversation_readings` keeps `first_read_at` from the first reading of that conversation and field, with `first_inbound_at`, the customer message that reading covered, and moves `last_read_at` on every later one. The flags count a conversation at `first_inbound_at` (see "Flags"); a theme's first and last seen, and the dashboard's references view, still go by `first_read_at`. `agent_id` is null on what the monitor reads; rows written by an agent before the change keep theirs.

## The monitored inboxes

Only conversations of `inboxIds` are read, fitted, assigned, flagged, copied to Chatwoot and counted on a dashboard. A theme member whose conversation is in another inbox (read before the monitor named its inboxes, or an inbox taken off the list) leaves its theme at the start of the next assignment, like a conversation whose reason was cleared; its readings stay, and it is placed again if its inbox comes back. Until then every read path (REST, MCP, the console and the dashboard source) filters a theme's conversations by the list saved now, so taking an inbox off takes its conversations off the counts, the first and last seen (and the list's order by them) and the theme's detail at once, and the save counts the flags and their reference again over the new list. The flags step always counts over the block saved at that moment, read under a share lock on the account's row, so a round that started with the old list cannot write back flags from an inbox already taken off. A theme with no member left is not listed.

The reading step asks, every round, which of the listed inboxes an agent receives right now (bound or observing). The mirror of those is fed by the agents' Chatwoot webhook as messages arrive; every other listed inbox (one no agent ever received, or one whose agent was unbound since it was listed) is listed through the Chatwoot API, below.

### Inboxes no agent receives

An inbox answered only by people has no agent and so no webhook: the conversation mirror (`conversations.last_inbound_at`), which feeds the reading queue, never hears of its customers. The monitor sweeps those inboxes itself (`src/modules/occurrences/sweep.ts`) with the instance's admin token, and changes nothing in Chatwoot: no bot, observer, webhook, status, assignee or label. An account webhook was rejected because it is a write into the customer's Chatwoot configuration and pushes every event of a busy human inbox at us for a real time the monitor does not need; a bot was rejected because it takes the inbox's new conversations away from its people.

The sweep is a job of its own (`OCCURRENCE_SWEEP`, one per monitor, key `occurrences-sweep:<monitorId>`), apart from the round: it is armed and cancelled with the round (switching the monitor on or off, a save, boot), re-arms one cadence after each run, is retired when the monitor is deleted, and has its own time, the scheduler's run deadline less a minute (`SWEEP_BUDGET_MS`), so the round's reading never shares its time with the listing. It only fills the reading's queue; the round reads what the last sweep queued. **What the operator sees:** a conversation in an inbox no agent receives can take up to one cadence longer to be read than one an agent receives, since it is queued by one sweep and read by the next round.

- **Listing.** Each such inbox, the one swept longest ago first (`occurrence_sweep_cursors.swept_at`), is listed by latest activity, every status (`GET /conversations?inbox_id=…&status=all&sort_by=last_activity_at_desc`, the listing the reconcile sweep uses), page by page, until a page holds an unpinned conversation whose activity is before the later of the monitor's cursor for the inbox (`occurrence_sweep_cursors.activity_at`) and the window's start (`windowMinutes`). Conversations the token's user pinned lead page one whatever their age, so only an unpinned one ends the listing, and an old pinned one is not queued; when the pins changed during the sweep (see Budget), the cursor does not move. A conversation two pages both list (it moved between the requests) is queued once, at its newest activity. At most 8 pages of 25 per inbox per round (`SWEEP_PAGES`). A page shorter than 25 is the end of the listing. The cursor moves, to the newest activity listed, only when the whole listing fit in its first page: the pages are by offset, so a conversation leaving the inbox between two requests slides the next one onto a page already read, and a single request is safe from that. A longer listing leaves the cursor where it was and the next round lists from the top again, so what slid is listed then, and the conversations past the 200th are not read while the inbox stays that busy. No messages are fetched here.
- **The queue.** Each conversation listed is put in the monitor's own read queue (`occurrence_conversation_reads.swept_activity_at`, moved forward only) at the activity it was listed with, and with the activity at which it last became due (`swept_due_since`: set when newer activity lands on a conversation whose last listing was covered, kept while it waits). A conversation the mirror does not have gets a bare row in `conversations` first (inbox, thread, status), inserted once and marked `sweep_only`, which the sweep never writes again. Only the mirror's rows of this inbox are queued: a conversation the mirror holds in another inbox (moved by Chatwoot) is not followed. The sweep writes nothing else to the mirror.
- **Due, and the reading.** Only while its inbox is swept (no agent receives it now): in an inbox an agent receives, the conversation follows its mirror whatever the sweep left pending, failures included, and its reading closes what the sweep left. A queued conversation is due when its listed activity is newer than the one its last reading covered (`read_swept_activity_at`), with or without `last_inbound_at`, and it shares the per-round cap (`READINGS_PER_ROUND`, 200) and the reading's order with every other due conversation, so one the cap left for later stays due. The reading fetches its transcript as for any conversation (one messages fetch) and finds its newest customer message (incoming, not private, not a reaction, after the last `/reset`). When that message is one the last reading already covered, or, never read before, was before the window as of the activity it became due at (so the team's later activity does not age out a message the cap left for later), the activity was the team's or an automation's: the conversation is marked read with no model call. Otherwise it is read as any other, and the covered message is that one (its time and Chatwoot id), as no mirror holds it. The listed activity is closed (`read_swept_activity_at`) only when the transcript was fetched a whole second after it: Chatwoot states activity in seconds, so a second customer message in that same second would not move it. A transcript fetched within that second keeps the mark of the message read and leaves the activity due, and the next round's fetch reads the other message, or finds the same one and closes it with no model call. A failed read is counted against the listed activity, and after `READ_FAILURES_MAX` the conversation waits for its next activity.
- **A failed listing.** The inbox is skipped by that sweep with its cursor where it was, its failure is logged and kept on its cursor (`unlisted_at`, cleared by the next listing that works), and each round while it stands says so once in `detail.skipped` (`reading: the conversations of the inbox "<name>" could not be listed from Chatwoot`, reason `inbox_unlisted`); the round still reads what its queue already had, and the next sweep lists again. Rounds from before the sweep may still carry `reading: no agent receives the inbox "<name>"` (reason `inbox_unreceived`).
- **Budget.** Each sweep makes at most 30 requests to Chatwoot (`SWEEP_REQUESTS_PER_ROUND`), pins and pages: a quiet inbox costs one request, and the inboxes that do not fit wait for the next sweep, first in line. The pins are asked once per Chatwoot account before the inboxes and once after, and the cursors are written at the end, only for the accounts whose pins did not change. Each inbox tried records the attempt at its start (`swept_at`), so one the sweep's time cut off, or whose listing failed, goes to the back of the line with its cursor where it was. Its Chatwoot clients expire where the sweep's time does. An inbox of a disconnected Chatwoot account is not swept.
- **`conversations.sweep_only`.** A row only the sweep inserted is no agent's, so the Conversations list (`buildConversationsWhere`), the analytics cohort (`cohortWhereSql`) and the dashboards' conversations source (`conversationWhere`) leave it out. The first webhook for the conversation (an agent bound to or observing the inbox later) mirrors it as a new conversation over that row, as a created row takes its state from the payload, and clears the flag; the read queue rows keep pointing at it. The dashboards' dirty trigger watches the flag, so the kept day that conversation reaches is counted again.

## Model

Every step runs on the provider, credential and model `model` names. No agent lends its key, its prompt or its reasoning effort. The model is resolved once per round; a credential deleted or of the wrong kind skips every step with one line each in `detail.skipped`.

Each call:

- asks the spend ceiling first, and a refusal skips that step for the round, leaving its input for the next;
- is billed to the account in `llm_usage`, with no agent, under the step's own node (`occurrence_reading`, `occurrence_canonical`, `occurrence_assignment` or `occurrence_consolidation`), with its model, cost and latency; a reading is tied to its conversation and inbox. The cost dashboard's split by call type shows the four as lines of their own ("Occurrences: reading", "Occurrences: reference names", "Occurrences: theme assignment" and "Occurrences: theme consolidation"), never under "Observer". The media recovery's two nodes are lines of their own too (see "Readings");
- is traced to the account's Langfuse when it has one;
- answers JSON, and an unreadable answer skips the step the same way.

The round sums its own calls into `model_calls` and `cost_usd`. The steps say why they skipped in `detail.skipped`.

## Canonical references

When the account reads a reference, every round each reference reading without a canonical is fitted:

1. The exact spelling is looked up in `occurrence_aliases`. A spelling decided before is never sent again.
2. Every spelling the dictionary has not seen goes to the model, in batches of 100, with the existing canonical names. The model answers an existing name or a new one. There is no case or accent folding: a spelling one letter away from a known one is still the model's decision.

An empty reference is the no-reference bucket. It is never sent and never becomes a canonical.

The dictionary and the canonical names belong to the reference field they were decided for (`field` on both tables): switching `referenceField` starts a new dictionary, so another field's values are never fitted with the old one's decisions. A name the model writes is stored as a reading is, without what a `text` column refuses.

When the reference field has `attribute: true`, the canonical name replaces the raw spelling in the conversation's Chatwoot attribute, so a folder filters by the canonical. The copy is written with the admin token, even when the canonical is the spelling itself, up to 200 per round, newest readings first, as the round's last step, so a slow Chatwoot spends only what the analytical steps left. A copy whose check could not read the reading or Chatwoot is not written and is tried next round. A `/reset` withdraws the conversation's pending copies before it clears the attributes, so a copy, one already queued included, never writes the reference back over the cleanup; an observation whose attribute write the fence admitted before the reset moved its mark stores its reading with the copy already withdrawn, since the reset's withdrawal may have run before that reading existed; the next reading of the conversation, in the new episode, makes it pending again. A copy that failed waits behind the ones never tried (`copy_tried_at`), so a conversation whose Chatwoot keeps refusing cannot take the whole batch, and a reading that changed between the check and the write keeps the name just posted among the leftovers it accepts, also when Chatwoot's answer to that write was lost (only a write its fence called off was surely not sent). `conversation_readings.canonical_written` says whether Chatwoot holds it: every write of the reading clears it, since the reading has just written its own spelling there, so a reading of the same spelling gets the canonical back next round, and a copy Chatwoot refused or the round had no budget for is tried again. The copy writes the name the conversation was given before when there is one (`written_name`, kept across merges, so a folder on an absorbed name keeps the conversation), and the survivor's otherwise. It asks, inside the conversation's write queue, whether the reading is still the one it chose and whether Chatwoot holds that spelling, nothing, the canonical, or what it may still hold from before this spelling (`remote_before`: the copy's last name, or every spelling since it, up to 5, leftovers of reading writes that failed), so a newer reading's write keeps its value even before its reading is stored. A write that slips between that read and the copy's own is rewritten by the next round, since the reading clears `canonical_written`.

A reading whose value changes loses its canonical, so a corrected reference is fitted again and a cleared one falls in the no-reference bucket. A spelling that changed while its fit was in flight is neither bound nor written to Chatwoot; it waits for the next round.

At each consolidation, the model may merge a canonical into another one that exists. The absorbed name's aliases and readings follow the survivor, and its redirect always points at the final survivor. A canonical is never renamed, since a folder may filter by it. Conversations already written to Chatwoot keep the name they have, so a folder built on the absorbed name keeps its conversations.

## Themes

`occurrence_themes`, with each conversation in at most one theme (`occurrence_theme_members`) and its own reason sentence kept verbatim.

**Assignment, every round.** The assignment model gets:

- the reason sentences no theme holds yet with that sentence, up to 100 per call and 5 calls per round;
- the open themes, up to 200, each with its title and up to 3 of its newest distinct sentences, taken from its 100 newest members.

It answers an open theme or a new title for each sentence. A conversation read again with the same sentence is not sent again, so it is never counted twice. A conversation whose sentence changed is assigned again and moves. A conversation whose reason was cleared, or that has no reading of the reason field since that field was switched, leaves its theme; the same words read for a new field are placed again with their own time. One changed or cleared while the model ran is not placed: it is the next round's. A call's answer is written in a handful of statements, whatever the number of sentences, so a full batch stays inside its transaction's budget.

**Consolidation, every `consolidationMinutes`.** The consolidation model gets the open themes with title, count and up to 5 sample sentences, never every conversation. It answers merges, splits and renames:

- A **merge** moves the absorbed theme's conversations to the survivor and redirects the absorbed theme to it. Every older redirect to the absorbed theme moves to the survivor too, so a redirect is never a chain. The merge is recorded in `occurrence_theme_events`, naming absorbed and survivor.
- A **split** names one part per concrete reason the theme mixes, as many as there are, and never cuts one reason across two parts; a theme whose sentences are all one reason is renamed, not split. The three calls (assignment, consolidation, partition) share the same definition of a theme, `THEME_IS` in `themes.ts`. A second call places each of the theme's sentences, up to 300, in one of them, with sentences that state the same reason in the same part. A sentence the answer leaves out goes to the first part, so no conversation is dropped. The split theme ends with status `split`.
- A **rename** changes the title and is recorded with the old and the new one.
- Each decision carries a **reason**: one sentence on what makes the themes the same reason (merge), what separates the parts (split), or what the old title failed to say (rename). It is stored in the event's `detail.reason`, cleaned like a title (no NUL, no lone surrogate, spaces collapsed) and clipped to 200 characters, never refused. An answer without a reason, or with one that is not text, is applied as before and its event has no `reason`. The reasons are the only thing the consolidation call asks for on top of the decisions: its input is the same, and the partition call is unchanged.

## Flags

Counted exactly at the end of every round, from the members of each open theme. A conversation counts at the customer message its first reading covered (`conversation_readings.first_inbound_at`, kept from the reading of the reason field the member was placed from), not at the instant it was read: a round reads late whenever the one before could not read everything due (the per-round cap, half the model budget, the spend ceiling, a failed model), and counting at the read would move a backlog into the window as a spike, raise a peak's flag late and keep it up after the peak. A reading stored before that time was kept (the 20261025120000 migration adds the column empty), or with no customer message to cover, counts at `first_read_at`. A member read after the round's own time does not count.

- Every flag needs at least N conversations in the recent window.
- **new**: none in the `previousDays` before the window.
- **above_usual**: the window's rate is X times the theme's own rate over the time the monitor actually covered before the window. Covered time is the previous days, or less when the readings start later, from the earliest conversation counted, by the time it counts at. Dividing by days nobody read would make every theme look unusual on the monitor's first day.
- **concentrated**: at least `concentrationShare` of the window's conversations share one canonical reference. Conversations with no reference count in the window but never as the concentrated reference. A monitor with no `referenceField` never raises it.

The theme keeps the reference most of its window conversations share (`flag_subject_id`, `flagReferenceId` in the code), and `flagged_at` while it stays flagged.

## Rounds

`OCCURRENCE_ROUND` is one perpetual scheduler row per monitor (`src/modules/occurrences/arm.ts`), keyed `occurrences:<monitor id>` with the monitor's id in its payload, so each monitor runs on its own cadence:

- it is armed when the monitor is saved on, and at boot for every monitor that is on;
- it is cancelled when the monitor is saved off or deleted;
- each save's reconcile runs alone per monitor and reads the configuration only once it holds the lock, so the last one reads the last save and an older save never cancels the round a newer one armed. It writes the job in that same transaction, so it never waits on a second connection from the pool.

When it runs:

- A round on a monitor that has been switched off or deleted, or a job that names no monitor, returns done and is not rearmed.
- A round whose configuration cannot be read retries in a minute.
- Every other round reschedules itself `cadenceMinutes` later.

A round runs, in order:

1. the reading of the monitored inboxes' conversations;
2. the canonical references, when the account reads one, so this round's flags already count by canonical;
3. the assignment of new sentences;
4. when no round consolidated within `consolidationMinutes`, the consolidation of themes and of canonicals;
5. the flags.

A round stops calling models a minute before the scheduler's deadline for the run, or as soon as the run is called off; each call is also capped at two minutes. Its calls go through the instance's model limit as background work, so they yield their permits to customers' turns, and the round's deadline holds across the wait for a permit, the call and a retry. What was skipped waits for the next round. A consolidation counts only when both passes completed, so one cut short, refused by the spend ceiling, answered unreadably or with a split it could not partition is tried again next round instead of a whole interval later.

Every round writes an `occurrence_runs` row before it reads anything, then closes it with:

- `status`: `ok` or `failed`;
- `finished_at` and `duration_ms`;
- `readings`: how many conversations this round's reading step read, the same number as `detail.reading.read`. A reading written outside a round is not counted. `counted_until`, which the earlier windowed count wrote, is no longer written;
- `model_calls` and `cost_usd`, the sum of the round's own ledger rows, with `unpriced_calls` for the calls with no price: `cost_usd` sums the priced ones, and is null when none had one, which the console shows as "No price" rather than a zero. The rounds are read from the ledger rows of the round's thread (`occurrences:<tenant>:<run>`), so a call an adapter finished after the round gave up on it, whose row lands after the totals were saved, is still counted; the saved totals answer for a run with no rows;
- `consolidated`, when the round ran the consolidation;
- `detail`: what each step did (`reading`: read, failed, withdrawn, pending; `canonical.asked` and `assignment.sent` count only what a call that reached the model carried, so a step that could not run, or a call the round's deadline ended while it waited for a permit, sent nothing), the steps it skipped and why (a provider's error sanitized, since it can echo the key; the same line said by many reads folded into one with its count, at most 20 lines), and `error` when the round failed, with the message sanitized.

A process that dies mid-round leaves the row at `running`.

The spend ceiling is the account's: every monitor's calls count toward it, before each call, as an agent's do. The 200 conversations a round reads at most are per monitor.

Every table of the monitor is under FORCE row-level security, with the tenant policy and the fleet super-admin policy.
