# Client channel

An agent embedded in a host application. The host's **server** calls `POST /api/v1/agents/:id/client/turn` with a tenant API key; its page declares the tools it runs itself, in the browser, with the signed-in user's session. A turn runs until the model answers or calls client tools; on the second it suspends (`src/graph/client-tools.ts`) and the caller gets the calls back as `pending`, runs them, and resumes the same turn with the answers on the same route. Each answer is clipped to the 20,000 characters the model reads before the turn resumes with it (`boundClientAnswers`), since the resume value is checkpointed as sent: a page that hands back megabytes stores what the model sees, not the whole payload.

**Off by default.** The channel runs only where `CLIENT_CHANNEL_ENABLED=true`, while it is tried with its first host. Off, the route answers 404 before routing (`src/api/lib/client-channel-gate.ts`, on `onRequest`), so before auth, the tenant selector and the body, exactly like a route that does not exist; it is left out of the API reference (`detail.hide`); and the console shows no client source (the ceiling's client bar and field, the dashboard's segment, the logs' filter), reading the switch from `GET /auth/me` (`clientChannelEnabled`). What is already recorded stays: usage, logs and threads are not touched by the switch.

Code: `src/modules/client-channel/` (`service.ts` runs the turn, `identity.ts` binds the thread, `case.ts` opens a case in the team's inbox, `stream.ts` and `progress.ts` stream its progress), the natives this channel offers in `CLIENT_CHANNEL_NATIVES` (`src/graph/tools/channel-natives.ts`), the thread shape in `src/graph/detached-thread.ts`.

## Trust model

The API key authenticates the host's server, and a key is a tenant admin credential: it can already read and configure everything the tenant has. So the user the server names in `user` is taken as given. The agents does not, and cannot, verify that the person in front of the browser is that user: the host's own session does that, and the key is the statement that the host is trusted to have done it.

What follows from that:

- The key never goes to a browser. A page that called the route directly would hand every visitor a tenant admin credential.
- A signed token per user (a JWT the host mints and the agents verifies) only becomes necessary when a browser calls the agents directly. That is what the SDK adds ("Embedding with the SDK" below); the key route above keeps working for a host that would rather proxy.
- The client tools run with the **user's** session, in the browser, so what the agent reads through them is what that user may read in the host, and nothing more. The agent's own server-side tools (knowledge base, HTTP, MCP) run with the tenant's credentials, the same for every user of the host.

## Embedding with the SDK

The route above asks the host to proxy every turn through its server. The SDK lets the page call the agents itself, with a JWT the host's server signs for the signed-in user, so the host's part shrinks to one route that signs. This section covers what exists today: the application the JWT is signed for, the turn the page calls with it, the anonymous visitor's session, and the widget that calls them.

**The application** (`client_apps`, `src/modules/client-apps/service.ts`) belongs to one agent and carries a `public_id` (`app_…`, random: what the page names and the JWT carries in `aud`), the exact origins its pages may call from, whether anonymous visitors are allowed (off by default), and their limits (`anon_sessions_per_hour`, default 20, up to 1000; `anon_messages_per_min`, default 10, up to 120), and an optional monthly spend ceiling of its own ([`spend-ceiling.md`](spend-ceiling.md), "An embedding app's own ceiling"). Origins are stored as the browser sends `Origin`: https, or http on loopback only, no path, no query, no wildcard (`URL` accepts `*` as a hostname character, so it is refused by hand).

**Its keys** (`client_app_secrets`) are HS256 keys the host's server signs with, named by `kid` in the JWT header. They are stored encrypted, not hashed, because verifying an HMAC needs the key itself, and returned once: by the call that registers the app (which mints the first key, since an app with no key signs nobody in) and by the call that rotates. Rotating makes the new key current and gives the previous one 24 hours (`ROTATION_GRACE_MS`), long enough for tokens it signed to run out (they live an hour at most) and for the host to deploy the new secret; a key still in an older grace window ends at that moment, so at most two keys verify at once. Revoking ends a key now, the current one included, for a key believed leaked. `resolveClientApp` reads the app by `public_id` before any tenant context (`asSuperAdminOn`, like the Agent Bot's route token) and returns only the keys that still verify.

**Who may do what.** Registering an app and rotating its key mint a credential, so both are a signed-in person's act confirmed with their password (`requireSession` and `confirmStepUp`, as minting an API key is) and neither is an MCP tool. Listing, editing, deleting and revoking a key are REST (`/v1/client-apps`) and MCP (`client_app_list`, `client_app_update`, `client_app_delete`, `client_app_key_revoke`). The console's place is the agent editor's Channels tab ("Embedding applications"). All of it follows `CLIENT_CHANNEL_ENABLED`: off, the routes answer 404 before routing, the MCP tools refuse, and the section is not drawn. Every change is audited (`client_app.*`), never with a key.

**The browser's turn** is `POST /api/v1/sdk/:app/turn` (`src/api/v1/sdk.controller.ts`), with `:app` the app's public id. Its body and answer are the proxy route's, JSON or SSE, without `user`; the user comes from the token:

- `Authorization: Bearer <jwt>`, verified by `verifyClientAppToken` (`src/modules/client-apps/token.ts`): HS256 only, `kid` choosing among the app's keys that still verify, `aud` the route's public id, `exp` required and at most one hour ahead (60 seconds of clock skew either way), `sub` required (1 to 255 characters); `name`, `email` and `scope` optional, with the proxy route's limits. The HMAC key is the secret's UTF-8 bytes, which is what a JWT library does with the string it is handed. Every refusal, unknown app included, is the same `401 errors.clientAppTokenInvalid`.
- **The user is the app's.** The token's `sub` becomes the external id `app:<app id>:<sub>`, so the same `sub` in two apps is two people with their own threads. The proxy route refuses a `user.id` that starts with `app:` or `anon:`, so the namespaces cannot meet.
- **CORS is the route's own.** The instance-wide policy (`CORS_ORIGIN`) is the console's; an app's pages get theirs here. The preflight is answered on `onRequest` (`sdkPreflight`, after the channel gate and ahead of the instance-wide plugin, which would otherwise answer every `OPTIONS` itself): `204` with the exact origin, `POST`, and the `authorization`, `content-type`, `accept` and `accept-language` headers for an allowed origin, `403` with no CORS header otherwise. On the turn, `sdkCors` (an `onRequest` registered after the instance-wide plugin in `src/app.ts`) replaces that plugin's headers with the app's, so every answer carries them, the body's `422` and a parse error included, which come before the handler: the page can read those, a `401` (and renew its token) and a `429`, whose `Retry-After` is exposed. Credentials are never allowed. A request whose `Origin` is not one of the app's answers `403 errors.clientAppOriginRefused`. One without `Origin` (a server holding a token) is decided by the token alone.
- **Limits.** With no host server in front, the instance limits the route itself: `CLIENT_CHANNEL_SDK_USER_PER_MIN` (default 30) per user of an app, then `CLIENT_CHANNEL_SDK_APP_PER_MIN` (default 600) per app, in memory like the other limiters (`src/modules/client-apps/limits.ts`). Over either, `429` with `Retry-After`. The user's budget is asked first, so one user over theirs does not spend the app's. Before the app is even looked up, the preflight and the CORS hook charge the client address (`chargeSdkLookup`, the instance-wide limiter's budget in a bucket of its own), since they read the database on requests no token has vouched for and run ahead of that limiter. That refusal reads nothing, so its CORS headers come from the origins the app had at its last lookup (kept five minutes, one entry per existing app): users behind one NAT share the address budget, and their page must still read the `429`. Buckets are swept once a window.
- The turn runs in the app's tenant, on the app's agent, with no principal behind it (`actorType: "system"`): the person is the thread's owner, never an actor.

**The browser's transcription** is `POST /api/v1/sdk/:app/transcribe`, the widget's microphone: a multipart `audio` recording, transcribed with the speech-to-text the app's agent has configured (`transcribePlaygroundAudio`, [`stt.md`](stt.md)), answered as `{ text }`. The page then sends that text as the turn's message, so the transcription is shown to the person before the agent answers it, and nothing of the audio is kept. The door is the turn's (`admit`): the same token, identified or anonymous, the same origins and CORS (the route is in the `sdkCors` path), the same per-user (or `anon_messages_per_min`) and per-app budget, which a transcription spends like a turn does. The app's monthly ceiling and then the channel's own (`errors.clientSpendCeilingReached`) are asked immediately before the provider call, once the agent's speech-to-text is known to run, so an agent that takes no voice is told so whatever the month's spend. The idle timeout is lifted for the request, as on the turn, since the provider's own 60 s deadline is longer than Bun's 30 s. A recording over 4 MiB is `413 errors.audioTooLarge`, refused by its declared `Content-Length` in `sdkCors` before the body is read, and again once read; one that is not audio is `415`; both before anything is charged. An agent with speech-to-text off, or whose credential is missing or unusable, answers `400` (`errors.sttNotConfigured`, `errors.sttCredentialMissing`, `errors.credentialKindUnusableAsKey`, `errors.baseUrlRequired`), and a provider failure `502 errors.sttFailed`. An empty `text` means nothing was heard.

### Anonymous visitors

For a public agent (a visitor chat, a help page), on an app whose operator allowed it. The instance stands in for the host's server (`src/modules/client-apps/anonymous.ts`):

- **The session.** `POST /api/v1/sdk/:app/session` answers `{ session, token }`. `session` (`anon_<id>.<signature>`) is the browser's to keep; `token` is a JWT with `kid: "anon"`, `sub` the session's id, `aud` the app, living ten minutes. Sent back with `{ session }`, the route answers a new token for the same session, so the same browser resumes its conversation; a credential the instance did not sign for this app is treated as absent and gets a new session, without saying why. With `{ session, renew: true }` the route only resumes: an unknown or missing credential answers `404 errors.clientAppSessionUnknown`, before the challenge and the address's hourly allowance, so a page that merely reopened opens and spends nothing. Nothing is stored: the credential's signature and the token's key are HMACs derived from `ENCRYPTION_KEY` per app, so rotating the app's secret ends no session, and whoever holds that secret cannot mint one. Changing `ENCRYPTION_KEY` ends them all, as it ends everything encrypted with it.
- **Who may ask.** Only an allowed origin, and here a request without `Origin` is refused too: nothing else vouches for the call. An app that does not allow anonymous visitors answers `403 errors.clientAppAnonymousDisabled`. The route shares the turn's CORS (the preflight and `sdkCors` cover both paths).
- **The defense is cost, not identity.** Anyone can write the `Origin` they like from a script, so the route limits what one address and one session cost: new sessions per address per hour (`chargeAnonSession`, the app's `anon_sessions_per_hour`; renewing a held session is not counted), and on the turn the app's `anon_messages_per_min` takes the place of the per-user budget. The per-app budget applies above both.
- **A human check, when the operator wants one.** The app may put a Cloudflare Turnstile challenge before a NEW session (`turnstileEnabled`, with its public `turnstileSiteKey` and its `turnstileSecret`; turning it on without both is `422 errors.clientAppTurnstileIncomplete`). The page sends the challenge's token as `turnstile`, and the route redeems it once against Cloudflare's `siteverify` with the secret (`verifyTurnstile`, `src/modules/client-apps/turnstile.ts`), after charging the address's hourly allowance, so a page that keeps failing spends it and Cloudflare is not called past it. A request with no token is refused before the charge: it calls nobody, and charging it would let a page whose stored credential the instance no longer knows spend the allowance on that probe and then be refused its solved retry. Anything but Cloudflare's explicit `success: true` refuses, an outage or a timeout (5 s) included: `403 errors.clientAppTurnstileFailed`, with `field: "turnstile"` so the page knows to show the challenge and ask again. Renewing a held session asks nothing, so an outage stops only new visitors. The secret is stored encrypted (`encryptJson`), never returned (the app says only `turnstileSecretSet`), set from the console or REST only (MCP toggles the check and sets the site key), and the audit trail records a fingerprint of the ciphertext, so replacing it is a recorded change that holds no secret. The site key's allowed hostnames are configured in Cloudflare, not here.
- **On the turn** the token verifies like the app's own, with the derived key, and only while the app still allows anonymous visitors: turning it off ends every anonymous token at once. The user is `anon:<app id>:<session id>`, with no name, email or scope. Escalation takes the address the visitor types in the chat, unverified (see "Escalation").
- **Idle conversations expire.** An anonymous conversation with no message for the app's `anonExpiryDays` (1 to 365, 30 by default) is deleted by the tenant's `CLIENT_ANON_SWEEP` job (`src/modules/client-apps/expiry.ts`), armed when an app is created or deleted and at boot for every tenant with an app or an anonymous user left, self-rearming daily and ending once neither is left. Arming leaves a pending pass alone, so restarts and app edits never push it back; a pass running now is re-armed, which discards its own outcome (`completeJob` only writes a row still claimed), so a pass that read no app just before one was created cannot end the sweep. "No message" is the thread's `lastTurnAt`, which every turn moves on entry. The checkpoint lives in another store and no transaction spans both, so each thread goes in three steps: a short write claims the row (`activeTurnId: "expire"`, for good) while it is still past the term, still that anonymous user's and held by no round-trip, so a turn arriving during the sweep (it moves `lastTurnAt`) and a hand-over (it moves the owner and holds the claim) keep it; then the checkpoint is deleted; then the row. A claimed row refuses every round-trip and hand-over from then on (`leaseClientThread` only takes a claim that ran out), and a pass that stopped after the claim is finished by the next one. Then the app's anonymous users with no thread left and not seen since the cutoff are deleted, in batches of their own transactions under the same time budget; a browser still holding its credential simply gets a new user on its next turn. The anonymous users of an app that no longer exists are a deleted app's: its tokens stopped verifying with it, so their conversations go on the next pass whatever their age. Which app ids are deleted is decided against `client_apps` in the same statement that lists them, since an anonymous user exists only after its app, so an app created during a pass is never taken for a deleted one. One run sweeps for at most 60 seconds, paging each app's candidates by `(lastTurnAt, threadId)`; past that it reschedules a minute out with a cursor (app, last thread handled) in the job's payload, so a large tenant makes progress run after run instead of timing out under the scheduler's deadline and starting over. A conversation handed over belongs to an `app:` user and is never touched. A conversation with a call billed this month (`llm_usage`) stays until the month is over, whatever the term and whether or not the app has a ceiling now: an app's month spend is summed by joining the calls to these thread rows, so deleting one would take its cost off the figure, and a call can be billed after the `lastTurnAt` its turn wrote on entry.
- **Signing in.** `POST /api/v1/sdk/:app/session/claim`, with the app's JWT for the signed-in user and `{ session }`, hands the anonymous session's conversations with the app's agent to that user, in the token's `scope` (`handOverAnonymousThreads`, `src/modules/client-channel/identity.ts`). Holding the credential is the proof: only the browser that had the conversation takes it. A thread a round-trip holds now stays behind, and so does one suspended on calls for the browser (`isThreadSuspended` reads the checkpoint's pending interrupt), since its answers are gone with the anonymous page. The hand-over is all or nothing, in three steps: it takes every thread's claim, as a round-trip does (each dated when taken), so no turn can start, suspend and let go of a thread in between; it reads the checkpoints; and one transaction moves every thread not suspended, failing if a claim ran out and a turn took the thread. Whatever fails, the claims it still holds are let go and nothing has moved. And a round-trip's claim holds only while the thread is still its user's in that scope (`leaseClientThread` with `owner`, in the same write): a turn let in just before the hand-over is told the thread does not exist. The answer is the threads handed over, newest first; afterwards the anonymous session gets `404` for them, and handing over again moves nothing. An anonymous token cannot claim, and a credential the instance did not sign hands over nothing, with no error. A database or checkpoint error fails the call, so the page keeps its credential and tries again.

### The widget

`<fazer-ai-agent>` (`src/sdk/`) is what a host puts on its page instead of writing a chat: a script and a tag.

```html
<script src="https://<instance>/api/v1/sdk/agent.js"></script>
<fazer-ai-agent app="app_…" token-url="/fazer-ai-agent/token"></fazer-ai-agent>
```

- **Served by the instance** at `GET /api/v1/sdk/agent.js`, bundled once per process from `src/sdk/agent.ts` (`Bun.build`, browser IIFE, minified) and cached in memory; `cache-control: public, max-age=300`. Under `/api/v1/sdk/` it follows `CLIENT_CHANNEL_ENABLED` and stays out of the SPA's routing and the assets' cache policy ([`routing.md`](routing.md)). It answers `cross-origin-resource-policy: cross-origin` explicitly: `elysia-helmet`'s default is `same-origin`, which would block the script on the host's page (today a bug in that plugin overwrites the header with `?1`, which browsers ignore, so nothing else depends on it).
- **A custom element in a shadow root**, with no framework and no dependency: a floating button opening a panel (the whole screen under 640 px), or `mode="inline"` in the tag's place, with no frame of its own: the host's container draws the border, and the tag itself takes CSS from the page. The floating button stays on screen while the panel is open and closes it (its icon, `aria-label` and `aria-expanded` follow), except under 640 px, where the panel covers it and its header's close button does that. The message box grows with what is typed up to 120 px and only then scrolls. The reply is rendered as a small markdown (paragraphs, lists, fenced and inline code, bold, italic, http(s) links) built with `textContent`, so nothing the model writes becomes markup on the host's page (`markdown.ts`).
- **Signing in.** `token-url` is fetched with the page's own cookies and may answer the token as text or `{ token }`; `agent.tokenProvider` hands one over instead. With neither, the widget opens an anonymous session and keeps its credential in `localStorage` under the app (`fazer-ai-agent:<app>#session`, a key no user's conversation key can take) and in memory, and renews the token with it. The first signed-in token after that hands the session over, once: the credential is forgotten, and the newest conversation handed over becomes the open one when the user has none open and has not pressed "New conversation" since the identity last changed, so neither a late hand-over nor a retry reopens a conversation the person set aside. A failed hand-over keeps the credential for the next token and does not stop the turn. With `turnstile-site-key` on the tag, a new anonymous session first shows the app's Turnstile challenge in the panel: Cloudflare's script (`challenges.cloudflare.com/turnstile/v0/api.js`, loaded only then, so a page with a Content-Security-Policy allows that origin in `script-src` and `frame-src`) renders into a child of the tag projected through a slot, since it does not render into a shadow root, and the widget removes it once solved. A held session renews without it; one the instance no longer recognizes is refused with `field: "turnstile"`, and the widget forgets that credential, shows the challenge and asks once more for a new session. A challenge that fails asks the instance nothing and says the sign-in failed. Opening the panel to show the earlier conversation asks only to renew (`renew: true`): a credential the instance no longer knows stops there quietly, and a new session waits for the visitor's first message. The token is renewed 60 seconds before its `exp` and once more when the turn answers `401`.
- **The turn** is the SDK's route above, with `Accept: text/event-stream`: each server tool's `tool` event is a step line, and `pending` runs the calls in the browser and resumes with their answers, keyed by `toolCallId`, up to eight round-trips. A turn still asking for tools on the eighth runs nothing (a result that cannot reach the turn would act unrecorded) and its suspended thread is abandoned for a new one; answers whose renewal named another user are not sent to that user's thread, and the turn stops. Answers that fail to reach the instance are lost, and the thread they answered, still suspended and refusing new messages, is abandoned the same way. The open conversation's thread is held in memory and kept in `localStorage` under the app, the token's `sub` and its `scope` when it has one (storage is persistence across page loads, so a browser that denies it still keeps the open conversation), so the same browser resumes the same conversation and another user, or the same user in another scope, does not. A renewal that names another user or scope switches to that user's thread and clears the previous user's messages; a resumed thread the instance answers `404` (not this user's, or gone) for, as the HTTP status or as the stream's `error` event, or `409` as the HTTP status (suspended on calls nobody will answer because the page reloaded, or busy in another tab), is dropped and a new one started. A `409` inside the stream is a turn that lost its claim after its tools may have written, so it is shown and the message is not sent again. "New conversation" forgets it, also when pressed before any token said whose it is. Answering a call re-declares its tool even if the page stopped offering it (a navigation removed a highlight target), since the instance refuses answers for an undeclared tool. A failure to reach the instance, or a context callback that throws, is shown as a failed answer.
- **The page's API.** `agent.tool({ name, description, label, parameters, run })` registers a tool that runs in the browser, shown while it runs as a progress line with its `label` (its name when there is none; pointing at an element gets no line, since it shows on the page); `agent.context(object | () => object)` is sent with each message, at most 20,000 characters as JSON (`MAX_SCREEN_CONTEXT_CHARS`, the bound a tool's answer gets), since it rides in the checkpointed message and the history ceiling never trims the current one: over it, the turn answers `413 errors.clientContextTooLarge` before anything is written, on this route and on the proxy's; `agent.navigate` defaults to `history.pushState` plus a `popstate` event; `agent.open()`, `close()` and `reset()`; `agent.identityChanged()` when the host signs another user in, or into another scope, without reloading: the token in hand stays valid until its `exp`, so nothing else would notice. It drops that token, the conversation on screen and any unsent draft, and a turn still running for the previous user writes nothing more. Replacing `tokenProvider` or changing `token-url` does the same. Enter sends, Shift+Enter breaks the line, and an Enter that confirms an input-method composition does neither. The panel shows the conversation again after a reload: the last 40 messages and replies of the open thread are kept in the origin's `localStorage` under the same owner key as the thread (user and scope), the panel asks for the token as soon as it is open to learn that owner (an anonymous visitor's only for a session the browser already holds, never a new one nor a challenge), and "New conversation" forgets them. They are the replies as the page received them, after the output guardrail, which is why they are not read back from the checkpoint.
- **Voice messages.** Where the browser has `navigator.mediaDevices.getUserMedia` and `MediaRecorder` (a secure context), a microphone button sits beside Send. Pressed, it asks for the microphone ("Waiting for the microphone…"), then records (`audio/webm;codecs=opus` where supported, else `audio/ogg` or `audio/mp4`, at 32 kbps) with a pulsing dot, an `mm:ss` timer, a cancel and a send button in place of the message box. Ten seconds before two minutes the timer turns red and says the recording will be sent by itself, which it is at two minutes. Esc, the cancel button, anything that hides the panel (`close()`, leaving inline mode), a change of identity and removing the tag each end the recording without sending it, and every way out stops the stream's tracks, so the browser's recording indicator goes off; a microphone the browser grants after a cancel is closed as it arrives, and an anonymous visitor's Turnstile challenge still pending for the voice message is taken down with it, so the next message asks for its own. A recorder that stops on its own (the microphone was unplugged) sends what it recorded, as Send would; one that fails says so and sends nothing. Sent, it shows "Transcribing…" while the route above answers; the transcription becomes the person's bubble with a small microphone mark (`aria-label` "Voice message", kept in the stored conversation) and runs as a typed message does. A recording under 0.7 s, an empty transcription, a refused or missing microphone, a `400` (the agent takes no voice), a `413`, a `429` (the instance's own sentence) and any other failure each show their own line and send nothing. The state is announced through an `aria-live` region and the timer is a `role="timer"`. All of its sentences are in `agent.texts` (`record`, `cancelRecording`, `sendRecording`, `requestingMic`, `recording`, `recordingEnding`, `transcribing`, `voiceMark`, `micDenied`, `micMissing`, `voiceTooShort`, `voiceTooLong`, `voiceEmpty`, `voiceUnavailable`, `voiceFailed`). A page with a `Permissions-Policy` that denies the microphone gets the refusal line.
- **Pointing at the page.** Any element marked `data-fazer-ai-target="<name>"` makes the built-in `highlight_element` tool available, offered only while the page has one and with the names it found as an enum. It scrolls the element into view and draws a fixed outline over its rectangle, re-measured every frame while the smooth scroll moves it, for six seconds, leaving the host's own styles alone. On a screen under 640 px, where the open panel covers the page, the panel closes during the highlight and reopens after it. A page tool cannot take that name.
- **Style.** `theme="auto|light|dark"` (`auto` follows `prefers-color-scheme`), the CSS variables `--fazer-ai-accent`, `--fazer-ai-bg`, `--fazer-ai-text`, `--fazer-ai-radius` and `--fazer-ai-font` (inherited by default) set on the tag, `--fazer-ai-offset-bottom` and `--fazer-ai-offset-side` (24px by default) to move the floating button and its panel off the page's own fixed bars (the panel keeps 64px above the button, narrows to what the side offset leaves, and still covers the whole screen under 640px), `position="bottom-right|bottom-left"`, `lang` (English and Portuguese built in, the browser's by default) and `agent.texts` to replace any sentence (assigning it repaints the widget), the panel's title included: the tag's `title` attribute is the browser's own tooltip and is not read.

## Who a thread belongs to

Every turn carries `user: { id, name?, scope?, email? }`:

- `id` is the host's own stable id for its user, opaque to us.
- `name` is for display. Sent, it refreshes the record; omitted, the record keeps the last one.
- `scope` is what the host scopes the conversation to, such as an organization. It belongs to the thread, not to the person: one user in two organizations is one `ExternalUser` with two threads.
- `email` is the address the team replies to outside the host, read only when the agent opens a case (see Escalation). Like `name`, sent it refreshes the record and omitted it keeps it. The model never sees it.

`claimClientThread` records the person (`external_users`, one row per tenant, channel and external id; on the SDK's turn the external id is `app:<app id>:<sub>`, see above) and returns the thread:

- no `threadId`: a new one, `tenantId:client:agentId:uuid`, bound in `detached_threads` to that person and scope;
- a `threadId`: resumed only when it is this agent's client thread **and** its row names the same person and the same scope. Anything else (another user, another scope, the same user without the scope, another agent, an id never minted, a malformed id) answers the same `404 errors.threadNotFound`, so the answer says nothing about which threads exist.

The binding is checked on every round-trip, so resuming a suspended turn with another user's identity is refused before the graph runs. Deleting the agent takes its client threads with it (`detached_threads` cascades), and their checkpoints live in another store where only these rows lead, so `deleteAgent` locks the rows, refuses with `409 errors.agentClientTurnRunning` while a round-trip holds one (its next checkpoint write would land after the delete; a thread the anonymous expiry claimed does not count), and deletes each thread's checkpoint after the commit, so a refused delete erases nothing. A process that dies between the commit and those deletes leaves the transcripts behind with nothing pointing at them. Deleting the tenant leaves every thread's checkpoint behind, on every channel, as it did before this channel. The agent is asked first, so a missing agent answers `404 errors.agentNotFound` with nothing written.

`ExternalUser` is keyed by `channel` (today only `client`) so a later channel without Chatwoot writes there without a schema change. Its `contactId` is the bridge to the Chatwoot mirror and is not filled yet: a case finds its Chatwoot contact on each call (see Escalation), and the mirror itself (`contacts`) is not written by this channel.

## A suspended turn's deadline

A turn waiting on the browser holds the thread's history at an open tool call, so a tab that closes would otherwise leave it waiting forever. `CLIENT_TURN_SUSPEND_TIMEOUT_MS` (default 2 minutes) bounds that, measured from the suspended checkpoint's own `createdAt`:

- **before the deadline**, a new message answers `409`: the browser may still answer, and the host should send the answers first;
- **past it**, the new message closes the old turn. Every pending call is recorded as unanswered (`The application returned no result for this call.`, the same text an absent answer gets on resume), written to the state as the `client_tools` node's output, with no model call for a reply nobody would read. The new message then starts its own turn on top, and a `tool` line with `detail.phase = "client_timeout"` and the call count goes to the flow log;
- the browser's answers can still arrive after the deadline when no new message came first, and they resume the turn as usual.

## One round-trip at a time

Each round-trip claims the thread (`detached_threads.active_turn_id` / `active_until`, a conditional update) and gives it back when it ends, refused or not. While one holds it, any other round-trip on the same thread answers `409 errors.clientTurnInProgress`. That is what settles the race between the browser's late answers and the user's next message: whichever claims first acts, and the other is refused, or, when it arrives after, finds nothing waiting. The claim lasts two minutes and is renewed every 30 seconds while its round-trip runs, since a round-trip has no overall deadline (each model call has its own, and the tool budget allows several in a row). It only expires when the process holding it stopped, which frees the thread two minutes later; a release only clears a claim that is still its own. A round-trip stops admitting work when its renewal finds the claim taken by another request, and also when renewals keep failing until half of the last confirmed claim is spent (counted from when that renewal was asked for, since its expiry is computed before the update goes out), so it never runs past the point where another request could take the thread. It stops through the graph's own cancellation path (`GraphBuildDeps.signal`, the one the scheduler's job deadline uses): the model call in flight is cancelled, a tool already running finishes and no new one starts, and the round-trip's checkpointer refuses every write from then on (`fencedCheckpointer`), so a tool that outlives the claim cannot land its result after another request took the thread. It answers `409 errors.clientTurnClaimLost`. Whatever a stopped or dead round-trip left behind, the next one starts by closing any call of the last assistant turn that has no answer (`This call was interrupted before it finished; its result is unknown.`), since the providers refuse a history with an unanswered call. A release that fails is logged and left to expire, since the turn's result is already checkpointed and replacing it with an error would lose a reply or a new thread id.

## Guardrails

The agent's guardrails run here as on the inbox and in the playground (`buildGuardrailGate`), with the agent's own configuration:

- **input**: a new message is screened before the graph. A violation skips the graph, so the message never enters the thread and no reply is billed; the turn answers `done` with what the policy says (the template, a generated replacement, or nothing when the action suppresses).
- **output**: the reply is screened before `done` is returned, and the host gets the screened text. A turn that resumes with tool answers carries no message of its own, so the checks that read the question (answer relevance) get the thread's last user message, without the screen context.
- the `handoff` action has no human to hand to on this channel (see Escalation), so it is carried out as `template`: the user gets the direction's template instead of a handoff message that would promise a transfer that does not happen, and the flow line records `template`, the action actually taken.
- the browser's tool answers are tool results, not the user's words, and are not screened on the way in, like any other tool result.
- **the external check** ([`guardrails-external.md`](guardrails-external.md)) runs after the output screening, on the reply that would be returned, as on the inbox and in the playground, with the turn's tool calls (the browser's included) and no conversation ids. A `block` and a held failure are carried out like the handoff action above: the user gets the output template.

There is no private note to write the verdict into, so the gate's own `guardrail` flow lines are the record, on the client thread: a trip is a `warn` line with the direction, the action carried out and the policy categories it named (never the rationale, which quotes the text). A clean verdict writes no line, as on the other channels.

## Escalation

Only the agent answers in the host's chat: there is no handoff to a person inside it (`handoff_to_human`, `private_note` and `resolve_conversation` are not offered). When a request needs the team, the agent opens it as a case in the team's inbox with `open_case_in_inbox`, the same tool and the same `crossInboxCase` config as on the inbox ([`chatwoot.md`](chatwoot.md), "Opening the case in another inbox"), and the team replies by email. The case operation is shared (`openCaseInInbox` with a `detachedOrigin`); what differs on this channel:

- **An email inbox only.** The destination must be an email inbox (`Channel::Email`), checked before the contact is touched; any other answers that the team's inbox cannot receive cases, with no contact created or changed. The team's email replies go to the contact's address, which follows the email the host states, while a phone channel (WhatsApp, SMS) replies to the number its conversation was opened with, which a later change of the contact does not move. Phone destinations are in [`roadmap.md`](roadmap.md).
- **The account.** The inbox's account is the instance the operator picked it from (`crossInboxCase.targetInstanceId`); a config saved without one is used only when the tenant has a single connected account. When the agent has no destination inbox or its account cannot be loaded, the tool is not offered (`CLIENT_CHANNEL_NATIVES` runs it `detached`, and without the thread's origin the builder leaves it out).
- **The contact** comes from the host, never from the model: the one marked `fazer-ai-client:<ExternalUser id>` when a case was opened for this user before (found by the contacts filter on the whole identifier), brought up to the email the host states now; else the contact that already holds that email (a customer the team knows); else a new one with the name, email and that mark. An email another contact already holds sends the case to that contact. The tool takes no `email` argument: with no email from the host, nothing is read or written in Chatwoot, the call answers that the team cannot be reached from here, and the model is told not to ask for one, since this chat cannot pass it on.
- **An anonymous visitor** has no host to state an address, so the tool takes an `email` argument on an anonymous session only, and its description tells the model to ask the visitor for an address and pass exactly what they typed. The address is used only when it is well formed and the visitor wrote it whole (`userTypedOnThread`, with the inbox path's `customerTyped` complete-address match): in this turn's message, handed in by the service since the checkpoint may not hold it yet when the tool runs, or in an earlier message on the thread, each without the screen context the page sent with it. So the model cannot invent, complete or truncate one, nor lift one from the screen context; with no address the tool asks the model to request one. The contact is the visitor's own for that address (`fazer-ai-client-anon:<ExternalUser id>:<address>`, created on their first case there; a new address is a new contact, and an anonymous call never changes a contact's address) and never one found by the address. A signed-in user whose address it is takes the contact over on their own case: `resolveCaseContact` clears the anonymous identifier and the mark, so the visitor no longer reaches it, and a contact whose address the team changed is not reached by the old one either (the takeover is checked on the contact before and after the visitor marks it; like every escalation here it is serialized only within a process, so a takeover on another worker during the visitor's case writes can still let that one case land, and the case it reaches carries the unverified note): nobody proved the address is theirs, and Chatwoot keeps one contact per address, so an address another contact already holds is refused and the model tells the visitor to sign in (`resolveAnonymousCaseContact`). The contact is marked with the custom attribute `email_unverified: true`, and a case opened (not an addition) carries a private note saying the reply address was typed by a visitor who was not signed in and is not verified.
- **The origin.** There is no conversation to write the case number or a link note on, so the thread records the case (`detached_threads.case_instance_id` / `case_conversation_id`) and the address it was opened under (`case_email`). A thread adds only to the case it recorded itself, while that case is still open, still the resolved contact's, and the user's email is still the one it was opened under; no other case of the contact is looked up, since nothing on this side knows which address another case answers (Chatwoot addresses a thread's next email reply from its earlier messages, and does not expose a conversation's own address). Anything else opens a new case. That can leave two open cases where one would have done (two threads of one user, an address change, two threads escalating at once), never an addition to a case that answers an address the user no longer states. An inbox set to continue or lock to one conversation per contact hands an old conversation back anyway; it then gets a private note telling the team the current address, which this side cannot enforce. The opening carries its recipient on the message (`to_emails`): the address the host states, since Chatwoot delivers it later and would otherwise read the contact's address at that moment, which another writer (an inbox turn's `update_contact`, say) can have changed. The escalations of one account run one at a time, from the contact to the recorded case, so no call changes a contact's address between another's reconciliation and its opening (two people of the host can resolve to one contact through a shared email). The case's note links the Logs page of the turn that opened it, and `origin_conversation_id` on the case holds that link. `originLabel` and `resolveOrigin` do not apply.
- **No fallback transfer.** On the inbox, a case that fails to open sends the conversation to people; here the call fails and the model tells the user it could not pass the request on. The opening message is screened by the turn's output guardrail like the reply; a refused one is not sent and the case still opens.
- **The team** the case is given to is the one pinned in `handoff` for that account, as on the inbox.

A human reply inside the host's chat (an API-channel inbox whose replies come back to the thread) is not built: see [`roadmap.md`](roadmap.md).

## Progress as a stream

The answer is JSON, and that is the contract. A host that sends `Accept: text/event-stream` gets the same answer as Server-Sent Events on the same route, so its page can say what the agent is doing while the turn runs (`src/modules/client-channel/stream.ts`):

- `tool`: `{ type: "tool", phase: "start", name }` when a server-side tool starts, and `{ type: "tool", phase: "end", name, ok }` when it ends; `ok` is false for a tool that threw and for one that returned a failure. Only the tool's name travels, never its arguments or result, since the events reach the host's browser. The host's own tools are left out (it learns of those as the `pending` calls), and so is `skip_reply`.
- `ping`: every 15 seconds without another event, so a proxy in front (Traefik, Cloudflare at about 100 seconds) does not close a silent response.
- `pending` or `done`: the last event, carrying exactly the JSON answer.
- `error`: `{ status, error }`, for a refusal raised after the first event, when the HTTP status is already sent. One raised before it (unknown thread, wrong user, spend ceiling, a turn in progress) answers with its own status and JSON body, as without the header: the route waits for the first event, the end of the turn or the first ping before it answers.

A host that stops reading does not stop the turn: its result still lands in the thread.

The model's reply comes whole, in the final event, not token by token: see [`roadmap.md`](roadmap.md).

**Bun's idle timeout.** Elysia starts Bun with `idleTimeout: 30`, and on Bun 1.4.2 that timer is not reset by what the server writes: a response, streamed or not, that takes longer is cut (measured: a stream writing every second was closed at the timeout). The route turns it off for its own request (`server.timeout(request, 0)`), since a turn has no overall deadline and its model calls and tools each have their own. The pings are for the proxies, not for Bun.

## Usage, logs and ceiling

The channel's usage rows, flow lines and Langfuse traces carry source `client`, and each usage row and flow line also says whether its turn served an anonymous visitor's session (`anonymous`, written by the turn from the user id, so a conversation that passes to a signed-in user keeps what its anonymous turns were). The Logs and the dashboard narrow the client source to one audience (`audience=identified|anonymous`, on REST and MCP too), and a turn card in the Logs marks an anonymous visitor. The channel has its own monthly ceiling (`spendCeiling.monthlyClientUsd`, refused with `429 errors.clientSpendCeilingReached`), and its warnings page alert channels like inbox traffic, with the inbox turn's model lines (`src/graph/model-telemetry.ts`): a fallback that took the turn, one that failed or could not be built, a retried empty response, a forced answer, a wait for a model permit, trimmed history. A knowledge suggestion proposed in a client thread is reviewed under the client ceiling. A widget transcription (`transcribeClientAudio`, `src/modules/stt/service.ts`) writes its own `stt` flow line, source `client`, naming the agent and `anonymous` as the turn's, with the agent's debug mode, under a turn id of its own (no thread exists yet), and no usage row: speech-to-text writes none on any surface, so its cost is outside both ceilings, which still refuse it once reached. See [`spend-ceiling.md`](spend-ceiling.md) and [`logs.md`](logs.md).

### What the claim does not cover

A checkpoint write admitted while the claim was held is not cancelled: `PostgresSaver` takes no signal, so a write that then waits on a connection or a lock can still commit after the claim expired. The round-trip stops admitting work with half a claim (a minute) to spare, so that write would have to stay blocked for over a minute past admission. Closing it fully needs a checkpointer that checks the claim inside the same transaction as the write; until a deployment shows that window in practice, the margin is the answer.
