# i18n

- Always update localization keys when adding or modifying user-facing text
- Never add keys manually to localization files; use `bun i18n:extract`
- Use magic comments like `// t('translation.key', 'Translation')` for localization keys inside static objects without access to `t`
- Always update non-English localization files with correct translations
- Client code uses `t` from `useTranslation()`; backend code uses `translate()` from `src/api/lib/i18n.ts`. Do not cross-use: the two extractor configs (`i18next-parser.config.cjs` and `i18next-parser.api.config.cjs`) key off these exact names
- **A new API error key does not exist until `bun i18n:extract` has run.** `ErrorTranslationKey`
  (`src/lib/errors.ts`) is `keyof` the generated `src/api/locales/en.json`, so a throw site naming a key
  whose magic comment was just written is a type error until the catalog is regenerated. `bun check` runs
  the extractor first for this reason; running `bun run build-check` on its own, before extracting, reports
  the key as unknown and the message does not say why

## Lint guardrails

Three groups of lint rules catch common i18n mistakes early:

- **`noJsxLiterals`** (built-in, `style` category): flags bare string literals inside JSX (`<div>Hello</div>`) since those never reach the extractor. Disabled for `tests/**`. Genuine non-copy glyphs are listed in `allowedStrings` (e.g. `·`, `•`, `?`). For one-off exceptions use `// biome-ignore lint/style/noJsxLiterals: <reason>`
- **`no-dynamic-i18n-key.grit`** (`biome-plugins/`, scoped to `src/client/**`): flags `t($arg, ...)` where the first argument is not a string literal (e.g. `t(tab.labelKey)`, `` t(`foo.${x}`) ``, `t("a." + b)`). Dynamic keys escape extraction; add `// t('key.path', 'Default')` magic comments nearby, then suppress with `// biome-ignore lint/plugin/no-dynamic-i18n-key: extracted via magic comments in <source>`. Use the full plugin-name form so only this rule is muted on the next line; bare `lint/plugin:` would silence every biome plugin including `require-page-container` and `no-dynamic-translate-key`
- **`no-dynamic-translate-key.grit`** (`biome-plugins/`, scoped to `src/api/**`): same rule but for the backend `translate(...)` wrapper
- **`no-t-rename.grit`** (`biome-plugins/`, scoped to `src/client/**`): refuses `const { t: $alias } = useTranslation()` and `const $name = useTranslation()`. Keeps the canonical `t` name so the dynamic-key plugin can find the call sites

## Known limitations

GritQL has no scope analysis, so the dynamic-key check can be bypassed by:

- Passing `t` as a prop or callback (`<Child t={t} />` then `props.t(foo)`); no AST-level detection possible
- Wrapping `t` in a helper (`const translate = t; translate(foo)`); same issue
- Using `i18next.t(...)` directly instead of the hook; not in the pattern

Treat `bun i18n:extract` + the CI `git diff --exit-code src/client/locales/` gate in `.github/workflows/build-check.yml` as the final safety net. The linter catches the common cases at author time; the CI ensures no keys actually go missing.

## Extract DELETES keys, and the pre-commit hook runs it

`bun run i18n:extract` is configured with **`keepRemoved: false`**, so every run deletes any key in `en.json`/`pt-BR.json` with no **static** `t("literal.key")` / `translate(...)` reference in source, and the pre-commit hook runs it via `bun check` — this fires on every commit, not only when you ask for it. Dynamically built keys (`` t(`x.${v}`) ``) are invisible to the parser and get pruned. On a shared tree that means an extract of yours can drop another session's not-yet-referenced keys.

Consequences worth knowing before you touch a catalog:

- **A `t()` inside another `t()`'s options object is not seen.** `t("a", "…", { state: cond ? t("b") : t("c") })` never extracts `b`/`c`. Compute the inner value in its own statement first.
- **Server locales are covered too** (`src/api/locales/*.json`). `AppError.translationKey` strings are localized centrally in `onError` and never reached by a literal `translate()` call, so a key added by hand survives `bun test` and is silently deleted by the next `bun check`. Anchor each one with a magic comment `// translate('errors.X', 'English default')` in the owning domain's controller. Extract re-adds pt-BR with the ENGLISH default, so translate it by hand right after.
- **A wrong value does not fix itself.** The parser preserves existing values, so changing the default in source does not change the catalog: delete the key from `en.json` and re-extract. And the magic comment is delimited by single quotes, so an apostrophe in the text (`this conversation's inbox`) truncates the sentence there and stores half of it with no error — write it without the apostrophe.
- The API config's `input` is `src/api/**/*.ts` only, so a magic-comment ledger has to live under `src/api/`, co-located with its route. A central ledger would keep dead keys alive forever, since `keepRemoved:false` is the thing that prunes.
- `src/api/lib/i18n.ts` uses `createInstance()`, NOT the i18next default singleton: the client's `src/client/lib/i18n.ts` inits that same singleton with CLIENT resources, and in a shared context (bun test workers) the last init won, making server translations silently fall back to their defaultValue.

## A missing key is invisible at runtime, so it is typed, not tested

i18next answers an unresolvable key with `defaultValue ?? key`, and `onError` passes `message` as the default — so a missing key does not throw, does not log, and **renders a plausible English sentence**. Measured on #256: 152 `errors.*` cited in source against 104 registered in `src/api/locales/en.json`, i.e. 48 keys missing across 112 call sites and 21 files, about a third of the API's localized refusals never localized. No behaviour test can catch that by construction.

The fence is a type derived from the catalog, in `src/lib/errors.ts`:

```ts
// `typeof import()` is type-only: it disappears at compile time and creates no cycle
type ApiLocale = typeof import("@/api/locales/en.json");
export type ErrorTranslationKey = `errors.${keyof ApiLocale["errors"] & string}`;
```

`AppError`, its subclasses, `translate` and `translateWithLocale` take that type instead of `string`. Applying it produced 113 compile errors, which is the red proof. It works because the API catalog has exactly one top level (`errors`) and was already imported by `src/api/lib/i18n.ts`. A Biome/GritQL plugin cannot do this — with no cross-file analysis it sees the literal and never the catalog (that limit is recorded below).

The type also catches what a text sweep cannot: a key held in a struct field (`Refusal.key`) and a key built by interpolation, where it named all three possible strings. It is blind in exactly three places, and each was a live defect: an `as` cast; a key used as a **comparison token** rather than an argument (`if (row.error === "errors.x")`), which never passes through a typed parameter; and a catalog that HAS the key and answers pt-BR with the English sentence. Cover those with tests. A key that crosses the server/client line becomes a shared map, with a coverage test **and an injectivity test** — two reasons pointing at one token pass coverage and tell the operator to fix the wrong thing.
