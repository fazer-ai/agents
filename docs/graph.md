# Agent runtime (LangGraph TS)

The runtime turns an incoming Chatwoot message into an agent reply. It is wired to the webhook receiver's seam (`processChatwootDelivery` → `runAgentTurn`). It ships a **minimal functional supervisor**; richer subgraphs, `agentNudge`, Langfuse, and per-node models compose onto it.

## Pieces

- **`src/graph/checkpointer.ts`** — `getCheckpointer()` returns a memoized `PostgresSaver` in the dedicated `langgraph` Postgres schema (created by `scripts/db-bootstrap.sql`, owned by the non-superuser runtime role). `setup()` runs once (memoized on `globalThis`, `bun --hot` safe). The thread key for the GRAPH (checkpointer memory) is **per contact-inbox**: `contactInboxThreadId(tenant, instance, contactInboxId)` = `tenant:instance:ci:<contactInboxId>`, where `contactInboxId` is Chatwoot's native `ContactInbox` id (one contact on one inbox/channel), mirrored onto `Conversation.contactInboxId` from the webhook payload. Memory spans the conversations a contact has **on one channel**, so a contact's parallel channels (WhatsApp vs Instagram, …) keep SEPARATE memories instead of mixing contexts. `resolveGraphThreadId(tenant, instance, conversationId, contactInboxId)` is the single resolver: the contact-inbox key when `contactInboxId` is known (the normal case — the mirror writes it before any turn), else it degrades to the per-conversation `chatwootThreadId` (NOT a contact+inbox composite — just null-handling on a legacy/edge row). BOTH the reactive turn (`runtime.ts`) and the follow-up nudge (`nudge.ts`) invoke the graph on this resolved key — keeping the follow-up's memory unified with the turn's (a prior bug invoked the nudge on the per-conversation thread, divorcing it). Everything else — debounce dedupe/watermark, follow-up job key, flow correlation, the tenant-fence anchor — stays on the per-conversation `chatwootThreadId(tenant, instance, conversationId)` = `tenant:instance:display_id`. All forms lead with the tenantId, so `threadBelongsToTenant` (the prefix fence) holds; these checkpointer tables are outside Prisma/RLS for now (RLS hardened in a later phase).
  - **`AgentThread`** (`agent_threads`, RLS-scoped, unique on `(tenant, instance, contactInboxId)`) is the per-thread sidecar: `lastConversationId` (the divider marker — the last conversation a turn/ingest ran on this thread; a NEW conversation reusing the thread gets the one-line `CONVERSATION_DIVIDER` written as its own `HumanMessage`, since the agent node strips system messages from history) and `lastSyncedMessageId` (the continuous-ingestion watermark — see Continuous ingestion). Tracking the divider per-THREAD (not per-contact) is what stops a multi-channel contact from getting spurious dividers mid-conversation. `/reset` deletes the contact-inbox checkpointer thread, the `AgentThread` row AND that thread's `AttendanceSummary` rows (this channel only; the contact's other channels keep their memory) — the compacted memory lives outside the thread, so deleting the thread alone would render it straight back on the next compaction.
  - **Required grant:** the runtime role needs `CREATE ON DATABASE` so `setup()`'s `CREATE SCHEMA IF NOT EXISTS langgraph` succeeds (the privilege is checked even when the schema already exists). The role stays non-superuser/non-bypassrls, so tenant RLS is intact. This grant lives in `db-bootstrap.sql`.
- **`src/graph/models.ts`** — `parseModelConfig` (zod) + `createChatModel` instantiate a LangChain chat model from `{provider, model, baseURL?, temperature?}`; providers: `openai`, `openai-compatible` (OpenAI client with `configuration.baseURL`), `anthropic`, `google`, `deepseek`. The API key is resolved from the **vault** by the runtime (never inlined, never logged). **`temperature` is dropped for OpenAI's reasoning families** (o-series, gpt-5, bare or OpenRouter-routed): they answer any non-default value with a hard 400 that kills the whole call, and the guardrail pass + the TTS speech normalization both pin `temperature: 0`, so on such a model every one of those requests would fail. **How each provider is asked for a schema-constrained answer** is a separate table in the same module (`verdictAskMode`), used today by the guardrail verdict (`src/modules/guardrails/verdict.ts`): `openai` and `anthropic` take the json-schema dialect, `google` takes the OpenAPI 3.0 subset its `responseSchema` speaks (nullability as `nullable: true` rather than a type union — measured live on gemini-3.5-flash and -flash-lite: the other dialect is refused with a 400 and every screen then costs two calls), and `deepseek` (json_object only), `openrouter` (support varies per endpoint behind the router) and `openai-compatible` (an arbitrary server) keep being asked in the prompt and answered in prose. A request that comes back REFUSED is remade in prose, so a model that takes ordinary chat but not this particular request costs an extra call instead of a screen that quietly stops running. A provider asked the wrong way does not degrade, it is refused every time: measured against a local server that ignores the parameter, the client retried the same call six times across a minute and never settled. **A second per-provider table lives outside this module**, and adding a provider here is a decision there too: `REPLAYS_OWN_BLOCKS` in `src/graph/graph.ts` names the vendors whose non-text content blocks survive being replayed to them, which is what lets a reasoning-only assistant turn stay in the history (see the silence rule below). Leaving a new provider out of it is the safe answer and the right default: the turn is then dropped, which costs context and never breaks a thread. Putting one in without checking its adapter is what breaks threads, so the entry is earned by reading how that adapter builds an assistant message, not by symmetry with this list.

- **`src/graph/model-fallback.ts` + `src/graph/fallback-settings.ts`** — the **second provider behind the agent's own** (`agent.settings.modelFallback`, issue #143). A fallback exists once the operator named a PROVIDER, which is what names a destination: the two sibling model overrides (the speech rewrite, the summariser) read "everything absent" as *run this on the agent's model*, and here that would be a second attempt against the endpoint that just failed. Resolved by the same `resolveModelOverride` those two use, so the rules about whose key may reach which host are written once — a fallback on another vendor carries its own credential or it does not run, and every refusal (unknown provider, key that did not resolve, model not named) leaves the install behaving exactly as one that configured none.

  **Which failures fall over is a policy with a decision table**, and it is deliberately narrower than "the primary failed": timeout, 408, 429, 5xx, plus an empty completion that already survived its own retry. NOT 400/401/403/404/413/422 — the second provider would answer those fine, and a fallback that covers a dead primary key covers it forever while the operator is billed by both and told nothing. A connection that never opened is excluded for the same reason vision's retry excludes it: far more often a wrong address, which is permanent, and a vendor that is actually down answers 503.

  **The bounds are the design, not tuning.** Measured through `createChatModel` against a local endpoint: with LangChain's default AsyncCaller a single 503 becomes SEVEN requests over 77s, a 502 99s, a `Retry-After: 1` 429 87s, and a provider that accepts the connection and never answers holds the turn forever (no adapter is given a request timeout today). A fallback behind that arrives after the customer has gone. So when — and only when — a fallback was built, both models run on one attempt (`maxRetries: 0`) with a 45s ceiling; an install that names no fallback keeps today's six retries and its unbounded wait, byte for byte. Measured end to end on a real turn: 82.071ms and no reply on the base code, 2.563ms and a real answer with the fallback. The spellings differ per adapter and are asserted off the built instances (`tests/graph/model-limits-transport.test.ts`): `maxRetries` lands on `caller.maxRetries` for all six, the ceiling is `timeout` on the four OpenAI-shaped clients and `clientOptions.timeout` on Anthropic, and **Google takes none** — so a hung Gemini endpoint is the one case still unbounded.

  **Once the fallback has the turn, it keeps it.** A tool call routes back through the agent node, so a turn with tools runs that node once per round, and asking the dead primary again on every round pays its failure again each time — the very budget above, reappearing inside one turn. Measured on a three-round turn (two tool calls, then the answer) with the primary failing in 200ms: 3 primary calls, 3 "the fallback took the turn" warns for one failover, 609.3ms; after, 1, 1 and 204.8ms. At the 45s ceiling those three calls are 135s of dead waiting. The demotion is a closure in `buildAgentGraph`, and the lifetime is the argument: the graph is built inside the turn and invoked once, so it is exactly "this invocation" — in graph state it would ride the checkpointer and demote the primary for every later turn on that conversation. A healthy primary keeps every round.

  **The model is required for the providers that need one, which is not all of them.** `modelOptionalFor` is the repo's existing rule — an `openai-compatible` server that serves a single model discards the name it is sent, which is why the primary's own schema lets it through empty and `createChatModel` sends `default`. That rule was written out inline in three places and this block was written as "both halves, always", so an operator pointing a fallback at their own llama.cpp server could not configure one without inventing a model id; there is one predicate now, read by the schema, the editor's save guard and here.

  **A half-named fallback is refused at the write, not repaired.** A provider named with no model (where one is required) stores cleanly, `hasModelFallback` answers false, and the editor's reader maps the bag back to *no fallback* — so the operator's choice is gone on the next load with nothing on screen to say why. `assertSettingsModelFallback` (in `src/modules/agents/service.ts`, beside the text-size and debug-window rules) refuses it on all three transports that reach the bag, and it is told which one it is on: REST **replaces** the settings column with the bag it was handed, while the MCP patch **merges** the block one level deep, so a body naming only the model is a complete statement on one and a half-named row on the other. Only a pair the write introduces or changes is refused, compared by value, so a stored half-named row does not freeze a save that edits some other section.

  **Who answered is recorded, and it is the node that says so.** `UsageCapture` would otherwise bill a fallback turn to the configured model's name, and nothing LangChain hands the handler settles it (`invocation_params.model` is undefined on Google; `response_metadata.model_name` is the vendor's dated snapshot, which would rewrite the value of every row already in the ledger). The graph node names the model in the CALL's own metadata — measured to MERGE with the turn's metadata and to reach the inherited handlers, unlike `callbacks`, which replaces them and would have cost the Langfuse trace.
- **`src/graph/graph.ts`** — `buildAgentGraph({model, systemPrompt, checkpointer, tools?, maxHistoryTokens?})` compiles a `StateGraph(MessagesAnnotation)`. With no tools it is a single `agent` node; with tools it is an `agent ⇄ tools` loop (`ToolNode` + `toolsCondition`) until the model stops calling tools — or until the turn is called off, see the tool boundary below. The system prompt is prepended per turn; the checkpointer persists the running messages per thread. `lastAssistantText` normalizes the reply content to a string (via `contentToText` in `message-text.ts`, shared with the token counter).
  - **History ceiling** (`agent.settings.limits.maxHistoryTokens`, OFF by default). The thread is per contact-inbox and nothing prunes it, so the whole of a returning contact's past travels on every turn: measured on one install at 79.8k tokens against a 15.8k floor of prompt + tool definitions. What bites first is not the bill but the provider's TPM limit, which counts CACHED tokens too. `selectHistoryWindow` (`history-window.ts`, pure + decision-table tested) keeps the longest suffix that fits, then opens the window on a HUMAN message so a `ToolMessage` never arrives without the `tool_call` that produced it (providers reject that outright), and never drops the turn being answered even when it alone exceeds the budget. Nothing is dropped unless the budget demands it. Tokens come from `token-count.ts`, which ESTIMATES rather than tokenizes: `tokenx` (84KB, no dependencies, ~3MB RSS), calibrated against `o200k_base`. Exactness would be false precision here — the ceiling bounds the history only, while the system prompt and tool definitions sit above it uncounted and were 15.8k tokens on the install that motivated this. A real BPE table costs ~176MB resident (measured in the deploy image on both arches), covers OpenAI only (Anthropic and Google expose counting ENDPOINTS, i.e. a network call per turn), and throws on a control marker like `<|endoftext|>` that a customer can simply type. Measured against `o200k_base` on a realistic clinic thread the estimate runs **-17.3%** (-7.1% on prose, -18.8% on JSON payloads), so a ceiling of N lets through roughly N×1.2 of what OpenAI bills; the operator hint says so. It counts `tool_calls` as well as content — LangChain's own counter reads `content` only, which scores a tool-calling assistant message at zero. The system prompt is NOT counted (it is prepended per turn and is not part of the history), so an operator's budget has to sit above it. A trim emits an **info** line on the `generate` stage; info rather than warn because warn/error fan out to the alert channels and a working ceiling trims on nearly every turn of a long thread.
  - **Memory compaction** (`agent.settings.memory.compaction`, **ON by default**, `src/modules/memory/`). The ceiling above bounds the history by DISCARDING, which is why it defaults off. Compaction is the other half and preserves instead: when an attendance ENDS, its raw turns are replaced by one summary of it, so the thread reads as "N summarized attendances + the current one, raw". Cutting on the attendance boundary is the point — it is what a human agent's notes look like, and "8 atendimentos resumidos + o atual" is explainable to an operator in a way "dropped 40k tokens from the middle" is not.
    - **Running it on a cheaper model is not the obvious win, and it was measured before the knob shipped.** This summary is the contact's PERMANENT memory: it is read on every later turn on that thread and is never rewritten, so a weaker model here degrades every future reply rather than one message. `scripts/measure-summary-battery.ts` drives the real `summarizeAttendance` over two scenarios; on the harder one (the customer changes a value mid-attendance), n=128 per model:

      | model | facts complete | kept the name | invented | non-Latin run | median chars |
      | --- | --- | --- | --- | --- | --- |
      | `gpt-5.4-mini` (the agent's own, in this battery) | 128/128 | 128/128 | 0/128 | 10/128 | 308 |
      | `gpt-5.4-nano` | 102/128 | 102/128 | 0/128 | 0/128 | 322 |

      Every incomplete nano summary was incomplete for the SAME reason: the customer's name was gone, on roughly one attendance in five, while it wrote slightly MORE than the model it was supposed to be cheaper than. That is the axis that rejected prompt variant C, and the trade reads the same here. The one place nano wins is the model artifact: mini emitted a run of non-Latin script inside a pt-BR summary in 10 of 128, which is cosmetic noise in a permanent record rather than a lost fact, and is a known limit rather than a solved one. So the override exists for the needs that are real (a second provider, a proxy endpoint, a self-hosted model) and swapping DOWN for cost is not recommended; the editor hint carries that one-in-five headline where the operator actually makes the call, without the table.
    - **Two triggers, one job.** A conversation transitioning to `resolved` (webhook) arms `MEMORY_COMPACT` with a 15-minute grace; a NEW attendance opening on the thread arms it immediately — from any of the three writers of the thread (`runtime.ts`, `ingest.ts` via its `onAttendanceClosed` callback, and `nudge.ts`), which all take the claim through `src/graph/attendance-boundary.ts`. The resolve trigger is what makes the RESUMPTION turn cheap — measured, the cache rate falls to ~0% past 24h, so the returning customer's first turn is the one billed fresh. The boundary trigger is what covers a deployment that never resolves conversations, which is the same population the ceiling exists for. A human agent's reply is one of the messages ingestion folds in, so an attendance the bot never spoke in opens and closes boundaries too: one summarization each, on a share of the traffic that used to be invisible to compaction.
    - **Where the boundary LIVES: on the messages.** Every message written to the thread carries the conversation it belongs to (`fazerConversationId` in `additional_kwargs`, written only by the factories in `markers.ts`), and `selectClosedPrefix` asks where the CURRENT attendance STARTS — the first message stamped with the last stamped conversation. Asking for the start rather than the previous end is what lets ASSISTANT replies go unstamped: the graph builds those, and each sits after the stamped human turn of its own attendance. The `CONVERSATION_DIVIDER` stays as PROMPT content (it tells the model a new attendance began) and decides nothing: it is one message that somebody has to notice the need for, write in the right place and keep, and every way that can fail — a concurrent invoke erases it, the transition goes unnoticed, the marker row advances on its own — is a way two attendances get summarized as one, silently. Metadata is inert on the wire: the OpenAI, Google and Anthropic adapters read only known keys out of `additional_kwargs`. Threads written before stamps existed read as one attendance in progress and compact on their next boundary. Recognizing the head and the divider by metadata rather than by their text is also what stops a customer who TYPES `<atendimentos-anteriores>` from having their message taken for the head — excluded from the summary and then replaced by it, i.e. deleted without ever being summarized.
    - **Three guarantees against compacting twice**: `SchedulerJob` is unique on `(tenant, kind, dedupeKey=threadId)` so both triggers collapse into one row; `AttendanceSummary` is unique on `(tenant, instance, contactInboxId, conversationId, lastMessageId)` and written with `upsert`, so a SEGMENT is summarized exactly once; and the job recomputes the cut on every run, so a second run finds an empty closed chunk and stops before spending a generation.
    - **Its own claim lane.** `MEMORY_COMPACT` is drained by a dedicated worker (`src/modules/memory/worker.ts`, `COMPACTION_WORKER_INTERVAL_MS`, default 15s, batch drained concurrently under the process-wide model semaphore), and `claimDueJobs` excludes it. The mirror image of the debounce split: the scheduler tick awaits its claimed jobs ONE AT A TIME, a summary is a model call with a 60s ceiling, and compaction is the only kind that fires for every agent on every closed attendance (it ships on by default) — so on the shared lane a batch of them would delay a follow-up or an appointment reminder by minutes. Nothing on this lane is time-sensitive in return: the resolve trigger already waits out a 15-minute grace.
    - **`selectClosedPrefix`** (`memory/cut.ts`, pure + decision-table tested) finds the boundary. The memory head is never part of the closed chunk: it is re-rendered from the rows on every compaction, so feeding it back would summarize a summary — each attendance is summarized ONCE, from its raw turns, which is what keeps a rolling summary's compounding loss out of the design.
    - **The rewrite** is optimistic, in the debounce supersede idiom: read state → summarize OUTSIDE any lock (a provider round-trip, seconds long) → under the SAME `ingest:<threadId>` advisory lock ingestion uses, re-read and verify the summarized messages are still the thread's prefix by message id → replace them. Anything that arrived meanwhile survives; a prefix that changed (a `/reset` landed) aborts and retries. The head is a `HumanMessage` carrying `<atendimentos-anteriores>` (one dated `<atendimento>` block per row, most recent 20, dated in the AGENT's timezone so a late-evening attendance is not filed on the next day), for the same reason the divider is: the agent node strips system messages.
    - **A rewrite must never land while an invoke is reading the thread.** A LangGraph invoke is a read-modify-write of the WHOLE message channel — it saves the state it loaded when it started, plus its own messages — so a rewrite in the middle of one is not merged, it is UNDONE when the turn finishes, and the raw turns it replaced come back. Turns claim the graph thread for the length of their invoke (`graph/inflight.ts`, COUNTED so overlapping turns do not release each other's claim), under the same advisory lock the rewrite holds while it checks, which is what makes the two exclusive rather than merely staggered. The job checks twice: once cheaply before the generation, so a deferred attempt costs no tokens, and once under the lock, which is what makes it correct.
    - **A row whose turns are still raw is OWED its rewrite.** The row is committed before the rewrite on purpose (duplicated memory is recoverable by reading it; lost memory is not), so a deferral between the two leaves one behind — and since the job's dedupe key is the THREAD, a later attendance re-arms the same row and the retry arrives with a wider prefix. The owed prefix is applied first, under its OWN conversation, and the job reschedules when the natural cut reaches past it.
    - **The rewrite removes BY ID and never clears the channel.** `REMOVE_ALL_MESSAGES` replaces the whole list with what the update carries; ingestion is held off by the lock, but a graph TURN writes to this thread holding none, so a message landing in that window would be erased. The head reuses the id of the first message it replaces, which is what keeps it at the front (the reducer replaces a same-id message in place and appends an unknown-id one at the end).
    - **One row per attendance SEGMENT**, keyed on the id of the last turn it summarized. A resolved conversation can be reopened by the customer and resolved again — ordinary Chatwoot, and by then the first pass already compacted it. The second cut carries only the new turns, so a row keyed on the conversation alone would either replace the first summary with a description of the tail or reuse the first for turns it never saw; both delete the new turns and lose half the attendance. Keyed on the last message id, the second pass writes its own row and both halves survive, while a RETRY of the same cut finds the same id and costs nothing.
    - **`attendanceAt`, not the row's `createdAt`**, dates the memory. The boundary trigger fires only when the contact comes back, which can be months later, and dating by the job would tell the model a returning customer's whole history happened today.
    - **Reset fences.** `/reset` cancels the thread's PENDING compaction job and, under the SAME `ingest:<threadId>` lock the compaction takes to write its row, deletes the summaries and the `AgentThread` row. A job already CLAIMED is past `cancelPendingJob`, so it re-checks — inside that lock, in the same transaction as the write — the `AgentThread` row id it started with: `/reset` deletes that row and the next message recreates it with a new id, so the id already in the schema is the generation token. Sharing the lock is what makes the check and the write atomic against the reset; a check that is not is a race the reset loses.
    - **The summary** (`memory/summarize.ts`) runs on the AGENT's own model and credential by default, and `agent.settings.memory.compaction` carries an optional OVERRIDE (`provider`, `model`, `credentialRef`, `baseURL`) resolved by `src/graph/model-override.ts`, the same resolver `tts.normalize` uses, so the pinning rules are one implementation rather than two copies that drift. All four absent is the default and runs on the agent's model. A provider other than the agent's inherits NOTHING from it (not the key, not the endpoint, not the sampling knobs) and requires its own credential; a model or a key with no provider is stored without complaint and leaves the summariser dead, so the attendance stays raw. The editor pins the provider the moment you pick either, which is what keeps that last state unreachable from the console. The transcript is fenced (`<transcricao>`, tag-stripped) and never interpolated into the system prompt. Tool RESULTS do not travel (heaviest, least summarizable, and restated in the reply that follows); a tool CALL travels as its name. A failure leaves the thread untouched and the job retries — reusing the summary already committed rather than paying for a second generation. An attendance with no text at all is a legitimately empty summary, which is a different state from a failure. The call carries the usual usage/trace callbacks under node `memory_compact`: it is billed like any other generation, and one nobody waits on is exactly how spend goes missing from the cost report.
- **`src/graph/tools/native.ts`** — `buildNativeTools(ctx, allowed?)` returns the bot-token Chatwoot tools the agent can call mid-turn: `handoff_to_human` (optional private-note summary + `toggleStatus("open")` so the conversation leaves `pending` and the bot goes silent), `private_note`, `set_custom_attribute` and `assign_label` (both take a `scope`: `conversation | contact | task`, the `task` option offered only when the conversation has a linked kanban card; contact resolves the Chatwoot contact id, task targets the card), `resolve_conversation`, `kanban_move_card` (move the conversation's card by step name, grounded by the enriched `KanbanContext`), `update_kanban_task` (partial edit of the linked card's `title`/`description`/`priority`/`startDate`/`dueDate` via `client.updateKanbanTask`; current card values grounded into the description; field set confirmed against Chatwoot's Kanban API; no-op without a card), `set_voice_preference`, `calculator`, `get_current_time`. `allowed` is the per-agent allowlist (fail-closed); absent ⇒ all native tools. Attachments (`send_image`, and the per-template document tools in `src/graph/tools/documents.ts`) do NOT post from inside the graph invocation: they queue on `TurnState.pendingAttachments` and the runtime delivers after the turn's gates, ahead of the reply text — see [`docs/documents.md`](documents.md). Each tool is bound to a `ToolCtx` (`{client, conversationId, …}`). Optional operator guidance is appended to a tool's model-facing description via `withOperatorNote` (`ToolCtx.toolInstructions`, populated in `prepare`): `handoff_to_human` / `kanban_move_card` read theirs from their grouped config (`agent.settings.handoff.instructions` / `agent.settings.kanban.instructions`); guidance for any other tool (today `set_custom_attribute` / `assign_label` / `update_kanban_task`) lives in the flat `agent.settings.toolGuidance` map (`readToolGuidance`), folded into the same `toolInstructions`.
- **System prompt composition (`src/graph/prepare.ts` + `prompt.ts`)** — the prompt the model sees is assembled in a fixed order: the tenant's own prompt (or an A/B variant / a playground draft), `+ GROUNDING_DIRECTIVE` when the KB tool is granted, `{{var}}` interpolation over sanitized contact/inbox/time values, `+ <attribute_values>` (the Chatwoot custom attributes the operator selected — mirrored, so no API call; see [`docs/chatwoot.md`](chatwoot.md)) and finally `+` the MCP server-context block at `buildModelAndGraph`. Everything appended AFTER interpolation is literal by construction — a stored attribute value containing `{{nome_contato}}` is never substituted.
- **`src/graph/status.ts`** — `AgentStatusReporter` is a LangChain `BaseCallbackHandler` that surfaces COARSE, live graph progress to the operator as a transient "agent is working" indicator on the per-tenant realtime channel (`broadcastAgentActivity`). `handleChatModelStart`/`handleLLMStart` → a `thinking` step; `handleToolStart` → a `tool` step carrying the tool's `runName`. Metadata only (an enum + a tool name); no-op when the conversation has no mirror row id; non-throwing and not awaited (a fire-and-forget publish, unlike `UsageCapture`). `runAgentTurn` adds the started/finished envelope (see below).
- **`src/graph/runtime.ts`** — `runAgentTurn` is the orchestrator:
  1. scoped read (no network): inbox → `Inbox.agentId` → `Agent` (systemPrompt, modelConfig) + the vault API key. Both silent, and reported apart because they are repaired differently (issue #318): an inbox with **no agent bound** ⇒ `no-agent`, which the webhook turns into an operator-facing `route` line; a binding that exists and will not load (**disabled agent**, missing row) ⇒ `agent-unavailable`, which writes nothing, being the operator's own decision. The two are classified inside that single scoped read, so a rebind during the turn cannot make the answer describe a different moment.
  2. build model + graph (checkpointer from `getCheckpointer()` or injected).
  3. invoke the thread (network: LLM), keyed by `thread_id`, with an `AgentStatusReporter` in the callbacks and a `started()`/`finished()` envelope around the invoke in a `try/finally` — so the operator's typing indicator appears before the first token and is **guaranteed to clear** on every exit (posted, empty, taken-over, or thrown).
  4. **re-check the live assignee** from the mirror before posting — a human may have taken over during the LLM call (`taken-over`). Small TOCTOU before the network POST; acceptable for the single-replica MVP. The `resolve_conversation` native tool is **deferred** through this gate: it records an intent on the per-turn `TurnState` and the runtime applies the actual `toggleStatus("resolved")` only AFTER the reply is delivered (`applyDeferredResolve`), on the `posted`/`empty` outcomes only — an immediate mid-turn toggle would make this recheck read the bot's own resolve as a takeover and discard the final reply (and the post would reopen the conversation anyway). Intent is discarded on `taken-over`/`superseded`/`blocked`/throw. Nudge turns and the playground don't pass `TurnState`, so the tool keeps the immediate toggle there.
  5. post the reply via the **bot token** (`loadChatwootClient` → `sendMessage`).

  All network I/O is outside transactions; scoped reads are short and DB-only. The function is injectable (`deps.makeModel`/`makeClient`/`checkpointer`) so tests run with a fake model, a stub client, and a `MemorySaver` (no real LLM/network).

- **Attendance boundary (`src/graph/attendance-boundary.ts`)** — the rule is a pure decision (decision-table tested) shared by the three writers of the thread: the reactive turn, the ingestion of an unanswered message, and the proactive nudge. It answers three things at once — does a divider go in, does the marker advance, and which attendance just ended — and it exists as a unit because it previously lived inline in two of the three and was MISSING from the nudge: a proactive follow-up that opened a conversation went in unstamped, so the next reactive turn put the boundary after it and the nudge was summarized away as part of the previous attendance. A new conversation reusing the thread is CLAIMED atomically, under the same `ingest:<threadId>` advisory lock ingestion takes: inside that lock the marker is read, the divider is written to the thread as its own message, `AgentThread.lastConversationId` advances, and compaction is armed just after. All-or-nothing on purpose, for three reasons that each bit: two deliveries for the same new conversation can run at once (debounce off), and both would have prepended a divider — compaction cuts at the LAST one, so the open attendance's first exchange would be summarized away as if it had ended; the marker must not advance without the divider landing, which is what happened while the divider rode inside the turn text and an input guardrail answered before the model; and with the divider durable at claim time, the compaction job can be armed immediately instead of waiting on the invoke. A side effect worth having: the guardrails now see the customer's raw words on both directions, because no turn text carries a system marker the customer never wrote.

- **`src/graph/ingest.ts`** — `ingestMessageIntoThread(...)` folds a conversation message into a contact-inbox memory thread WITHOUT running a model, via `graph.updateState({ messages: [msg] }, "noop")` on a MINIMAL graph (`StateGraph(MessagesAnnotation)` + a single `noop` node). The channel schema is identical to the real agent graph, so the same checkpointer thread interoperates — the appended message is visible to the next real turn (validated by `tests/graph/ingest.test.ts`: real turn → ingest → real turn round-trip). A customer's message becomes a `HumanMessage` (rendered via `renderInboundMessage`, so audio/image markers + transcription ride along); a human agent's reply becomes a marked one carrying its raw text (`role`, required rather than defaulted — the field reaches every call site, and a default would let the next writer inherit `customer` silently, which is the misattribution back). At-most-once is the monotonic `AgentThread.lastSyncedMessageId` (CAS under a per-thread advisory lock, which also serializes concurrent appends so they can't clobber each other's checkpoint). The markers live in `src/graph/markers.ts` (a near-leaf module — messages only — so the pure compaction cut stays pure), and every message this writes carries its conversation id in `additional_kwargs`, which is what the cut reads. Whether the message also CONSUMES an attendance boundary is decided by `src/graph/attendance-boundary.ts`, not here.

## Tool preconditions

An operator can declare, per granted tool, a condition the runtime checks BEFORE running it. Unmet, the call does not happen and the model is handed a sentence saying which attribute is missing, so the turn continues instead of ending. Motivated by an agent that was told in five separate places never to hand off without the article URL and called `handoff_to_human` three times out of three anyway, writing the unmet condition into its own `reason` argument (issue #101): a tool grant was binary, so every constraint on tool use was an instruction, and an instruction is re-decided by the model every turn.

- **Stored** at `agent.settings.toolPreconditions`, a map keyed by **tool name** — `{ "handoff_to_human": { "kind": "attribute", "scope": "conversation", "key": "article_url" } }`. `equals` is optional; without it the rule is "the attribute holds any non-blank value". The name key is what makes one map reach all six tool sources: `buildToolset` merges native, document, HTTP, MCP, toolpack and RAG into one name-unique list, so a name is the identifier every source already agrees on.
- **Applied** in `src/graph/tools/precondition.ts`, wrapping each named tool at that merge point. A tool with no condition is returned untouched, so an agent that configured none pays nothing.
- **The state is read per CALL**, not once per turn (`preconditionStateLoader`, a scoped read of the two mirrored attribute bags). That is the turn the issue describes: the customer gives the value, `set_custom_attribute` writes it, and the guarded call comes after — a snapshot taken at turn build would refuse a condition the same turn had satisfied.
- **Fail-closed.** A state read that fails refuses the call, the same way the contact-authorization gate does: a precondition exists because running the tool wrongly costs something the operator cannot undo.
- **The refusal is not a failure.** It returns as a normal tool result, not a `ToolFailure`, so it never pages an alert channel. It does emit a `tool`-stage flow-log line at level `info` carrying the tool, the condition kind and the attribute KEY (never the value) — visible in the Logs page, which is where "the agent stopped handing off" gets answered.
- **A state read that FAILED is a different line, and it does page.** Failing closed is the right answer to the model and the wrong one to the operator: a pool timeout refuses every guarded call for as long as it lasts, so it is reported at `warn`/`error` with phase `precondition_unreadable` and the error's CLASS (never its message, which carries the failing query). The model is told the same sentence either way, so a database fault never becomes a customer-visible difference in what the agent says.
- **NATIVE tools only, in the API as well as in the console.** The write boundary refuses a rule on any other name (`isGuardableToolName`), and the console offers exactly that set from the same predicate. The reason is identity, not taste: a native name IS the tool (not renameable, not namespaced, first in `dropDuplicateToolNames`), whereas an MCP tool is exposed as `mcp__<slug>__<tool>`, derived from the connection's display **name**, and two integration instances of one catalog type expose the SAME names, with grant order deciding which survives. Both of those are now anchored on the source's name rather than on a row id: the grant read orders MCP by connection name and integration by (catalogType, name) instead of by id (#412), and the slug's fallback for a name that yields no ASCII is a digest of that name instead of the connection id (#389 had anchored the same order on the row the grant points at, which is stable inside one tenant and means nothing across two — an export/import reassigns those ids, and where the destination already holds one of two colliding sources the pair inverts and each name reaches the *other* server). What still moves the exposed name is a **rename of the connection**, and an imported settings bag is copied verbatim, so a rule keyed on an MCP name can still stop matching. A precondition that follows a name onto a different tool, or stops matching, is a guard that silently stops guarding. Extending past native waits on a name that a rename cannot move. The MCP `agent_settings_set` is a closed list of behavior blocks and does not carry this one yet.
- **A tool dropped for a duplicate name says so too (#389).** Two sources can claim one name, and the assembly keeps the first and drops the rest rather than refusing to build the toolset over one name. The drop now emits a `duplicate_name_dropped` line at `info` (same reasoning as the bullet above) naming the tools that lost, alongside the process warning that was previously the only record — on a managed deploy the operator may have no way to read stdout at all, and what they see otherwise is an agent that quietly stopped doing one thing. The line does NOT prescribe a rename: that is an action for an MCP connection, whose slug comes from its display name, and no action at all for two instances of one toolpack, whose names come from the pack.
- **A rule that matches nothing says so.** An agent import copies the settings bag verbatim, and a grant can be removed later, so a rule can end up naming no assembled tool. The runtime reader does not drop it (the name may still match), and assembly emits a `precondition_unmatched` line at `info` plus a process warning — `info`, because a static misconfiguration must not page once per turn, and reported at all because "the console shows a rule and the tool runs anyway" is the one outcome that looks exactly like protection.
- **Not a condition over the transcript.** The obvious rule for the reported case ("a link on this host was given") needs the message history, and a tool cannot reach the graph state: `getCurrentTaskInput()` throws outside a Pregel run, and the mirror does not hold message bodies. Express it by extracting the value into an attribute with `set_custom_attribute` and requiring the attribute.

## The tool boundary, when the turn was called off (issue #449)

A turn's caller can withdraw it — an operator types `/reset`, a job is retired — and `runLoadedTurn` asks about that at every seam it owns: before the divider, after the claim, before the invoke, and at each outward write. All of those sit BETWEEN two steps, and a tool call happens inside one. So a command landing once the model call is in flight is refused on its memory step, says so in the acknowledgement, clears everything else it can reach, and the turn's tools then write an attribute, a label and a kanban card back onto exactly that.

- **The ask is handed to the graph and made at the tool node.** `buildAgentGraph({stillWanted})` takes the caller's own question and asks it once per tool-calling HOP, in the node every tool source passes through — native, HTTP, MCP, integrations, documents. A guard per tool is the per-call-site enforcement this repo keeps having to undo: the tool added next week would simply not have one. Absent for callers with nothing to withdraw them — the playground, and any caller that scheduled no work — and absent means the node is what it was. The **nudge passes one too**, and for the same reason it makes fifteen other asks: it runs from a scheduler job, `/reset` retires that job, and a retirement landing inside its model call left `assign_label` and `set_custom_attribute` free to write.
- **The refusal is a tool result, and the turn ends on it.** Routing away from the node leaves an assistant turn carrying `tool_calls` that no `ToolMessage` answers, and that thread is what the next turn loads and replays — `@langchain/openai` replays those calls out of `additional_kwargs` (see the silence rules below), so the provider is handed a call with no answer and rejects the history: the conversation stops working, which is worse than the write being prevented. Answering the refusal back INTO the model invites it to call the same tool again, round after round to the recursion limit, on a conversation the operator already cleared. So each pending call gets `CALLED_OFF_TOOL_RESULT` and the graph goes to `END`. The runtime's own send gate refuses the post of a called-off turn, which is what keeps that text out of the conversation.
- **It refuses by RETURNING, never by throwing, and that is measured.** Elsewhere the fence's `strict` option lets an unreadable answer stop the run by throwing, on the reasoning that it is asked before anything is written. By the time this node runs the assistant turn carrying the calls is already checkpointed: against the real checkpointer, a tools node that throws leaves the thread `[human, ai(tool_calls=call_x)]` with no `ToolMessage` — the exact broken sequence above, produced by the mechanism meant to prevent it. Several of the fences the runtime hands down read a job row and throw on a database transient whatever the strictness, so the graph catches and treats an unreadable mark as "still wanted": the same trade the sends make, since silence is not evidence that anybody withdrew the run.
- **And it does not END on the refusal.** `lastAssistantText` reads the reply off the last message whatever its type, so a turn ending on the `ToolMessage` offers the refusal's own sentence as the text to post. The send gates refuse a called-off turn today, but the fences handed down are not all monotonic — the channel-redirect one answers false while an agent is disabled and **true** once it is re-enabled — so "called off here, still called off at the send" is a property of the caller, not of this seam. The batch is therefore closed with the same empty assistant turn the silence protocol ends on, which makes the refusal unpostable by construction.
- **The rollback has to know nothing ran.** `planTurnRollback` keeps a turn that acted on the world, because no removal here can undo a write that already left — and a refused call looks exactly like one that ran. So each refusal carries a marker only the graph writes (`called_off`, in `markers.ts` beside the divider and the nudge). Not the tool's NAME, which is the operator's and covers every source; not the content, which any tool may return. The pairing is **positional**, which is what the mechanism actually is: the boundary refuses a BATCH, either answering every call of the assistant turn it just read or none, and it emits those answers directly after that turn — so the turn a refusal follows is the one whose calls did not run. (Pairing by `tool_call_id` was the first version and read the wrong axis: a provider may emit a call with no id, the refusal then carries `""`, and the cancelled turn came back as "a tool ran".) Positional rather than "the slice contains a refusal", because a turn can run a tool on one hop and be refused on the next: that first result is a real act and the slice stays whole.
- **The caller is told, off the RESULT rather than off its own fence.** A refused turn ends on an empty assistant message, byte for byte what a turn that chose silence ends on — so read as silence it advances a follow-up ladder or a handled watermark over a message nothing answered, and rolls nothing back. Asking the fence again does not answer it: the fence is the thing that can have changed its mind. `turnWasCalledOff(result.messages)` reads the shape the boundary emits (the refusals, then the empty turn that closes them), and both `runLoadedTurn` and `runAgentNudge` ask it before the line that drafts a reply.
- **What it costs**: one read per tool-calling hop, and none on a turn that calls no tool.

## Saying nothing (issue #454)

An agent turn that decides not to write has to say so somehow, and the shape of that "somehow" is the whole feature. `src/graph/silence.ts` is the one rule; everything else reads it.

- **Silence is a TOOL CALL, not a token.** The follow-up used to be told to answer with exactly `[[SKIP]]`, because "reply with an empty message" produces narrated emptiness instead ("(vazio — nada a fazer)"), which is non-empty text that gets posted. But the memory thread is keyed per contact-inbox, so every silent follow-up left an assistant turn whose whole content was that token, and a later ORDINARY turn for the same contact reproduced it — delivered verbatim on an email inbox, a real email to whoever wrote in. The directive now asks for `skip_reply`, whose call leaves no imitable text.
- **Nothing the model wrote BESIDE the decision survives either.** A model can put text in the very message that calls `skip_reply`, and that text is never delivered — the runtime posts the last assistant message, which is the empty one the turn ends on. Left in the channel it is a sentence the customer never saw, read by the next turn as something they were told. The message is replaced by id with its TEXT removed and everything else carried over — the tool calls (so no `tool_call_id` is orphaned), the invalid ones, and the metadata. Text is removed wherever it lives and nothing else is: a block list keeps every non-text block, because Anthropic's signed `thinking` / `redacted_thinking` must be replayed unchanged before the tool result they precede; and the raw `output` array `@langchain/openai` keeps in `response_metadata` for the Responses API loses its text parts too, because for those models the history is serialized from THAT and not from `content` — and an item the filter emptied goes with them, since an assistant message with an empty content array is that API's own version of the empty text block (an item that ARRIVED empty is the provider's own and stays). Blanked the moment the decision is SEEN, and blanked in what the model is SENT as well as in what is persisted — the update lands after the call, so the extra round would otherwise still read it: a parallel batch is not terminal, so a rule that only ran on the way out left the narration standing whenever a companion tool bought another round and the turn still finished silent. Scoped to the decision: a preamble beside an ORDINARY call is followed by a reply that may lean on it, and rewriting every tool-calling turn's history is a different change.
- **Terminal only when the decision was ALL the model did.** `skip_reply` beside `react_to_message` is the documented way to answer with a reaction alone — the reaction IS the reply — so ending the turn on the skip when that call did not happen leaves the customer with nothing at all. Whether it happened cannot be read off the result: business-level refusals are normal operation and are forbidden from using `toolFailure`, so `react_to_message` declines with an ordinary success string when the last message is itself a reaction, and `send_image` does the same for a disallowed host. Telling those from a tool that really acted needs a per-tool contract every future tool would have to join. So the question is asked of the CALLS and answered conservatively, the way `actedOnTheWorld` answers its own: a batch that called anything else produced information the model has not seen, so it decides again — including a call whose arguments did not parse, which LangChain files under `invalid_tool_calls` and a check reading `tool_calls` alone would not see. The cost is one more model round on that batch, and it is the point — when the reaction did not happen, answering is what the customer needs. The wrap-up instruction still does not land on that round: choosing silence and ending on it are two questions. Nor does the HARD limit talk the decision out of itself — its path invokes the raw model with no tools, to force a text answer, so a turn that chose silence and has a companion to inspect gets `skip_reply` alone bound instead: the budget stops the tools that act and leaves the one that does not, and the model either reaffirms silence (terminal) or answers, which is what the customer needs when the companion failed. `onToolLimit` fires once per turn: two rounds now cross the cap (the batch, then the reaffirmation) and it is one event, whose handlers write an operator line and can page.
- **The empty terminal message stays in the CHANNEL and never reaches the model.** It is what keeps `lastAssistantText` reading `""` instead of the skip tool's acknowledgement, which would otherwise be delivered to the customer as the reply — so it cannot simply be omitted. It also cannot be sent: `@langchain/anthropic` renders string content as a text block and Anthropic refuses an empty one, so a thread that accumulated one would stop answering entirely. `agentNode` drops empty assistant turns from the history it sends, which covers the marker and the empty message a model returns on its own. **Empty means no content, not merely no text**: a turn whose whole content is a signed `thinking` block is output, and dropping it deletes exactly what the blanking rule above preserves. That exemption is bounded by where the block can still be rendered, because only the vendor that emitted a non-text block re-serializes it: `@langchain/openai` builds an assistant message from the text blocks alone, so an Anthropic `thinking` block reaching an OpenAI-shaped model arrives as `content: []` and the request is refused. The turn is therefore kept only when its own `response_metadata.model_provider` is a vendor that replays its own blocks (`REPLAYS_OWN_BLOCKS` in `src/graph/graph.ts`, `anthropic` alone today) AND every model that can receive this turn (the agent's, and the cross-vendor fallback's when one is configured) is that same vendor. Anything unanswerable — unknown origin, no nameable destination, two vendors — drops the turn, which is always safe.
- **The decision is TERMINAL.** `skip_reply` is a tool, so the graph loops back to the agent node with its result, and "produce no message now" was the model's to keep. It usually does, being told to; when it does not, a turn that chose silence writes to the customer anyway, which on the proactive path is an unsolicited message. So `agentNode` ends the turn on the decision — no further round at all, whatever the tool budget says. The call still COUNTS, which is what bounds a model that loops on `skip_reply`.
- **A MARK is the identity: not the name, and not the text.** `skip_reply` is a native name, so an operator may declare a precondition on it, and an unmet one returns a NORMAL tool result under that same name telling the model to carry on. Read by name that is silence, and the turn ends with nothing where a customer is waiting. Nor is the acknowledgement enough: it is published here, and with natives revoked a custom HTTP tool may hold this name and return a body its operator does not control — a third-party API, or a customer's own words echoed back — so a body beginning with the ack would end the turn without answering, by injection. The tool returns a whole `ToolMessage` carrying `SKIP_REPLY_MARK` in `additional_kwargs`, which no response body can set (the same direct-tool-output passthrough `failableTool` uses), and `skipReplyRan` reads that. Anything unrecognised is not silence, and the turn goes on to answer.
- **The channel is decided by the toolset that was BUILT, never by the config that asked for it.** `withFollowupSilenceChannel` grants `skip_reply` and drops any precondition standing on it — refusing only when the native is not already granted AND a custom HTTP tool carries that name (with the native granted it wins the name anyway, so refusing there would protect nothing and skip the precondition cleanup) — HTTP is the one source whose exposed name is free operator text, since MCP tools are namespaced `mcp__<slug>__<tool>`, document tools are `send_<slug>` (and a colliding slug is refused at write), and toolpack names come from a closed catalog we ship, because natives come first in `dropDuplicateToolNames` and granting ours would evict the operator's from every follow-up. After assembly, `withoutLoneSilenceTool` takes it back out when OUR tool turns out to BE the whole toolset — ours, asked of `inertToolsFor` and never of the name, because with natives revoked the lone tool under that name is the operator's and removing it would delete their only tool: every other source yielded nothing, so this agent is tool-less in practice (a plain chat model, or an `openai-compatible` endpoint that answers 400 to any function schema), and binding one no-op tool there costs the whole follow-up instead of leaking one token. Asking which sources were CONFIGURED is not the same question — an MCP server that is down is configured and yields nothing. `followupSilenceChannel(cfg, tools)` then reads the same assembled list for what the directive may ask for, so the binding and the directive cannot disagree.
- **Removing the lone protocol tool belongs to the FOLLOW-UP alone.** On a reactive turn an agent granted `skip_reply` and nothing else is the operator's own configuration — it is how their agent answers "ok" with silence — and production keeps the tool bound. The playground's reactive path does too; only its simulated follow-up passes `silenceProtocol`.
- **A reopened session is sanitized by the rule that produced it.** The rebuild (`playground/sessions.ts`) reads a follow-up slice with `proactiveReply` and an ordinary one with `customerFacingReply`, told apart by the nudge fence on the slice's opening turn. One rule for both showed the operator a different reply from the one they were given: the proactive rule strips a stray token from a real answer, the reactive one keeps it on purpose.
- **The playground simulates the protocol, it does not mock it.** OUR `skip_reply` is exempt from `applyToolMocks` and from `buildSimulatedNativeTools`, for one reason: its RETURN is the whole tool, and the runtime recognises silence by that acknowledgement. A canned result under its name is not read as a decision to stay quiet, so the graph asks the model again and the simulation writes a follow-up production would have suppressed — lying about the one decision the playground exists to show. A tool of the OPERATOR'S that merely shares the name takes its mock like any other: it really calls something, and refusing the mock would have the playground hit the live endpoint, which is the one thing a simulation must not do.
- **The reactive rule is narrower than the proactive one, deliberately.** Nothing in an ordinary turn's prompt asks for emptiness, so only a reply that reduces ENTIRELY to the token is silence there (quotes and repetition tolerated); one that merely CARRIES it keeps its text and reports `silenceTokenInReply`, because editing a real answer to remove a substring is the data loss the standing rule below prohibits. The proactive rule adds the narrated-emptiness family, because that path asked for the token until this change.
- **A silent PROACTIVE turn takes its own words back out too.** A follow-up that ends `silent` is not refused — it concluded correctly — but the model may have written the sentinel, or a narrated "(nada a fazer)", to say so, and none of it reached anyone. Left in the shared contact-inbox thread it is a sentence the next ordinary turn reads as something the customer was told, and reproducing it now costs that customer their answer entirely (the reactive rule reads a reply that is only the token as silence). That is issue #454's own defect in the one place the tool channel does not reach — the tool-less agents — so `runAgentNudge` removes it, through the REACTIVE plan rather than the proactive one. The two are not interchangeable: the proactive plan takes directive and answer together, and therefore keeps EVERYTHING the moment a tool ran, which is right for a refusal and would leave the token untouched on any follow-up that labelled the conversation before going quiet. The reactive plan names the trailing assistant run, so the act and the directive stay and only the sentence nobody read comes out — an event the agent chose not to answer is what actually happened. A turn that produced no text at all left nothing to take back and pays no round trip (`wroteText`). The playground's simulated follow-up does the same, with one difference forced by its shape: its directive is a plain `HumanMessage` (`nudgeMessage` stamps a conversation id and there is none here), so the proactive plan finds no marker to cut at and the REACTIVE plan names the removable part directly — the trailing assistant run, which is exactly the token. The directive stays there, as it already does after every simulated follow-up.
- **A token-silenced turn is ROLLED BACK.** The raw message is already checkpointed by the time any rule sees it, so leaving it feeds the defect: the thread is shared per contact-inbox and the next turn reads one more sentinel answer. `undoRefusedTurn` takes it back out on the inbox path and in the playground alike. A turn silenced by the token can still be REFUSED afterwards (a takeover, a supersede, a `/reset`), and every refusal exits through `refuse`, whose own rollback removes the same messages — so the two race, and the armed one reads `already-gone`. That is the goal reached, not a miss, and it is logged as such: `return refuse(...)` is not awaited, so the `finally` runs while that rollback is still in flight and no flag cleared inside `refuse` can be seen in time. Reading the OUTCOME rather than the ordering is what makes the answer stable. The turn TRACE keeps the raw token on purpose — it exists to show what the model produced.
- **The rollback is an append, so it takes the claim appends take.** It writes the message channel from outside an invoke, and it runs just after the turn released its own durable claim — exactly when a turn on another replica may start. It therefore takes `claimIngestWrite` (see the note in `thread-claim.ts`): held, a starting turn waits and then loads a channel the token has already left; held by someone else, this stands down as `another-invoke-is-reading`; and the release is best-effort, like ingestion's, because it runs after the removal is already written and stops the lease renewal before it touches the database — throwing there would turn a clean rollback into an error and strand the claim either way. The durable TURN claim would not do — `turn_holders` is counted, so two turns share a thread by design. An invoke ALREADY reading the channel still wins, and a thread with no `contactInboxId` has no row to claim; both cost exactly what no rollback costs.

## What an HTTP tool's response hands the model

By default the whole response body, clipped at `maxResponseChars` (`MODEL_RESPONSE_CHAR_LIMIT`, 4000, declared in `src/modules/tool-definitions/response-template.ts` so the editor's preview can clip by the same number), prefixed `HTTP <status>`. That default has a failure mode worth naming, because it is not about tokens: **a clipped payload does not read to a model as missing data, it reads as a gap to fill from training data.** Measured on #456 against a public CNPJ lookup — a 7,982-char response whose first 2.3k are five third parties' names and masked tax ids, and whose registration status sits at char 7,806. The agent answered with a status that was not in the tool result at all, twice, past an explicit system-prompt guard telling it not to infer one.

So a tool may declare **what its response should look like** by the time the model reads it, in `ToolDefinition.outputSchema`:

```json
{ "mode": "template", "template": "**{{razao_social}}** — {{municipio}}\nSituação: {{descricao_situacao_cadastral}}" }
```

- **The path grammar is the appointment declaration's** (`src/modules/tool-definitions/json-path.ts`): dot-separated keys, a numeric segment indexing an array (`data.items.0.name`), and no filter expressions — the whole surface an operator learns is one sentence. The walk and the picker are shared; what each feature brings is its own rule for what a path may END on, and they differ on purpose. An appointment id may not be a boolean or the empty string; a template that could not render `"active": false` would show the model a blank where the API said no.
- **These tokens are NOT the request-side tokens.** `{{contact_name}}`, `{{secret}}` and the AI-filled fields belong to the URL/headers/body and have no dots. A response template addresses the response body and nothing else, so `{{secret}}` in one resolves as an ordinary (missing) path, never as the credential.
- **The decision lives in `projectToolResponse`**, in `modules/tool-definitions/response-template.ts`, not in `http.ts`: the console's preview has to make the identical one, and a second copy of these rules is how a preview stops being one. `http.ts` keeps the reporting, which is the runtime's alone.
- **A template with no tokens needs no body.** `Done.` is a legal declaration, and the endpoint that most wants a constant answer is the one that returns 204 with nothing in it — so the render is not gated on the body parsing as JSON. With a token, a body that is not JSON still falls back to the raw response and warns: the token has nothing to resolve against, and an empty render would be worse than the body it replaced.
- **A stray `{{` or `}}` is refused at the write, not left for the model.** `{{a}` matches no token, so the token scan cannot see it; `unmatchedTemplateDelimiter` looks at what is left once the real tokens are removed. It costs writing a literal double brace in a template, which is a typo far more often than it is content.
- **It renders BEFORE the clip**, which is the feature rather than an optimization: every status-bearing field in the measured response sat past char 4000, so rendering after the cut could never have reached one. The clip still applies to the rendered text as a backstop, and one long value is cut where it happens (with `…[truncated]` in place) so the fields after it survive.
- **A path that does not resolve renders `(not returned)`**, never an empty string, and the paths are named to the operator on the `tool` stage (`phase: "response_template"`). A path that resolved to `null` or `""` renders the same marker and is NOT reported: the path is right, the API answered with nothing, and sending the operator to fix a correct template is as wrong as leaving the model a blank.
- **Only on 2xx.** A non-2xx body is the provider's own error message and the model needs it verbatim; a template aimed at success fields would paper it over with a block of absent markers. `expectedStatuses` does not change this — it says a status is a result rather than an integration failure (a lookup's 404 meaning "no record"), not that the 404 body carries the success fields.
- **A body that is not JSON** keeps the raw clip and says so on the same stage. The request succeeded; refusing the call would be wrong and an empty render would be worse than the body it replaced.
- **With no template, a response that WAS clipped now says so** (`phase: "response_clipped"`, with the char count and the limit). Truncation was otherwise invisible from both ends: the model reads `…[truncated]` as an end, and the operator reads a plausible answer. When the body was longer than what the runtime READS (below), the note carries `readCap` and says so instead of blaming the template: past that cap the JSON arrives truncated, so a template that would have applied reports itself as "not JSON", and the advice would send the operator to fix something that was never wrong.
- **Back-compatible by construction.** `outputSchema` has been writable through the MCP tool since it existed, unvalidated and read nowhere, so a row may hold a real JSON Schema. Only `mode: "template"` opts in; anything else declares nothing and still writes. A DECLARED template the reader would not honour is **refused** at the write instead of stored and ignored — the operator wrote it and is the one who can fix it.
- **A list of unknown length renders through a block** (#459): `{{#each path}}…{{/each}}` repeats its content once per item, a path inside it is relative to the item, and `{{.}}` is the item itself (`{{#each .}}` walks a body that IS the list; `.` is the current scope everywhere, so the grammar stays one sentence). Blocks do not nest, deliberately: the second level is where "relative to which item" stops being one sentence, and no measured tool needed it. Both markers are well-formed tokens to the token pattern, which is why `parseTemplate` runs first and the token scan sees what is left: a `{{/each}}` judged as a path would be refused as malformed, and one left to the token render would reach the model literally. A marker alone on its line takes the line with it (Handlebars' "standalone" rule), so the natural shape (marker, one line per item, marker) renders one line per item. **At most `MAX_EACH_ITEMS` (50) items render, and the rest is COUNTED** (`(and N more not shown)`), never dropped: at the 4,000-char cap that is 80 characters per item, about one line of a search result, and past it the clip would cut mid-item; a model reading "and 120 more" knows to narrow the query, and one reading a list that simply ends does not. An empty list renders `(none)`: "no results" is an answer, and a label followed by nothing is the gap being closed. A block over something that is not a list renders the absent marker and is reported; over `null` it renders the marker and is not, the same three-way rule a scalar token follows. **A field an item lacks is reported once, at the first index lacking it** (`resultados.3.preco`): in-grammar, so the operator can paste it into the sample field, and deduped per field rather than per item, or a fifty-row list missing one column would name it fifty times. A block with no token inside still needs the body (`templateNeedsBody`): how many times it repeats is the body's answer.

`POST /v1/tools/test` (`src/modules/tool-definitions/test-run.ts`) runs an **unsaved** definition once so the editor can offer the paths out of a real response. It goes out through `buildHttpTool`, so the allowlist, the SSRF guard, the redirect refusal and the timeout are the same code rather than a second copy, and it wires **no** appointment closures and no ack: testing the tool that books must not book.

### The bound on an outbound call

`src/lib/outbound.ts` is the one place that fetches a third party and reads what came back. Every caller goes through `fetchBounded` (text), `fetchBoundedBytes` (a download) or `fetchBoundedNoBody` (a call whose whole answer is the status), and each hands back the body rather than an unread `Response` — which is the point, because there is then no second read for a caller to leave outside the bound.

- **The budget covers the whole exchange, not the headers.** The shape it replaces armed an `AbortController` for the fetch and cleared it in that fetch's `finally`, so the body was read with nothing left to end it. Measured on #464 under a 300ms bound against a provider that answered at once and then stalled: still pending at 3,002ms, and nothing would have ended it. Mid-turn that is a tool call that never returns.
- **And it covers SIZE.** `.text()` buffers the whole body before any limit can apply — 1,438 MiB of resident memory from a single call in the same probe, three seconds in and still climbing. `readCappedBody` keeps a prefix (`MAX_OUTBOUND_BODY_CHARS`, 1,000,000) and **counts the rest**: the count is what tells an operator their provider answered with three million characters, and draining to get it is what the time bound above makes affordable. The binary twin refuses instead of truncating (half a file is not a smaller file) and cancels the stream at the cap.
- **The cap is generous on purpose.** The model is handed 4,000 characters, but a response template addresses fields anywhere in the body, so the parse must see far more than the model ever will.
- **A body nobody reads is CANCELLED, not drained, and both places that decide so decide it on the headers.** `readWhen` turns down a download the status or the declared size already rules out: the Drive send used to pull 15 MB before consulting `Content-Length`, which on a slow link spends the whole budget and turns "that file is too large" into a generic download failure. `fetchBoundedNoBody` covers the call that never had an answer to read — the Google revoke, which the disconnect awaits before it removes the local tokens, so a stalled body there is a spinner on the operator's screen for the entire budget.
- **`OutboundTimeoutError` says the bound was OURS.** A body cut mid-read surfaces as `EncodingError`, the same shape a provider that really broke its stream produces, so without a type of its own our own timeout reads as the provider's fault — a 502 where the operator should see a 504, and "The operation was aborted." where the model should read something it can act on.
- **Who is on it:** the HTTP tool, the three toolpacks, the two Google integration services, and both OAuth clients (`vault/mcp-oauth.ts`, `vault/google-oauth.ts`). `src/modules/chatwoot/client.ts` reaches the same property another way — `AbortSignal.timeout()` stays armed through the body read, with no timer to clear — and is left alone. `tests/lib/outbound-family.test.ts` holds that list, because the difference between the right shape and the wrong one is two lines apart and invisible in review.

## Continuous ingestion (production + enabled)

So the agent has full context even for messages no turn handled, the receiver (`processChatwootDelivery`) folds the GAP into the contact-inbox thread — but ONLY for an **enabled + production** agent (`inboxAgentRuntime`): a disabled/unbound inbox does nothing (no cost), and a test-mode agent ingests nothing while silent (only the normal turn accumulates after `/teste`).

- **Eager media** (`runEagerMedia`) — STT + vision run on EVERY new incoming message, BEFORE the gate, for a production+enabled agent, so a message it won't reply to (out of hours, a human handling) still gets its transcription/extraction for the thread. Idempotent (guards on the already-set field), so the answer-path call for a freshly-activated test agent is a no-op when production already ran it.
- **`ingestUnhandledMessage`** — after the gate, for production+enabled, two disjoint cases. A CUSTOMER incoming the bot won't answer (silenced out of hours `act && consumed`, or not bot-handled `!act` — a human owns it); and a HUMAN agent's outgoing reply (`isNewHumanAgentMessage`: `outgoing`, not private, `sender.type === "user"` — the fork's own serializer emits `user` for a User, `agent_bot` for a bot and no `type` at all for a Contact), whatever the gate decided, since no turn ever covers one. The second case is the business half of a handed-off attendance: without it the memory of the most ordinary shape of a real deployment — agent qualifies the lead, a human closes the sale — was a conversation in which only the customer spoke, and compaction turned that from visibly-partial history into one confident paragraph of it (issue #187). It enters through `humanAgentMessage`, marked, and the summarizer renders it as `atendente:` — it rides as a `HumanMessage` like every other marker here, so unmarked it would be remembered as the CONTACT's own words, which is worse than the omission. Nothing else is ingested: our own bot's outgoing is already in the thread from the turn, another account's bot is not this agent's dialogue with the contact, and private notes (the operator's own team) plus templates and activities never enter.

  **And the END of that stretch is written down too** (`HUMAN_HANDBACK_NOTE`, issue #457), which for a long time it was not. The note above marks a person answering, the agent's own `handoff_to_human` call sits above that, and the return to the bot left no trace at all — so an operator prompt as ordinary as "após transferir, não responda mais" kept applying to a condition that had ended. Measured live against two models: one went silent (`outcome=empty`, exactly the reported symptom) and the other sent the silence to the customer as text ("(Silêncio, pois a conversa agora é entre você e o atendente humano.)"). The note is written by the first turn that runs while the bot owns the conversation again — the reactive turn and the proactive nudge alike, in the same guarded section each writes its divider in — and it lands ahead of the customer's message, which is the order the model reads.

  **Whether it is owed is DERIVED from the channel** (`src/graph/handback.ts`), never from a column tracking ownership. The first shape of this fix carried a `humanTakeoverAt` stamped by whoever observed a takeover, and two review rounds produced nine findings all of the same shape — a writer that observes a takeover and does not stamp (the console's own handoff, a disabled agent), one that stamps when it should not (a stale event, the `takeover.onHumanReply` opt-out), and a consumer racing the state the column was a copy of. Reading the thread backwards to the first thing that decides — a hand-back note (nothing owed), a human agent's message, or a handoff that SUCCEEDED — answers the same question from the evidence the MODEL is looking at, and makes a second announcement impossible without any bookkeeping. The handoff is read off the tool's RESULT and not its call: the AI message carrying the call is checkpointed before the tool runs, so it is there just as much when `toggleStatus` throws and when a precondition refuses the call, and both leave the conversation bot-owned. The result is matched by the tool's NAME as well as its prefix, which is why the assembly now RESERVES every native name the agent's allowlist left unbuilt (`tools/unique-names.ts`) — ordering alone defends only a name a native actually claims, and an agent with the transfer tool off left it free for an HTTP or toolpack tool to answer under. Two gates around the write, both of which cost nothing because nothing is consumed: a FRESH ownership read (a person can take the conversation over between the pre-gate and the write, and no later probe can unwrite a message), and a deferral while an older invoke is reading the channel — that invoke saves the channel it loaded, so an append beside it is erased. What is deferred is the durable append and never the correction: the note rides in that turn's own invoke input, because the turn that owes it is the one that would otherwise answer from the transfer context. **Compaction carries the evidence rather than erasing it**: a conversation resolved while a person still held it is summarized away with the handoff and the human messages, so the `memory_head` that replaces the stretch is stamped with what it ended in, and the decision reads that stamp like the raw form — as metadata, because the summary text is model-written. It **states a fact and orders nothing**, and that was measured against the alternative: a note telling the model it is responsible for replying also works and makes the product overrule the operator's own prompt, while stating what changed is enough. The summarizer drops it (it is not dialogue, and unmarked it would be remembered as the contact's words — #187 again). Resolving `inboxAgentRuntime` for an outgoing message is the widening this cost, and it is contained: every other reader of `rt` needs `isNewIncoming`/`hasLateMedia`, and the redirect follow-up arm sits inside `act && isNewIncoming`.

## Three standing rules for prompts and tool descriptions

- **Fix a leak at the source, never by stripping the reply.** When the agent leaked citation markers like `[1]` into a customer reply, a `stripCitationMarkers` regex over the reply was rejected, and correctly: a support answer legitimately contains bracketed numbers (an order `[12345]`, a protocol `[88]`), so the strip trades a rare cosmetic leak for silent data loss. The cause was that we were ASKING for the marker (the grounding directive) and SHOWING the pattern (the `search_knowledge` payload arrived as `[1] (source: KB) …`). The directive now asks for a natural answer with no markers, and the tool content lost its `[n]` prefix, so the model has nothing to copy. This holds for any model-artifact leak: remove the cause, do not scrape the symptom.
- **Dynamic per-turn data goes in an XML block at the END of a tool description.** Fixed order: static base (what the tool can do) → `Operator guidance:` → the XML block (live state), so the snapshot sits immediately before the decision. The tags mirror the tool's own **arguments** wherever there is an equivalence, and a descriptive tag otherwise. Escape every value with `xmlEscape`/`xmlAttr` from `src/lib/xml.ts` — they come from operator and customer data, and the helper is deliberately neutral so toolpacks import from `@/lib`, never from `@/graph`. Native tools take the block as `withOperatorNote`'s fourth argument, always last. Test gotcha: a `<knowledge_base>` tag contains the substring "knowledge_base", so a single-base test must assert the absence of the directive sentence, not of the substring.
- **The system-prompt cap is deliberate friction, and its UX is not to be improved.** `AGENT_PROMPT_MAX_CHARS` (default 100,000, parity with Anthropic Managed Agents) is enforced in the service (`assertPromptSize` on create/update/import and the `prompt_set` dry-run) with a localized `errors.promptTooLong` carrying `{{len}}`/`{{max}}`, and TypeBox deliberately has **no** `maxLength`, because a raw 422 would kill the friendly message. The limit is a teaching checkpoint ("a prompt that size should be a KB"), and a counter or warning in the editor, and any mention of the env var in the error text, were both explicitly rejected: whoever wants past the limit should have to find the variable themselves (`.env.example` documents it). Do not add a preventive UI warning or name the override in an error for a future product limit here without asking first.
