# Chatwoot integration (dual identity)

fazer.ai agents talks to a Chatwoot account through **two token profiles over one HTTP client**, receives Agent Bot webhooks on a **dedicated receiver**, and obeys the rule **attribution = source of truth** (the bot acts only while no human owns the conversation). The agent runtime that decides replies lives in [`graph.md`](graph.md); this doc covers the transport, auth, provisioning, and gate.

Payload shapes, the HMAC scheme, the bot-token capabilities, and the ack/timeout behavior below were confirmed by reading Chatwoot's Agent Bot webhook source, not guessed: `lib/webhooks/trigger.rb`, `app/listeners/agent_bot_listener.rb`, `app/jobs/agent_bots/webhook_job.rb`, `app/presenters/conversations/event_data_presenter.rb`, `app/models/{message,attachment,contact}.rb`, `app/controllers/concerns/access_token_auth_helper.rb` (the `BOT_ACCESSIBLE_ENDPOINTS` allowlist).

## Client — two profiles (`src/modules/chatwoot/client.ts`)

`createChatwootClient(config, deps?)` validates the tenant-configured `baseUrl` once (anti-SSRF, https-only) and returns a `ChatwootClient`. Auth header is `api-access-token` (hyphenated so it survives reverse proxies that drop underscores — `CHATWOOT_AUTH_HEADER` in `constants.ts`); the conversation id in every path is the **display_id** (per-account, see below).

- **bot-token** — the whole gate loop: `sendMessage` (outgoing + `private:true` note), `sendPrivateNote`, `sendAudioMessage` (voice note), `sendTemplate` (HSM), `assignToAgent` (handoff), `toggleStatus`, `toggleTyping`, `setConversationCustomAttributes`. Chatwoot's `BOT_ACCESSIBLE_ENDPOINTS` (`conversations` → show / toggle_status / toggle_typing_status / toggle_priority / create / update / custom_attributes; `conversations/messages` → create; `conversations/assignments` → create) confirms the bot can do all of this; the upstream authorization issue #11985 does **not** apply to this build. NOTE: `show` is in that allowlist but only since **2026-06-05** (upstream #14655), so every conversation READ stays on the admin token — a bot-token read answers 401 on any older instance, and self-hosted Chatwoot versions are not ours to pick. NOTE: `toggle_typing_status` IS bot-accessible, so `toggleTyping` uses the bot token (the indicator is attributed to our bot, not the admin agent).
- **admin-token** — everything outside the bot allowlist: read history (`getConversation`, `getMessages`), the STT transcription write-back (`updateAttachmentMeta` — `attachments#update` is **not** in the bot allowlist), provisioning (`createAgentBot`, `setInboxAgentBot`), and labels — `assign_label` is scope-aware (`conversation | contact | task`), backed by `get/setConversationLabels`, `get/setContactLabels` (same `LabelConcern`, POST `{labels}` **replaces**, so the tool reads-then-appends), and `setKanbanTaskLabels` (PATCH `/kanban/tasks/{id}` `{task:{labels}}`, current set read from the kanban card snapshot) — plus contacts, agents, and the Kanban driver. Confirmed against Chatwoot's Kanban API: `GET …/labels → { payload: string[] }`, `POST …/labels { labels }` replaces the whole set (`LabelConcern#update_labels`).

**Handoff targeting** (`agent.settings.handoff`, read by `src/modules/handoff/settings.ts`): `route` (default — just `toggle_status open`, Chatwoot's inbox routing assigns whoever), `pinned` (assign a fixed agent/team after the open), or `agent_choice` (the model passes an `assignTo` NAME, resolved against the live lists at call time). `assignToAgent`/`assignTeam` reuse the bot-accessible `assignments` endpoint (`assignee_id` vs `team_id`); `listAgents`/`listTeams` (admin token) feed both the editor's picker (`GET /v1/chatwoot/agents-teams` → `listAgentsAndTeams`) and the `agent_choice` name match. Assignment is best-effort (a failure never breaks the turn — the handoff already happened). Confirmed against Chatwoot's API: `/agents` & `/teams` index render bare arrays of `{id,name,…}`; `POST …/assignments { team_id }` assigns the team (`AssignmentsController#set_team`).

`ChatwootApiError` carries `status` + `endpoint` and **never** the response body (it is customer PII / message content). On **401/403** it appends a reason, but only ever one drawn from a fixed allowlist of Chatwoot's own auth messages: parsing a body as JSON does not prove it came from Chatwoot (the base URL is tenant-configured, and anything in front of it can answer `{"error": …}`), so an unrecognized reason is reported as exactly that and the text is dropped. The allowlist exists because `render_unauthorized` answers `{error: message}` with **401** for both "Invalid Access Token" and "Access to this endpoint is not authorized for bots", so the status alone cannot tell a missing credential from a forbidden endpoint. A call made with an **empty** token never leaves the process: it raises `ChatwootMissingTokenError`, which says the client was built without that token instead of reporting Chatwoot's 401 for it. The base URL host is fixed per call; the DNS-rebinding caveat from `src/lib/ssrf.ts` applies (tracked).

## One Agent Bot per persona

The Chatwoot Agent Bot **is the message sender** shown in the conversation (its name + avatar), so each of **our** `Agent` personas gets its **own** bot: the model is **one `ChatwootAgentBot` per `(ChatwootInstance, Agent)`** (table `chatwoot_agent_bots`, unique on `(tenant, instance, agentId)`). Each bot carries its own `outgoing_url` (route token), HMAC `secret`, and `access_token` (used to post AS that persona). Chatwoot natively supports many agent bots per account, one per inbox (`AgentBot has_many :inboxes through :agent_bot_inboxes`; an inbox has at most one bot), so a persona serving N inboxes connects its single bot to all N.

Which persona handles a conversation is decided per inbox: the `Inbox` mirror row carries `agentId`. The receiver routes `inbox_id → Inbox.agentId → Agent`, and the runtime posts with **that persona's** bot token (resolved by `loadAgentBot`/`prepare.ts`). An event for an inbox we do not manage (`agentId` null) is a **no-op** on the wire: we ack 2xx and stay silent, never crash and never escalate. Silent to Chatwoot is not silent to the operator, though — the mirror creates that `Inbox` row for any inbox that sends traffic, so an inbox nobody bound accumulates real customer messages nothing will answer. A new incoming message that finds no agent therefore writes one `route` line (`{outcome: "no_agent", chatwootInboxId}`, level `warn`, `agentId` null and the mirrored `inboxId` naming what to repair) from either exit that reaches the state: the direct turn's `no-agent` outcome and the debounce flush's bail below its gate, both through `emitUnroutedMessage` (issue #318). See [`logs.md`](logs.md).

**Binding IS the wiring (no separate "provision" step).** Setting `Inbox.agentId` (the `PATCH /v1/chatwoot/inboxes/:id` → `bindInbox`) is the single operator action that wires an inbox end-to-end, and it keeps the Chatwoot side in sync: bind/switch (→ agent) lazily provisions **that persona's** bot (`ensureAgentBot`, named after the persona) and `setInboxAgentBot(inboxId, botId)` to connect it (Chatwoot's `set_agent_bot` replaces any prior bot on the inbox); unbind (agent→none) calls `setInboxAgentBot(inboxId, null)` to **disconnect** the bot (so Chatwoot stops delivering events that would otherwise strand new conversations as `pending` on a bot we ignore); rebinding the SAME agent is a no-op. The network side runs outside the tx; a Chatwoot/SSRF failure surfaces as a uniform 502 and we never persist the new `agentId`, so our state and Chatwoot stay consistent. One failure is not a desync: an **unbind whose inbox was deleted on Chatwoot** gets a 404 from `set_agent_bot`, and "no bot is connected to this inbox" is already true of an inbox that is gone, so the local binding clears instead of being stuck naming a persona for an inbox nobody can reach (#327). Renaming a persona propagates to its bot(s) via `renameAgentBots` (best-effort `updateAgentBot`; our row is the source of truth).

**Removing the mirror of a deleted inbox (`DELETE /v1/chatwoot/inboxes/:id` → `removeInbox`).** `syncInboxes` deliberately never prunes (a sync that cannot reach an inbox would otherwise delete a binding the operator configured), so an inbox deleted in Chatwoot leaves its row behind; this is the explicit action that trade-off assumes, and until #307 it did not exist. **The removal is fenced on Chatwoot answering that the inbox is gone**, and the fence is the feature rather than caution: the mirror recreates an `Inbox` row for any inbox that sends traffic (`upsertInbox`), so deleting the mirror of a LIVE inbox removes nothing — the next message rebuilds the row with no agent bound and the customer lands in `emitUnroutedMessage` with nobody to answer. So the row only goes when `getInbox` 404s (`remoteInboxIsGone`); a live inbox is refused with 409 and anything else with 502, because "we could not ask" must never read as "it is gone". A 403 in particular proves the inbox EXISTS: `fetch_inbox` runs `authorize @inbox, :show?` after the `find`. Nothing is written to Chatwoot and nothing needs to be — the inbox is gone, so no persona bot of ours is connected to it. Past conversations survive and stop naming an inbox (`Inbox.conversations` is `onDelete: SetNull`); `llm_usage.inbox_id` and `execution_logs.inbox_id` are bare columns with no foreign key, so past spend and past log lines survive with a dangling id and the dashboard renders them as an unnamed bucket. Whole-account cleanup remains `removeChatwootInstance`, which cascades the inboxes.

`display_id` is **account-scoped** (Postgres trigger `nextval('conv_dpid_seq_' || account_id)` + unique `(account_id, display_id)`), so it does not collide across inboxes within an account. The thread key `tenant:instance:display_id` is therefore collision-free without `inbox_id`.

## Webhook receiver (`src/modules/chatwoot/webhook.ts`)

Mounted at `CHATWOOT_WEBHOOK_MOUNT` = `/api/v1/chatwoot/webhook/:routeToken` (`src/api/v1/chatwoot.controller.ts`), JWT-less. The Agent Bot `outgoing_url` is derived from the **same constant** at provisioning time (`chatwootOutgoingUrl`), so the two can never drift — a 404 ack would make Chatwoot move the conversation `pending→open`. A unit test asserts the constant and a POST carve-out smoke proves the path reaches Elysia (never the SPA HTMLBundle).

Flow:

1. **Resolve** the per-persona Agent Bot by `routeToken` — a constant-time `SHA-256` probe on `ChatwootAgentBot.webhookRouteTokenHash` (cross-tenant ⇒ `asSuperAdmin`); the row yields tenant, instance, the persona's `chatwootAgentBotId` (the gate's "our bot"), and the HMAC `secret`. The instance's `disconnectedAt` comes back through the relation in the **same** query, not a second one. **Cached in process** (`route-token-cache.ts`, keyed by the hash, misses cached too), because this is the ack path: every query here is an interactive transaction competing for a pool shared with turns, ingest and compaction, and a slow ack costs the conversation (see below). The cache answers only what the process can still back up: fresh inside the 30s TTL; past it, served **and refreshed behind the ack** while the last lookup reached Postgres; past it with a *failed* lookup, a miss, so the ack blocks and fails honestly and Chatwoot's own retry ladder carries the event rather than a 2xx losing it (the payload is not stored, see Known limitations). Rule three is what keeps rule two truthful, and it costs nothing in the case rule two exists for: an idle instance on a healthy database. A request that arrives while a refresh is deciding waits on that one refresh instead of starting its own, and **inherits its outcome**: a refresh that could not reach Postgres fails all of them together, rather than resolving and sending each one down the blocking path to open its own transaction against the pool that just refused. Misses are held apart from hits and bounded, since an unknown token is what a prober loops on and this endpoint is public. Every writer that changes what a route token resolves to calls `invalidateRouteTokenCache()` **after its transaction commits** (provisioning/re-provisioning, connect, reconnect, soft-disconnect, instance removal, agent deletion, the last two because `ChatwootAgentBot` cascades), and a lookup that started before an invalidation is refused on write, so an in-flight read cannot resurrect what was just retired. The route token namespaces the bot, so multiple bots on one instance never collide. The plaintext lives only inside Chatwoot's stored `outgoing_url`; only its hash is in our DB, never logged.
2. **Authenticate after resolution**: verify the HMAC with the bot's decrypted `webhookSecret`. Scheme (verified against Chatwoot): `X-Chatwoot-Signature = "sha256=" + HMAC_SHA256(secret, "{ts}.{rawBody}")` in hex; `X-Chatwoot-Timestamp` = unix seconds (we enforce a ±300s anti-replay window); `X-Chatwoot-Delivery` = UUID. Unknown token and bad signature **all return the same uniform 401** (no oracle).
3. **Parse + normalize** the raw body (`normalizeChatwootEvent`, tolerant of both shapes: `message_created` nests the conversation under `.conversation`; `conversation_*` carries it at the top level). A non-event payload is `ignored` (still acked).
4. **Ack**, carrying the delivery id. **Nothing is written on this path** (see the ack budget below).
5. `recordAndProcessChatwootDelivery` runs **detached**: it writes the idempotency ledger row, then processes.

**The ack budget.** Chatwoot allows ~5s (`WEBHOOK_TIMEOUT`) and treats a slow or non-2xx ack as a bot failure. Since the bot only answers a `pending` conversation and `Message#reopen_conversation` never returns an `open` one to `pending`, an escalation there takes the bot off that conversation for as long as the customer keeps writing, while the turn itself may have completed correctly and had its reply discarded. That is why the resolution is cached and the ledger insert moved off this path: with both, a healthy ack needs **no** Postgres round-trip at all, so pressure anywhere else in the process cannot cost a conversation. Pinned by a test that hands the receiver a client which throws on `$transaction`.

**Idempotency ledger**: `ChatwootWebhookDelivery`, keyed by `(chatwoot_instance_id, delivery_id)`. A `delivery_id` is reused across the upstream's retries (transport dedup) but is fresh per distinct event. The ledger stores event name, status and two ids — the **conversation's display id** and the **inbound message id** — but **not** the payload, which is PII; the normalized event is handed in-memory to the detached processor. The two ids exist for one reason: they are what lets the stranded-delivery sweep tell a row that lost a customer's message from one that lost nothing (see below).

A **redelivery is dispatched too**, and the CAS decides. The ledger row existing is not the same as the work having been done: the dispatch is detached and fires after the ack, so a process that dies in between strands the row on `PENDING` with nothing running, and Chatwoot, holding a 200, never sends that message again. Dropping redeliveries on the strength of the row would make that loss permanent. `processChatwootDelivery` opens with a CAS on `status: "PENDING"`, so a row already `PROCESSING`/`PROCESSED` matches nothing and returns `skipped`; nothing double-processes. (A crash *after* the CAS still strands the row on `PROCESSING`, and nothing on this path can close that window — the process is gone. What the **stranded-delivery sweep** below does is make sure it stops being silent.)

`processChatwootDelivery` does a CAS `PENDING→PROCESSING`, **mirrors the event metadata**, evaluates the gate, hands the normalized event to the runtime seam, then CAS `→PROCESSED`. Network/LLM work belongs **outside** the transaction (the runtime does it under `withEntityLock(threadId)` + a live re-read of the assignee before posting).

**Stranded-delivery sweep** (`delivery-sweep.ts`, issue #228): a per-tenant `DELIVERY_SWEEP` scheduler job, armed at boot and when a Chatwoot account is connected, self-rearming every 5 minutes, looks for rows still on `PENDING` or `PROCESSING` more than 30 minutes after the **current attempt** started.

The current attempt, not the receipt: tx1 stamps `claimed_at`, and the sweep measures a claimed row from that. A redelivery is deliberately allowed through to the CAS on a row stranded on `PENDING`, so a live attempt can begin long after the row arrived — dated to the receipt it looks abandoned the instant it starts, and the sweep would mark it `DEAD` and page an operator while the process answering it is still running.

Both non-terminal states strand, and for the same reason: the ack is spent before the ledger row is even written. A death between the insert and the CAS leaves `PENDING`, and #226's answer to that — a redelivery goes on to the CAS instead of being dropped — only helps when a redelivery actually arrives, which it usually does not, because Chatwoot holds a 200.

**It does not answer the customer, and that is the design.** Recovering the turn means running one, and a turn run from a sweep is not the turn the delivery would have run: the flush machinery re-checks ownership and contact authorization itself, but the test-mode gate, the availability window and the redirect gate are applied by the delivery path and are gone with the process that died. A recovery that skips them replies out of hours, or on a conversation whose test mode was never activated. That half is issue #295.

What the sweep does close is the other half of the harm, completely. Every stranded row becomes terminal, and **which** terminal state says what happened: `PROCESSED` when nothing was lost, `DEAD` when a customer message went unanswered.

Nothing was lost when the delivery could not have carried an inbound message, and that is asked of the **event name** first: Chatwoot sends an agent bot far more than messages, and `normalize.ts` reads a conversation id from nothing but the two shapes that are a conversation or a message (issue #257), so a contact being created reaches the ledger with both ids null. The event name is the one column every build has written, so it answers before any question about the ids does. Below it, nothing was lost when a message event carried no inbound message — read only on a row whose build was recording one. A row this build never touched is reported rather than closed, because its nulls are **unrecorded** and not "nothing was there" — during a rolling deploy the previous release keeps serving while the new one migrates, and it writes none of these columns. Two signatures, one per state, because each state promises a different column: tx1 stamps the claim on every row this build works, so a `PROCESSING` row without one came from an older build; nothing has claimed a `PENDING` row, so what speaks there is the conversation, written at insert for every event that reaches the ledger.

The backfill leaves rows younger than the same 30 minutes alone, for the same reason: it runs while the previous release is still serving, and a row that release inserted seconds ago is about to be claimed by it. Closed by the migration, that `PENDING → PROCESSING` CAS matches nothing and the upgrade itself discards a live customer message. Everything else that is still non-terminal at that age is terminal by rollout, and **which** terminal state is the same question the classifier asks first: `event` is not one of the columns the migration adds, so a conversation update, our own media write-back and a widget being triggered are closed rather than reported, and only a legacy `message_created` — ambiguous because neither id column is backfilled — lands `DEAD`. Measured against the local fork (4.16.0) by pointing a real Agent Bot at a capture endpoint: `AgentBotListener` dispatches exactly seven events (`conversation_resolved`, `conversation_opened`, `conversation_status_changed`, `conversation_updated`, `message_created`, `message_updated`, `webwidget_triggered`), and `webwidget_triggered` is the only one whose body is not a conversation — it carries a contact_inbox, so it is the only event a CURRENT build files with both ids null. There is **no watermark arithmetic left in the decision** — that is the design, arrived at by deleting three successive versions of it.

**The turn says what it covered, on the row.** When a flush answers a burst it retires the ledger rows of the messages that burst contained (`retireCoveredDeliveries`), the gate exits that consume a burst without a turn retire everything up to the id whose watermark they advance, and the receiver settles its own message the moment its fate is decided rather than waiting for tx2 (after advancing the watermark, never before: a death between those two writes must leave a false line in the loss list rather than a message that is terminal on the ledger and still below the watermark, which a later flush would answer) — on **every** outcome, where the flush holds two of them back. The same word means different things on the two paths: `superseded` on a flush hands the burst to a re-armed flush that will answer these same messages, while on the receiver the graph has already run over the message and it is the newer message's own delivery that carries the reply, so a row left open there is a lost-message alert every time the process dies in the tail after a deliberate supersede. `stale` does not arise on the receiver at all, since nothing queued that turn for a `/reset` to retire. This normally updates nothing: a delivery that completed already reached `PROCESSED` on its own. It matters in exactly the case that makes the sweep hard — a burst re-read from Chatwoot can contain a message whose own delivery died mid-processing, and rescuing those is what re-reading the thread buys. Retired there, a row still sitting non-terminal is one nothing covered, which is a fact about the row rather than an inference.

The write is keyed by **account, conversation and message** (display ids and message ids are numbered per Chatwoot account) and takes **`PROCESSING` and `DEAD`** — except where **another AgentBot** holds the conversation, and there it narrows. Chatwoot fans a message to up to two routes (`agent_bots_for` returns the conversation's assignee bot and the inbox's, each with its own delivery id), so the other bot's delivery for the same message may be `PROCESSING` right now, and retiring it would take a live loss out of the list: the receiver settles only its own row, and the flush's gate exits retire nothing at all, having no row of their own to name. A **human** holding the conversation is the opposite — they answer the message whichever route carried it — and keeps the wide key, as does any gate that consumed the message while the conversation was still ours. `DEAD` is a correction rather than a contradiction: the sweep reaches its verdict by inference — nothing has moved this row — while a turn that ran over the message is direct evidence, and it wins. A row corrected that way leaves the worklist and gains a second `delivery` line next to the one that reported the loss, because the alert for it has already gone out and cannot be recalled — `answered_late` when a reply actually posted, `consumed_late` when the message was taken deliberately (a gate, an empty model reply, a human taking over mid-turn). Which one it is comes from the caller, since only the caller knows. The two writes are separate statements, the `DEAD` one returning what it moved, so the correction cannot be lost to a row turning `DEAD` mid-read nor written twice by concurrent retirees. Never `PENDING`. That last one is the state whose owner has not arrived yet, and a burst legitimately contains a message whose own delivery is sitting between its ledger insert and its opening CAS. Retiring that row would make the delivery's CAS match nothing and return `"skipped"`, so its mirror write never runs and `lastInboundAt`, the contact and the attribute bags stay behind — preempting a delivery rather than rescuing one. The case that leaves out is a delivery that died in the sliver between its insert and its CAS: it is reported as a loss even though a later burst answered it.

The three deleted versions all compared the stranded message against a mark on the conversation, and each failed differently: `>=` closed the crash window between the post gate's claim and the send; the handled watermark closed every message a later *deliberate skip* advanced past (a human takeover, a failed authorization), which is the most likely companion to a strand since a deploy causes both; and a dedicated "answered" high-water mark still closed a message a later burst **excluded**, because the skip had raised the burst's floor above it. The shared reason is that a watermark is a per-CONVERSATION high-water value and this is a per-MESSAGE question, so no scalar reading of it can be right.

`SELECT ... WHERE status = 'DEAD'` is the list of customers who are **still** unanswered, and each one also leaves an error-level `delivery` line on the conversation — what the Logs page renders and the alert channels dispatch. The row is retired **before** that line is written, deliberately: `writeFlowEvent` dispatches the alert as it writes and nothing can retract it, so a line written first pages an operator every time a redelivery claimed the row in between.

Two windows are known and left open. A turn that outlives the 30-minute threshold (nothing bounds a model call or a tool) has its row judged abandoned and its loss dispatched while the process is still working; the turn then completes and tx2 writes `PROCESSED` over the verdict **by id**, so the row ends up true and only the alert was wrong. And the legacy `message_created` rows the migration reports at rollout land in the DEAD list without a line or an alert, because both id columns are added by that same migration and nothing there knows what those rows carried — they are the ones matching `status = 'DEAD' AND conversation_id IS NULL`.

The ledger carries two ids and a timestamp for this and nothing else: the conversation, the message the delivery was about, and when the current attempt claimed the row. The second is written only for a **new incoming** message — the exact set that drives a turn — so a conversation update, the bot's own reply coming back as a `message_created`, and an incoming `message_updated` (usually our own media write-back coming around) all leave it null and none of them can put a row in the loss list.

**Losing the gate** is reported as two different things, because it is two different events: `handoff` with `outcome: "taken_over"` when a **human** holds the conversation, and `outcome: "ownership_lost"` with the observed status for anything else (most often Chatwoot auto-escalating `pending → open` after a slow ack, sometimes another party's bot). Both mean the bot stays silent, but only one of them means somebody took over. The reading is one unit, `describeClosedGate` (`src/modules/chatwoot/gate-close.ts`), because **three** gates close on that question and an operator filtering the log for one outcome has to get all three: the webhook on each event, the debounce flush before the turn, and the post-LLM recheck before posting. Which one a case reaches is a matter of timing, and the escalation reaches the first two rather than the last — it lands seconds after the ack, so no turn ever starts (issue #271). The webhook's line is deliberately narrower than its branch: one row per **new incoming customer message** on a closed gate, and none for a disabled agent, so the trail stays one line per message the bot did not answer instead of one per webhook event.

## Mirror sync (`src/modules/chatwoot/mirror.ts`)

`mirrorChatwootEvent` upserts conversation/inbox/contact **metadata** (no message body) into our DB, powering the UI conversation list + read API and giving the runtime fresh state to route on. It runs for every event (not only actionable ones), before the gate.

- **Contact** and **Inbox** upserts are atomic (`INSERT ... ON CONFLICT DO UPDATE`, safe under concurrency, never abort the tx). Contact keys on `(tenantId, chatwootContactId)` (the unique added by the `contact_chatwoot_unique` migration); Inbox on `(tenantId, instanceId, chatwootInboxId)`.
- **Conversation** is a read-modify-write serialized per conversation by `withEntityLock(threadId)` and guarded **monotonically**: an event whose `last_activity_at` predates the stored `lastEventAt` is skipped, so out-of-order deliveries (Chatwoot does not guarantee order) cannot regress status or assignee. `prevAssigneeId` is captured before the overwrite for the REENGAGE flow.
- **Same-second regression fence (status)**: the monotonic guard is second-granular and strict, so it cannot order events sharing one `last_activity_at` (a "reply + resolve" macro; a resolve never advances the field by itself). Message payloads are additionally **frozen at enqueue** by Chatwoot's `AgentBots::WebhookJob` — a delivery retry re-sends the pre-resolve snapshot. So only a BRAND-NEW incoming message (`message_created` + `incoming`, i.e. `isNewIncomingMessage`) may move a stored `resolved`/`snoozed` back to `pending`/`open`. Every other message event is fenced — an outgoing cannot reopen a conversation in Chatwoot, and a `message_updated` of an incoming message (our own STT/vision write-back) carries the same frozen snapshot. The fence also preserves the stored assignee fields. Legit reopens still apply: a new incoming message (ReopenService) and every `conversation_*` event. This staleness is what once made follow-ups fire on operator-resolved conversations.
- Field sources (verified against Chatwoot): contact ← `meta.sender`; inbox name ← message-event `inbox.name`; `channel` ← `EventDataPresenter` conversation `channel`; `last_activity_at` ← push_timestamps.
- **Resolution origin.** `Conversation.resolvedBy` records WHO closed a conversation, written by the four paths that close one themselves (`agent` for `resolve_conversation`, `followup_abandonment`, `redirect_closing`, `console`). Chatwoot never tells us: an operator resolving in its UI, an automation rule, and `auto_resolve_after` all arrive as a plain status change, so those stay NULL and the dashboard treats an unattributed close as not the agent's. Confirmed on 4.17.0: an operator's resolve leaves `meta.assignee_type: "AgentBot"`, i.e. no human, which is exactly what the old inference read as "the AI resolved it". Chatwoot also never reports a TRANSITION (`toggle_status` answers `{success, conversation_id, current_status, snoozed_until}`, and `success` is `save!`'s return), so the stamp carries `resolvedByAt`, the status version the closing caller observed, saying WHICH close it is about. When the stamp dies is one rule, `clearsResolutionOrigin`, asked by this mirror and by the live reconcile: the conversation left `resolved`, or a close of ours stated `resolved` and lost the ordering, or a brand-new incoming message reopened the episode — the last two guarded by that version floor so a retried delivery cannot erase a close made after it. The console is the exception and does not consult the ordering: an operator commanding a non-resolved status is a command, so it clears on both of its write paths. See `src/modules/conversations/resolution-origin.ts`.
- **Custom attribute bags** are mirrored too (`Conversation.customAttributes` / `Conversation.kanbanAttributes` / `Contact.customAttributes`) — see the attribute-context section below. Chatwoot ships the WHOLE jsonb on every event, so each is **assigned wholesale**, and only when the payload actually carried it (a degraded payload never wipes the stored snapshot). A stale event (monotonic guard) skips them like everything else. The conversation bags are covered by the conversation's own `lastEventAt` guard (they are written inside the per-conversation lock, past the stale check); the CONTACT bag cannot be, because the contact upsert runs before that lock (the conversation row needs the contact id) and one contact is shared by all its conversations — so it carries its own source watermark, `Contact.customAttributesAt`, and the write is a single compare-and-set `UPDATE … WHERE custom_attributes_at IS NULL OR custom_attributes_at <= $eventAt`. An explicit `{}` in the payload is a real "everything was cleared" and does clear the stored bag; an ABSENT bag does not.

## Attribute context: the agent READS what it wrote (`src/modules/chatwoot/attributes.ts`)

`set_custom_attribute` is the write side (conversation | contact | kanban card). The read side is a per-agent selection of attribute KEYS whose CURRENT values are rendered as an `<attribute_values>` block appended to the system prompt in `loadAgentConfig`, so the agent knows what has been collected and — via `filled="no"` on a selected-but-empty key — what is still missing. Without it the agent writes an attribute and is blind to it on the next turn (memory lives only in the checkpointer, which `/reset` wipes).

- **No API call.** Every Agent Bot payload already carries all three bags: `custom_attributes` (conversation), `meta.sender.custom_attributes` (`Contact#push_event_data`) and `kanban_task.custom_attributes` (the Pro fork's `FazerAi::Conversations::EventDataPresenter` + `Kanban::Task#common_event_data`). `normalize.ts` extracts them, the mirror persists them, and turn prep reads the columns it was already loading. This is why the mechanism works identically on the debounce flush and the proactive nudge, neither of which has a webhook payload in hand.
- **Config**: `agent.settings.attributeContext = { conversation: [], contact: [], task: [] }` (keys per scope, trimmed/deduped/capped at 20 keys of ≤64 chars by `readAttributeContextConfig`; see the prompt-injection bullet below for what happens to the VALUES). Empty everywhere ⇒ no block at all. Editor: Behavior tab → "Data in context", fed by `GET /v1/chatwoot/custom-attributes/:agentId` (definitions across the agent's instances, same best-effort contract as the label picker). Also on the `behavior-settings` surface, so REST v1 and MCP `agent_settings_get/set` project it.
- **Prompt-injection bound**: values are ultimately customer-authored, so each goes through `sanitizePromptValue` (control chars/newlines collapsed, then capped) and then XML escaping. One effective cap per call site: `ATTRIBUTE_VALUE_MAX = 400` **with a trailing `…`** for attribute values, the default `VALUE_MAX = 120` (no marker) for the `{{var}}` identity variables. The block is appended AFTER `{{var}}` interpolation, so a stored value containing `{{nome_contato}}` stays literal.
- **Freshness**: the mirror is refreshed by the very event that triggers the turn, so a reactive turn always reads current values. `set_custom_attribute` additionally write-throughs into the mirrored bag (`mirrorAttributeWrite`), which closes the only real gap: a nudge fired without a preceding inbound event, and the contact scope (Chatwoot does not deliver `contact_updated` to agent bots). That write-through is a single `jsonb || jsonb` UPDATE, not a read-modify-write: a turn's tool calls run concurrently, so two `set_custom_attribute` calls on the same scope would otherwise clobber each other's key. On the CONTACT scope the same statement also advances the watermark (`custom_attributes_at = GREATEST(custom_attributes_at, NOW())`), because Chatwoot accepted the key a moment ago and every event generated before that carries a pre-write snapshot: one of those, delivered late but still stamped after the last mirrored event, would otherwise pass the compare-and-set above and erase what was just written, with no `contact_updated` ever to put it back. Chatwoot remains the source of truth — the next event overwrites the bag.
- **Card caveat (`task` scope).** `Kanban::Task#dispatch_conversation_events` only re-dispatches `conversation_updated` when a card is LINKED or UNLINKED from a conversation; moving it between steps or editing its fields/attributes goes out over ActionCable (`kanban.task.updated`), which agent bots never receive. So the mirrored `kanbanAttributes` advance only when some conversation event arrives — in practice the next customer message, which is also what triggers the turn, so a reactive turn is still current. This is ALSO why `loadKanbanContext` still reads the card live instead of using the mirror: `kanban_move_card` must act on the step the operator sees right now, and a board-side drag leaves no trace in the webhook stream.

## Pre-turn gates in the receiver

Before a new incoming message reaches debounce/the runtime, `maybeConsumeCommandOrGate` evaluates
the operator-facing gates in a fixed order: redirect **cross-link** → **test-mode** (`/teste`,
`/reset`) → the WhatsApp→chat **redirect** ([`channel-redirect.md`](channel-redirect.md)) →
**availability** (business hours + away message) → **contact authorization**
([`contact-auth.md`](contact-auth.md), the external allowed/denied check). A gate that consumes the
delivery still advances the handled watermark, and the message is folded into the memory thread
like any other unanswered one.

## Attribution gate (`shouldBotHandle`)

The bot owns a conversation only while it is `pending` **and** no human is assigned. The gate is ours to enforce: Chatwoot delivers the event even when a human is assigned. With multiple bots, Chatwoot also delivers to a conversation's `assignee_agent_bot`, so we additionally require, when `ourAgentBotId` is known, that the conversation be unassigned or assigned to **our** bot — never to a different `AgentBot`:

```
act ⇔ status == "pending"
    ∧ assignee_type != "User"
    ∧ ¬(assignee_type == "AgentBot" ∧ assigneeId is known ∧ assigneeId != ourAgentBotId)
```

The third line is a **pair**, and passing half of it buys the first two lines only. `ourAgentBotId` without an `assigneeId` to compare against leaves the id unknown, so the clause cannot fire and every `AgentBot` reads as ours — silently, since the call still looks strict. Three scoped reads shipped that way (#210). Every caller that supplies `ourAgentBotId` therefore selects `assignee_id` too, and a test walks the source to hold that (`tests/modules/chatwoot-receiver.test.ts`); the other half, that the column reaches the literal, is a type error when the select omits it.

## Kanban driver + client loader

Chatwoot's Kanban owns the funnel/board/step/card model (the agents has **no** Funnel/Card tables). We drive it via admin-token methods on `ChatwootClient` — `listKanbanBoards`, `createKanbanBoard`, `updateKanbanBoard`, `listKanbanSteps`, `createKanbanStep`, `setBoardInboxes`, `setBoardAgents`, `listKanbanTasks`, `createKanbanTask`, `moveKanbanTask`, `updateKanbanTask` — against the Kanban routes `/kanban/{boards, boards/:id/steps, boards/:id/update_{inboxes,agents}, tasks, tasks/:id, tasks/:id/move}`. Create/update bodies wrap the Rails-required root key (`board`/`step`/ `task`); bind/move params (`inbox_ids`, `agent_ids`, `board_step_id`, `insert_before_task_id`) are confirmed against Chatwoot. `updateKanbanTask` PATCHes a partial `{ task: {...} }` (camel→snake: `startDate`→ `start_date`, `dueDate`→`due_date`) limited to the scalar fields `title`/`description`/`priority`/ `start_date`/`due_date` (the `update_kanban_task` native tool; `value`/`board_step_id`/`labels`/ `custom_attributes` keep their own paths). Permit list + `Task::PRIORITIES` (urgent|high|medium|low) + the `start ≤ due` validation confirmed against Chatwoot's Kanban API. The inner board/step/task shape is owned by the `/desenhar-funil` wizard.

The agent's **read** path is `loadKanbanContext` (`src/modules/chatwoot/kanban.ts`), resolved at turn prep when `kanban_move_card` is granted: `conversation.kanban_task_id` → `getKanbanTask` (board + current step + the **card snapshot**: `title`/`description`/`priority`/`status`/`value`/`startDate`/ `dueDate`/`custom_attributes`) → `listKanbanSteps` (board steps with the operator's per-step `description` + `cancelled` flag, cached 60s/board). `parseSteps` tolerates the `{ steps }` (current Chatwoot jbuilder), `{ payload }`, and bare-array shapes. This context is surfaced in the `kanban_move_card` description so the agent sees where the card is, the available steps (with their notes), and the card's data; the operator's funnel guide (`agent.settings.kanban.instructions`) is appended after it.

`loadChatwootClient(tenantId, instanceId, { botToken? })` (`src/modules/chatwoot/instance.ts`) is the single place that resolves an instance and decrypts the **admin** token into a ready `ChatwootClient`; the **bot** token is admin-only (`""`) by default and supplied by the posting paths via `botToken` (the persona token from `loadAgentBot`/`AgentConfig.agentBotToken`). The scoped instance read happens first; the SSRF-validated (DNS-resolving) client construction follows, outside the transaction.

## Provisioning (`src/modules/chatwoot/provisioning.ts`)

Provisioning is **lazy** and **per-persona** — there is no operator-facing "provision the bot" step. `ensureAgentBot(tenantId, instanceId, agentId, agentName, client, deps?)` runs the first time that persona is bound to an inbox of the instance (see `bindInbox`); the caller owns the admin-capable `ChatwootClient` and connecting the bot to specific inboxes.

1. Read the `(tenant, instance, agentId)` bot row (scoped). If present, **verify it still exists on Chatwoot** (`listAgentBots`) — an operator can delete the bot out-of-band. If alive → **return it** (idempotent), decrypting its access token. If **gone** → re-provision and refresh the row in place (so re-binding the inbox self-repairs; the dead id/token would otherwise 401 every reply).
2. **Outside any transaction**: generate the route token, derive `outgoing_url`, `createAgentBot` (name = the persona's name; returns `id` + `access_token` + `secret`).
3. **Persist** a `ChatwootAgentBot` row (`chatwootAgentBotId`, `accessToken`/`webhookSecret` encrypted, `webhookRouteTokenHash`, `name`). A `P2002` on the `(tenant, instance, agentId)` unique means a concurrent first-bind won the race: the freshly-created bot is orphaned on Chatwoot (rare — admin-only) and we adopt the winner's row (logged).

The bot's `secret` **is** the HMAC key the receiver verifies — provisioning and the receiver agree on it by construction (covered by a round-trip test). An explicit reset path (reaping orphaned/old bots on Chatwoot) is future work. Instance creation auto-runs `syncInboxes` (best-effort) so the inbox list is populated before any binding.

## Instance setup: account discovery (`listChatwootAccounts`)

The setup form takes **url + admin token** and discovers the `accountId` instead of making the operator hunt for the numeric id. `fetchChatwootProfile({ baseUrl, token })` (in `client.ts`) hits the **user-scoped** `GET /api/v1/profile` (NOT the account-scoped `/api/v1/accounts/:id/...`, which needs an id we don't have yet), and `parseChatwootAccounts` shapes `profile.accounts[]` into `{ id, name, role }[]`. `listChatwootAccounts` (management) is **stateless** — it does NOT persist the token (the operator supplies it again at create-time); any failure (bad token/URL, SSRF block, unreachable, or a token attached to zero accounts) surfaces as a uniform **502** (`errors.chatwootProfileFailed`, never echoing the URL/token) which the UI converts into a **manual-id fallback** field. Endpoint: `POST /v1/chatwoot/instances/list-accounts` (TENANT_ADMIN), a static sub-path with no overlap against the dynamic `/instances/:id` routes.

### Why the Chatwoot creds stay inline-encrypted (NOT in the vault)

The `ChatwootInstance.adminToken` plus the per-persona `ChatwootAgentBot.accessToken`/`webhookSecret` are **encrypted columns**, not `VaultEntry` rows, **by design** — and this is the answer to "should Chatwoot creds move to the vault?": **no.** The inbound webhook resolves the bot by `webhookRouteTokenHash` **before any tenant context exists** (the route token IS how we learn which tenant/instance/persona a delivery belongs to). A `VaultEntry` is tenant-scoped (RLS) and can only be read **after** `tenantId` is known, so sourcing the bot secret from the vault would be a resolution deadlock: we'd need the tenant to read the secret, but we need the secret (HMAC verify) to trust the request that tells us the tenant. Keeping the creds inline-encrypted on the row we resolve by hash sidesteps the chicken-and-egg, at the cost of a second secret-storage mechanism (accepted: it is a justified architectural decision, not debt). The vault remains the home for **agent-facing** creds (LLM keys, HTTP-tool credentials, STT/TTS providers) where a tenant context always exists at read time.

## Known limitations

- **A stranded delivery is reported, never re-answered.** The sweep marks the row `DEAD` and leaves a `delivery` line; nothing re-sends. The gates the delivery path applies before a flush (test mode, availability, redirect) do not survive the process that died, so a turn run from a sweep is not the turn the delivery would have run. Issue #295.
- **Runtime tools that act ON Kanban from the graph** (move card on stage change): the driver methods exist now but nothing calls them automatically yet.
- **Payload shapes verified at source.** The agent-bot delivery body is exactly `payload.to_json` (no envelope), built by `EventDataPresenter#webhook_data` / `Message#webhook_data`. Field paths our code depends on, all verified: conversation `id` = **display_id**; `message_created`/`message_updated` nest the conversation under `.conversation`, `conversation_*` carry it at the top, and **every other event's body is a different subject** (a contact, a contact_inbox, an inbox, a kanban card, a message) rendering its own primary key under that same `id` key — so which id a body holds is knowable only from the event NAME, which is why `normalize.ts` allowlists the two conversation-bearing shapes and reads a conversation id from nothing else (issue #257); top-level `message_type` is the **enum string** ("incoming"…) while the nested `conversation.messages[].message_type` (and the REST messages API `_message.json.jbuilder`) is the **integer** `message_type_before_type_cast`; audio attachments expose `data_url` (inline_audio_url) + `file_type:"audio"` + `meta.transcribed_text`; contact is `meta.sender` with `phone_number`; `changed_attributes` is an array of single-key `{ key => { previous_value, current_value } }` hashes. `signing.ts`, `normalize.ts`, and `messages.ts` all match. NOTE: `attachments#update` runs `@attachment.update!(meta: …)`, which **replaces** the whole `meta` column — the STT write-back only sends `{ transcribed_text }` (n8n parity, acceptable) but it is not a merge.
- **Wire-confirmed field paths.** The real `EventDataPresenter` / `Message#webhook_data` output confirms every field path above on the wire. `message_created` nests the conversation under `.conversation` (top-level `message_type:"incoming"` string; nested `conversation.messages[].message_type:0` int); `conversation_updated` carries `id` = **display_id** at the top; `meta.assignee_type` is `null` when unassigned; `meta.sender` carries `phone_number`/`email`/`identifier`; `channel:"Channel::Api"` for the WhatsApp-via-baileys inbox.
- **`unassign` does NOT set `pending`** (this corrects the plan's residual assumption "confirm unassign → pending"): a live probe showed clearing the assignee leaves `status` unchanged ("open" stays "open"), and `toggle_status → pending` does NOT clear the assignee (`conversations_controller#toggle_status` only saves the status; it auto-assigns the acting agent solely on `open`). So returning a conversation to the bot requires BOTH an explicit unassign AND `status=pending`: `returnConversationToAgent` now calls `client.unassignConversation` (`assignee_id:0` → `AssignmentService` sets `assignee=nil`) **and** `toggleStatus("pending")`. Without the unassign, the gate (`assignee_type !== "User"`) would keep the bot silent on the next inbound message.
