# Passkeys (WebAuthn)

Passkeys are a full way into a console account, next to the password and Google: registered and managed from Settings → Security, used from the email field's autofill on `/login` or from the "Sign in with a passkey" button. **Off by default**: `PASSKEYS_ENABLED=true` turns them on. The server is `src/api/features/passkeys/` (on `@simplewebauthn/server`), the browser side is `src/client/lib/passkey.ts` (on `@simplewebauthn/browser`), the screen is `src/client/pages/settings/SecurityPasskeysSection.tsx`, and `tests/api/features/passkeys/` drives the real library with a software authenticator (`tests/utils/fake-authenticator.ts`).

## The switch

- **Off** (`PASSKEYS_ENABLED` unset or anything but `true`): every `/api/auth/passkeys/*` route answers `404 {"error":"Not Found"}`, what a route that does not exist answers, before its body is parsed or its schema runs (an `onRequest` hook in the controller, asked per request). `/api/auth/me` reports `passkeysEnabled: false`, and the console shows no passkey button, no passkey autofill, no passkey section in Settings → Security and no passkey offer.
- **On**: everything below.
- **The schema does not depend on it.** The tables exist either way; a passkey registered while the switch was on stays stored while it is off, and signs in again when it is turned back on. Turning it off is not removing a credential: a person who relied on a passkey alone, with no password and no Google sign-in, cannot get in while it is off.

## `PUBLIC_URL` is the relying party

The RP ID is the hostname of `PUBLIC_URL` and the expected origin is its origin; the hostname is also the RP name the authenticator shows, so a white-labelled install shows its own domain. A passkey only works on the domain it was created for, so:

- a `PUBLIC_URL` that does not match the address people actually open breaks passkeys outright (every registration and every login fails verification);
- moving the console to another domain strands every existing passkey, unless the new domain serves `/.well-known/webauthn` (Related Origin Requests) naming the old one. People still have their password or Google to get in and register a new passkey.

Browsers allow WebAuthn on `http://localhost` and on HTTPS only, so a dev server reached by a LAN IP over plain HTTP has no passkeys.

## What carries the guarantee

- **Discoverable credentials, user verification required** (`residentKey: "required"`, `userVerification: "required"`). Login is one button with no email field, which also says nothing about which emails have an account, and a passkey is a full credential, not a second factor.
- **Challenges are single use and live 5 minutes, and the two kinds are kept differently.** A registration challenge is a row in `webauthn_challenges`, deleted *before* the response is verified, so a replayed response has nothing to match and a rejected one spends its challenge too; the owner is checked after the delete. A sign-in challenge is **not stored**: `/auth/passkeys/login/options` returns it inside a signed token (`challengeId`, its own key derived from `JWT_SECRET` through `src/api/lib/action-token.ts`), because `/login` asks for one on every view to start the autofill request and a row per page view is a write anyone can make. Its single use is at the other end: `/auth/passkeys/login` checks the signature and the expiry, then inserts the challenge's hash into `webauthn_consumed_challenges` (primary key) *before* verifying the response, so a replay, a rejected attempt or a second request racing the first hits the key. Both tables are in the database rather than in memory because the options and the verify can land on different replicas, and both sweep their expired rows on every insert. The spent-challenge sweep and insert read the **database** clock, the insert refuses a challenge already past expiry by it, and the clock is read again (`clock_timestamp()`) after a successful insert, so a replay that waited on the unique index behind a sweep cannot slip in. A challenge presented on the wrong path is a 400 like any other bad challenge.
- **The `userHandle` is bound to the credential's owner on login.** Without `allowCredentials` the library only checks the field's type, so the service compares it with the owner's handle itself. That handle is 32 random bytes stored on the account (`users.webauthn_user_handle`, set on the first registration), never the account id: two apps on one RP ID would hand out the same small integers, and an authenticator replaces a discoverable credential that shares RP ID and user handle.
- **The counter is a compare-and-swap** (`updateMany where counter = the value read`): two concurrent logins cannot write out of order and move it backwards, which would hide a cloned credential. The login that loses the write re-reads and retries while its own counter is still ahead of the stored one, and is refused when it is not. Authenticators that always report 0 (most synced passkeys) keep working.
- **The session is the one a password login issues.** `setAuthCookie` with the row's current password hash, as Google sign-in does, so a password change still revokes a session a passkey opened, and a logout ends it like any other (`jti`, `ended_sessions`). The membership rule is the same too: a person with no tenant to enter is refused, with the same answer as an unknown passkey. The passkey itself survives a password change.
- **Adding a passkey asks for the credential the account already has**, not just the session: the current password (through `confirmStepUp`), or a fresh Google sign-in whose `sub` is the account's own Google identity (`proveAccountOwner`, before the registration challenge is issued). A session alone would let whoever holds a stolen cookie plant a passkey that outlives the password change meant to evict them. `users_auth_method_check` guarantees every account has one of the two. A password changed while the ceremony runs revoked the session that started it: the insert locks the user row and re-checks the session's password fingerprint, and answers 401.
- **API keys cannot touch passkeys.** Every authenticated passkey route refuses a Bearer key with 403 (`requireSession`): a key's principal names its creator for audit and does not act as them on their own account.
- **List, rename and remove are scoped by `(id, userId)`.** Another account's passkey is a 404.
- **Only the sign-in itself and the proof are on the strict credential budget.** `POST /auth/passkeys/login` and `POST /auth/passkeys/register/options` (it takes a password) share the bucket with the other logins (`CREDENTIAL_ROUTES` in `src/api/middlewares/rateLimit.ts`). `/auth/passkeys/login/options` is on the global budget only: it takes no secret, writes nothing, and the autofill request asks for it on every view of `/login`, which on the strict bucket would let a few reloads lock a whole office out of every login.
- **`excludeCredentials` on registration.** The browser answers a second registration on the same authenticator with `InvalidStateError`, which the screen shows as "this device already has a passkey for this account"; `NotAllowedError` and `AbortError` (cancelled, timed out, no passkey for this site) are silent.

## The offer after a password sign-in

Right after a password login, an account with no passkey is offered one, in two layers.

- **The browser's silent upgrade first.** Where `PublicKeyCredential.getClientCapabilities()` reports `conditionalCreate` (Safari 18+, Chrome 136+), `PasskeyOffer` asks for options with `conditional: true` and calls `startRegistration({ useAutoRegister: true })`, which is `navigator.credentials.create({ mediation: "conditional" })`. The password manager that just filled the password decides, with no UI; a refusal is a silent `NotAllowedError`. Such a passkey is created without a prompt, so the authenticator reports neither user presence nor verification: the options ask for verification as `preferred` and the challenge is stored as `CONDITIONAL_REGISTRATION`, the only type whose response may skip both. Every sign-in with that passkey still requires verification.
- **Then a floating card**, only when the first layer made nothing. It sits at the bottom right (full width at the bottom on a phone, clear of the safe-area insets) but is not a toast: no timer, its own layer (`--z-floating-card`, under drawers, modals and toasts), no focus taken when it appears. "Not now" and "Create passkey" carry the same weight, and the X records the same refusal as "Not now"; ignoring the card is not a refusal. It is decided once per sign-in (a `sessionStorage` mark that every sign-in and sign-out clears), so a reload or a navigation does not bring it back.
- **"Not now" is recorded on the account** (`passkey_prompt_dismissed_at`, `passkey_prompt_dismiss_count`), not in the browser, so another browser does not reset it: 30 days away, and after the third time for good. Settings → Security is always the way in.
- **The server decides whether to offer** (`GET /auth/passkeys/offer`): a password sign-in in the last 5 minutes, no passkey, outside the cooldown and under the cap.
- **The recent sign-in is proven by the session token, not by the client.** `setAuthCookie` takes the method the person just used and stamps `auth_method` and `auth_time`: `password` (login, signup, `/setup`), `google` or `passkey`. Within 5 minutes of a password or Google sign-in, `/auth/passkeys/register/options` accepts a body with no proof. A passkey sign-in never opens the window (it proves the device, not the account's credential), and neither does a password change, which re-signs the cookie without being a sign-in, nor accepting an invitation. A token minted without a method is never recent. A proof that is sent is checked even inside the window.
- **Every number lives in `src/api/features/passkeys/offer.ts`** (`PASSKEY_OFFER`). The cooldown and the cap are vendor guidance (Corbado), not research.

## Decisions worth knowing before changing them

- **The last way in cannot be removed.** `users_auth_method_check` keeps a password or a Google identity on every row, but a stored Google identity is no way in once `GOOGLE_CLIENT_ID` is unset, which leaves a Google-only account with its passkeys alone. Removing the last passkey of an account with no password and no usable Google sign-in is refused with 409, under a lock on the user row so two concurrent removals cannot both pass the count, and the Settings row disables the button and says why.
- **Removing a passkey does not end the sessions it opened.** Sessions are bound to the password, not to the credential; changing the password is what signs every other session out.
- **The email field offers saved passkeys (conditional UI).** With the switch on, the field carries `autocomplete="username webauthn"` (the saved password is still offered from the same suggestions), and where `PublicKeyCredential.isConditionalMediationAvailable()` says yes the page keeps a `navigator.credentials.get({ mediation: "conditional" })` waiting in the background (`passkeyAutofill` in `src/client/lib/passkey.ts`). Nothing shows until the person picks a passkey from the suggestions; picking one signs in like the button. A page may hold one WebAuthn request at a time, so every other way in stops it first (the button, a password submit, a Google credential, leaving the page) and a failed attempt starts it again. A request the browser ends on its own is not restarted, which would loop. Because a conditional request can wait far longer than the 5 minutes a sign-in challenge lives, it is re-armed with fresh options every 4 minutes (`AUTOFILL_REFRESH_MS`).
- **The provider name** comes from the AAGUID through a short list of the common ones (iCloud Keychain, Google Password Manager, Windows Hello, password managers). Apple reports a zero AAGUID, so for those the browser and OS from the registering request's user agent stand in.
