# Dashboard

The operator's dashboard (`src/client/pages/DashboardPage.tsx`, blocks under `src/client/pages/dashboard/`) is organised by the question an operator brings, not by the table the data lives in: is the agent doing its job, why does it hand over and what are people asking, what does it cost, is it healthy, and what else does it do on its own. This page maps every block to the query behind it, so the next change does not reintroduce a second source.

**Every figure comes from this app's own records.** Money is `llm_usage.cost_usd`, priced when the call was written and re-priceable after (`scripts/reprice-usage.ts`). No figure is read from Langfuse: it holds only the turns that were traced, which can be a share of them (`docs/graph.md`, Langfuse tracing), prices only at ingestion and delivers best-effort, so its sum is not a total. Langfuse appears only as the "Open in Langfuse" link (`DashboardCosts.langfuse`), and the page renders the same numbers with it unreachable.

## The one filter

Period, agent, inbox and source live in the URL (`?range=7d|30d|90d|12m|all|custom&from=&to=&agent=&inbox=&source=&audience=`, `src/client/pages/dashboard/filters.ts`). `audience` (`identified` | `anonymous`) refines the client source only: it is read, shown and sent under `source=client` and dropped under any other, and every block applies it (`audienceSql`, from the `anonymous` column each turn writes on its usage rows and flow lines). A value at its default is left out, a value that does not parse falls back to its default, and an agent or inbox id this account does not have is dropped from the URL rather than shown as an empty view. What the agent and inbox selects offer comes from `GET /v1/metrics/filter-options` (`src/modules/analytics/options.ts`): every agent and inbox, whole rather than paged, readable by anyone who can read the dashboard. An inbox whose name another inbox of the tenant also has (two connected Chatwoot accounts with a "SAC WhatsApp" each) carries `account: {id, name}`; this page's inbox select and the Dashboards panel editor's inbox filter read it as "SAC WhatsApp · <account>" ("Account 7" while the name has not synced, `inboxOptionLabel` in `src/client/lib/inboxOption.ts`), as the Dashboards panels' rows do. A link's ids are checked against that list only once it has arrived; an unreadable list keeps them. The window is half-open `[since, until)` in the browser's own days (`docs/ui.md`, "A day is defined by the viewer's browser timezone"), and the previous period is the same number of days before it. A window still running (a preset, or a custom range that reaches today) is read up to the instant the view was opened (the API query ends there; its days and drill-down links keep the whole window) and compared up to the same local time of day, N days back: the last 7 days at 10:00 against the 7 before them up to 10:00, never against whole days, which would read as a drop every morning and a rise late in the day. A window already over is compared with the whole days ending where it starts; "all" has none.

Every route takes the same query (`dashboardFilterQuery`, `src/api/v1/dashboard.controller.ts`) and every service builds on the fragments of `src/modules/analytics/filter.ts`:

| fragment | means |
|---|---|
| `cohortWhereSql` | **the view's conversations**: created in the window (`conversations.created_at`, when the conversation reached us), in the filtered inbox, and under an agent filter, the ones whose inbox is bound to that agent or that the agent ran on |
| `agentRanSql` | **the agent ran on it**: a real-traffic ledger row that is an agent turn (`node` null or not in `NON_AGENT_TURN_NODES`), by the filtered agent when there is one |
| `outcomeSql` | `classifyOutcome` in SQL (handoff, resolved by the agent, resolved before tracking, resolved by someone else, unresolved); fenced against the TypeScript rule by `tests/modules/analytics-outcome-sql.test.ts` |
| `usageWhereSql` | **the view's ledger rows**: billed in the window, in the source and audience, by the agent, in the inbox |
| `logWhereSql` | the same for `execution_logs`, which carries the same columns; under an inbox filter a line that names its conversation and no inbox (a takeover is logged from the webhook) is its conversation's inbox's. The Logs page reads the same rule (`inboxLogLineIds`, `src/modules/flowlog/read.ts`, bounded by the page size) |

**Every route reads through the metrics pool and answers within a bound** (`src/modules/analytics/budget.ts`, issue #1277). The reads, and the authentication of the `/api/v1/metrics` routes, run on a pool of their own (`METRICS_POOL_MAX`, default 3), so a page load queues there and never takes the connections turns need. Each request has one budget, `METRICS_TIMEOUT_MS` (default 15000), counted from its arrival and shared by the wait for a connection and the run of its reads; past it, or past the lock timeout, it answers 503 (`MetricsTooSlowError`, "try a shorter period, or again in a moment") and Postgres has already stopped the query. A block that gets that 503 says so in its slot, with its retry; any other failure keeps "Could not load metrics." The MCP `metrics_get` and `metrics_timeseries` return the same sentence. Sizes and the budget: `docs/deploy.md`, "Connection budget". Every request to a `/api/v1/metrics` route writes one info line, `metrics request` (`src/api/lib/metrics-request.ts`): the route, the status it answered, the window's length in days (`windowDays`, null for an all-time view; never an instant), whether each filter was set (`agent`, `inbox`, `source`, `audience`, as booleans, never an id), the `dimension` or `breakdown` asked, how many metrics reads ran (`reads`), how long the request waited for a connection of the metrics pool (`waitMs`) and how long its statements on it ran (`runMs`), and the request's whole time (`totalMs`). Both times include the session or key lookup in front of the route, which runs on the same pool and is where a request behind a held connection usually waits. A request refused before any read (no session, a bad parameter) writes the route, the status and `reads: 0`, and nothing about what it asked for. Each read reports its own times (`runMetricsScoped`), and a read the budget refused reports the wait it spent.

**What a page load costs the database.** The metrics pool runs with `jit=off` whatever the server says (`src/api/lib/pool-options.ts`): these reads are a few large aggregates, and compiling each one on every request costs more than it saves. The planner estimates the sums reads above `jit_above_cost` even on a small tenant (a `generate_series` over parameters is estimated at 1000 rows, and a lateral branch per day multiplies it), so on a server with the JIT available (the `pgvector/pgvector:pg17` image on amd64 has it on by default) the setting is what keeps a page load from compiling. Measured on the synthetic tenant at 3x a large production tenant, sums caught up, on a loaded machine, median of three: every request of a console opening sent at once, plus `timeseries` and `/api/v1/metrics` (which the console does not send) in the same burst. The flow-log figures (handoffs by cause, silences, where the transfers went, follow-ups) reach their lines through the partial index `execution_logs_dashboard_lines_idx` on `(tenant_id, stage, created_at)`; a new figure over those lines writes a predicate that implies one of the index's arms, or it reads every line of the window, `generate` lines and their stored prompts included. A conversation's outcome and whether the agent ran on it are worked out once per conversation (`outcomeCountsSql`, the labels), not once per figure. The cost block reads its figures and the Langfuse configuration of its link in one transaction, so a cost request holds one connection of the metrics pool. The console sends each distinct request once per load ("How the console loads").

Conversation figures are real traffic by construction (a playground turn has no conversation). Ledger figures follow the source toggle.

## How the console loads

Every block asks its own route (`useMetricsBlock`, `src/client/pages/dashboard/useMetrics.ts`, issue #1732), with the page's query and, for the KPIs, the funnel trend and the costs, the previous period's too. Each route computes its figures when asked, within the request's one `METRICS_TIMEOUT_MS`, from the sums the `LEDGER_SUMS` job keeps and from the records for whatever the sums cannot answer ("Ledger and conversation sums" below), so a late change to an old conversation (reopened, relabelled, repriced) is in the next request's figures, before the job has summed it again. A block shows its own skeleton, in a `role="status"` region, until its answer arrives, and its figures are final when they show: there is no partial state. A fast block shows at once and a slow one holds only itself. A block whose route fails or is refused shows its failure and its retry in its own slot, and every tile that reads the same answer shows that failure with it, never a figure it did not get (the four cost tiles share one failure card; the KPI tiles and the funnel share one), and the retry asks that block's route again, and only it. Two blocks that read the same route with the same query (the cost block's cached input and the usage table's agent rows, the latency and problems blocks) share one request. A new view (a filter, a period, a new local day) is a new opening, at a new instant: every block asks again, the previous view's figures leave the screen at once, and its requests still running are aborted; on the server a metrics read whose caller is gone runs nothing (`runMetricsScoped`), so it does not hold a connection of the pool the new view needs. A block that compares against the previous period (the KPIs, the funnel trend, the costs) shows both or neither: it holds its skeleton until both answer, and when either request fails it shows its failure, and its retry asks again whichever of the two failed (`withComparison`). A block's retry belongs to its view. The flow-log blocks wait for the retention the filter options carry; options that cannot be read are asked again after one and four seconds, and past that those blocks show their failure and their retry, never "none in the period".

**When the database runs short of shared memory.** The heavier reads (costs, the breakdowns, health) run with parallel workers, which pass rows through dynamic shared memory, kept in `/dev/shm`. Docker gives a container 64 MB of it unless its compose sets `shm_size`, and three of those reads at once can fill it: Postgres refuses with 53100 ("could not resize shared memory segment"). `runMetricsScoped` then runs the same read again, inside the same budget, with `max_parallel_workers_per_gather = 0`, which takes no shared memory; the reads are pure, so running one twice changes nothing. Rows that tie keep one fixed order (`problemOrder` and `latencyOrder` in `src/modules/analytics/health.ts`), since Postgres hands tied groups back in whatever order its plan made them.

**The kept days' tables, for one release.** `dashboard_days`, `dashboard_dirty` and the `dashboard_dirty*` triggers that queue late changes stay in the database, untouched, for the release that removed their reader: `migrate deploy` runs while the previous container still serves, and a rollback to it needs its kept days and every invalidation queued since. Nothing reads or deletes them now. The triggers fire only for changes to rows older than a day, so the queue grows by late changes alone; a rollback's engine processes the whole queue and computes again every day it names, as on a first read. The release after drops the triggers, their functions and the tables.

**What "no data" means.** The flow log keeps `FLOWLOG_RETENTION_DAYS` (sent with the filter options as `flowLogRetentionDays`, with `firstRecordAt`, the tenant's first conversation or ledger row, where an all-time view starts). A day before the one the retention cutoff falls in is not read, even while the daily sweep has not yet emptied it (`flowLogFloor` in `src/modules/analytics/filter.ts`), so a figure does not change when the sweep runs; the handoffs, follow-ups and health routes take that floor once per request and answer it as `flowLogFrom`, and the console marks the days before it, so a view opened before midnight and read after it marks the day the read left out, and the blocks that read the flow log (handoffs, silences, follow-ups, problems) say so ("no data for N days", `flowLogCoverage`) rather than show it as zero: their charts draw those days under a dotted "no data" band (an all-time chart's axis starts at the first of them, `axisStart`), their tables leave them blank, and a block with nothing to show over a window with such days does not say there was none in the period (`hasNoData`). The day the cutoff falls in is read as the reader reads it, since the sweep is still emptying it.

**How the cost block reads the ledger.** `getDashboardCosts` reads the window's ledger as quarter-hour sums (below) and adds them up per local day, model and call type in one pass: every zone's offset is a whole number of quarter hours, so a quarter falls in one local day. One `GROUPING SETS` pass over those few thousand rows gives the period's total, the days, the models, and the days by model and by call type. The divisors are the funnel's per local day, counted per quarter first so the day is worked out once per quarter, and the period's are the days' added up, since a conversation falls in one day.

## Ledger and conversation sums

The figures do not add up the ledger and the conversations row by row. The `LEDGER_SUMS` job (one per tenant, armed at boot for every tenant and when the first-run setup or an admin creates one, and rearmed every minute under the scheduler's lease, `src/modules/analytics/ledger-sums.ts`) keeps them added up, and the readers add up the sums.

| table | grain | written from |
|---|---|---|
| `ledger_quarter_sums` | quarter hour of UTC, source, audience, agent, inbox, model, call type | `llm_usage`: cost (null when nothing in it is priced), requests, unpriced requests, the four token counts |
| `ledger_day_sums` | UTC day, the same keys | added up from the quarters, for the reads grouped by week or month (issue #1837) |
| `ledger_latency_days` | UTC day, the same keys, a 5%-wide bucket of `duration_ms` | `llm_usage`: calls, and the smallest and largest duration of the bucket |
| `conversation_agent_runs` | conversation, agent (0 for a turn with no agent) | the ledger's agent turns (`ledger_is_agent_turn`, fenced against `USAGE_NODE_IS_AGENT_TURN` by `tests/modules/analytics-conversation-sums.test.ts`) |
| `conversation_quarter_sums`, `conversation_label_quarter_sums` | creation quarter, inbox, outcome (`outcomeSql`), whether any agent ran, the agents that ran, whether labelled (or the label) | `conversations` and their runs |
| `conversation_day_sums`, `conversation_label_day_sums` | the same per UTC day | added up from the quarters |
| `conversation_first_response_days` | UTC day of creation, inbox, the agents that ran, a 5%-wide bucket of seconds | the sampled conversations of the first response tile: count, smallest and largest |

**The mark.** `ledger_sums_state.summed_until` is where the sums stop: every quarter below it is summed, and the readers take everything at or above it from the rows. The job moves it at most one day per step and never past five minutes ago (`GRACE_MS`), and only over rows no transaction can still write: a step records the instant and its own transaction id as the candidate, and the next step moves the mark to that instant, less the grace, only once the oldest transaction still open (`pg_snapshot_xmin` of its snapshot) is past that id. A transaction open at the candidate, or one that commits a row stamped earlier than the instant it commits, holds the mark back until it ends. While it waits, the job gives its turn back and runs again a minute later rather than polling. A candidate still waiting is kept, not replaced by a newer one on the next step, so transactions that overlap without end, each ending in time, do not hold the mark back forever. A long transaction anywhere in the database delays the mark by as long as it stays open, and the figures stay right meanwhile, read from the rows above the mark. `tests/modules/analytics-ledger-sums.test.ts` holds a leg per case: a row inserted late with an old time, a transaction open across the candidate, an application clock behind the database's by more than the grace.

**Late changes.** Statement triggers on `llm_usage` and `conversations` (with transition tables, so a statement of a thousand rows writes one set of marks) append the quarters a change below the grace touched to `ledger_sum_marks` or `conversation_sum_marks`, and a change to a conversation's agent turns appends the conversation, a new turn by an agent already kept included: a rebuild of its runs may be dropping that run in a transaction the turn cannot see, and only the turn's own mark brings it back. Settling the marks of a minute of turns (60 conversations created over the last two days, on a synthetic tenant at three times a large production tenant, under load) takes about 250 ms of the job. An inserted conversation appends itself, not only its quarter: a conversation removed and written back has lost its runs to the cascade while its turns are still in the ledger. A conversation update marks only when a column the figures read changed (status, assignee type, who resolved, inbox, labels, the sweep flag, the creation and first reply times). The webhook rewrites conversations on most events, and most of those touch none of them. A marked quarter is read from its rows until the job sums it again and deletes its marks in the same transaction, so a repricing, a reopened conversation or a removed label is in the next request. A step takes the earliest marked quarters, a day's worth at most, and sums each run of adjacent ones in one statement, and a run that spends its budget with work left runs again at once. On the synthetic tenant at three times a large production tenant, under load, a repricing of two months (1.2 million rows, every quarter of the range marked) settles in 61 steps of about 1.1 s, a little over a minute of the job. Until it does, a window over the repriced months reads them from rows, as fast as the rows read without sums. So `scripts/reprice-usage.ts --apply` does not leave that minute to the job: before it returns it runs the same step for each tenant it repriced, on the `DATABASE_URL` its writes used (the step relies on RLS for its tenant, so the script refuses a role RLS does not bind), one step per tenant per round, until none of the marks on the quarters it wrote rows in, as they stood when the settle began, is left, and exits 1 if any is still there after ten minutes. A repriced quarter at or above the tenant's mark (a row inside the triggers' grace is never marked), or of a tenant not summed yet, is read from the rows until the job sums up to it, and so is a repriced quarter a later write marks again while the script settles, which it leaves to the job: the script names both. A step that throws (one waiting on the job's own step past its transaction budget) is retried until the ten minutes run out. Each step is the job's own transaction and deletes only the marks it read, so a mark of concurrent traffic waits for the next step as it would for the job. A tenant's deletion removes its sums through the foreign keys and writes no marks. Measured on a synthetic tenant at three times a large production tenant, 2,000 single-row statements each, the triggers add about 0.01 to 0.02 ms to an update that changes nothing the figures read, 0.02 to 0.04 ms to a status or label change, and 0.07 to 0.11 ms to a ledger insert of an agent turn on a counted conversation, which writes its mark.

**The invariants, and the test that holds them.** Four rules keep the sums equal to the rows while writes run against the job, and each one is a reason the code is shaped the way it is.

1. No row the figures read is left out. A quarter below the mark is either summed with every row committed in it, or marked, and a marked quarter is read from its rows. A write below the mark commits its mark in its own transaction (the triggers), so a reader sees the row and its mark together or neither.
2. A mark leaves only with a recount that saw its write. A step deletes the marks it read and no other, by id: a mark committed after the step read the marks, for the same quarter or the same conversation, stays for the next step, even when the step's recount happened to see its row.
3. The mark moves only over rows no transaction can still write. The candidate is waited out against the oldest open transaction (above), so a write open across a step holds the mark back and never lands below it unmarked.
4. A step does not fail or deadlock on a write in flight. Before writing a conversation's runs, a step takes the conversations it writes them for with `FOR KEY SHARE`, in id order. A removal of one of them still uncommitted is waited out there and the conversation left out, its runs gone with it through the cascade. Writing the run first would fail the step on the foreign key, or meet the removal's cascade on the runs the other way round. An ordinary update of a conversation does not wait on that lock.

`tests/modules/analytics-sums-interleavings.test.ts` holds these against every write the figures read (a turn written back, a second agent's turn, a repricing, a call moved a day, a turn removed, a conversation written back with its turn, resolved and relabelled, removed), each on rows of its own, against a job step cut before each of its statements in turn. Each write commits in the gap, stays open across the whole step, or begins in the gap and commits after the step. A write that waits on a lock the step holds, or that the step waits on, commits as soon as the wait is seen in `pg_stat_activity`. After each cut the figures read from the sums are the figures read from the rows, and again once the job catches up. Two more legs hold a step that meets a conversation's removal in flight, one where the removal commits and one where it rolls back: the step waits on it, ends without error, and the database counts no deadlock. Deleting the marks of a quarter instead of the marks read, or every mark of a conversation, fails it, and so does writing the runs before taking the conversations.

**The first run.** A tenant's sums start at the UTC day of its earliest ledger row or conversation, whichever is older, so nothing written before the migration is left out of them. Its runs follow one another until the tenant is summed: the synthetic tenant's year took 366 steps and about two minutes.

**Reading them.** A reader first takes the bounds (`sumsBounds`: the mark, and the window cut to whole quarters) as a statement of its own, so the planner sees them as constants and reaches the sums through their indexes. Then one statement adds up the sums of the unmarked quarters inside the bounds, the rows of the marked quarters and of the window's edges outside them, and the rows at or above the mark. A read that does not split by local day (the funnel's totals, the labels, the breakdown's conversation columns, the first response and latency histograms) takes the UTC days wholly inside the bounds with no marked quarter from the day tables, and the rest from the quarters. A tenant with no state yet reads everything from the rows, and so does a tenant still being summed for the stretch above its mark. The conversation figures read the counts and the runs only while the mark is less than an hour behind and fewer quarters are marked than a step settles (`withRunsMark`): whether an agent ran on a conversation read from its row then takes the ledger above the mark, and the marked quarters, as one small set. Past that the set is millions of rows, too many to hash, and the planner scans it once per conversation, so the route reads the conversations from their rows instead, the same read as before any sums. On the synthetic tenant with the mark 200 days back, a 30-day agent drill-down reads in 1.4 s and the instance metrics under an agent in 6 s, against 0.8 s and 7 s for the rows read without sums at the same moment. While the marks of a two-month repricing drained through the job alone, a 90-day window read in 3 to 9 s (about a minute), and in 0.1 s once they had, which is where the reprice script leaves it. The figures are the rows' figures, to the last digit, filter by filter: the tests read both ways and ask for the same answer.

**Percentiles from a histogram.** The first response and latency percentiles are read from 5%-wide buckets (below one second too, with zero in a bucket of its own), interpolated the way `percentile_cont` interpolates between values, with each bucket's values standing for the bucket's geometric middle held between the smallest and largest value it holds. A percentile is within 2.5% of the exact one, and exact when the values around it fall in buckets of one value each. The sample sizes and call counts are exact.

## Long windows: weeks and months

A chart of the page has one point per local day up to 92 days, one per local week (Monday to Sunday) from 93 to 730 days, and one per local month past 730 days (`src/modules/analytics/grain.ts`). The number of days is the window's local days in the request's `tz`, first and last inclusive; a window with no `since` starts at the tenant's first conversation or ledger row (`firstRecordAt`), so "all" is grouped by how long the tenant has been here. The route takes the grouping from the window, never from the caller, and answers it as `grain` (`trend.grain` on `/outcomes`, `handoffs.grain`, `costs.grain`, and `grain` beside `points` on `/timeseries` and the MCP `metrics_timeseries`), so the API, the MCP tools and the console draw the same groups. Each point's `date` (`bucket` on the timeseries) is the first local day of its group, the Monday or the first of the month, even where the window starts later: a group at either edge of the window holds only the window's days.

A group is read as one window, not added up from its days. The SQL groups the rows by the group's key (`localDayStartSql` with a grain, `date_trunc('week'|'month', …)` in the zone, whose week starts on Monday), so every figure of a point is what a view of exactly that group's days would show: a conversation handed over on two days of a week counts once in that week, and a count of distinct conversations or a rate is never a sum or an average of daily points. The tiles and the period totals do not change with the grouping.

**Which sums a grouped read takes.** A quarter of UTC falls in one local day, so in one week or month of any zone: the ledger's series and the funnel are keyed per quarter, exactly. Both also have UTC day rows (`ledger_day_sums`, `conversation_day_sums`), and a grouped read (the cost and calls series, the trend, its split, the cost's divisors, the timeseries' conversations) takes them for the UTC days that lie wholly inside one local group (`insideOneGroupSql` in `src/modules/analytics/grain.ts`: the group of the day's first instant is the group of its last) and hold no marked quarter, and the quarters only for the day that holds a group's first instant, as for a marked day. A twelve-month window so reads about a seventh of its ledger quarters, those of the boundary days. A day grouping reads quarters only, since every UTC day of a zone off UTC holds a local midnight. The job writes a ledger day from its quarters when a step completes the day, and again when it recomputes a marked quarter of it.

The console reads `grain` from the answer (`src/client/pages/dashboard/period.ts`). The axis names a week by its first day in the window and a month as "Mar 26"; the tooltip, the detail of a stacked point and the keyboard label name the week by the days it covers in the window ("Mar 11 to 15" for a window that starts on that Wednesday, "11 a 15 de mar." in Portuguese: `formatRangeToParts` in the viewer's language, with the dash between the two ends replaced by the locale's word, `dashboard.chart.rangeTo`) and the month in full; a stack's total reads "Week total" or "Month total"; the table and the CSV call the first column "Week (starting Monday)" or "Month" and keep the raw key. Clicking a point of the funnel trend opens the conversations created in that group's days inside the window. The previous period has as many days as the window, so the same grouping, and its group at the same position is the comparison. A group is no data only when its last day is before the flow log's cutoff: the group that holds the cutoff shows the days after it, and the legend counts weeks or months.

## Log facts

The handoff, silence and follow-up figures read a few lines out of the busiest table of the database, and what each line counts as is decided by keys inside its `detail`. So those lines are also kept as **log facts** in `dashboard_log_facts` (issue #1731, migration `20261107220000_dashboard_log_facts`): one row per line that is a transfer (with its cause and, for a hand-over line, where it went), a `skip_reply` call that ran (with its reason) or a follow-up step that reached the customer, carrying the line's own time, conversation, agent, inbox, source and audience, so the filter reads them exactly as it reads the log (`logWhereSql`). Triggers on `execution_logs` write a line's fact when the line is written and remove it when the line is deleted, whatever deletes it (the retention sweep, a tenant's deletion, a test), rewrite it when the line is rewritten, and empty the facts on a `TRUNCATE`; the app never writes them. The figures over the facts are the figures over the log, filter by filter and to the last digit, and `tests/modules/analytics-log-facts.test.ts` reads both ways and asks for the same answer.

**One cause is decided when it is read.** Whether a `taken_over` line is a person taking the conversation depends on the conversation's other transfers and turns (the rule is in the table below), and those can be written after the line (a transaction that commits late, a line written with an earlier time) or swept before it. So the fact keeps `taken_over` as itself, and the reader decides it over the facts (`FACT_CAUSE_SQL` in `src/modules/analytics/activity.ts`), which hold every transfer of the conversation, looking up the agent's turns in the ledger as the log reader does. A transfer the retention sweep removes therefore changes the cause of a later takeover exactly as it does over the log.

**Lines from before the facts.** The migration writes no fact: it marks every tenant that existed as waiting (`dashboard_log_facts_state`), and the `DASHBOARD_LOG_FACTS_BACKFILL` job, armed at boot for each waiting tenant, fills its lines one hour of log per transaction, oldest first, for up to 30 seconds per run before it gives the lane back, and marks the tenant done when it reaches the present (`src/modules/analytics/log-facts.ts`). It locks the lines it fills (`FOR SHARE`) before writing their facts: a delete or rewrite still uncommitted when the batch reaches a line holds the batch, which then writes what the line has become (nothing, for a deleted one); one that comes later waits for the batch, and its trigger finds the fact. Until a tenant is done its figures are read from the log as before, and a SUPER_ADMIN's view of the whole fleet reads the log until every tenant is; a tenant created after the migration reads the facts from the start. A job that dies leaves the tenant reading the log, slower and still right, until the next boot arms it again.

## The blocks

The filter and the section index sit in one band across the top of the page, which stays on screen while the page scrolls (from the `lg` breakpoint). The index is a row, not a column beside the blocks: at a laptop's width a column took a quarter of the room the blocks need. Each section's title carries the icon its entry carries in the index.

The funnel's five tiles are laid out by the width the page has (a container query on their row, `KPI_GRID` in `PerformanceSection.tsx`), not by the window's, since the app's sidebar takes a share a window breakpoint cannot see: five across from 70rem, three and two below it, two by two below that with the last tile across the row. No width leaves a tile alone beside a gap.

## Series colours, order and the tooltip

A chart's series take the `--color-chart-1` to `--color-chart-8` tokens of `public/index.css`, never cycled: a categorical palette stepped per theme whose neighbours stay apart under colour-vision deficiency, and that does not borrow the theme's semantic tokens (accent, success, error), which can sit close in hue. Every colour clears 3:1 against the card surface in both themes (the light steps of aqua, yellow and magenta are darker than the dataviz reference for that). A series' colour follows the series, never its rank: the first render gives the kept series their slots in the caller's order, and from then on a series keeps its slot while it stays kept, so a colour does not move when another series joins or leaves the group or a new answer changes the ranking; a newcomer takes the free slot (`assignSlots` in `chart-series.ts`).

The series are ranked once per window by their total over it (`arrangeSeries` in `chart-series.ts`), never per day. Past eight, the smallest form one "Others (N)" group in the neutral muted ink, always last: a stacked chart sums them into one layer on top of the stack, a line chart draws them as thin neutral context lines, since rates do not add up. The legend under a chart reads that ranking left to right: on a stack, from the base (the largest series) to the top, then "Others (N)"; hovering, clicking or tapping "Others (N)" lists its members (the app's `Popover`, which a click, a tap or Enter opens): the eight largest over the window, then "and N more", so the list never outgrows its box and never needs a scroll the keyboard cannot reach; every series stays in the block's table and CSV, and in a stack's day detail. A chart hides only its drawing from a screen reader, which reads the block's table instead; the legend and the day detail stay reachable. Every vertical list reads the chart as drawn, top to bottom: a stack's tooltip and day detail start with "Others" and end with the base, a line chart's tooltip lists the day's values highest first, which is where the lines sit that day, with "Others" last.

The tooltip (`TooltipCard` in `charts.tsx`) is a summary: exactly the legend's series, each on a line of its own (a zero segment left out), and the legend's "Others (N)" group as one line with the legend's count, so the tooltip, the legend and the day detail show the same group; the day's total in the header on a stack; and on a stack a hint that a click shows everything. Clicking or tapping a day of a stacked chart (a segment names its day from its row, a transparent column per day behind the bars names it for the empty room and the loading bands), or pressing Enter or Space on it from the keyboard (one tab stop over the plot, the arrows move between days), opens its detail under the chart (`DayDetail`); the day never comes from the hover state: every series, the group's members under its line, each with its value and its share of the day, closed by its button, by Escape (heard anywhere on the page while it is open; the focus moves into it) or by clicking the same day again. A line chart's click stays the drill-down to the day's conversations, by the same rule: a point names its own day and line, a day's column (reaching past the plot's edges, so the outer half of a point at 0% or 100% counts) names the day alone, and a line between its points lets the click through. The table view and the CSV are built from the unfolded series, so they keep every one.

## Export and accessibility

Each block exports what it shows as CSV (`src/client/pages/dashboard/csv.ts`): raw numbers, a header row, the same rows the screen shows. A text cell that starts like a formula (`=`, `+`, `-`, `@`) is written behind an apostrophe, since agent, inbox and label names come from outside. A chart is hidden from the accessibility tree and a table with the same figures stands in its place (`Block`, `src/client/pages/dashboard/Block.tsx`); while a block's figures are loading it offers neither, since its table does not hold them yet; figures shown beside a chart that are not in its table (the handoff block's period totals and silences) go in the block's `footer`, which stays readable; the CSV and that table are built from one `BlockTable`, so they cannot disagree. Chart colors are read from the theme's CSS variables and re-read when the theme flips (`useChartPalette`).

Each block loads on its own (`useBlock`). A new filter takes the previous view's figures off the block at once, so nothing of the old view stays on screen or clickable while the new one loads; a refresh of the same view (the ceiling's poll, a retry) keeps them until the new ones arrive. A block whose request fails says so, with a retry, and offers no CSV: an empty result and a failed one never look alike.
