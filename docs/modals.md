# Modals

The `<Modal>` component in `src/client/components/Modal.tsx` is the canonical wrapper for Radix Dialog. State is owned by a controller hook in the parent, and descendants pick it up via context. The shape:

```tsx
const modal = useModalController<License>();          // parent owns state

<Button onClick={() => modal.open(license)}>Open</Button>
<LicenseModal modal={modal} />                        // ALWAYS rendered

function LicenseModal({ modal }: { modal: ModalController<License> }) {
  return (
    <Modal modal={modal} title="Attach license">
      <Body />
    </Modal>
  );
}

function Body() {
  const { payload: license, close } = useModal<License>();   // any descendant
  // ...
}
```

## Rules

- **Always render the `<Modal>`, never `{flag && <Modal/>}`**. Radix keeps `Dialog.Root` alive through the exit animation via its internal `Presence` component. Unmounting the root skips the animation and snaps the modal closed. (This is why the `HelpFab` in older code animated correctly while newer wrappers didn't.)
- **`useModalController<T>(opts?)`** returns `{ isOpen, payload, open, close }`. `payload` is retained across `close()` so the body can keep rendering real data while Radix plays the exit animation; it's only overwritten on the next `open()`. Don't clear it in `close()`.
- **`useModal<T>()`** is the descendant hook. Reads the controller from context that `<Modal>` provides. Use it in body/footer/submodals to avoid prop drilling. Throws if used outside a `<Modal modal={...}>` subtree.
- **`useOnModalOpen(modal, effect)`** fires `effect` each time the controller's `isOpen` transitions from `false` to `true` (with optional cleanup on close). Use it for per-open state resets (form defaults, prefilled fields, etc.). It takes the controller directly (not `modal.isOpen`) because the hook is typically called in the wrapper component *before* `<Modal>` mounts its context provider; tried the context-only variant but it crashes at runtime for that reason. Don't reach for `useEffect(..., [modal.isOpen])` by hand; `useOnModalOpen` makes the intent explicit and is the pattern the biome plugin recognizes.
- **Reset state on the next open, not in the close handler.** Flipping disclosure/expansion state (`showAdvanced`, `isExpanded`, form sections) synchronously inside the close callback runs during Radix's exit animation, so the panel snaps shut mid-fade (visible flicker). Push those resets into `useOnModalOpen` instead; the modal is hidden between close and the next open, so the reset is invisible. This is also why `close()` on the controller does not clear `payload`: Radix needs to keep rendering real data through the animation.
- **`closeOnOutsideClick={false}`** for flows where accidental dismiss is costly (pricing, checkout, destructive confirmation). Esc still closes.
- **`onCloseRequest`** intercepts user-driven close (Esc, outside click, X). The handler is responsible for eventually calling `modal.close()` (or not), typically after a confirmation submodal. Programmatic `modal.close()` calls from the parent are unaffected.
- **`busy`** says a request this modal started is in flight. Every user-driven close (Esc, outside click, X, Cancel, Back) does nothing and the discard prompt never opens; the unload prompt stays armed while dirty. It takes precedence over `unsavedChanges` and `onCloseRequest`, and it holds the console's own reloads of a stale tab, clean form included (docs/routing.md, "A tab older than the server").
- **Footer "Cancel" must close through the guard, never `modal.close()` directly.** `modal.close()` is a PROGRAMMATIC close: it bypasses the unsaved-changes confirmation by design (the parent calls it after a successful save). A footer/body "Cancel" button is a USER-driven close, so it must funnel through the same guard as Esc/outside/X — otherwise a dirty form is discarded silently and item-27-class bugs reappear. Use the **`<ModalCancelButton>`** primitive (renders a `secondary` Button, label defaults to `common.cancel`, accepts `disabled`/`children`), or call **`useModalClose()`** from any component rendered inside the `<Modal>` subtree (footer prop included — it renders inside the Modal's context providers, even though the JSX is authored in the parent). The hook returns `requestClose`, so a dirty form gets the "discard changes?" prompt and a clean form closes immediately. Reserve a raw `modal.close()` for the post-success "Done" button on modals that hold nothing dirty.

Nested modals stack automatically: `<Modal>` reads a depth from context and computes its `z-index` as `calc(var(--z-modal) + depth * 2)`. The overlay sits one step below the content. A warning fires once nesting depth reaches 5 (which collides with `--z-toast` at 90). If you need deeper nesting, bump the z-index tokens in `public/index.css` instead of silencing the warning.

Enforced by `biome-plugins/always-render-modal.grit` (scoped to `src/client/**`): any JSX element whose name matches `*Modal` (or the bare `<Modal>`) wrapped in a `{cond && ...}` short-circuit or a `{cond ? ... : null}` ternary fails lint. The plugin rejects the unmount-on-close anti-pattern directly; the fix is to lift state into `useModalController` and always render the wrapper.

## A modal that changes height while open: slide to the center, then hold still

A modal that fetches what it shows is drawn first with its loading state or an empty body and then with the answer, at another height. Centered on its own height, it moves its top edge by half the difference in one frame, which users report as "opens off-center and jumps to the center" (downstream, in fazer-ai/projects: "Move task" showed its loading rows at 286px and rose 51px when the projects landed at 388px). What `<Modal>` does about it went through three versions, each measured, and the reasons the first two were dropped are the reasons for the rules below.

**History.**

- **The pin (fazer-ai/projects#250).** The top edge stayed where the first painted frame put it and every later change of height happened at the bottom edge. It stopped the jump, but left the end state to chance.
- **The resize drift.** The pin was a height in pixels against a `50dvh` that moves with the viewport, so a resized window drifted the dialog off center: measured with the pin alone, a dialog resized from 844 to 1100px sat 381px from the top and 220px from the bottom (downstream: opened at 900px and resized to 1100px, 116px from the top and 16px from the bottom). A `resize` was made to re-center it.
- **The bottom-edge cut.** Pinned on a short loading frame, a dialog could only grow downwards and was cut at `max-height` with the top of the screen empty (measured with the pin alone: 253px from the top, 16px from the bottom). Reaching the bottom edge with room above was made to re-center it, in one snap (bunfire#415).
- **The pinned end state, rejected.** A body that shrinks after opening left the dialog wherever the pin was: measured at an 860px viewport, a list going from 10 rows to 3 ended 151px from the top and 457px from the bottom. A dialog that ends off center looks broken even when no frame jumped. Re-centering after the fact with a plain `top` transition was prototyped and not chosen: it paints the new height at the old top first (the bottom edge jumps, then the whole dialog slides), so one edge still moves twice.

**The rule now.** The dialog opens centered on its first frame's height: the box's height is read when it mounts (the box is the inner `div` of `Content`, see Centering below) (in the commit, before paint) and the dialog is placed at `max(1rem, 50dvh - height/2)` through `--modal-top`, with no vertical translate. `origin-top` keeps the entry zoom from moving the top edge. From then on:

- **Until the person touches the dialog** (a `pointerdown` or `keydown` whose target is inside the box), every change of height slides to the new center. Inside the `ResizeObserver` callback, which runs after layout and before paint, the node is put back at the height it was last painted at (inline `height`, `top` where it was painted, `overflow: hidden`, `max-height: none`, no transition, a forced reflow), and then `top` and `height` transition together (260ms, `cubic-bezier(0.2, 0, 0, 1)`) to the new height, capped at the viewport less `2rem`, and its center. On the `transitionend` of `height` the new height becomes `anchorHeight` (committed with `flushSync`, so `--modal-top` already holds the new center when the inline values are removed in the same task). Both edges move together, each in one direction, and no frame is painted at the new height first. A timer settles a slide whose `transitionend` never arrives.
- **A press or a keystroke in the middle of a slide freezes it where it is painted.** Marking the dialog as touched only stops the next slide, and the running one kept moving the controls under the pointer, so a pressed button could move away before `pointerup` (bunfire#416, review round 1). The computed `top` and `height` (the values painted mid-transition) are written back with no transition, the pin moves to the height whose center is that top, and the height stays inline until the pointer comes up, since letting it go changes the bottom edge, where a footer button may be. A keystroke releases it at once.
- **After the person touched it**, the top edge stays where it is and a change of height happens at the bottom edge, so nothing moves under the cursor or the caret. The exception is a dialog that reaches the bottom edge with room above it: it slides to the center the same way, since a cut dialog is worse than a dialog that moves, but not while a pointer is pressed inside it; that slide waits for the `pointerup`. The check is in layout units (the computed `top` and `height`), so the entry zoom does not count, and it runs on every report, the first one included: the observer starts from the height the top was centered on, not from its first report, because a body that grew before that report was taken as the painted height and left the dialog cut with room above, and a dialog capped at `max-height` does not change size when it grows further, so nothing would report it again.
- **A close in the middle of a slide fades out where the panel is painted.** Radix keeps the panel on screen through its exit animation (the same reason `payload` is retained and resets wait for the next open, under Rules), and clearing the slide's inline values on close snapped it back to the old pin and to its natural height while it faded out (bunfire#416, review round 2; measured: a panel closed at 202.6px with 454.6px of height faded out at 260.3px and 579.4px). The effect's cleanup writes the computed `top` and `height` back with no transition and leaves them until the node unmounts. A keystroke in the middle of a slide lets the frozen height go on the next frame, not at once, because the Escape that closes the dialog is a keystroke too and the close must still find the box held. A reopen that catches the panel still fading out (the same node comes back) starts fresh whatever state it closed in: what was frozen comes off, the pin is dropped and measured again, and it is centered on the height it has; a later opening is a new node and is centered on its own first frame. The reset is keyed on the node being retained, not on it being frozen: a panel closed while idle is not frozen, and one that a touch had pinned off center (a change of height after the first touch grows at the bottom edge) came back there, with a baseline that matched what it showed, so no report corrected it (found downstream on a port of bunfire#416; measured in Chromium: typed in and grown to 233.3px from the top and 33.3px from the bottom, reopened at 233.3/33.3 on all 42 frames, now 133.3/133.3).
- **Measuring changes nothing the person can see.** The natural height is read with `max-height` lifted, which grows the scroll area to its content and clamps its `scrollTop` to 0 (measured in Chromium and WebKit: 300 before, 0 after, and restoring the cap does not bring it back). It is only measured when the height changed or the dialog is cut, so a report of a change of width only (a narrower window) does nothing, and every scrolled element inside the dialog gets its scroll position back after the measurement.
- **A dialog that does not change is left alone, at any fraction of a pixel.** Every comparison of positions in the slide (cut at the bottom edge, height changed, the target already where it is painted) is on the computed `top` and `height`, which are fractional, with a tolerance of half a pixel; `offsetTop` and `offsetHeight` round to whole pixels. Found downstream on a port of bunfire#416: at a 900px viewport an unchanged 865px dialog is centered at 17.5px, `offsetTop` read 18, `18 + 865` read as cut, and a slide that moved nothing started, settled on its 400ms timer and started again for as long as the dialog was open (measured in Chromium and WebKit: 116 of 121 frames with a transition and 70 style writes in two seconds; under reduced motion 480 style writes). A slide whose end is the painted height at the painted top is never started.
- **An untouched dialog always ends centered on the height it has, even when its baseline agrees with that height.** A baseline can be read after the pin and disagree with it: a body that changes height in its own mount effect (a list whose data is already cached, any `setState` on mount) commits after `<Modal>` measured the pin and before it read the baseline, because React flushes those effects before the render that the pin's own state update starts. The baseline then matched the new height, the first report saw no change, and the dialog stayed centered on the height it had for one render (found downstream on a port of bunfire#416; measured in Chromium and WebKit: a body grown by 200px stayed at 260.3px from the top and 60.3px from the bottom, one shrunk by 200px at 160.3/360.3, on every frame). So every report of an untouched dialog checks where it is painted against the center of its own height, not only its height against the baseline, and moves it when they disagree; every baseline is followed by a report (the first one after opening, or the one that observing again delivers), so that check sees each one. The center is computed against the height `dvh` resolves to, read from a fixed element `100dvh` tall that lives while the dialog is open, not against `innerHeight`: the pin and the max-height are CSS on `dvh`, and a center computed from another viewport height would disagree with where CSS put the dialog whenever the two differ by half a pixel, which this check would read as off center and slide again forever.
- **A change of viewport size** (`resize` on the window: a resized window, the browser's zoom, Safari's toolbar in full screen, a rotation) drops any slide and re-centers at once on the height the dialog has, synchronously, so the observer's next report does not read it as a change to slide.
- **`prefers-reduced-motion: reduce`** skips the slide: the dialog moves straight to the new center before the frame is painted. The node gets `transition: none` while that happens, because the global reduced-motion rule in `public/index.css` shortens transitions to 0.01ms instead of removing them, and `transition-property` defaults to `all`, so `top` would otherwise paint one frame at the old place.

### The states of a slide

Three review rounds in a row (bunfire#416) found a hole where two of these rules met: a press freezing a slide, the release letting it go, and the close freezing it for the exit. So the whole machine is here, every cell checked, and a change to `Modal.tsx` is checked against every cell, not only the one it is about.

A fourth round (bunfire#416, round 4) showed what the holes had in common: the geometry lived in two places, the observer's closure (a `painted` height, the frozen box, the pending release) and React state (the pin, `anchorHeight`), and every bug since round 2 was one of them read at a moment the other, or the DOM, had not caught up. Round 4 itself: a panel reopened while it faded out was measured before its dropped pin committed, at the old capped height, and slid from there (measured in both engines: 16px from the top and 65px from the bottom, growing downwards from 778.8px to 828px). Two rules close that class:

- **The DOM is the only source for anything painted.** No height or top that can be read is kept in a variable. What a change is compared against and what a slide starts from (the **baseline**) is read from the node; while a slide runs, its painted frame is the last post-paint sample.
- **A baseline is taken only after the commit that set the pin**: in a layout effect keyed on the pin and on a counter of openings (so every opening takes one, even when its pin did not change), or right after a handler's own `flushSync`, or in the observer's callback (after layout) when a change is accepted without moving the pin. Never in the same tick as a `setState` that has not committed.

States: **idle** (no inline values; "touched" or not), **sliding** (a transition is running, the node is unobserved), **held** (a slide frozen by a press: the pin is at the painted top, the height is inline, the node is unobserved; "releasing" once the pointer is up and the release waits for the next frame), **exiting** (closed: the effect is gone and the node is marked as retained; a panel closed in the middle of a slide or held is also frozen inline until the node unmounts).

| Event | idle | sliding | held | exiting |
| --- | --- | --- | --- | --- |
| open (the commit that opens it) | the pin is the first frame's height; the baseline is read after that commit (and after any commit a mount effect of the body adds), before the first report, which moves a dialog not centered on its own height | (cannot happen) | (cannot happen) | see "reopen" |
| a report (compared against the baseline and, untouched, against the center of its own height) | not touched, and the height changed or the dialog is not centered on it: slide from the baseline to the center (reduced motion: move there now, baseline read after that commit). Touched: the baseline becomes what the node shows now; the change happens at the bottom edge; cut there with room above, slide to the center, waiting for the frame after the pointer is up while one is pressed inside | unobserved; seen when it is observed again after the slide | unobserved; seen when it is observed again on the release | observer disconnected |
| a report of a change of width only | nothing, nothing measured (untouched, only when it is also centered on its height; otherwise as above) | unobserved | unobserved | observer disconnected |
| `pointerdown` inside | touched, pressed | frozen at the last painted frame (not the computed value of the moment), held; the baseline is read after the pin commits | pressed again; a pending release is skipped | listeners removed |
| `pointerdown` outside (the backdrop) | nothing | the slide goes on; nothing inside is under the pointer | nothing | listeners removed |
| `pointerup`, `pointercancel` | not pressed; a waiting bottom-edge slide runs on the next frame | nothing | releasing: the height is let go on the next frame | listeners removed |
| `click` | nothing | nothing | nothing: the release has not run yet, so a closing click finds the box held | nothing |

| unmount | gone with the node; the next opening is a new node, centered on its own first frame | gone | gone | gone |

Two details of the table were measured, not assumed. The release waits for the next frame because the `click` that follows a `pointerup`, and the close it makes (committed in a microtask), come before it; releasing in the `pointerup` let the height go before the close could freeze it, and a click on the X in the middle of a slide faded out at its natural height (round 3, both engines: frozen at 142px with 575.9px of height, and from the release on it faded out 603.4px tall). And a press is frozen at the last frame known to be painted (read in `requestAnimationFrame` and confirmed by a message posted from there, which arrives after the paint), because Chromium can deliver a `pointerdown` after the next frame's animations were updated: the computed value of that moment is one frame ahead of what was pressed on.

**The observer must not see its own writes.** Writing the observed node's height inside its own callback made the browser report "ResizeObserver loop completed with undelivered notifications" (seen in a real session). The node is `unobserve`d before its height is written and observed again after the inline values are removed; observing again delivers the size it has at that moment, so a change made during the slide is picked up then. It is never observed again from inside the callback (the reduced-motion path waits a frame): an observation added there is not deeper than the one being delivered, so the browser skips it and reports the same loop error.

The pin is dropped when the node unmounts, so the next opening is centered on its own first frame; a modal that never changes height is exactly as centered as before.

None of this replaces "Open when the content is known" under Async flows, which is still the better fix for a modal you own: a dialog that opens at its final height moves no edge at all. `biome-plugins/no-dialog-outside-modal.grit` refuses a Radix dialog imported anywhere in `src/client/` but the files `biome.jsonc` exempts (`Modal.tsx`, `DiscardDialog.tsx`, the mobile drawer in `Sidebar.tsx`), each with why it cannot change height while open, so a new dialog gets this behavior by being a `<Modal>`; `tests/lint/dialog-rule.test.ts` runs the rule through the real Biome.

`tests/client/components/Modal.test.tsx` covers every row of the table with stand-ins for layout (happy-dom has none). This repo has no Playwright layout suite, so what a browser paints was measured by hand when the behavior was ported, in Chromium and WebKit at 1280x844, sampling the box on every painted frame (a `MessageChannel` message posted from `requestAnimationFrame` arrives after that frame's paint): a growth of 200px goes from 273px above and below to 173px in 16 frames, each edge in one direction; a growth to near full height ends at 16px and 16px; after typing, a growth keeps the top at 273px; a growth to the bottom edge after typing slides to 16px and 16px; three resizes stay centered; reduced motion paints no frame in between; and a press, a click on the X, a click on the backdrop, a footer button pressed and released, a press dragged outside and Esc, each by real input in the middle of a slide, leave top and height unchanged on every frame until the release or the unmount, with the next opening centered. The flex centering this repo had before moved the same 200px growth from 273px to 173px in one frame, in both engines. When you change `Modal.tsx`, repeat that check, with `page.mouse` and the keyboard, never `HTMLElement.click()`, which dispatches no pointer events and so never reaches the code that freezes a slide.

## Centering: a layer that holds the box

`Content` here is a full-viewport layer (`fixed inset-0`) and the visible box is the `div` inside it, which holds `contentRef`. The layer exists for this repo's outside-click handling: Radix's own outside dismissal is switched off (`onPointerDownOutside` is prevented) and a pair of document `pointerdown`/`pointerup` listeners decides, from the box's geometry, whether a press and its release both landed outside it; a press over the box with a nested picker open is inside even when its target is the overlay. So the box, not `Content`, is what every geometry reads: the outside-click check, the slide, the bottom-edge check and the tests.

The layer does not center anything. The box is `absolute`, placed horizontally with `left-1/2 -translate-x-1/2`, and vertically by the slide above: `top-[50dvh] -translate-y-1/2` until its first frame is measured, `--modal-top` from then on. The layer carries only the fade, since Radix's `Presence` plays the exit while the `Content` node's own animation runs; the zoom is on the box, through `group-data-[state=…]`, with `origin-top`.

Do not put `flex items-center justify-center` back on the layer on the theory that flexbox centering "does not depend on the box's height" and so stops an async body from painting low and jumping. `(viewportHeight - boxHeight) / 2` depends on the height exactly as much as `translateY(-50%)` does: measured on the flex version this repo had, a box that grew by 200px moved its top edge from 273px to 173px in a single frame, in Chromium and WebKit, which is the jump the slide removes. bunfire measured the same equivalence (`top: 260` to `top: 150` in both schemes on every frame).

For the record on why the translate is safe here: Tailwind v4 emits translate utilities as the standalone CSS `translate` property, while `tw-animate-css` writes `transform`. They compose instead of fighting, which is why the zoom never disturbs the centering.

## Async flows (future guidance)

The template's two modals (HomePage playground and `SupportModal`) are sync; the patterns below aren't needed for them. They come from ~7 rounds of review on heavily-async modals in a downstream project and are worth reaching for once a modal starts fetching or mutating on the backend. Keep the list by your side when you add the first "modal that makes an API call" to your app.

- **Drop stale responses with a session token.** Bump a `sessionRef = useRef(0)` in `useOnModalOpen` (and inside any action that re-fetches). Async callbacks capture the current token; on return, bail if `sessionRef.current` changed. Prevents close+reopen races and payload switches from flashing wrong data or spawning child modals for the wrong entity.
- **Parent close invalidates nested state.** When a modal owns child modals (parent opens a nested one while open), return a cleanup from `useOnModalOpen` that bumps the session token and calls `child.close()`. Without this, child dialogs linger past the parent session.
- **Guard user-driven close while loading.** During an in-flight request, pass `busy={loading}` AND `disabled={loading}` on Cancel/Confirm/row triggers. The typical bug this catches: a stale `onSuccess` firing and closing a freshly reopened session. Never a no-op `onCloseRequest` for this: `unsavedChanges` takes precedence over it, so on a dirty form Esc, the overlay and the X open the discard prompt, and "Discard" closes the modal with the write still on its way (#1439). The lint rule `no-noop-close-request` refuses the idiom.
- **Confirm modals: close only on success.** Handlers for confirm-delete/detach/disable return `boolean`; the parent closes the confirm modal only on `true`. Failures stay on-screen so the user can retry without re-opening.
- **Skip resync effects when closing.** If the parent effect that writes into the modal's state runs during close (typical on a refetch-on-data-change pattern), guard it with `if (!isOpen) return`. Otherwise a late fetch can resurrect a modal mid-animation.
- **`useOnModalOpen` + `useEffect([payload.id])` together.** `useOnModalOpen` catches reopen transitions only. For modals that stay open across in-place payload swaps (`open(newPayload)` without closing first), pair it with a `useEffect` keyed on the payload's identity so state resets in both cases.
- **Force re-fetch on reopen by listing `modal.isOpen` in `fetchData` deps.** The instance-id / user-id driving `fetchData` stays the same across close+reopen, so a naive `useCallback([id])` won't re-run. Include `modal.isOpen` in the dep list (and in the effect that calls it) so the false→true transition re-fires the fetch. A separate `fetchCounter` ref bumped in `useOnModalOpen` works too, but double-fires when the id also changes in a separate render pass; prefer `modal.isOpen` alone.
- **Reset state synchronously with `useLayoutEffect`.** For state that would flash the previous session's content during the close→reopen paint window (e.g. `loading`, `products`, `error`), reset it from `useLayoutEffect` keyed on `isOpen` instead of `useEffect`. Also bump any `fetchSessionRef` in the same layout effect so in-flight requests from the prior session are invalidated before the new paint commits.
- **URL-driven auto-open is mount-only.** Effects that open a modal from a URL param (`?cart=1` → open acquire modal) should run once on mount (`[]` deps). Including the modal controller in deps re-runs on every open/close.
- **Check the `{ error }` branch from the typed client.** Elysia's typed client returns `{ data, error }` from mutations. Inside a modal's submit handler, inspect `error` explicitly, surface the API message, and do NOT close the modal on error.
- **Prefer titled modals.** Every modal in practice ended up with a title; `ariaLabel`-only flows needed shims and drifted visually. The template keeps `title?: string` optional for flexibility, but the default answer is "give it a title".
