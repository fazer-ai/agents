# Factual grounding

An output check of the guardrails (`guardrails.factualGrounding`). Before a reply goes out, a reviewer model compares it with what the agent's tools returned in that turn and with the recent conversation, and lists the claims the tool results do not support. Off by default.

Code: `src/modules/guardrails/grounding.ts` (what the reviewer reads, the prompt, the verdict), `src/modules/guardrails/grounding-gate.ts` (when it runs, the flow line, what each action leaves behind), the `reviewReply` hook in `src/graph/graph.ts`, and its two callers, `src/graph/runtime.ts` and `src/modules/playground/service.ts`.

## Settings

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Needs `guardrails.enabled` too. Independent of `output.enabled`: an operator can run grounding without moderation. |
| `sourceTools` | `[]` | Tool names whose results count as sources. With no source tool and no reference base, the check never runs. |
| `referenceKnowledgeBaseIds` | `[]` | Knowledge bases of the tenant (decimal ids, at most 20; a repeated id is stored once) whose READY documents the reviewer reads whole on every reviewed reply, whether or not the agent searched them (below). A write that names a base the tenant does not have is refused with 404 (`errors.knowledgeBaseNotFound`), on REST and on MCP alike; a base deleted after it was picked is simply not read. An export names the bases instead of their ids, and an import points at the destination's bases of those names, warning `groundingReferenceNotFound` for a name it has none of and `groundingReferenceAmbiguous` for a name two of its bases answer to (that name is skipped, not bound to one of them), and keeping at most 20. |
| `action` | `observe` | `observe`, `revise`, `template` or `handoff`. |
| `contextMessages` | `24` | Earlier messages of the thread the reviewer reads (0 to 40, `GUARDRAIL_RANGES.groundingContextMessages`, its own range: the input check's stays 0 to 20). 0 reads the turn alone: no conversation, no earlier source, no memory. A stored value is kept; only an agent that never set it reads the new default. |
| `reviseWithTools` | `true` | `revise` only. The rewrite may call the source tools that are read-only, and what it writes is reviewed once more (below). Off, the rewrite runs without tools and is not reviewed again. |
| `reviseMaxToolCalls` | `3` | Calls the rewrite may make, from 1 to the agent's `limits.maxToolCalls` (itself at most 50), since they come out of the same turn budget. The schema refuses a value outside 1 to 50, and the write boundary (REST and the MCP preview, `assertSettingsReviseToolCalls`) refuses a value above the agent's limit, read from the bag being written, when it differs from the one the agent runs with (the default 3 included, so a console save that writes the default back under a turn limit of 1 or 2 goes through). The reader clamps to 1 to 50. Lowering `limits.maxToolCalls` later does not refuse the save: at run time the rewrite's room is also clamped to what the turn has left. The console's hint reads the limit from the Behavior tab. |
| `provider`, `model`, `credentialRef`, `baseURL` | `null` | The reviewer's own chat model, an override of the guardrails chat model resolved by `resolveModelOverride` (`resolveGroundingReviewer` in `settings.ts`), the same rule the suggestion reviewer and the choice check follow against the agent's model. Nothing set is the guardrails model whole, key and endpoint included. A model or key needs a provider (refused as `override_without_provider` otherwise; the console pins the guardrails provider when one is picked while it inherits). On the guardrails provider and endpoint, a blank model or key inherits theirs; on another provider a key of its own is required (`credential_required`), except a keyless `openai-compatible` endpoint, which runs on no key; a reviewer inheriting a guardrails model that is itself a keyless `openai-compatible` endpoint runs keyless too. A reviewer that does not resolve is a failed review (`credential_not_found` when its key did not resolve, `model_unavailable` otherwise), never a clean one. The console draws these four fields with `ModelOverrideFields`, like every other model of its own (docs/ui.md). |

The console draws it in the Guardrails tab (section `gr-grounding`), the reference bases with the same selectable cards the Knowledge tab picks the agent's bases with (`KnowledgeBaseCards`); REST (`PATCH /v1/agents/:id`) and MCP (`agent_settings_set`) write it through the same schema, which refuses an action outside the four.

`generated` and `silent` are not offered. The reviewer has no tools, so a replacement it wrote would have to invent the fact it found missing, and silence leaves the customer unanswered on a false positive.

## When it runs

On every reply, with the check on and at least one source tool picked (with none picked there is nothing to judge a reply against, and the check stays off). A reply is reviewed whether or not a source returned something (a non-empty result that is not a tool error), in this turn or in an earlier turn that the reviewer's conversation window still shows (#1767). Two cases cost most when missed: a later answer, under the customer's pressure, repeats from memory what a tool returned turns ago and gets it wrong without calling the tool again; and an answer states an in-scope fact (a price, a date, a sector, what a ticket includes) having consulted nothing at all. Stating such a fact with no source is a violation, so a reply with no source in either place is reviewed too, with the reviewer told that nothing was consulted (below). "Thank you" answers are reviewed as well; that is the price of the coverage, and with no source the review is short. It runs on the text that would go out: the answer that ends the turn, or, when that is empty, the reply written beside an earlier call that the runtime recovers, only when it would recover it: not after a transfer or once something was delivered or queued (on a stalled turn too, where a revise has no model call left and reads as an empty rewrite). A revise takes that draft out of the thread. The playground does not recover such a reply, so there it is not reviewed either. Once per turn, on the reactive inbox turn and on the playground turn. Not after a transfer the turn completed: the model's text is dropped then, so there is nothing to review. Proactive follow-ups are not reviewed.

## Reference bases

An agent usually carries house rules (procedures, policies) that live in a knowledge base the operator keeps, and often in its prompt too. The reviewer never reads the agent's prompt, so without this a reply that repeats such a rule correctly is flagged as unsupported whenever the turn did not search the base. The agent's prompt is not the answer: a prompt used as a source would validate anything written in it. The reference bases are: the documents the operator curates as the source of those rules.

The documents are read once per turn, at the start of it, so an edit counts from the next turn on. Only READY documents (indexed) count. They travel whole, ordered by base id and document id, in a `<reference_sources>` block that closes the system message, after `GROUNDING_REFERENCE_PROMPT`, one `<reference_document base="…" title="…">` per document: the documents are sources whether or not the assistant consulted them. A review with a reference is a sourced review, so the no-source instruction is not sent; a reply that states something the reference does not support is still an unsupported claim, and one that states something different is a contradiction. With bases picked and no READY document in them, the review runs as it would with none (`referenceDocs: 0`).

Above 200,000 characters of reference documents (`GROUNDING_REFERENCE_MAX`) the review does not run and the flow line says `reference_too_large`, the same failure as `sources_too_large`: the block is sent whole on every review, so a base that outgrows it is a configuration to fix, not to cut. The size is measured in the database before any document is read, so a base past the ceiling costs the turn one count, not its bodies.

## What the reviewer reads

One system message with the generic policy (`GROUNDING_SYSTEM_PROMPT`), closed by the reference when there is one (above), and one user message with `<now>` and three fenced blocks. Nothing of the turn rides in the system message, so it is the same bytes on every review of the agent while the bases do not change. When no call in `<tool_results>` is a source, the system message also carries `GROUNDING_NO_SOURCE_PROMPT`: no source was consulted for this reply, so every in-scope fact it states is an unsupported claim, while what was out of scope stays out (how the service works in general, greetings, offers of help, asking the customer for information, saying the information is not available, and what the customer said or showed). It rides at system level because whether a source exists is the gate's fact, not text a customer or a tool could write; the sourced policy is not touched.

The policy judges four violations: an unsupported claim, a contradiction, a false absence, and a customer detail repeated wrong (a phone number, e-mail or order number the customer gave, compared character by character with the conversation, with or without sources). It does not count as violations: applying a rule a source states to the customer's case, once every condition the source attaches holds; saying the information does not state something when no source states it, since the silence of the sources is what supports it; questions to the customer; general guidance about how the platform works, except availability and eligibility (a quantity, buying for a given person), which stay in scope; and what the assistant does in the conversation and the state of the customer's request with the team, while the outcome of that request stays in scope. The examples in the prompt are generic on purpose: they hold for any tenant.

- `<now>`: the instant the turn's prompt was rendered, as weekday, date and time in the agent's timezone (`groundingNow`), the same clock the agent's `{{data_atual}}` reads, simulated time included in the playground. The policy tells the reviewer that "today", "tomorrow" or "that already started", computed from it, is arithmetic.
- `<conversation_context>`: the last `contextMessages` messages before the turn, each labeled customer, assistant or attendant. The window is the thread the agent reads, so it crosses the attendance divider: a customer who comes back continues the same conversation, and until compaction the earlier attendance is still in the agent's thread. The divider's own text does not travel, the customer message it carries does. When the thread opens with the memory head (the summaries of the contact's closed attendances, docs/graph.md), the block opens with a `memory:` line carrying it, at most its last 4,000 characters (`GROUNDING_MEMORY_MAX`), and the policy tells the reviewer it is what the customer said, never a source. A customer message carries what vision read from an image they sent, so a reply that repeats what a customer's print shows counts as grounded. Each message is bounded at 8,000 characters.
- `<tool_results>`: first the source calls of the earlier turns in the window, then every tool call of this turn (empty when the turn called nothing and the window holds no source), each with its arguments and its whole result, sources marked `source="yes"`. An earlier call carries `turn="earlier" turns_back="N"` (N customer messages ago), and the policy tells the reviewer it is still a source. Results are never cut. A call with the same tool, the same arguments (in any key order) and the same result as a later call in the block, in an earlier turn or in this one, travels once: the latest, with its own marking (`withoutRepeatedCalls`). A follow-up about the same event usually asks the catalog again, and the reviewer then reads that result once, as this turn's call, instead of once per turn; two identical calls in the same turn travel once too. The same arguments with a changed result (the catalog moved between turns), other arguments, or another tool are evidence, and all of them travel. Above 400,000 characters of results in the block, counted after a repeated call is dropped, the review does not run and the flow line says `sources_too_large`.

  The earlier calls come from the agent's own thread (the checkpoint), where each `ToolMessage` is kept as the model read it, never from the flow log, which cuts values at 2,000 characters. They come from the same history the agent's model was sent, so with the history ceiling (`limits.maxHistoryTokens`) on, a result the model no longer saw is not a source either. The window is wider than the one `<conversation_context>` shows: the last 60 messages of the thread (`GROUNDING_SOURCE_WINDOW`, or `contextMessages` if larger), across the attendance divider like the conversation, and none when `contextMessages` is 0. A turn counts when any of its messages is in it, so the calls behind the oldest reply in it come with it. A reply repeats what a tool returned 15 or 30 messages ago far more often than it quotes the conversation that far back, so the sources reach further than the conversation shown and the review does not pay for the whole conversation to reach them; the 400,000 ceiling bounds the total. Only earlier SOURCE calls travel; an earlier call to any other tool is no ground for this reply. A compacted attendance keeps no `ToolMessage`, so its sources are gone with it.
- `<reply>`: the reply under review.

The agent's system prompt is never sent. Everything customer-written or tool-returned rides at user level, with any text that could close a fence removed, as the other checks do.

The verdict is `{violated, claims: [{claim, type, evidence}], rationale}`, asked with the same constrained-output modes as the moderation verdict and read by the same rule: exactly one verdict, or the review counts as failed.

## Actions

- `observe`: the reply goes out as written. The flow line and the trace carry the claims.
- `revise`: the graph asks the agent's model once more, with a late system note (`reviseNote`) quoting the draft and listing the claims. The draft never enters the thread; the rewrite does, with any calls it made. A rewrite that comes back empty sends `output.templateMessage` instead (flow line `revision_empty`), never the refused draft.

  With `reviseWithTools` on (the default), the note also names the tools the rewrite may call, and the model is bound to those alone: the source tools the agent is granted that are read-only (`isReadOnlyTool`: an HTTP GET with no ack message and no appointment declaration, a code tool, `search_knowledge`, a utility native) and run on the server. Any other source is never offered, even when it was picked as a source: a native action, `handoff_to_human`, an HTTP tool with another method, a GET whose ack posts a message to the customer or whose declared appointment is registered from its response, and an MCP or integration tool, which an observation reads as a read only because nothing says what it does (it may send an e-mail or create a charge). The tool node runs only the calls the rewrite's round admitted (`src/graph/revision-calls.ts`): a call to any other name, or past `reviseMaxToolCalls`, is answered with a refusal and does not execute. The cap counts calls asked for, so a model that keeps asking for a refused tool still ends; once it is spent the model is asked without tools, and a call it writes anyway is dropped. The calls run through the same tool node, fences and flow lines as the turn's other calls, and count toward the turn's tool budget. What the rewrite writes is then reviewed once, with its calls among this turn's sources. Clean, it is delivered; still flagged, `output.templateMessage` goes out and a private note is posted, as with `template`. There is no third generation.

  The default is on because a rewrite with no tool to consult can only drop the claim or say the information is missing, and that is the wrong correction exactly when the agent erred by not consulting the source it had. Off keeps that older behavior: one tool-less generation, not reviewed again.
- `template`: the reply is replaced with `output.templateMessage`, and a private note is posted.
- `handoff`: the reply is not sent, `output.handoffMessage` is, and the conversation goes to the team, through the same path as an output-moderation hand-over.

`template` and `handoff` cannot act from inside the graph, so the gate keeps the decision (`pending()`) and the runtime's output step applies it in place of the moderation screening. A transfer the turn completed wins over it, with its closing line or in silence: the conversation is a person's now. The text reviewed is the customer-facing one, so an answer that is only the silence token is not reviewed.

A review that fails (no key, an unusable model, an error, an unreadable answer, results or reference past their ceiling) lets the reply through with a warn line, unless `guardrails.onFailure` is `hold` and the action is not `observe`, in which case the conversation is handed over.

## Logs

One `guardrail` line per review, clean or flagged, `check: "factual_grounding"`, so the rate of the check is readable from the log in any mode, `observe` included. Every line carries `verdict` (`clean` or `violated`), `claimCount`, whether any source result was in front of the reviewer (`sourced`, `true` or `false`, so the two groups are measured apart), the source tool names (`sources`, empty when unsourced), the size of the results the reviewer read (`resultChars`, a repeated call counted once), how many of the sources it read came from earlier turns (`earlierSources`, the earlier calls sent, not the copies dropped because a later call repeated them), how many reference documents were sent and their characters (`referenceDocs`, `referenceChars`, 0 with no reference), the latency (`latencyMs`) and the reviewer's tokens (`inputTokens`, of them `cachedInputTokens` read from the provider's cache, and `outputTokens`). A clean line is `info` with no `action`, the same contract as the external check's `allow` line: it is not a trip, so it is not an observed trip either and does not move the alert selectors. A flagged line is `warn` and adds the action and `categories: ["factual_grounding"]`. The claims and their evidence are model text quoting the reply and the tool results, so they are on the line only with `observability.logToolValues` on (new agents have it on). A review that could not run writes its failure line instead (above), and the Logs page shows each review with a headline of its own. Reading the sources the reviewer judged, days later, depends on keeping the turn's full tool results (#1761).

A rewrite with `reviseWithTools` on writes one more line, `outcome: "revision"`, in place of a second review line: the calls it ran (`toolCalls`, and their names in `tools`), the calls it asked for and was refused (`refused`), its own generations' tokens (`revisionInputTokens`, `revisionOutputTokens`), and the second review's `verdict` (`clean`, `violated`, or `empty` when the rewrite wrote nothing and was not reviewed), with that review's size, latency and tokens as on a first review. A `violated` revision line is `warn` and carries `action: "template"`, and no `categories`: the first review already counted the trip. The calls themselves are ordinary `tool` lines of the turn. A second review that fails writes the failure line with `pass: "revision"`, and the rewrite goes out unless `onFailure` holds it. Reading the sources the reviewer judged, days later, depends on keeping the turn's full tool results (#1761).

## Cost

One reviewer call per reviewed turn, billed on its own ledger node, `guardrail_grounding`, under the reviewer's model, so its cost reads apart from the moderation calls on `guardrail` in the cost dashboard and in each turn's usage. It counts as part of the agent's turn and is covered by the turn's spend gate, like `guardrail`. Plus one agent generation for each `revise`; with `reviseWithTools` on, one generation per round of the rewrite (a round that calls sources, then the one that writes), the source calls themselves, and the second review on `guardrail_grounding`. The rewrite's generations are the agent's, billed on the agent's node like any other generation of the turn. Measured with the battery: about 8,100 input tokens at the median (about 11,400 at most) and 290 to 350 output tokens per review. The input is dominated by the tool results. A review with no source sends only the policy, the conversation window and the reply: measured with 10 synthetic unsourced cases (half stating an invented in-scope fact, half asking or explaining a procedure), about 1,700 input and 105 output tokens per review on Sonnet 5.5, and about 880 input and 105 output on gpt-5.6-luna, a fifth of a sourced review; both caught every invented fact and flagged none of the others. A source asked again on every follow-up is paid once, since a repeated call travels once (above): measured on 14/11/2026 with gpt-5.6-luna on a synthetic four-turn conversation about one event, the catalog (26,076 characters) asked with the same arguments and result in turns 1, 2 and 4, the review of turn 4 read 30,719 input tokens when every copy travelled and 11,345 with one, against 11,248 for turn 1; with a reference base the system message kept being read from the cache on turns 2 to 4 (5,324 tokens) as before. A cascade of a cheap reviewer confirmed by a stronger one, and prompt caching of the sources, are tracked in #1763.

The system message, policy and reference, is the same bytes on every review of the agent while the bases do not change, and that is what the providers cache. On OpenAI, gpt-5.6-luna reuses a whole identical system message and nothing past it: measured on 13/11/2026 with a synthetic base of 12 documents (about 11,600 input tokens), three reviews with different conversations, replies and minutes read 0, 11,540 and 11,540 tokens from the cache; with the reference at the start of the user message, as #1776 first shipped it, the same three read 0, 0 and 0, since the turn followed it in the same message. On Anthropic (and a Claude model behind OpenRouter) the mark `src/graph/prompt-cache.ts` puts on the last system block covers the policy and the reference together.
