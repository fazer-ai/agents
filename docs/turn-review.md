# Turn review

A guardrails check of the agent's own steps (`guardrails.turnReview`). Before a write tool call runs, and before the final reply is sent, the guardrails chat model judges that one step against the agent's instructions and `guardrails.customPolicy`. Under `revise` a flagged step goes back to the agent with the reviewer's reason, so it can fix what it did inside the same turn. Off by default.

It exists because the output checks judge the reply after the turn is over, when every call has already run. What goes wrong in a turn is often an action: a handoff before the question the instructions require, a handoff of a question a search of the same turn answered, a reply that promises a transfer no call made, an answer to a subject the instructions send to a person. `prompt_adherence` sees these but can only replace the reply. [Factual grounding](factual-grounding.md) has the same shape for one question (is the claim backed by a source?), and this check follows it.

Code: `src/modules/guardrails/turn-review.ts` (what the reviewer reads, the prompt, the gate), `src/graph/reviewed-calls.ts` (the veto at the tool boundary), the `reviewCall` and `reviewTurnReply` hooks in `src/graph/graph.ts`, and their two callers, `src/graph/runtime.ts` and `src/modules/playground/service.ts`.

## Settings

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Needs `guardrails.enabled` too. Independent of `output.enabled`. |
| `action` | `observe` | `observe` (record the verdict, the step goes on) or `revise` (send the step back). |
| `maxAttempts` | `1` | `revise` only. Steps sent back per turn, 1 to 3 (`GUARDRAIL_RANGES.turnReviewMaxAttempts`). |
| `fallback` | `handoff` | `revise` only. How the turn ends once the attempts are spent and a step is flagged again (that step does not happen): `handoff` (`output.handoffMessage` and a transfer), `template` (`output.templateMessage`) or `silent` (nothing is sent). |

The reviewer has no model of its own: it is the guardrails chat model with its key (`turnReviewer` in `prepare.ts`), whichever classifier screens, under the screening gate's rule: with no key resolved no model is built, and the review writes `credential_not_found`. The configuration health panel checks the reviewer's chat key on its own when Decisions screens (issue `turnReview`), since a good classification key says nothing about it. The console draws the block in the Guardrails tab (section `gr-turn-review`), keeps the chat model fields in reach when screening uses Decisions (one predicate, `guardrailsChatModelShown`, decides both where they are drawn and where a refusal of their key points), and edits the fallback's message (the same `output.templateMessage` or `output.handoffMessage` the Output section edits) in the block itself. A reviewer with a key makes the playground's "Run guardrails" toggle usable (`playgroundGuardrailsUsable`), so a test turn can skip it. REST (`PATCH /v1/agents/:id`) and MCP (`agent_settings_set`) write it through the same schema.

The block is its own and not a new value of `output.action`: every reader of `GuardrailAction` keeps its meaning, and `observe` lets an operator measure the rate on real traffic before letting the check act, as factual grounding does.

## When a step is reviewed

- **A write call**, in the graph's `tools` node, after the contradicted-handoff veto and before `ToolNode` runs. A write is a call to a tool of the set that is not read-only (`isReadOnlyTool`, `src/graph/tools/reads.ts`): the native actions, `handoff_to_human`, `skip_reply`, an HTTP tool with a method other than GET, and every MCP or integration tool, since nothing says those only read (`isReadTool` marks them for the observer, which is a different question). Read-only tools (an HTTP GET, an effect-free tool, a utility native) are never reviewed. Each write of a step is reviewed in the order the model wrote it. A call that already has an answer in the thread is left alone, and a factual-grounding revision round, which runs only the sources it admitted, is not reviewed. The reviews are awaited model calls, so the tools node reads again whether the turn is still wanted (the called-off veto) before anything runs.
- **The final reply**, in the agent node, after the filler cleanup and before the factual-grounding review. Only a turn that answers somebody: no reply channel, a silent turn, or an answer with tool calls is not a candidate. When the final text is empty, the reply under review is the one written beside an earlier call that the runtime would recover (`replyWrittenThisTurn`), and a flagged one leaves the thread before the redo. Every review of the reply, the factual-grounding one included, reads the thread as delivery will read it, with the drafts taken out so far, so an older draft a blank redo uncovers is reviewed before the runtime can recover it. On the stalled exit, where no model call is left, that recovered reply is reviewed with no redo (`canRedo: false`): a flagged one meets `fallback` at once and its draft leaves the thread.

Every path that leaves a reply for the runtime reaches the review exactly once with its final text, through one helper in the agent node (`reviewHeadedOut`):

| Path | Reviewed | Redo |
|---|---|---|
| The final answer | yes | yes |
| The silence retry's answer | yes, after the retry | yes |
| A redo the review asked for | yes, again | yes, while attempts last |
| A blank redo | gets the turn's one silence retry first, built from the redo's request (its note kept, the flagged drafts out), then its answer is reviewed | yes |
| The draft recovered beside an earlier call | yes, on the thread as delivery reads it | yes |
| The recovered draft on the stalled exit | yes | no: a flagged one meets `fallback` |
| A factual-grounding rewrite (asked on the thread as delivery reads it, flagged drafts out) | yes, before grounding reviews it again | no: a flagged one meets `fallback`, and grounding skips its own review |
| The fallback message | no: it is the operator's text | |

The reactive turn and the playground pass the hooks. A proactive turn (follow-up, re-engagement) does not, so it keeps its behavior. Once the turn completed a transfer, its reply is no longer reviewed (nobody reads it), but a write call still is: the graph goes on, and the ownership fence admits a call once this very turn handed the conversation over. Ownership is read again after a reply's review flags it and before the redo, and a turn lost meanwhile is called off with nothing generated: the refused recovered draft is taken out first, and the empty terminator carries the `called_off` marker that `turnWasCalledOff` reads (`calledOffTerminator`), so an owner back by delivery cannot recover the refused text. A review that halts (held, or a call flagged past the attempts) refuses the whole batch on the spot, with no further review and one ownership read: a turn lost by then is called off, so a stale turn applies no fallback, and otherwise the batch is held. Otherwise it is read again between two reviews of a batch, and the first read that finds the turn lost refuses the whole batch as called off, whatever a later read says, and once more after the batch when a review ran in it, since a batch of reads awaited nothing.

## What the reviewer reads

One system message with the policy (`TURN_REVIEW_SYSTEM_PROMPT`), the instructions the graph gave the model for that step fenced in `<agent_instructions>` (its system prompt, MCP server instructions included, the spoken-reply notice of that round, the tool-call limit's instruction when the limit took the tools away, and the turn's standing notices, such as a document waiting on approval, captured on every model call and handed to both reviews of the step as `instructions`; the agent's stored prompt when absent), each write tool the graph binds as the model is given it, built only when a review hook is passed (`boundToolDescription`, read from the bound schema with `convertToOpenAITool`, or the description alone when the schema does not convert, as `buildToolTraceMetadata` does: the description, the operator's note and per-turn context in it, and the description of each argument) fenced in `<tool_instructions>` (a description past its clip marked `truncated="true"` with its whole length, and the reviewer told that rules past the cut are unknown, to neither flag nor clear a step on them), and each read-only tool the same way in its own `<read_tool_instructions>` block (never reviewed, at the tool node, but its notes are rules), each entry clipped to 4,000 characters, since what the operator wrote on a tool reaches the agent there and not in the prompt, so a tool left out of the toolset is not described, and the additional policy when there is one (under the decisions classifier, written as a yes/no question whose yes is a violation, and handed to the reviewer as such). One user message with `<now>`, the last 24 messages of the conversation (`<conversation_context>`, the same window as factual grounding, each message an element whose `role` attribute names the writer, plus the conversation coming back from a person as a `role="system"` message, a recorded fact that no text inside a message can forge, so a rule that hangs on an earlier transfer is not read as still in force), the calls with their results (`<tool_results>`, each result clipped to 8,000 characters, a clipped one marked `truncated="true"` with its whole length in `chars`, so the reviewer concludes no absence from the part shown, the same in the earlier calls' block), the calls of earlier turns still in that window with their results (`<earlier_tool_calls>`, the latest 12, each result clipped to 600 characters), the customer's messages in this attendance, whole and escaped, the most recent last (`<customer_messages>`, `customerTurn`: every customer message of the open attendance, `selectClosedPrefix`, the cut the memory and the choice check make, back to a new conversation's divider marker at most on a thread from before stamps, never its sentence, which a customer can type, the platform's notes, a person's words and a marked nudge left out, and a human message that past every marker still carries the data fence (a nudge from before the marker, or a customer who typed the token) kept and marked `origin="unverified"`, which the reviewer is told never counts as the customer authorizing a step (a write, or sharing what needs their consent) while what it says against an action (a consent withdrawn, a request not to do something) does, since failing closed on it would let a customer switch the review off by typing the token, with no guess about which reply reached the customer, read for the reply's review from the thread before the history ceiling trims it, as the call reviews read it), since the conversation clips each message at 8,000 characters and leaves some out, so a consent withdrawn at the end of a long message still reaches the reviewer. When together they pass 100,000 characters (`CUSTOMER_TURN_MAX`) the review is unavailable (`analysis_failed`, under `onFailure`), never clean, since judging without one of them is worse than failing closed, never clean, the summary of earlier attendances when the thread carries one (`<agent_memory>`, `groundingMemory`, bounded and escaped like every block, where a call answered by a refusal is not listed as a tool used, and text written beside it is kept with a line saying that call did not run (`não executou`), since the runtime may have recovered and sent that text, as `renderTranscript` pairs each call with its result), which records actions whose calls were compacted away, so a reply that reports an action already done (yesterday's booking) is not read as a promise no call kept, and the step (`<proposed_step>`): the call with its arguments, or the reply with the names of the tools the turn called and, when the tool-call limit left the round fewer tools than the toolset, the ones it could call (and the limit's instruction, only for the text that round or its redo wrote, both bound the same, never a draft recovered from an earlier round), so a reply is never flagged for a call the agent could not make. A call is shown with the writes of the same step already admitted, listed as not yet run, so two bookings in one batch are judged together. Angle brackets in the data of every block are escaped as entities (`&lt;`, `&gt;`), so no text, however nested, can open or close a tag. The reason and the refused draft fed back to the model are escaped the same way.

The verdict is the shared guardrail JSON (`VERDICT_SCHEMA`), and the rationale is one sentence addressed to the agent, in the conversation's language, saying what to do instead. The policy flags only a step that does what the instructions forbid or skips what they require in that situation. Style, tone, wording and anything left to the agent's judgment are not violations, and the prompt says to not flag when in doubt.

## Actions

- `observe`: the step goes on as written. The flow line and the trace carry the verdict.
- `revise`, a flagged call: the call does not run. A `ToolMessage` marked `turn_review_veto` (`turnReviewVetoToolResult`) answers it with a note (`turnReviewNote`, Portuguese like the other agent-facing notes) saying the call was not executed and why, and the model continues the turn. A read in the same step still runs. The marker keeps the vetoed call out of the side-effect accounting of a superseded reply (`turnActedBeforeItsReply`, `actedToolNames` in `refused-turn.ts`), by call id, so a sibling write that ran still counts.
- `revise`, a flagged reply: the draft never reaches the thread. The graph asks the model again, bound to the whole toolset, with a fixed instruction as a late system message (`TURN_REVIEW_REDO_INSTRUCTION`) and, after the history in a message of its own, the reviewer's reason and the refused draft fenced as data (`<parecer_do_revisor>`, `<rascunho_recusado>`, `turnReviewFeedback`): the reason is model text that can quote the customer or a tool result, so it never goes into a system message. With the whole toolset, a reply that promised a transfer can now make the call. A vetoed call's result fences the reason the same way. A call in the new answer goes to the tools node and is reviewed there. A new reply is reviewed again.

Each step sent back spends one attempt. Once they are spent, a step still flagged does not happen, and the review stops for the rest of the turn. A call is refused with its whole batch, each call answered with the held marker (`turnReviewHeldToolResult`, read as not run), and the round ends the graph, `handoff_to_human` included, so the model never transfers on a flagged call. A reply is not sent. Either way the turn ends on `fallback`, applied by the caller's output step (`pending()`) exactly as an output trip's action is, ahead of the factual-grounding decision and in place of the moderation screening: `template` sends `output.templateMessage`, `silent` suppresses the reply, `handoff` sends `output.handoffMessage` and transfers once, through the output guardrail's own hand-over. Delivery, a partial send, the thread's record of what the customer read and a takeover all follow that path, with nothing of the turn review's own after the graph. Once that decision is pending, the factual-grounding review of the reply is skipped, since nobody would read its rewrite. After a transfer this turn completed, the closing line stands: it was reviewed with its `handoff_to_human` and approved, and the fallback replaces only a step the review refused, so a later write still flagged past the attempts is refused and ends the turn with no second transfer.

Every reader that decides something from a call honors these markers through one pairing (`pairedResults` and `callsRefusedByReview` in `src/graph/markers.ts`): a `skip_reply` the review refused is no declared silence (`calledSkipThisTurn`, and `replyWrittenThisTurn` still recovers the text beside it), a refused call is not an act (`turnActedBeforeItsReply`, `actedToolNames`), and it is no act for either reviewer: `groundingToolCalls` (which also pairs a completed call with no id in its batch) keeps it with its refusal as the result, marked `ran="no"` and never a source (a refusal before running that another boundary wrote carries the same `set_aside` marker through `markedSetAside`: a precondition of `guardedTool` (a call envelope with no id included, answered with an empty one), `ToolNode`'s answer to a name the bound toolset lacks (checked against the toolset, never by the answer's text), arguments the schema rejects, recognized by the typed refusal (`isSchemaRefusal`) where it is thrown, before any handler runs, and an MCP tool's arguments its adapter refused before sending (`isMcpArgumentRefusal`). A server's failure and a response that fails validation stay ambiguous. Any other error result is marked `status="error"`, this turn's and an earlier one alike, and the reviewer reads it as a call whose running is unknown, judged by what its result states, since only `ran="no"` proves a call did not run), so a reply that says an action was done again over an earlier call meets the proof that this turn's one did not run. Results are taken one by one from their batch in call order, by id or, with no id, by name, so two calls repeating an id each get their own. A held review on a grounding rewrite also stops grounding from reviewing that rewrite again.

The held refusals are errors (`status: "error"`) like the veto, so a refused read never reads as a source that answered. Vetoes and holds on a call a provider sent with no id are matched by name inside their batch. Answers set aside for different reasons are put back by id and name, so a repeated id never hands a call another call's answer. The calls the graph answers without running for reasons of its own, a handoff beside a close and a call a grounding rewrite may not make, carry a `set_aside` marker and read as not run the same way.

A review that fails (no key, an unusable model, an error, an unreadable answer) lets the step through with a warn line, unless `guardrails.onFailure` is `hold` and the action is not `observe`. Then the turn stops reviewing, the tools node refuses every call of that step and ends the round (`halted()`), and the conversation is handed over before any write runs. The refusals carry their own marker (`turn_review_held`), never `called_off`: a called-off turn exits before the handover (`turnWasCalledOff`), and a held one must reach it.

The review's private note on the conversation (a held step, a fallback past the attempts), and its line in the turn's error note, wait for delivery: the inbox turn posts it only once the decision passes the write fence the fallback's own delivery passes (`writeCalledOff`), so a turn that lost the conversation, or whose completed transfer came first, leaves neither, and the verdict stays in the flow log either way.

## Logs

One `guardrail` line per review, `check: "turn_review"`, with `step` (`call` or `reply`), `tool` on a call, `verdict` (`clean` or `violated`), `latencyMs`, `inputTokens` and `outputTokens`. A flagged step is `warn` and carries `action`, and under `revise` `outcome` (`revised` with the `attempt` number, or `exhausted` with the fallback as `action`). The rationale is logged only with `logToolValues` on (scrubbed, 500 characters), otherwise only its length (`rationaleChars`). A failed review writes `outcome` (`credential_not_found`, `model_unavailable`, `analysis_failed`) with `unchecked: true`, or `held: true` under `hold`. The playground reads a reply a fallback emptied as suppressed by the same verdict rule live and in a reopened session (`suppressedByGuardrail`). A call the review could not judge reads as a call the review did not block (never as a reply let through), or as one that did not run when held, on the Logs page and in the playground. The playground trace shows each review as a guardrail row, named by its step and tool, a call's row right after the call it judged (paired by the call's id, `callId`, and its tool name, in order, and by the id alone only when the verdict names no tool or no other call carries that id, and for a call with no id by its place among the turn's calls, `callOrdinal`), a reply's row, and a factual-grounding rewrite's `revised` row, after the results of the turn's last call before the draft (`afterCallId`, or `afterCalls`, the count of the turn's calls, when that call has no id, and 0 ahead of every call) and before a call a redo made, a redo's row with the reviewer's reason, live and in a reopened session, and the Logs page names an observed call or reply and says only that the review did not block it: running and delivery come later and have their own lines.

## Cost

One reviewer call per reviewed step, billed on its own ledger node, `guardrail_turn_review`, under the guardrails model, and covered by the turn's spend gate. A turn with two writes and a reply pays three calls. Plus one agent generation for each step sent back. The system message is the same bytes on every review of the agent while its prompt does not change, so providers that cache a prefix read it from the cache.
