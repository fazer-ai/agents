# UI — screen map & conventions

The operator console is a React 19 SPA (`src/client/`) projecting over the REST v1 surface (one of the three transports). Routing is `BrowserRouter` with the `serve.routes` carve-out (see [`routing.md`](routing.md)). All screens follow the bunfire invariants: `<PageContainer>` per page, Eden-derived types (`Awaited<ReturnType<typeof api...>>`, never hand-declared), `t()` for every user-facing string, theme via CSS vars, `<Modal>` render-always.

## Navigation (`src/client/lib/navigation.tsx`)

`Dashboard` (`/`, admin) · `Conversations` (`/conversations`) · `Agents` (`/agents`, admin) · `Building blocks` (`/resources`, admin) · `Channels` (`/channels`, admin) · `Approvals` (`/approvals`, admin) · `Audit` (`/audit`, admin) · `Admin` (`/admin`, admin) · `Settings` (`/settings`). `filterNavItems` hides admin items for `AGENT`.

## Screens

- **Dashboard** (`pages/DashboardPage.tsx`). Automation funnel KPIs (Involvement / Resolution / Automation — Resolution counts only conversations the AGENT closed via `resolve_conversation`, read from the recorded `Conversation.resolvedBy` rather than inferred from status + assignee, with conversations resolved before the instance started recording reported separately under the funnel) with an absolute/% toggle, a funnel-bar card, a daily usage chart (calls/tokens toggle, range 7d/30d/90d/all), LLM cost summary + cost-by-model from Langfuse (`/metrics/costs`). Consumes `/metrics`, `/metrics/kpis`, `/metrics/timeseries`, `/metrics/costs` (+ `/agents` for id→name). Charts are dependency-free (CSS bars), CSP-safe. Cost comes from Langfuse (which has an up-to-date price table); tokens/calls stay local in `LlmUsage` for KPI calculations.
- **Conversations** (`pages/ConversationsPage.tsx` + `ConversationDetailPage.tsx`). List with status filter + live merge via `useTenantEvents` (known row merges in place + re-sorts; unknown id refetches; refetch-on-mount is the disconnect safety net). Detail = message thread (incoming/outgoing/private-note bubbles) + reply composer (private-note toggle) + ops: handoff, return-to-AI, resolve, status select. All ops go through the Tier 3 REST and reconcile via the realtime channel. The thread is fetched live from Chatwoot (no message mirror), so `getConversationDetail` **degrades gracefully**: a slow/unreachable Chatwoot returns the metadata shell with `messagesUnavailable: true` (a shorter interactive `getMessages` timeout, fail-fast) and the UI shows a retry instead of a hard error. **Live agent status**: `onAgentActivity` (same channel) drives a chat-style typing bubble in the detail (`Pensando…` / `Transferindo para um humano…` / `Consultando a base de conhecimento…`, mapped from `stage`+`tool` via a static-key switch so the i18n extractor sees the keys) and a per-row "working" dot in the list. Both clear on the `finished` phase, with a ~30s client-side TTL as the safety net for an event lost to a socket gap.
- **Agents** (`pages/AgentsPage.tsx` → `pages/agents/AgentEditorPage.tsx`). List → create (name only) → editor. The **editor uses progressive disclosure**: tabs General (name/prompt/enabled), Model (provider/model/credential/temperature/baseURL → `modelConfig`), Tools, Knowledge, Behavior (business-hours + follow-up selectors + transfer-with-summary), A/B. Clone + delete in the header.
  - **Tool selection** (`ToolGrantsEditor.tsx` + `KnowledgeGrantsEditor.tsx`) edit ONE shared `grants` working set and PUT the whole set (replace-the-set). `ToolGrantsEditor` owns NATIVE/HTTP/MCP/INTEGRATION and preserves the RAG grant; `KnowledgeGrantsEditor` owns RAG and preserves the rest. **NATIVE semantics**: no NATIVE grant (or empty allowlist) = all native tools; the editor's "restrict" toggle sends an explicit subset. **RAG**: enabling sends the rag tool names + selected KB ids; empty = no RAG (fail-closed). MCP exposes a per-server discover→allowlist; INTEGRATION shows per-toolpack tool checkboxes.
- **Building blocks** (`pages/resources/ResourcesPage.tsx`). Tabbed pools the editor draws from: Tools (HTTP `ToolDefinition`), MCP servers (+ discover), Knowledge bases (+ ingest text, view chunks), Hours, Follow-ups, Integrations (catalog → instance, inbound route-token shown once), **Vault** (mask-after-save — values are write-only, list shows names + "set" only, plus a usage/references view).
- **Channels** (`pages/ChannelsPage.tsx`). Chatwoot instances (connect with admin token, provision the Agent Bot, delete) + the load-bearing **inbox→agent binding** (a select per inbox). Tokens are write-only; the DTO exposes only presence flags.
- **Audit** (`pages/AuditPage.tsx`). The trail, newest first, over `GET /v1/audit`: filters in the URL, keyset pagination over a cursor stack, one expandable card per row. The action filter is a **picker** over `AUDIT_ACTIONS`, not a text box, and the list is kept honest by the TYPE (`AuditEntry.action` is `AuditAction`, so an action absent from it does not compile) plus a producer sweep for the direction no type can check — an entry whose producer was deleted, which is a value that can never match. Each row carries a shortcut that filters to its own action. The period is a **list of windows** (today, yesterday, this/last week, month and year, the last 30 days) with two date inputs kept for `custom`; the arithmetic lives in `client/lib/auditPeriod.ts`, is pure, and takes the day as an argument, because the suite runs at UTC where a preset that read its own clock could not be told apart from a broken one. A preset is not derivable from its bounds — `custom` names every window some other preset also names, and on a Monday `this-week` is `today` — so the mode travels beside the bounds in the URL as a HINT: honoured only while its own arithmetic still yields those bounds, which is what keeps `period=today` from claiming yesterday's dates tomorrow. A timer at local midnight is what lets that correction run on a page nobody is touching. What a draft window may commit depends on what is applied: a pair on screen commits only as a usable pair (a date input reports `""` mid-edit), a one-sided window commits one bound, because the pair rule otherwise refuses every edit to it for as long as the page is open. Picking an action from `FLEET_LEVEL_ACTIONS` gets an empty state that says the record belongs to no tenant, rather than "no entries match", which reads as "it never happened" — the fleet READ is #520. `before`/`after` render as a **field-level diff** rather than two JSON blobs: measured on a self-hosted tenant, half the rows carry two full system prompts of ~11k characters each, so the row that says the most would otherwise be the one that shows the least; values over 160 characters are clipped (through `clipText`, never a bare `slice`) with the full text one click away. The `undisclosedChanged` marker leaves the field list and is stated in words instead: the write side puts it IDENTICALLY on both projections on purpose, so a diff by equality would erase the one row that says a value the trail does not carry was changed, and render it as "nothing was recorded". The page renders only what the row recorded and never re-reads the live record, because the projection was allowlist-sanitised at WRITE time and the record has moved on since. A date the picker could not have produced is refused rather than parsed, canonical shape included, so a hand-edited URL cannot filter by a day the input is unable to display; the endpoint itself refuses a bare date, like every other instant filter. **The page does not render `latestAt`** (#526): the response still carries it for the REST and MCP transports, but a freshness line exposes ingestion lag and this trail has none on any path the console reaches — and as a MAXIMUM over the whole trail it answered the missing-row question *wrongly*, since any later row from another family carries it past the gap and the comparison then reports "covered". Each load carries a token so a slower answer to an older, wider filter cannot land on top of a newer one.

## Pointing at a field in a tool's response (`pages/resources/ToolEditModal.tsx`)

Two features of the HTTP tool editor need the operator to name a place inside the tool's response: the **appointment declaration** (which key holds the booking id, the start, the title — `docs/graph.md` → tool preconditions' neighbourhood, and `src/modules/tool-definitions/appointment.ts`) and the **response template** (what the model receives at all). Both are typed as dotted paths, and typing is where the expensive mistake lives: the form catches a MALFORMED path, and nothing catches a well-formed path aimed at the wrong key — it passes every check and simply finds nothing, silently, all the way to production.

So the screen has one **Sample response** field and a picker beside each path field:

- **One sample for the whole modal.** Both features point into the same body; asking twice would read as two different questions. It is local state, never submitted, and deliberately **not** part of the dirty comparison — pasting a sample must not raise the discard dialog. It is also cleared on every open: a response pasted for tool A offering its paths while editing tool B is worse than no offer.
- **The picker offers exactly what the reader accepts**, and the two readers accept different things, so the sample is walked twice (`sampleLeaves` for appointment paths, `templateLeaves` for template tokens; `collectLeaves` in `src/modules/tool-definitions/json-path.ts` is the shared walk). A picker that offers a leaf its own reader then refuses is worse than no picker — that pairing is the invariant, not the walk.
- **`PathPicker` replaces the field; the template's picker INSERTS at the cursor** (`insertToken`), because that box holds a block of text rather than one path. It is rendered as a SIBLING of its `FormField`, never inside it: `FormField` wraps children in a `<label>`, which forwards a click on the field title to the first focusable descendant.
- **The template's picker is caret-aware, and offers lists as blocks** (#459). Outside every block it offers the absolute fields plus the sample's lists (`templateLists`), each inserted by `insertEachBlock` as `{{#each path}}` / `{{/each}}` on lines of their own with the caret left on the empty line between them. With the caret inside a block (read leniently by `enclosingBlock`, because the moment the operator most wants the item fields is right after inserting the marker, while the block is still unclosed) it offers the fields of that list's items instead, relative, as the union over the first ten items (`templateItemLeaves`: a field the first row happens to lack is still a field of the list), under a heading naming the list. The caret is read when the picker OPENS, not per keystroke: clicking the picker's button moves focus without moving the textarea's selection, and the offer only has to be right for the click that follows. That toggle is also the only way to re-read the caret, so it must survive an offer that is empty for this caret (a block over an empty list, or over items with no fields): `emptyLabel` keeps it rendered with a line saying so, where the first draft unmounted the whole control while it was open.
- **The template shows a live preview** rendered against the sample, absent markers included. That is the point of the section: a template is a promise about the model's input, and this is the only place an operator can read that input before a customer does.
- **The sample no longer has to be pasted.** "Send a test request" opens a nested `ToolTestModal` with one input per value the definition needs (its AI fields plus the conversation placeholders it writes), runs `POST /v1/tools/test` against the real API with the UNSAVED definition, and fills the sample with the raw response. The parent's `useOnModalOpen` returns a cleanup that closes it, per the nested-modal rule in `docs/modals.md`.
- **That dialog answers the runtime's questions, not its own**, and each of the three ways it can stop agreeing is a run that fails for a reason the operator did not put on screen. Which placeholders get a box comes from `contextNamesReferencedBy`, which normalizes the definition through `normalizeToolShapes` first — an OpenAPI-style `{contact_id}` is a supported spelling, and a scan for `{{name}}` alone offered no box for it. It then scans the four places the runtime interpolates and no others (the URL, the TOP-LEVEL values of headers and query, the body's `raw` or `kv` row values, and a legacy fixed field's `value`): as a generic deep walk it also found placeholders inside a field's DESCRIPTION — prose written for the model — and inside a nested header value, which `headers[k] = interpolate(String(v), …)` sends as `[object Object]`, placeholder and all. Over-reporting costs the operator a box for a value that will not be used whatever they type in it. **And a row's identity is its origin plus its name, never the name alone**: a tool may declare an input field called `contact_id`, which the runtime resolves with an explicit precedence (AI input → fixed → context), so the AI row and the context row are separate slots — keyed by the bare name they shared one box, and the case that precedence exists for, the model omitting the argument so context can fill it in, could not be expressed here at all. **The boxes themselves come off the definition the dialog will run**, through `testFieldsFrom(payload.inputSchema)`, not off the form rows: `schemaFromAiFields` writes an object, so two rows that trim to one name collapse to the last, and reading the rows rendered both — two controls on one slot, with the losing row's `required` or type judging a value the saved definition never declares. A legacy `source: "fixed"` entry gets no box either, matching `parseToolInputSchema`, which keeps `source === "ai"` alone. Which control a field gets comes from `fieldUsesPicker`, so an enum with no declared values renders a text input, because that is what `zodFor` reads it as. And what counts as a filled-in form comes from `argProblem`, which refuses a value the declared type cannot take AND a required field left blank — both of which the declared schema rejects before the request goes out, so the button is disabled and the reason sits under the field. The button that OPENS the dialog carries Save's whole URL gate, `relativeWithoutBase` included — that condition is deliberately outside `urlTemplateInvalid`, and reading only the first half spent a real request against the operator's provider to be told what the form already knew.
- **The preview does not restate the runtime's rules, it calls them.** `templatePreviewFor` hands the sample and its status to `projectToolResponse` (in `modules/tool-definitions/response-template.ts`, imported by `graph/tools/http.ts` too) and clips the result with `clipToModelLimit`. It was written as a second reader of the same rules and drifted from them in two consecutive review rounds — the 2xx gate, the token-less render, the clip on a projection — each time producing a box labelled "exactly what the agent would receive" that said something the runtime does not. The status travels because `projectResponse` gates on 2xx: outside it the body reaches the model raw, and null status (a hand-pasted sample) reads as 200. **And the REASON travels back**: `projectToolResponse` distinguishes three ways a template does not apply, so the preview carries its `skipped` verbatim instead of a boolean. Collapsed, one sentence covered two causes — a 2xx body that simply is not JSON (a CSV, an XML, a plain `OK`) was explained to the operator as "outside 2xx", with the absent status of a hand-pasted sample interpolated as `null`. Same defect as the runtime's own clip notice one round earlier, one layer up: a two-branch message for a three-branch outcome.
- **The Save gate is the service's reader, not a subset of it.** `templateSaveProblem` runs `readResponseTemplateResult` — the same function `toolDefinitionCreateSchema` refines with — so a template past `MAX_TEMPLATE_CHARS`, or carrying a NUL or a lone surrogate, is refused inline instead of leaving Save enabled on a payload the server was always going to reject. The two problems the screen can phrase well (an unusable token, a stray brace) keep their own localized sentences; the rest shows the reader's.
- **A response too large to be a sample is not offered as one.** Past the endpoint's 100k wire cap the raw body comes back as a PREFIX, which is not a JSON document: both pickers would go dark and the field would say only "not valid JSON". The dialog leaves the sample alone and says what happened instead.
- **A blank box is not always nothing.** The empty string is a VALUE for a string field (a PATCH that clears a provider field sends one), and a text input renders "left out" and "empty" identically. A REQUIRED string cannot be omitted, so blank there is the empty string and Send stays enabled; an OPTIONAL one reads as left out, with a switch under the blank box to say otherwise. The switch's label is FIXED and the state lives in the box's own placeholder (`not included in the request` / `goes in empty: ""`), with the OFF half in the switch's `help`: a switch's label only ever describes what turning it ON does, and here OFF is the half nobody guesses — the field disappears from the payload with nothing on screen saying so: it began as a text link whose whole sentence rewrote itself on click, which is a control with no identity to scan a form for — it had to be read twice to be used once, and it was the only text link in a form of inputs. The switch also matches the vocabulary already on the same screen, where an enum's first option is `Leave out`. `fieldTakesEmptyString` decides which types this applies to, and its test asks `parseToolInputSchema` the same question.
- **And there is no way out while one is in flight.** `onCloseRequest` is a no-op while `running`, because the session token makes a late answer harmless without un-sending the request: a test of a POST is a real write, so dismissing with Escape (or the overlay, or the X, none of which a disabled Cancel covers) and sending again would run the provider's operation twice with the first result dropped in silence.
- **One request belongs to one opening.** `ToolTestModal` bumps a session token in `useOnModalOpen` and in its cleanup, and everything past the `await` bails when the token moved. Without it, a slow run whose dialog was dismissed still writes its result into the next session and hands the editor a sample from a definition that is no longer on screen (`docs/modals.md`, "Drop stale responses with a session token").

## The code tool editor (`pages/resources/CodeToolEditModal.tsx`)

The sibling of the HTTP tool editor for the kind whose wiring is a JavaScript function body (issue #363). Same label-to-identifier derivation (`normalizeToolName`), same `AiFieldsPanel` for the typed arguments (extracted from `ToolEditModal.tsx` so the two editors cannot drift on what a field is), a required description, and the body as a monospace `Textarea` capped at `SANDBOX_CODE_MAX_CHARS` (from the import-free `graph/tools/code-sandbox-limits.ts`; the sandbox and the worker must never reach the browser bundle, fenced in `tests/client/bundle-boundary.test.ts`).

**The syntax warning is advisory, on both ends.** While the operator types, `lib/code-tool-syntax.ts` (acorn, lazy-loaded on the first keystroke, CSP-safe where `new Function` would throw `EvalError` in production) parses the body as `function (input, context) { … }` and the modal draws the result as a `<p className="-mt-2 text-warning text-xs">` sibling under the field, never in `FormField`'s `description` (that slot is shared with `error` and disappears on a refusal). After a save the server's `warnings` take its place. Save is never gated on it: invalid code is stored as written and fails at call time, as the operator's failure, and a half-typed body must be savable from the one place it can be edited. The "Test" button runs the unsaved body through `POST /v1/code-tools/test` with arguments typed from the schema (`testFieldsFrom`) and shows the exact text the agent would receive, a failed badge, and the console output.

In the agent editor the kind has its own section (`tools-code`) between HTTP and MCP, its own capability-map group, and the Tools page lists HTTP and code tools in one list with a kind badge.

## Shared primitives (`src/client/components/`)

Added alongside the existing Button/Input/Card/Badge/Modal/Toast/Tooltip: **Select**, **Textarea**, **Switch** (role=switch button — wrap in a `<div>`, not a `<label>`, since a button isn't a labelable element), **Tabs** (in-page tablist with roving focus; routed sections still use `<Outlet>`), **FormField** (label + control + error/description), **ConfirmDialog** (payload-carrying confirm modal — one per page, render-always), **DataBoundary** (the loading/error/empty/content switch every list repeats), **EmptyState**, **Skeleton** (decorative `animate-pulse` placeholder; compose several to mirror a layout).

**Loading states are skeletons, not spinners** (see CLAUDE.md → UX). `DataBoundary` is the chokepoint: its `loading` branch renders a generic row-skeleton by default, or a caller-supplied `skeleton={<…/>}` for distinctive layouts (Dashboard, Conversations list, Channels, the Agent editor); it owns the `role="status"` + sr-only `common.loading` announcement, so a bespoke skeleton is purely visual. Pages outside `DataBoundary` (admin tables, Approvals, the conversation message thread) compose `<Skeleton>` inline with their own `role="status"` wrapper. Spinners survive only for `<Button loading>` and the boot/auth/invite-token splash. Skeleton bars are `bg-bg-tertiary`, so don't nest them inside a `bg-bg-tertiary` shell (zero contrast) — drop the shell's bg and let the bars read against the card.

## Where a server refusal goes

The API answers a refusal as `{ error, field? }` (`src/api/lib/refusal.ts`): the sentence, already localized for the request's `Accept-Language`, and — when the refusal is about one input — the server's own name for that input, identical in every language. `field` is a column (`systemPrompt`), a key of a patch (`document`), or a dotted path into a bag the server owns (`guardrails.output.templateMessage`); it is **absent**, never null, whenever the refusal is not about one input, which is most of them.

Two client pieces read it, and which one a call site wants depends on whether it is a form:

- **`apiErrorMessage(e)`** (`lib/apiError.ts`) → the sentence, or `null` for a transport failure with no server behind it. For actions that are not a form (a delete, a retry, a connection test), where a toast is the answer either way.
- **`useFieldRefusal(fields)`** (`hooks/useFieldRefusal.ts`) for a form. The form **declares** the server names it can render (`useFieldRefusal(COMPANY_FIELDS)`), passes `error={refusal.at(name, draft[name])}` to each `<FormField>`, and its submit handler does `const toast = refusal.capture(error, fallback, sent, current); if (toast) showToast(toast, "error")` — `sent` being what the request carried and `current` what the inputs hold now.

The rule the mechanism holds is that the two channels are **exclusive and exhaustive**: a refusal about a declared input renders at that control and raises no toast; a refusal about anything else — another screen's field, no field at all, or no server at all — is a toast. Silence is the outcome that must never happen, and a message shown at the control *and* in a toast is the noise that teaches people to dismiss toasts unread. `placeRefusal` (`lib/fieldRefusal.ts`) is that decision as a pure function, with the table in `tests/client/field-refusal.test.ts`.

The decision is about whether the operator will actually **read** the message, not merely whether the field was declared, and three cases separate those. The form may have unmounted while its own save was out (a modal body does this), in which case the mark goes to state nobody renders. The operator may have corrected the value while the request was out, in which case marking the box blames a value the server never saw. And a refusal about a field the request never carried is about what is *stored*, so there is nothing to be stale against and the mark stands. All three are rows in the same table.

The mark then expires **by value**: `at(field, value)` shows the message only while the input still holds what was refused, so an edit takes it off with no `onChange` line to forget. `clear()` exists for the save that goes through, which the value key cannot recognise on its own.

Declared rather than discovered, because the submit handler needs the answer *before* the next render; matched exactly rather than by prefix, so a form rendering a parent path does not claim every leaf under it. The state is per form instance: a modal over the panel that opened it has its own, and both have a `name`.

Reference wiring: `pages/resources/documents/CompanyProfileCard.tsx`.

**Where the console actually stands**, because the two paragraphs above describe the destination and not today. Every error toast now shows the server's sentence when there is one — `tests/client/error-toast-reason.test.ts` holds that as a rule, and a handler that discards an error it has fails the suite. Rendering the refusal **at the input** it names is wired on that one card and nowhere else: `AdvancedPanel`, the vault picker, Channels and the admin surfaces all receive a `field` today (`requireVaultRef` names `embedding.credentialRef`, `SettingsTextTooLongError` names the settings path) and all of them still show it in a toast. Issue #320 tracks that, per screen, and it is deliberately separate: declaring the server's names for a form's inputs has to be read screen by screen, and doing it inside the sentence sweep would have meant editing the same handlers twice.

Refusals rendered into **local error state** rather than a toast are a third population, unswept and unfenced: issue #329.

## Where help goes

Sibling to the section above, and the same kind of rule: that one decides where a message about
what went **wrong** lands, this one decides where an **explanation** lands. Both turn on the same
question, will the operator actually read this, and both are rules rather than preferences, so a
new field does not need a fresh discussion (issue #411).

**Three outcomes, and a test that picks one.** Two outcomes are not enough: the best pattern in the
app already uses the third, and without a name for it the next capped field gets a 200-character
sentence instead.

| | outcome | the test |
|---|---|---|
| 1 | **inline**, under the control (`description`) | *Can they act correctly without reading it?* No → inline. |
| 2 | **on the control, revealed by state** | *Can the app tell that this now applies?* Yes → the app says it, at that moment. |
| 3 | **behind the affordance** (`help`, the `?`) | *Is it read once and then remembered?* Yes → behind the `?`. |

Outcome 1 is what no state can reveal: a format example, a cross-field dependency, a statement of
the default. Outcome 3 is why the thing exists, when it applies, what it costs: a **decision**, and
a decision is made once.

Outcome 2 is the one that gets forgotten, and the worked example is already shipped. Six settings
fields carry a text cap (`modules/agents/text-caps.ts`; exceeding one is a refused save, so by the
outcome-1 test a cap is the strongest possible candidate for permanent prose) and **no hint in either locale
declares one of those caps**. (`2000` does turn up twice, as a token floor and a log-truncation
limit; neither is the cap of a capped field.) `Textarea` declares the cap itself: a counter from
80% of it (`COUNTER_FROM`) and the consequence sentence only past it. The case with the highest cost
of going unread, solved with zero standing prose.

**Length is a symptom, not the rule.** A long string is a prompt to re-run the test, never the
verdict, and the threshold is applied **per key in the source language**, not per locale. The
catalogue is bilingual and pt-BR runs about 6% longer, so a length rule applied per file puts the
same field inline in one language and behind a `?` in the other, which is worse than either answer.
Measured before this rule landed: 2252 en keys / 2260 pt-BR, of which 45 and 49 were ≥200
characters. `tests/client/help-placement.test.ts` enforces the cap on **en alone** for that reason,
and checks the three-paragraph shape of `*Help` in both.

**Two constraints the mechanism imposes.**

- `FormField` renders `error` and `subtext` in the **same slot, exclusively** (`{error ? error :
  subtext}`). A constraint that lives only in the inline text therefore disappears at the exact
  moment it is violated: the refusal replaces the sentence that would have explained it. That is an
  argument for outcome 2 independent of screen real estate, and it is why `Textarea`'s counter is
  right to sit outside that slot: it survives its own error.
- The `?` is `HelpPopover`, a **Popover and never a Tooltip**. A Radix tooltip cannot be opened by
  touch at all: three handlers close every route in, measured in the note on `Popover.tsx`, and the
  console has a mobile drawer. `Tooltip` stays for what it is good at, a one-line label on a control
  whose icon is not self-evident, and its `children` is now **required** for that reason: it used to
  render its own `?` when given none, which is how a tooltip came to be used as a help affordance in
  the first place. The template it came from still does (`bunfire`, `HomePage.tsx`).
- The field's `<label>` **points** at its control (`htmlFor`) and does not wrap it. A wrapping label
  forwards a click on any NON-interactive descendant to the control it labels, and ARIA makes the
  `?` operable without making it *interactive content* in the HTML sense: measured on a field
  wrapping a checkbox, where clicking the `?` toggled the checkbox. The earlier version with a real
  `<button>` had the mirror-image defect, since `button` IS labelable and so became the labelled
  control. So the control has to CARRY an id, which `FormFieldContext` hands down; a field whose
  children are not one focusable control takes `group` instead, and in that mode the context hands
  down neither an id nor a label, or every child would be renamed after the group.
- `HelpPopover` takes a `label`, and every surface that has one passes it (`FormField` its label,
  `Section` its title, `KpiCard` its caption, `SwitchField` its label). Without it every trigger on
  a page is announced identically, so a screen-reader user tabbing a form of twelve fields hears
  the same three words twelve times. The name is **composed** (`"Show help: History ceiling"`) and
  not interpolated, because an accessible name that depends on `t` interpolating breaks under the
  `react-i18next` stub nine client test files install and leak.

**The awkward cases, answered.**

| case | outcome | why |
|---|---|---|
| a footgun (`google_calendar` is reserved) | 2 | only actionable when somebody types it, and a refusal naming it then reaches an operator that a permanent sentence never would |
| a cross-field dependency ("same value on the tool that cancels") | 1 | the one kind of help the field can never reveal, because the fact lives on another screen |
| a statement of the default ("empty, no reminder is sent") | 1 | and cheap: `editor.contactAuthDenyMessageHint` does it in 86 characters, right at the catalogue median |
| a destructive action's consequence (`editor.deleteWarning`, `channels.removeInboxWarning`) | 1 | it is read at the moment it matters and nowhere else; a confirm dialog IS the state-revealed moment |
| a detected misconfiguration (`editor.configIssue*`) | 2, already | the app found the condition and is saying it. Not a `?` candidate: what these need is shorter prose, not another home |

**This is about help, not about forms.** A KPI whose methodology takes five sentences, a section
whose purpose is not obvious from its heading, a diagnostic that only parses for somebody who knows
the subsystem: all outcome 3, and `HelpPopover` goes **next to the caption or heading**, not under
it. `dashboard.kpi.firstResponseNote` is the finding that forced this to be said out loud: 574
characters of Chatwoot methodology set loose in the middle of the panel, under no field at all.

**The shape of an outcome-3 text**, because the `?` is not a licence for the wall of prose it just
took off the page. Three short paragraphs: **what it is**, **what it does**, **the caveat**. They
are separated by a blank line in the catalogue and `Popover` splits on blank lines to render them,
so no markup goes into a translation file, where a translator cannot see it and a lint rule cannot
check it. `editor.limitsMaxHistoryTokensHelp` is the reference.

## i18n gotchas

- `t("key", "Default")` everywhere; `bun i18n:extract` auto-adds keys to `en.json` AND `pt-BR.json` (copying the English default into pt-BR — **new pt-BR keys must then be translated**). Run `bun check` (which runs the extractor) after adding strings.
- The extractor **fails on conflicting defaults**: the same key must use the identical default string at every call site (e.g. a Switch `aria-label` and its visible label sharing a key must match). Use distinct keys or align the defaults.
- Decorative punctuation in JSX text must be in `biome.jsonc`'s `noJsxLiterals.allowedStrings`, or computed into a variable (`{pctLabel}`); dynamic `t()` needs a `// t('key','Default')` magic comment + `biome-ignore`, so prefer passing already-translated strings to helpers.

## Two standing product rules for anything that persists or shows a date

- **`localStorage` is not admissible for product data.** History, "save", "remember", resume: all of it is designed with a backend (a Prisma table with `tenant_id` + RLS, or an existing store like the LangGraph checkpointer). This is a real multi-user product, so persistence has to sync across browsers and devices, survive a cache clear, and be auditable and tenant-scoped. Pure UI preference (theme, sidebar) stays fine in `localStorage`; conversation or content data does not.
- **A day is defined by the viewer's browser timezone.** The frontend sends `tz = Intl.DateTimeFormat().resolvedOptions().timeZone` as `?tz=` and the backend buckets in that zone, returning `bucket` as a LOCAL `YYYY-MM-DD` via `to_char`. A fixed `DASHBOARD_TIMEZONE` env and a per-tenant setting were both rejected. **The non-obvious part** is that `created_at` is `timestamp WITHOUT time zone` (Prisma's default for `DateTime`), holding a naive UTC wall clock, so `created_at AT TIME ZONE $tz` shifts the wrong way — it reads the value as already being in `$tz`. The correct form is the **double shift**, `created_at AT TIME ZONE 'UTC' AT TIME ZONE $tz`: first stamp it as UTC (a real instant), then render it as wall clock in the target zone. `normalizeTimeZone(tz)` validates the IANA name via `Intl.DateTimeFormat` and falls back to `UTC`, so Postgres cannot blow up on `AT TIME ZONE`. Accepted caveat: the cost metric comes from the Langfuse Metrics API, which takes no timezone parameter, so cost keeps a UTC day boundary. The same bug class reappears in any report by date — always bucket in the operator's zone, and remember the double `AT TIME ZONE`.

## App shell and page composition

- `ProtectedRoute` wraps children in `<Layout>`. Page components must NOT wrap themselves in `<Layout>`, they render content only
- Only `ProtectedRoute` (in `src/client/components/ProtectedRoute.tsx`) should render `<Layout>`: it is the single source of the app shell
- `<Layout>` composes `<Header>` (logo, mobile hamburger, `<UserMenu>`) + `<Sidebar>` (desktop aside or Radix Dialog drawer on mobile) + `<main>`. Navigation items are defined centrally in `src/client/lib/navigation.tsx`
- `<UserMenu>` (`src/client/components/UserMenu.tsx`) is the single entry point for user-level actions: theme picker, language picker, Settings shortcut, logout. Do not add those controls to the header or sidebar directly
- `<Sidebar>` exposes a footer block (`SidebarFooter`) with external links (support / website / repo), configured via `SUPPORT_LINK` and `SECONDARY_LINKS` in `src/client/lib/navigation.tsx`. The footer is pinned below the scrollable nav, collapses to icon-only with tooltips when the sidebar is collapsed, and does not render if both constants are empty/null. Icons come from `lucide-react` except GitHub, which uses the inlined Octocat in `src/client/components/icons/GithubIcon.tsx` (lucide 1.8 does not export a GitHub glyph)
- `<SidebarProvider>` (`src/client/contexts/SidebarContext.tsx`) owns sidebar state: `collapsed` and `width` persisted in `localStorage` under `@app:sidebar-*`, plus `mobileOpen` for the drawer. Keyboard shortcut Cmd/Ctrl+B toggles collapse (via `useSidebarShortcut`)
- `<TooltipProvider>` wraps the app in `App.tsx`; any `<Tooltip>` call (`src/client/components/Tooltip.tsx`) inherits a 200ms delay. `<Modal>`, `<Tooltip>`, `<Toast>`, `<Sidebar>` mobile drawer and `<UserMenu>` are all thin wrappers over Radix primitives (`@radix-ui/react-{dialog,tooltip,toast,dropdown-menu}`) to get focus trap, collision detection, and ARIA correctness for free
- `<PageContainer>` (`src/client/components/PageContainer.tsx`) is the single source of page-level max-width and horizontal centering. Every top-level page in `src/client/pages/*.tsx` must wrap its root JSX in `<PageContainer>`. Accepts `size="narrow" | "wide" | "full"` (default `"wide"`): `narrow` = `max-w-3xl` (forms, settings, reading), `wide` = `max-w-7xl` (dashboards, tables), `full` = no max-width (ultrawide tables, canvas). This rule is enforced by `biome-plugins/require-page-container.grit`, scoped to `src/client/pages/*.tsx`. Sub-pages under a layout route (e.g. `src/client/pages/settings/*.tsx`) are out of scope because their parent layout already wraps `<Outlet />` in `<PageContainer>`. Auth pages (Login, Signup) suppress the rule with `// biome-ignore lint/plugin: <reason>` because they render outside the main app shell
