# The decisions engine of a monitoring agent

A monitoring agent decides in one of two ways, chosen by `settings.monitoring.engine`:

- `llm` (the default, and what any absent or unknown value reads as): the ordinary graph with the agent's prompt and tools, run on a muted client (docs/chatwoot.md, "Monitoring").
- `decisions`: the tick asks a classification API typed questions about the conversation and turns the answers into tool calls by rule. No chat model runs.

The mode stays `monitoring` either way, so everything that keys on the mode is unchanged: the agent never answers, it attaches as an observer, several observers share an inbox, the Conversations filter and the dashboard list it as before. Only the brain of the tick changes. Issue #1135.

## What is shared with the `llm` engine

`runObserve` (`src/modules/observe/job.ts`) runs the same steps up to the decision: arming (debounced burst, or on resolve, by `monitoring.analysis`), the claim and the fences, the window and transcript (with transcriptions and image descriptions from the media pass), current labels, notes and label history, the toolset build, and the spend ceiling. What differs is after the ceiling: the `decisions` engine builds no model and calls the provider instead.

The provider reads the same evidence the model would, rendered by `observeEvidenceText`: the label, note, label-change and transcript blocks without the frame that tells a model how to act. TypeSafe documents that accuracy drops when the state carries irrelevant text, and instructions about tools the API does not have are exactly that.

## The block

```json
{
  "monitoring": {
    "engine": "decisions",
    "decisions": {
      "provider": "typesafe",
      "model": "jev-latest",
      "credentialRef": "vault:12",
      "questions": [
        { "name": "pede_reembolso", "type": "yes_no", "instructions": "O cliente pede o dinheiro de volta?" },
        { "name": "assunto", "type": "choice", "instructions": "Assunto principal",
          "options": [{ "value": "reembolso", "description": "estorno" }, { "value": "outro", "description": "outro assunto" }] },
        { "name": "irritacao", "type": "score", "instructions": "Quão irritado está o cliente?",
          "levels": [{ "value": "calmo", "description": "" }, { "value": "frustrado", "description": "" }, { "value": "muito_irritado", "description": "" }] }
      ],
      "rules": [
        { "when": [{ "question": "pede_reembolso", "minProbability": 0.7 }],
          "action": { "tool": "set_labels", "args": { "add": ["reembolso"] } } },
        { "when": [{ "question": "assunto", "equals": "reembolso", "minConfidence": 0.8 },
                   { "question": "irritacao", "minLevel": 2, "maxLevel": 2 }],
          "action": { "tool": "handoff_to_human", "args": {} } }
      ]
    }
  }
}
```

- `provider`: `openai` (OpenAI Decisions, `POST /v1/decisions`, public beta, `gpt-6-luna` only) or `typesafe` (Jev, the official API at `api.typesafe.ai/v1/systemone`; `jev-latest` is an alias, a version such as `jev-1.13.0` pins it). `model` defaults per provider. The provider is kept apart from the agent's chat `modelConfig` on purpose: `typesafe` is not a chat provider and is not in `MODEL_PROVIDERS`.
- `credentialRef`: a vault entry holding the provider's API key. Listed in `SETTINGS_CREDENTIAL_PATHS`, so MCP takes and answers a name, export and import translate it, and config-health reports it missing, pending, gone or of the wrong kind (`decisions`, degraded) on a monitoring agent whose engine is `decisions` (a watcher switched to production keeps its stored block and is not judged by it). A credential entry's base URL, when it has one, replaces the provider's. The vault has a kind per provider (`openai`, and `typesafe` since issue #1452, sent as a bearer token, with an optional base URL and a Test that lists the account's models, which runs no classification); the Classifier's key list offers the provider's own kind first and still takes a generic key, which is what a TypeSafe key was stored as before its kind existed, so those agents keep working with the entry they have.
- `questions`: up to 50. `yes_no` answers a probability; `choice` (2 to 255 options, values unique within the question) answers one option's `value`, its confidence and every option's probability; `score` (2 to 10 levels, lowest first) answers a probability-weighted mean of level indices, its confidence and every level's probability. Probabilities are keyed by the option's or level's `value` for both providers.
- `rules`: a rule fires when EVERY condition holds. A `yes_no` condition needs `minProbability`; a `choice` condition needs `equals`, one of the question's option values, and may ask `minConfidence`; a `score` condition needs `minLevel` and `maxLevel` (inclusive, the score read as the nearest level) and may ask `minConfidence`. A provider that omits confidence does not pass a condition that asks for one. Two rules firing the same tool with the same arguments run it once; the line lists the action under the first rule's index and names the others in its `merged`. A rule may say when it acts (`trigger`, below).
- `action.tool`: `set_labels`, `handoff_to_human`, `private_note` or `set_custom_attribute`, with fixed `args` in the tool's own schema, or one of the tenant's own tools (below, "Custom tools"). The call goes through the same tool object the `llm` engine's model calls, after the same fenced wrapper, so protected labels, the pinned handoff target, allowed labels, the label queue and at-most-once counting apply unchanged, and the tool writes its own `tool` flow line. A `handoff_to_human` rule's `reason` is the rule's own text and is always left as a private note; the agent's `transferWithSummary` switch, which gates a model's summary, does not apply to it, and an empty reason leaves no note. A tool the agent was not granted does not run (`not_granted`): grants are the operator's, as for the model. The agent's `limits.maxToolCalls` caps the actions one tick dispatches; a rule past it reports `over_budget`.
- **When a rule acts** (`trigger`, issue #1222). A rule's conditions can hold on many observations in a row, and since #1195 an observer can run once per message. `each_time` acts on every observation in which they hold; `on_start` acts on the observation where they start holding, does not act again while they keep holding, and acts again only after an observation in which they did not; `once` acts the first time and never again in that conversation. Absent, the rule follows its action (`defaultTriggerFor`): `set_labels` and `set_custom_attribute` converge (a second identical write changes nothing, and acting each time puts back a label a person took off), so they act `each_time`; every other action adds something on each call (a note, a transfer), so it acts `on_start`. A value outside the three is refused with a 400 at `monitoring.decisions.rules.N.trigger`. The state lives in `decision_rule_states`, one row per rule that acted and is held back, per agent and conversation, keyed by `ruleStateKey` (the rule's conditions, action and resolved trigger, not its index): it survives restarts, editing a rule's conditions, action or trigger starts that rule over while the others keep theirs, a reorder keeps every rule's state, and a key no rule of the block has any more is dropped by the next tick that decides. A rule's latch is written before its action is dispatched, and released once the action is known to have written nothing: one that could not run, wrote nothing (`no_effect`), failed before its handler ran (`invalid_arguments`) or with an error the Chatwoot client says sent nothing (`sentNothing`: every failed read, and a refusal before dialing such as the deadline) while the call had reported no write yet (`committed`, which every action a rule can run reports after each of its writes), or that a fence refused tries again on the next observation in which it holds; a call that threw otherwise may have written, and its rule stays latched, so a grant or a contact that arrives later is not met by a rule that counts itself done. An action still in flight when the tick's deadline ended it may or may not have written, and its rule stays latched: holding it is safer than posting the note twice. The latch goes out before the action's fence is asked, so a withdrawal that lands while it is written stops the dispatch, and a latch for an action that never started is released, also when the deadline ended the tick first. A latch that cannot be written fails the tick before the action is dispatched. Two observations of the same conversation can overlap (a message re-arms the watcher while an older tick still waits on a write), and the state holds one invariant: an older observation never changes the state a newer one read. Every read takes a generation of the agent and conversation (`decision_rule_claims`) in the scheduler's order, the observe job's row id and `claim_seq`, so a run the scheduler already superseded takes none and ends `skipped: superseded`; a tick adds, releases or drops rows of `decision_rule_states` only while that generation is still its own, checked and locked in the same transaction; a tick that a newer one has read past writes nothing more, except to withdraw its own reservations (rows it wrote, for actions that never wrote anything), which no newer tick wrote (the line says `triggerStateSuperseded: true`), and one whose latch ahead is refused that way is withdrawn before it dispatches. A finished tick writes no latch after its actions: they all went out ahead. The tick reads the state before the provider call and fails before paying if it cannot (`failed: "trigger_state"`), since acting without it could repeat a note; a write that fails after the actions is said on the line (`triggerStateWritten: false`) and does not undo them. A rule its trigger held back is listed in the line's `held`, apart from `notFired`, so "did not fire" and "fired and was held" read apart. The trigger is left out of the block's mark (`decisionsFingerprint`), so choosing one keeps the history the console counts. A dry run applies the triggers it is given and latches nothing.
- **Custom tools** (issue #1223). A rule may run an HTTP, code or MCP tool granted to the agent, named as the model knows it: an HTTP or code tool by its normalized name (`normalizeToolName`), an MCP tool as `mcp__<server>__<tool>`. Any other built-in (`send_image`, `search_knowledge`...) is refused at `action.tool`. A classification API answers yes or no, an option or a level, and never pulls a value out of the text, so each argument is either fixed in `action.args` or filled from what the observation knows, in `action.fill` (argument name to field, `src/modules/decisions/tool-args.ts`): `contact.name`, `contact.phone`, `contact.email`, `contact.identifier`, `contact.attribute.<key>`, `conversation.display_id` (the number Chatwoot shows and links to; the internal id is not offered, since nothing outside Chatwoot's database can use it), `conversation.inbox_id`, `conversation.link`, `conversation.attribute.<key>`, and this observation's answers: `answer.<question>.choice` (a `choice` question's option), `.level` (a `score` question's level value) and `.level_index` (its number), `.probability` (a `yes_no` question's). The contact and inbox come from the same context an HTTP tool's `{{contact_phone}}` reads, the attributes from the mirror's bags, refreshed by the event that queued the tick. The block's schema refuses a `fill` on a native tool (`fill_on_native`), an argument both fixed and filled (`arg_twice`), a field it does not know (`unknown_field_source`) and an answer field of a question that is missing or of another type (`unknown_question`, `fill_question_type`), each at `rules.N.action.fill.<arg>`. On save the server asks the tool's own input schema (`assertDecisionActionArgs`, `src/modules/agents/service.ts`): a name the tenant has no HTTP or code tool for is a 400 at `action.tool` (`errors.decisionToolUnknown`); a required argument with no value, an argument the tool does not have, a fixed value of another type and a field of another type are a 400 naming the argument at `monitoring.decisions.rules.N.action.args.<arg>` (or `.fill.<arg>`). Types follow the source: text fills any text argument, a whole number fills a whole or a decimal one (and a text one, as its digits), a probability fills a decimal one; an attribute is text, whatever Chatwoot holds. Only an action the save introduces or changes is asked, so a tool edited after the rule was saved fails at the tick (`invalid_arguments`) instead of blocking an unrelated save. An MCP tool's arguments live on its server, read at discovery: its name and arguments are asked at the tick, as the model's calls are, and a filled number goes into an argument its JSON Schema types as text as its digits. An HTTP tool with an acknowledgement asks the model for the holding message; a watcher's client is muted and sends none, so a rule's call gets a placeholder for it. An HTTP tool that refuses before sending (a `{{conversation_ref}}` it cannot mint, a missing URL value, the deadline) says so on the call's own reporter, so the action is `no_effect` and its latch is released. At the tick every action's arguments go through one pipeline before anything is charged, latched or sent (`prepareArgs`, `src/modules/decisions/arguments.ts`): the fills are resolved for this observation, each value is fitted to the tool's ORIGINAL schema (the zod schema an HTTP or code tool is built from; an MCP tool's server schema, with local `$ref`s and `anyOf`/`oneOf`/`allOf` read, not the simplified declaration the model gets), and the whole call is checked against that schema with the adapter's own validator; an argument an HTTP or code tool no longer declares (renamed after the rule was saved) does not fit, rather than being dropped from the call in silence. A call that does not fit is not dispatched: the action is `failed` with `missing_value` (a field the observation had no value for, named in `missing`) or `invalid_arguments`, spends no call of `limits.maxToolCalls` and holds no latch. The save and the MCP preview ask the same check (`sampleArgsUnfit`) with a sample of each field's type in place of its value. A custom tool is not convergent, so its rule defaults to `on_start`. The action's line entry carries `args`, the arguments the call got: fixed ones as written, filled ones as values only when the agent's `observability.logToolValues` is on and otherwise as `{ "from": "contact.phone" }`, since they are the contact's data; the tool's own `tool` line follows the same switch. Two actions that resolve to the same tool and the same arguments (one fixed, one filled with that value) are one call, the second listed in the first's `merged` and latched with it. An MCP call its adapter refuses for its arguments (checked against the server's full schema before anything is sent) is `invalid_arguments` and releases its latch. The call counts against `limits.maxToolCalls` and runs after the same fence as a native one. The MCP preview of `agent_settings_set` and `agent_create` asks the same check as the apply. A custom tool is called as a tool call, so a failure it answers with (an HTTP status outside the expected ones, a code tool's sandbox error) is `failed` / `tool_error`, latched like any call that may have reached the other side, except a code tool's, which leaves nothing behind by construction and releases its latch. A schema the validator cannot compile (an MCP server's external `$ref`) fits no call: that action is `invalid_arguments` and the tick's other rules still run. A bundled tool an import stores under another name takes its rules with it (`renameDecisionActionTools`). An MCP name two servers may answer to (two servers whose names reduce to one slug, two tools that meet once a long tool name trims the slug, or a name a collision suffix may land on: `ambiguousMcpNames`, `src/graph/tools/mcp-names.ts`) is not offered in the console, and a stored rule on it is `failed` with `ambiguous_tool` at the tick, without the call, the budget or the latch, since the assembly tells such tools apart by a suffix that depends on the order it reads the servers in. A disabled HTTP or code tool or MCP connection is out of the toolset, so the console does not count its grant as runnable.
- **Every rule that fires runs.** The block had an `apply` switch (a simulation mode that decided, paid for the call and wrote nothing) until issue #1224 removed it: a block that carries `apply` is refused with a 400 naming `monitoring.decisions.apply` (`errors.unknownSettingsField`), on REST and on MCP's partial patch alike, while an agent import drops it quietly, since an export from an older release carries it. The upgrade's migration (`20261010180000_remove_decisions_simulation_mode`) removed the key from every stored block and DISABLED every agent that was in simulation, with an `agent.disabled_by_upgrade` audit line giving the reason: its rules were written to be watched, and would otherwise have started writing unreviewed. Deciding without writing survives as an internal flag of `applyDecisions` (`dryRun`, outcome `decided`), not a setting, for a caller that only shows the decisions. The tick's fence asks the engine again before every action, so switching engines while a call is in flight ends that tick with `skipped: engine_changed` instead of letting it write.

`engine: "decisions"` without a block (absent or `null`) is refused at `monitoring.engine`, judged against the whole monitoring block. REST and MCP refuse a block the tick could not run, with a 400 naming the field (`decisionsSchema`, through `assertSettingsClosedValues`). A missing field is named at the object that lacks it, since the boundary compares by value at the issue's path and an absent key equals an absent stored key. A cross-field problem is judged against the whole block instead: renaming an option, deleting a question or shortening a scale that an unchanged rule still names is refused (naming the rule's field), while a stored block re-sent untouched still saves. On MCP the block is a partial patch like any other: `agent_settings_set` takes it without the cross-field rules (`decisionsPatchSchema`), merges it into the stored block, and asks the merged block the full schema already in the preview, so `{ "decisions": { "model": "gpt-6-sol" } }` changes one field of a working block and a patch that leaves the block incomplete is refused before it is stored. The tick reads the block again (`readDecisionsConfig`) and stops on a problem instead of acting, because a row written before this schema, or re-sent untouched, still reaches it.

`readMonitoringConfig` carries `engine` and the `decisions` block: it is the reader every rewrite of `monitoring` goes through (the MCP merge, the console's Behavior save, the audit projection), and a block it did not carry would be deleted by them. It carries the declared fields only (`projectDecisionsBlock`), picked by name at every level, so a key pasted beside them (an `apiKey`) never reaches an audit row; `action.args` goes as written, and `action.fill` names fields, never their values. The console edits the block through this same reader ("The console", below).

## The console

The editor of a monitoring agent follows its engine (issue #1224; the block's screen came with #1176). The screen never says `llm` or `decisions`: the engines are "Language model" and "Questions and rules".

- **General** draws the engine as two cards right under Mode, ahead of the instructions, on either engine (`EngineChoice.tsx`), each with a sentence on what it does, since the choice swaps half of the editor and comes before what it decides. On Questions and rules, the agent instructions and the Model card are not drawn; the **Classifier** card (`ClassifierFields`: provider, model, empty meaning the provider's default, and the API key from the vault) takes the Model card's place. Under the cards, a line says what is still missing for the setup to be saved, with the way to each place.
- **Tabs.** On Questions and rules, Knowledge is not drawn (the engine searches no base) and a **Questions and rules** tab is, after Channels (`editorTabs.ts`). Tools stays on both engines: its grants, handoff target, label permissions and preconditions fence a rule's action as they fence the model's call. On Questions and rules it draws what a rule can run: the four natives a rule fires and the tenant's HTTP, code and MCP tools; no integrations or documents, no summary switch and no "Let the AI choose" destination (a stored one stays visible, disabled, under a warning); a Tools save there writes the grants and the settings of the tools it does not draw (labels on close, the case inbox, image hosts) as stored, and an edit made to them on the language model before the switch stays a draft for a switch back. The tabs change with the card, before any save; a URL naming a tab not drawn lands on General.
- **Questions and rules tab** (`DecisionsFields.tsx`): the activity total, then the questions, then the rules as "when <conditions> then <action>" with each tool's arguments as fields (labels and conversation attributes listed from the agent's Chatwoot account). With no question it offers starting points (`decisionsStarters.ts`): customer sentiment (a five-level score and one label rule per level that takes the other four off), main subject (a list written to a conversation attribute) and asks for a person (yes or no and a label), plus a blank question. Each adds a question and its rules to the draft, in the console's language, and writes nothing: the stored block still needs one question, and a Save before then writes nothing and says so (below). A rule whose tool the agent was not granted says so on its card, with an **Allow** that adds that one native tool to the saved grants at once (`withNativeToolGranted`); with grant changes pending on the Tools tab it opens Tools instead, so one grant is not written beside a selection nobody confirmed. Tools stays editable while the grant is written, and what changes there meanwhile is kept (with the tool added) rather than replaced by the set the request carried (`grantsAfterAllow`). The action list carries, under "Your tools", the custom tools the agent has as saved (`customToolsOf`, from the tool catalog's `toolName` and `args` and the MCP grants' enabled tools); picking one draws a row per argument of its schema, each **Fixed value** (typed for the argument: a number field, yes or no, the enum's values) or **From the observation**, a list of the fields above narrowed to those of a type the argument takes (a number argument is not offered the contact's name). An MCP tool's rows are named by hand, each with the type its fixed value is stored as (text, number, yes or no, JSON). No MCP name two servers may answer to is offered (above), and switching a rule to another tool starts its rows over. A required argument with neither is a problem at its row, by the same check the server asks (`actionArgIssues`), so the Save writes nothing until it is filled. A custom tool the agent does not have sends the operator to its card on Tools instead of offering **Allow**: its grant may need more than a click (an MCP server's tools).
- **Behavior**, Observation, keeps only when it looks: when to classify, messages read, burst window and ceiling. For an agent on Questions and rules, Memory and Fallback provider are not drawn (no chat model runs) and their validators do not hold the Save.
- **What each Save writes.** The setup (engine, classifier, questions, rules) is one editor section, `decisions`, drawn on two tabs: General's dot lights for the engine and classifier, the tab's for the rest. Either tab's Save writes the whole setup merged onto the synced settings (`saveDecisions`), so the first save after a switch is never refused for a block split across two saves. General's Save under Questions and rules writes the identity without the instructions or the chat model, which stay pending for a switch back. Behavior's Save writes its timing with the setup as stored (`withDecisionsOf`). Discard on either tab puts the whole setup back.
- **Warnings.** The classifier's key warning points at General, Classifier. A watcher on Questions and rules gets no warning about its chat model, and none about knowledge bases.

- **One schema.** The form is a pair of pure functions over the stored block (`decisionsFormState.ts`), and what it marks is what `decisionsIssues` reports for the block it would write: the same parse the write boundary runs, with a stable `code` and the numbers a sentence needs, so the screen words a problem in the operator's language without parsing the server's English. A missing field, which the boundary reports at the object that lacks it, is drawn on the input whose value is missing. The block asked is the one a save would write: for a form nobody touched that is the stored block itself, not the form's reading of it, since the form fills in what a stored block lacks to draw it (a question with no `type` shows the type as still to pick). Any problem is counted in a banner at the top of the tab; a classifier problem is a line there with the way to General, and a problem at a path with no input is spelled out in that banner, so nothing that blocks the save is silent. **Save stays pressable on both tabs and is never a silent click** (`saveAttempt.ts`): pressed while the setup has a problem and the press would write the setup, or would write nothing at all (a stored setup that is incomplete, nothing edited), it writes nothing (on General, not the name either; a name edited with the setup untouched is saved and the setup stays as stored), turns the banner and General's "to save" line from neutral into errors, scrolls to the first problem on that tab and focuses it. That is the field when the fix is on the tab, and the line's button to the other tab when it is not (the classifier's key from Questions and rules, a missing question from General). Before the first press, what is missing is said in a neutral tone, so a new agent's first look is the starting points and not a list of errors.
- **A broken rule.** A rule whose condition names a question, an option or a level the questions no longer have is drawn as broken, apart from an incomplete one: nothing is missing, what it points at is gone. Conditions name a question by its `name`, as the stored block does, so renaming a question breaks the rules that named it until they are pointed again, which is what the server would refuse.
- **What a save writes** (`decisionsBlockToStore`). A block nobody touched goes back as stored, so saving another field never rewrites it. With the engine on `llm` the stored questions and rules are kept, and a draft that could not run is not written over a block that can: the server would refuse the whole save for a block the operator switched away from. A first switch to `decisions` starts from an empty block (`withEngine`), and so does an agent stored on `decisions` with no block at all (every tick of which is skipped), so what is missing is on screen. Texts are written as held, never trimmed: the engine compares a condition with a question name or an option value literally, and tidying one side of a stored pair would break a rule that works. An agent flipped to production has the whole setup hidden, so its save writes the stored engine and the stored block back as a pair: a choice nobody can see is not a choice to save.
- **A refusal from the server** about a field of the block is kept with the block that was sent and shown at that field while the form still writes that block (`decisionsRefusalFrom`); the API key is one of the editor's owned credential fields and is marked by its own path (docs/ui.md).
- **When it acts.** Each rule shows the choice of when it acts in words (every time the conditions hold, when they start holding, once per conversation), preselected by its action until the operator picks one; only a picked choice is stored, so a rule left alone keeps following its action's default when the action changes.
- **What it has been doing.** Beside each rule, how many decisions fired it and whether the action ran, could not run, was refused by a fence inside the tool (named: a protected label, the allowed labels, the tool's condition) or was held back because the rule already acted (a line from before the simulation mode was removed, with a `shadow` action, counts as fired and as neither). A question carries no answers here: one answer means something only next to its conversation, and the conversation page shows every tick's answers in context (#1426). The counts are read from the engine's own `observe` lines (`decisionsActivity.ts`), the newest 100, and only the lines that ran the block being shown are counted. A line names a rule by its index, and an index means nothing without the list it indexes, so every decided line carries `block`, a short mark of the questions and rules the tick ran (`decisionsFingerprint`, keys sorted, over questions and rules only so changing the classifier or its key keeps the history). The console computes the same mark for the stored block and matches by it: a line written before the rules were reordered, or by a tick that was in flight across the save, is left out rather than counted against whatever sits at that index today. Two rules firing the same tool with the same arguments run it once, under the first one's index: the action names the second in `merged`, and it is shown as fired with the same action as an earlier rule and that action's outcome. A line written before `merged` existed lists the second neither among its actions nor among its `notFired`, so it is found by elimination and counted as fired with no outcome of its own. A rule added on screen says it has decided nothing, and the counts follow a rule when it is reordered before the save.
- **On the conversation page** (issue #1401). Each tick of the observer is a marker on the conversation's timeline, read from its `observe` line (`decision-trail.ts`, `DecisionTickMarker.tsx`): collapsed, the classifier's version, the duration and what the tick did ("1 label added, 1 label removed, 1 attribute, handed off", or no rule fired; a label write is counted by what it changed when the line records it in `labels`, and as writes when it does not); and, when there is an earlier decided tick of the same agent in the conversation, which answers moved since ("sentimento: neutro → negativo"; a yes/no moves when it crosses one half; a score is compared only when both ticks ran the block shown, since an edit can reorder its levels; the first tick says nothing more). Expanded, it takes the trail's width, with questions and rules side by side on a wide screen (the rules get the wider share). Each question is one line, its answer and confidence, flagged as a close call when the runner-up is within 15 points of the chosen option; a click opens the bars of every option or level (a `yes_no` with the threshold of each rule that reads it). The rules come in groups: the ones that fired, with their action's outcome and what made them act (the answer the tick measured and every bar the condition sets: a threshold, a confidence, a level range), together with, on a line written before `merged`, a rule the line names nowhere (it fired an earlier rule's identical action); the ones whose conditions held but whose trigger held them back ("Already acted"), apart from the fired since they did not act this tick; the near misses, within 15 points of their threshold or a score one level outside the range, each on one line on a wide screen with its short reason ("sentimento at level 1 (negativo), score 1.46; asks for level 0 (muito_negativo)": a one-level range names that level, a real one reads from-to); and the rest, folded into one line ("27 rules did not fire") that opens the list. The option and level descriptions and the rules' thresholds come from the agent's settings only when the line's `block` is the current block's mark; otherwise the marker shows what the line stored and nothing else. A tick that was skipped for a reason the operator must fix (an invalid block, a credential the vault cannot hand over) or that failed (the classifier's call) is a marker in the error style with its reason. The answers, misses and outcomes are option names and numbers only, so they are shown whatever `observability.logToolValues` says; an action's `args` and `missing` can carry what a custom tool was given, so they reach the page only when the agent logs tool values, the same rule the action markers of the tick follow. The trail carries the newest 60 ticks on top of its 60 tool and proactive rows, so an observer that decides on every message does not push the tool rows out, and a tick is drawn right before the action markers of its own turn, though its line is written after them.
- **Scope.** A labels or attribute action shows where it writes (the conversation unless `args.scope` says the contact) and the attribute picker lists that scope's keys; changing the scope drops the key, which belonged to the other one.
- **Labels and attributes** come from the accounts of the inboxes the agent answers or observes (`agentInboxScope`): a monitoring agent is attached through `InboxObserver` and answers none.
- Cards open folded, one line per question and per rule, so a block of thirty rules reads as a list; a card with a problem is always open, and stays open once the problem is fixed, so the keystroke that completes a field does not fold the card it is typed in.

## Testing an agent on a conversation

A tenant admin can run an agent's SAVED questions and rules once on one conversation and see what it would do, without anything acting (issue #1499). The question it answers is the one an operator has after editing a rule: on this conversation, which I know, would the agent now act? The button is **Test an agent** in the conversation page's header (`DecisionsTestButton`, `DecisionsTestModal.tsx`), shown to tenant admins; the modal lists the tenant's agents that observe on Questions and rules (picked already when there is one), and the result is the conversation timeline's own decision marker (`DecisionTickMarker` with `test`), open on its rules: "Test, nothing was run", how many rules would act, each fired rule as "would run" and each rule its trigger holds back as already acted. The result lives in the modal and is never stored.

The test (`tryDecisionsAgent`, `src/modules/decisions/try.ts`; `POST /v1/conversations/:id/decisions-test`, MCP `conversation_decisions_test`) is the tick without its writes:

- **The same evidence and the same classifier.** The conversation is read by `readObserveEvidence`, what the tick reads (the window, the labels, the protected labels, the reset point), with the agent's classifier and vault key. A conversation with no customer message is skipped before the call, as the tick is, so it costs nothing. So is one the contact gate's conditions leave out (`skipped: contact_gate`), asked as the tick asks them before it spends anything, without its endpoint and without a line; the tick also asks them again between actions, of what the earlier ones wrote, and a test does not.
- **Nothing acts.** The agent's toolset is built as the tick builds it, before the paid call and under the test's 60-second deadline (discovering its MCP servers, which have no timeout of their own; a toolset that cannot be built is `failed: toolset_build` and costs nothing), and its arguments are filled from the same context, so a rule whose tool is not granted is `not_granted` and a required argument left empty is `missing_value`, as on a tick. `applyDecisions` then runs with `dryRun`: the rules are evaluated, deduplicated and counted against the call budget as on a tick, a rule that would act is reported `decided`, and no tool is invoked. The fences a tick asks inside the tool are asked by the test in rule order (`withFences`): a tool's precondition (`settings.toolPreconditions`) of the same mirrored attributes, and a `set_labels`'s protected and allowed labels on every scope, through the handler's own `applyLabelDelta` (of the labels read for the evidence on the conversation, and of the contact's, read when a rule writes them; a card's are not read, so there a refusal is told whole only when the call asked nothing else). A contact write on a conversation with no contact linked to Chatwoot is `no_effect`, as on a tick, and its attribute is not counted as written. So is a label rule that names no label. What a tool finds out only by running (a card that is not there, a write Chatwoot refuses, what an HTTP or MCP tool answers) is not previewed: the test says the rule would act, and the tick reports what happened. What an earlier rule would write (an attribute, a label set, with its fixed arguments) counts, since on a tick the later fence reads it. A write a fence refuses whole is `refused` with the fence; one it refuses in part reads "would run, in part". The count "N rules would act" includes the rules merged into an earlier rule's identical action.
- **The conversation's trigger state is read, not claimed** (`readLatchedRules`): a rule that already acted here and acts once is reported as held, as the real tick would hold it, and the latch is not touched.
- **No `observe` line.** A test is not a tick of the conversation, so the timeline and the activity counts beside each rule do not move.
- **Billed as the playground.** The classification is recorded under node `decision` with `source: "playground"` and gated by the playground's ceiling (`assertPlaygroundSpendCeiling`, 429 when reached), never the inbox's: testing must not spend the budget that keeps the agent working for customers.
- An agent that is not a monitoring agent on Questions and rules is refused with `errors.agentNotDecisionsObserver`; an invalid block or a key the vault cannot hand over returns the marker's error, with the same reason a tick would log.

## How the actions reach Chatwoot

Actions run in rule order, one at a time, each after the observation's fence. The exception is the actions whose tool commits calls that arrive together as one write (`sharedWriteKey`, `src/graph/tools/native.ts`): every `set_labels` on the conversation, and every `set_custom_attribute` on the conversation. Those that are NEIGHBOURS in rule order are dispatched together, after each has passed its own fence, so three attribute rules cost one read and one write instead of three of each, and two label rules cost one read and one write of the set they add up to; the label write and the attribute write go out side by side, since they touch different things. Nothing else changes: the same actions run, the line lists each one in rule order with its own outcome and its own label counts, and a write Chatwoot refuses fails exactly the actions that rode on it. Only neighbours are grouped, so no action ever runs ahead of one the rules put before it: a note or a transfer between two attribute rules keeps them apart, and putting the label and attribute rules next to each other is what makes them one round trip. A tool that carries a precondition (`settings.toolPreconditions`) is never grouped: its condition reads what the rules before it wrote, so it waits for them. And a watcher whose contact gate has conditions (`settings.contactAuth.rule`) groups nothing at all: the fence asks those conditions of the same labels and attributes the actions write, so an action that takes the conversation out of the rule must have landed before the next one is admitted, and such a watcher pays one read and one write per action. The grouping is asked again once the group's fences have run, since they are what read the live settings: a gate saved while the provider was answering is seen there, and the group falls back to its first action alone. The same watcher's tools do not share a write either (`ToolCtx.writesAlone`), which is what covers the `llm` engine, whose model calls its tools in parallel: each call queues an entry of its own and is admitted by its own fence after the write ahead of it. Calls that had already joined one write when its fence first read such a gate are split there: the first is written, and the others follow inside the same queue entry, one read and one write each and each asked again, so a writer queued meanwhile stays behind all of them. The mirror updates of one conversation's attributes are applied in the order the writes reached Chatwoot, so two neighbouring rules naming one key leave the mirror on the value Chatwoot kept. A fence that refuses while a group is being admitted stops the whole group, since none of it has started. An action whose arguments its tool's schema refuses is dispatched in its place and fails before its handler runs, so it writes nothing and rides inside the run it sits in: an invalid rule between two attribute rules is that rule's `invalid_arguments`, and the two around it are still one write. The label rules are applied to the labels the tick read for the evidence, one provider call earlier (`ToolCtx.conversationLabelsRead`, trusted for ten seconds), and a later label write of the same tick to the set the earlier one left; the price is that a label another writer puts on inside that window is not in the set written back, which is why the `llm` engine, whose model thinks for seconds, reads again. A decision with labels, three attributes and a note on a conversation shorter than a page is six requests: the window, the labels, the label write, the attributes read and written, the note (issue #1177).

## The tick's outcomes

One `observe` line per tick, with `engine: "decisions"`, the provider and the requested model (on every exit, a fence refusal after the call included), and:

| Outcome | Status, level | Detail |
| --- | --- | --- |
| Decided | `ok`, `info` | `block` (the mark of the questions and rules the tick ran, on every decision line), `modelVersion` (what the provider says answered; TypeSafe resolves the alias; kept only when it is the requested model, its dated snapshot or, on TypeSafe, a numeric `jev-` version, null otherwise, since a credential's base URL may point anywhere), `answers` (numbers and option names only), `actions` (`ran`, `refused` with the `fence` that refused the whole call: `protected_label`, `allowed_labels` or `precondition`, `no_effect` when the tool could not write (the contact or card it targets is not there, or the run was called off while it waited; a label already as asked is still `ran`), `not_granted`, `over_budget`, `failed` with `invalid_arguments`, `tool_error`, `missing_value` (with `missing`) or `ambiguous_tool`, plus `committed: true` when the call wrote something that stays before it threw (a handoff's note); a call a fence refused only in part, such as a free label beside a protected one, is `ran` with `fence` and `partial: true`; `merged` names the later rules the action answers for; a custom tool's entry carries its `args`, above), `held` (the rules whose trigger held them back, with the trigger), `notFired` (per rule, the first condition that failed and why: `below_threshold` with the value, threshold and measure, `other_choice`, `outside_levels`, `refused`, `unanswered`), `acted`, `messagesRead`, `labelsBefore`, `labels` |
| An action could not run | `ok`, `warn` | as above, with a `not_granted`, `over_budget` or `failed` action |
| Block invalid | `skipped`, `warn` | `skipped: "decisions_config_invalid"`, `problem` naming the field |
| Credential unresolved | `skipped`, `warn` | `skipped: "decisions_credential_unresolved"` |
| Trigger state unreadable | `error`, `info` with `willRetry` while the job retries, `warn` on the last attempt | `failed: "trigger_state"`, before the provider call |
| Provider failed | `error`, `info` with `willRetry` while the job retries, `warn` on the last attempt | `failed: "decision_call"`, `failure` in the closed vocabulary (`HTTP 503`, `timeout`, `provider error`); the response body is never read into the error |

A problem never falls back to the `llm` engine: an operator who chose classification did not choose to pay for a model turn when it is misconfigured. The conversation text is sent to the provider and never written to the line.

## Cost

A successful call is recorded through `recordDirectUsage` under node `decision` (`USAGE_NODE_IS_AGENT_TURN`: false; `SPEND_GATE_FOR_NODE`: gated, by the same check the `llm` tick asks right before its call). Both providers bill input tokens only, so the row carries `completionTokens: 0` even when TypeSafe reports output tokens. `gpt-6-luna` is priced by the LiteLLM table's input rate ($0.10 per 1M, the rate the Decisions guide states). TypeSafe is not in that table; its rate is pinned in `PUBLISHED_RATES` (`src/modules/pricing/price.ts`), $0.042 per 1M input tokens, from docs.typesafe.ai/models read 2026-10-07. `typesafe` is in `PRICE_OVERRIDE_PROVIDERS`, so a tenant may override that rate and `reprice-usage --provider typesafe` corrects past rows. A failed call records nothing.

## Known limits

- Text only, on both providers. OpenAI accepts inline images; sending them to one provider and not the other would make the two incomparable on the same agent, and the observer already reads image descriptions as text.
- Questions are independent. A question that depends on another's answer needs a second request (OpenAI says so); not supported.
- No chat `modelConfig` is needed. The observe job loads the agent with `chatModelUnused` when the engine is `decisions` (`loadAgentConfig`): a missing or unbuildable bag stands in as the default, with no key, only to name the run, and its credential is not resolved, so a deleted chat key does not stop the tick. The `llm` engine still requires a model that builds. Config health does not report the chat model of a decisions watcher (`model`, `modelNotRunnable` and the endpoint keys), and memory compaction stands down for one (`compact.ts`), since compaction is what a chat model would run.
