# Execution-flow logs, alerting & retention

Verbose, per-stage operational telemetry for agent turns, plus external alerting and the read/UI surface. Lives in `src/modules/flowlog/`.

## Model

- **`ExecutionLog`** (`execution_logs`): one row per pipeline stage per turn (`route`, `stt`, `vision`, `embed`, `generate`, `normalize`, `tts`, `tts_check`, `split`, `handoff`, `memory`, `observe`) plus errors. `turnId` correlates a turn's stages; `source` is `inbox` | `playground`. High-write, retention-bounded. **NEVER carries message text / PII** — `detail` is allowlisted ids/counts/enums and is passed through `redactSecretsDeep` on write; `errorMessage` through `sanitizeErrorMessage`. Both cut through `scrubbedClip`, which repairs, scrubs and only then cuts: the patterns have minimum lengths and no maximum, so a cut landing inside a credential leaves a prefix too short to match and publishes the rest of it. `detail` scans the cut plus a margin, because a tool result is not bounded by anything and cannot be read end to end for every line; the margin is counted in REPAIRED characters, since the repair deletes every NUL and a value full of them would otherwise spend the whole margin on characters that no longer exist; `errorMessage` scans whole, because it already walks the string to flatten it and because the words after a token are the message. A JWT is recognised by its head as well as whole, since its match needs two separators that a real payload puts hundreds of characters in — no margin recovers a structure that was cut. That promise is what makes the Logs page and `GET /v1/logs` exportable, so it is checked rather than asserted: `tests/modules/flowlog-detail-pii.test.ts` runs a real turn with a marker seeded into each customer-authored channel (the contact's name and phone, a custom attribute, the message itself) and fails if any of them reaches any row of that turn. The harness seeds the AGENT'S OWN REPLY as well, and walks the AUDIO path, because those two gaps were found together (issue #763): every scenario used to end in a text reply, so the `tts` line was never written and the promise was never read on it, and no marker covered the reply, which is the widest channel of all — it says the customer's name and number back at them. A change that logged the whole spoken reply on the `tts` line passed this file with 12184 tests green. A `memory` line is written by a scheduler job rather than a turn, so that harness cannot reach it; `tests/modules/memory-dead-letter.test.ts` carries the same check for that road, with the marker in the place only that road exposes — the provider's own refusal text, answering a request that carried the whole transcript. `detail` and `errorMessage` are checked together, since an operator exports the row and not the column, and the harness drives a FAILING stage as well as a succeeding one: every scenario used to end in a turn that worked, so `errorMessage` was null in every row the invariant read and half the promise was asserted against nothing. It is the half with the wider door, because `detail` is assembled by us key by key while an error message is written by whoever threw. What a provider failure is allowed to say is one closed vocabulary (`timeout`, `HTTP <nnn>`, `provider error`) owned by `src/lib/provider-failure.ts` and applied at the boundary where the call is made, which is the only place the provenance of an error is known; the vendor's own words are kept as the error's `cause`, so the process log still carries them. The same substitution is what keeps them out of `alert_deliveries.summary`, `conversations.last_error` and the private note a failed turn writes into the customer's Chatwoot conversation, since all four read the message of whatever was thrown.
- **`AlertChannel`** (`alert_channels`): a Discord or generic-webhook sink. `url` is an `encryptJson` blob (a Discord URL embeds a token) — stored encrypted, returned only **masked** (`scheme://host/…`); the operator re-enters it to change it (like the vault). `secretRef` is an optional vault ref for the generic-webhook HMAC, and unlike the url it is RETURNED by the read (alongside the derived `hasSecret`): it is a `vault:<id>` reference and never the secret, so the console can show WHICH credential signs and let the operator take it away. The write is three-valued — absent leaves it, null clears it, a value sets it — and the editor picks between them by comparing the picker against what it loaded: untouched OMITS the key. Omitting rather than echoing matters because this column accepted any string until #126, so live rows hold `vault: 7`, `vault:0007` and bare names, which every reader resolves and `requireVaultRef` refuses. Sending the key unconditionally, on a blanked picker, is what made every save of the edit dialog unsign the channel (#435).
- **`AlertDelivery`** (`alert_deliveries`): the dispatch ledger — **no PII**, only `stage`/`level`/`summary` + a coalesced burst `count`, plus the `turn_id` and `conversation_id` of the window's first event (issue #665), which the body turns into console links.

All three are in `TENANT_SCOPED_MODELS` with the standard `tenant_isolation` RLS policy.

## Emit (`stages.ts`, `service.ts`)

- `FLOW_STAGES` / `FLOW_LEVELS` are validated Strings, never Prisma enums (adding a stage is no migration).
- `emitFlowEvent(ctx, ev)` is **fire-and-forget**: it schedules the row write without awaiting (unlike `UsageCapture`, which awaits its single billing row) so the hot WhatsApp path never pays log-write latency; losing a line at process shutdown is acceptable. Each emit has its own try/catch — a failed write (or alert dispatch) never escapes into the turn. That swallowing is why the CONTENT of `detail` has to be writable by construction: `detail` is a `jsonb` column, Postgres refuses an unpaired surrogate inside one outright, and a refusal here is invisible — no error, no row, just a stage line that is not there. Every string (and every key) of `detail` therefore passes through `replaceLoneSurrogates` on the way in, and every text cap in the tree cuts with `clipText` so a truncation cannot manufacture one; `tests/lib/astral-cap-sweep.test.ts` is the list of those caps.
- `withFlowStage(ctx, stage, meta, fn)` measures `fn`, emits `ok`/`error` (then **re-throws**), and is a zero-overhead pass-through when `ctx` is absent.
- `settleFlowEvents()` awaits every emit already scheduled, and `scheduledFlowWrites()` counts them. **Nothing in production calls either** — the SIGTERM handler exits synchronously and losing a line at shutdown is acceptable (above). They exist because a caller that EMPTIES `execution_logs` needs the difference between "the write did not happen" and "the write has not landed yet": a plain `DELETE` clears the rows that exist, and the write the previous case only scheduled lands afterwards, into a table the next case believes it owns (issue #375). In tests that clear is spelled `clearFlowLog(db, where)` (`tests/utils/flowlog.ts`) and nothing else — `tests/modules/flowlog-reader-scope.test.ts` fails on a raw one, alongside the reader-scope ledger it already carried.
- A turn generates one `turnId` (`crypto.randomUUID()`) in `runLoadedTurn` / `runPlaygroundTurn`. STT is **eager** (before the turn), so it has its own `turnId`; correlate it in the UI by `threadId`.

### Seams wired

`generate` (runtime + playground graph invoke; carries two lines about the configured fallback provider, both at level `warn` because a turn that used it SUCCEEDS and would otherwise read as clean: `{fallbackFrom, fallbackReason}` when the second provider took the turn — `fallbackReason` is already the closed vocabulary's word, never the vendor's sentence — and `{fallbackUnavailable}` when a fallback is configured and could not be built, which is the state indistinguishable from having configured none. A third, `{fallbackFailed}`, records that the fallback ALSO failed, and it is the one at level `info`: the `generate` stage emits its own `error` when the turn throws, and alerts coalesce on (channel, stage, level), so a second `generate`/`error` for the same failure pages the operator twice. The stage owns the alarm; this line only says which model died. All three lines are stamped with the FALLBACK's `provider`/`model`, never the primary's: the handler that writes them has the primary's labels in scope and the working model's name on a warning about the broken one is how these lines were published for one round; also carries the history-ceiling line `{historyKept, historyDropped, historyTokens}` at level `info` when a turn had to drop older attendances to fit `limits.maxHistoryTokens` — counts only, never a fragment of what was dropped), `stt` (`transcribeInboundAudio`), `vision` (`extractInboundFile` + the playground's `extractPlaygroundFile`; the two-step playground UI logs it under step 1's `extract` call), `tts` (`synthesizeReply`, one line per synthesis with `detail.attempt`), `tts_check` (the corrupted-audio detector's verdict on a synthesized reply, issue #779: `{mode, attempt, outcome, corrupted, score, verdict}`, `warn` whenever the audio was corrupted or the detector could not answer; see [`tts.md`](tts.md)), `split` (`deliverReply`), `channel_error` (a reply the CHANNEL refused after Chatwoot accepted it, issue #587: the failure arrives as a `message_updated` carrying `content_attributes.external_error` on a message the route's own bot sent, and the line is `{messageId, code, codeRead, class, action}` at level `warn` — `class` is `media` (131052, 131053: the same reply goes out as text once, `action: "text_fallback"`, or `"no_text"` when the message carries none), `delivery` (131026, 131047) or `unknown`, and `action: "none"` for the last two; never the channel's sentence nor the reply; see [`tts.md`](tts.md)), `route` (the step before all the others: the delivery is matched to the agent that answers this inbox, and the line is written only when there is NONE — `{outcome: "no_agent", chatwootInboxId}` at level `warn`, `agentId` null by construction and the `inboxId` naming what to repair. The mirror creates an `Inbox` row for any inbox that sends traffic, so an inbox nobody bound is a real row that consumes deliveries and answers nothing; both exits that reach it write this one line through `emitUnroutedMessage` (`flowlog/unrouted.ts`) — the webhook's direct turn, whose `runAgentTurn` returns `no-agent`, and the debounce flush's bail below its gate, which does NOT advance the watermark so the burst survives a later rebind. Issue #318), `handoff` (an ownership gate that closed: the webhook's per-event gate, the debounce flush's gate, or the assignee re-check in `runLoadedTurn`), `memory` (a closed attendance folded into the contact's memory by the `MEMORY_COMPACT` job — `{attendanceConversationId, messagesCompacted, summaryChars, reason}`, at level `info`; counts and one id, never a fragment of the transcript that was compacted, and never the summary itself). `observe` (what a watching agent did to a conversation it does not answer, written by the `OBSERVE` job (issues #477, #568) — `{reason, acted, toolCalls, messagesRead, labelsBefore}` at level `info`, plus **`labels`** when the turn wrote any: one entry per scope, `{scope, added, removed, after}` (issue #635), on whichever line closes the tick — a refusal and a failed model call carry it too, because a write that already committed is never retried and the line is its only record. **Counts, never titles**: `set_labels` takes the model's array and Chatwoot CREATES a title it does not have, so the account's own label list stops being evidence one cache refresh later — a filter against it would name the invented string itself. Which labels moved is answered by the operator-declared list (`settings.setLabels.allowed`, issue #638): when the agent has one, each entry also carries `addedTitles`/`removedTitles`, the moved labels that are IN the list (operator configuration, not message text), and under `outsideAllowed: "accept"` a count `outsideAllowed` of the titles that went in from outside it, never their text. Without a list the entry is the four counts. A turn that is not an observation (a reply, a follow-up) has no line of its own to carry these, so each label write there is its own `tool` line with the same fields plus `{tool: "set_labels", phase: "labels"}`. `error` when the model call itself failed (`{failed: "model_call"}`, `warn` instead when a tool had already committed, which stops the retry); `status: "skipped"` with `{skipped}` when the tick stops without an answer: at `info` for every reason that is the world moving under it (a newer message re-armed the row, the conversation reopened or was reset, the operator switched the agent off, changed its analysis or took it off the inbox, a window with no customer message), because each is the tick being right to stop and nobody has anything to do about it, and at `warn` only for the spend ceiling (issue #611; the per-refusal decision is `REFUSAL_ENDING` in `observe/job.ts`). Label titles and the operator's own group names only, never the model's `reason` sentence, which goes into the private note on the conversation and nowhere else.) **`embed` is in the vocabulary but not yet wired** — RAG search runs inside the `generate` span, so an embedding failure surfaces there; threading a flow context through the shared toolset builder is a deferred follow-up.

The `guardrail` line records what the guardrail DID (`direction`, `action`) and the policy keys it can name. Both model-written fields are handled at the emit rather than trusted: `rationale` never enters the row at all (it explains what in the message violated the policy, so it quotes the message), and `categories` is filtered to `GUARDRAIL_CATEGORY_KEYS`, the keys the prompt actually asks for, with anything else counted as `categoriesUnnamed` (`src/modules/guardrails/log-categories.ts`, decision table in `tests/modules/guardrail-log-categories.test.ts`). The count is what keeps a violation visible when the row cannot name it: an operator's `customPolicy` is given no key by the prompt either, so a violation of it has no name to record. The full verdict still reaches the operator wherever the caller announces it: on the inbox path a private note on the conversation the text came from, and in the playground an entry in the turn's own trace (`GuardrailAnnounce`, issue #136).

The `generate` line also carries `detail.systemPrompt`, so an operator can inspect the prompt the agent was given on that turn, as the **audited** version and never the resolved one (`src/graph/prompt-audit.ts`). Resolving is where the customer enters a prompt: `{{nome_contato}}` becomes a real name, and the attribute-context block (whose values are, by its own builder's words, "ultimately customer-authored") is appended whole. So the values go and their provenance stays: a resolved context variable is written as `{{nome_contato: string(11)}}`, a time variable keeps its value (no person authored it), a placeholder that did not resolve stays literally as it was typed, and an appended block is reduced to its label, its size, and the keys the OPERATOR selected where the block has such keys (the authorization-context block has none: those keys were authored by the operator's endpoint, per contact, so they are customer data like the values). The operator's own text is untouched, which is what the field is read for. The rule is a pure function with a decision table (`tests/graph/prompt-audit.test.ts`); `AgentConfig.systemPromptAudit` is built beside the real prompt, from the same parts, and is never given to a model.

A stage that talks to a provider names **what it sent**, not only what we call it internally: the `tts` line carries `detail.providerFormat` (`opus_48000_64`) beside `detail.format` (`ogg_opus`, our container name), and its `errorMessage` carries the provider's own error code when the failed response supplied one (`TTS elevenlabs failed with 400 (voice_not_found)`). The response BODY is still never stored — only a slug-shaped code, so free-text provider/billing detail cannot ride along. See [`tts.md`](tts.md).

### `dead_letter`: a unit of work the system gave up on

The one stage that is about no turn at all, and the only one written by four different subsystems (issue #356). A **terminal** failure is work the platform accepted and will not retry: a scheduler job past its budget, an alert the bus could not deliver, an inbound integration event that cannot be processed, a document that will not be indexed. The operator has no way to infer any of them — nothing happens afterwards, by definition — so the row IS the report, and `detail.unit` (`job` | `alert_delivery` | `inbound_delivery` | `knowledge_document`, `stages.ts`) says which bus, with the ids to act on beside it. It is one stage rather than four because a channel subscribes to a stage, and "tell me what the system gave up on" is one subscription.

The **level is decided per site, never defaulted**: `error` where work was accepted and lost, `warn` where the operator has their own way back to it (a failed document shows FAILED in the knowledge base with a re-index in reach). Nothing is `info`, because `AlertChannel.minLevel` does not accept it and a line nobody can subscribe to is not an announcement. For scheduler jobs the answer is per KIND and lives in `JOB_DEATH_LEVEL` (`src/modules/scheduler/lanes.ts`), a `Record<SchedulerJobKind, FlowLevel>` beside the lane tables: a kind added to the enum does not compile until its death has been given a meaning.

The scheduler is the biggest half and it announces at ONE place — `dispatchDeadLetter` in `scheduler/worker.ts`, which both roads to `DEAD` converge on (`failJob`'s cap, and the reaper via `announceReaped`). A kind may still register a richer, conversation-attached hook (`MEMORY_COMPACT`, `DEBOUNCE`), and a registered hook OWNS the announcement including the decision not to write one.

**The alert bus is the one unit that can never be alerted about.** Its own dead delivery is announced in the trail like everything else, but `dispatchAlertsForEvent` refuses to turn that line into an alert: routing it would queue a delivery to the channel that just died, which dies and queues another. Coalescing does not bound it (it bumps a PENDING row, and the row this would follow is DEAD), and excluding the dying channel does not either — two broken channels would alert about each other forever.

`tests/modules/terminal-failure-fence.test.ts` is the census: every write of a terminal status in `src/`, what announces it, and a sweep that fails while one sits outside the list.

### Tool lines and integration failures

`ToolFlowLogger` (`src/graph/tool-flowlog.ts`) emits one `tool` line per tool call. **A tool call's arguments and result are stored as their SHAPE, never their values** (`describeShape`, `src/modules/flowlog/shape.ts`): `{ cpf: "12345678900", limit: 5 }` is written as `{ cpf: "string(11)", limit: "number" }`. Arguments are whatever the model chose, shaped by an operator-authored schema, so a tool that takes a document number or an address would otherwise write exactly that into a column documented to hold none of it, and `redactSecretsDeep` cannot help — it keys off credential-shaped NAMES, not off a value that is sensitive by content. A tool result is a provider's response body and is no more allowlisted than the arguments that produced it. Keys are named only where their provenance is known: the top level of the ARGUMENTS, matched against the parameter names that tool declared (`toJsonSchema(tool.schema).properties`, handed to the logger with the toolset). A key the model invented under a free-form record parameter, every key of a nested object, and every key of a result are counted rather than named, because none of them has a declaration behind it. The failure TEXT of a failed tool lives in `errorMessage`, under `sanitizeErrorMessage`, and keeps only the part WE wrote: the first line. A tool that RETURNS a failure returns a string built to serve the model, and for an operator-authored HTTP tool that string is `HTTP <status>` followed by the other end's response body, and a business API answers a failed lookup with the customer's own record in it. Since the newline is ours and `toolFailure(...)` is only ever called with a message we compose, the first line is the diagnosis (`HTTP 422`, `Google Calendar returned HTTP 401.`) and everything after it came from the other end. Same rule the `tts` line follows with the provider's error code. `logToolValues` keeps the whole string, exactly as it keeps the arguments and the result.

**The escape hatch is per agent**: `agent.settings.observability.logToolValues` (`src/modules/flowlog/settings.ts`), off by default, surfaced on the editor's **Logs** section beside the other behavior blocks (and therefore on REST + MCP through `BEHAVIOR_SETTINGS_KEYS`). The shape answers "what happened and in what form"; it cannot answer "which record did it look up", and for a production turn this table is the only operator-visible record of what the model passed to a tool (the conversation does not show tool arguments, and its trail is built from these same rows). Turning it on stores the values as sent, for that agent, which is the granularity the workflow actually has: switch it on for the agent you are investigating, reproduce, switch it off. It is deliberately not gated by edition — taking the values away by default and charging to see them again would leave the Free edition with no way to find out what a tool received. A tool that **throws** is logged `warn`/`error` via `handleToolError`. A tool that degrades gracefully — returns a friendly string to the model instead of throwing (toolpacks, operator HTTP tools) — marks provider/credential failures with `toolFailure(...)` (`src/graph/tools/failure.ts`, built via `failableTool`): the model still sees the exact same string, but the line is logged `level: warn`, `status: error`, with the string as `errorMessage` — so alert channels with `minLevel: warn` fire on integration failures (expired OAuth, provider outage, rejected payloads). Business-level replies ("no free slots", policy limits, bad model input) stay `info`/`ok` — they are normal operation. For operator-authored HTTP tools every non-2xx counts as a failure **unless the tool declares it as a result**: `ToolDefinition.expectedStatuses` (editor field "Statuses that mean 'no result'", `expectedStatuses` on REST, `expected_statuses` on MCP) lists the statuses this API uses as ordinary data — typically `404` for a lookup where "no record" is the answer. Those responses stay `info`/`ok` and reach no alert channel; every other non-2xx is unchanged. Empty is the default, so nothing moves until an operator declares something. The model-facing contract does not change either way: the tool returns the same `HTTP <status>` text with the same body, so an agent that already handles "not found" keeps working. This exists because coalescing dampens a burst, not a steady stream — a declarative lookup that answers 404 all day turns the alert channel into noise, and noise is how a real outage gets missed. Note the flip side: a status listed here is a status nobody will be paged about, so `401`/`403` belong on that list only if the operator genuinely means "this API answers that for a normal question". Some entries are dropped rather than stored, and the drop is visible because the field shows the normalized list back: a `2xx` (already a result, so the entry is a harmless no-op), any `1xx` (`fetch` consumes informational responses itself and exposes only the final one), and the five redirect statuses `301`/`302`/`303`/`307`/`308` — the tool fetches with `redirect: "error"`, so one of those arriving with a `Location` rejects before any status is inspected. The last two would be promises the runtime cannot keep: a status that never reaches the check can never suppress an alert. Other `3xx` codes are delivered normally and stay declarable (`304` for "nothing changed" is a genuine "no result"). The rule is one function, `isExpectedResult` in `src/graph/tools/http-status.ts`.

**The other escape hatch is the SIZE of what is stored**: `agent.settings.observability.fullDetailUntil` (issue #58). Every string in every `detail` is cut at 2,000 characters on write (`MAX_STRING`, `src/lib/redact.ts`), and the field where that bites is the audited system prompt on the `generate` line — a long operator-authored prompt stops being readable exactly where the operator stopped being able to check it. While the mode is armed, every flow line of that agent — reactive turn, follow-up and playground alike — keeps its `detail` strings whole, under a ceiling of `max(2000, AGENT_PROMPT_MAX_CHARS × 3)` **that is also a budget for the whole line**: a per-string cap bounds no row, since `detail` is a tree and nothing bounds an object's key count, so fifty leaves at 300k each would be a 15 MB row. The number is spent as the walk proceeds, and what is charged is what is WRITTEN (the `…[truncated]` marker is bytes in the column too, and so is the `‹redacted›` the key layer writes in place of a credential-named field — a tool result full of `password`-ish keys would otherwise grow the row one placeholder at a time). Past exhaustion the remaining leaves go out **empty**, marker included, because `truncate` appends its marker whenever the string is longer than the allowance and an allowance of nothing makes that every string, empty ones included — one marker per field is an allowance that grows with the field count, which is not a bound. The marker on the string that spent the budget is what says where the row was cut. The `generate` line never notices any of this, holding one string; a tool line under both switches is where it bites. That ceiling is derived rather than chosen: the audit is the operator's own template with its context placeholders rewritten as `{{canal: string(1234)}}`, which expands it by 1.08x on ordinary prose and by at most 2.56x in the worst case the closed context-variable set allows, and `detail` also carries tool results that nothing bounds, so the cap is raised rather than removed.

It is stored as **the instant it ends**, not as a boolean, and that is the mechanism rather than a detail of it: there is no representable state where the mode is on and nobody said when it stops, no writer can arm it without declaring the end, and a deployment that was down when the window closed comes back with the mode already off — nothing has to RUN for it to expire. The `FULL_DETAIL_MAX_HOURS` (24h) bound is enforced in **two places, and they do different jobs**. At the WRITE, `assertSettingsDebugWindow` sits beside `assertSettingsTextSizes` on the boundary every transport converges on (REST create, REST update, the MCP patch) and refuses a deadline past the horizon outright — only what the write introduces or changes, so a legacy bag does not block an unrelated save. At the READ, `readObservabilityConfig` refuses one anyway, because `settings` is an arbitrary bag and a value can reach the column without passing a writer. The read-side bound is a sanity check and **not** a permanent quarantine: the comparison moves, so a deadline 48h ahead is refused today and sits inside `now + 24h` tomorrow. That is exactly why the write refuses it. It refuses rather than clamps: clamping to `now + 24h` would renew the window on every read, turning "too far ahead" into "permanently on". The stored value must be an ISO 8601 instant that **names its offset**: `Date.parse` also reads `08/26/2026 10:00` and resolves it in the server's local timezone, so the same text would mean different moments on two installations. The console arms for `FULL_DETAIL_ARM_HOURS` (half the ceiling) rather than the maximum, because the deadline is chosen in the browser and judged against the server's clock. Both client reads of the window take the server's clock for that rather than the machine's — the component's ticking instant and `observabilityToForm`, which decodes the deadline on load and is the one that PERSISTS, since a window it reads as expired becomes the `null` the next unrelated save writes back (`src/client/lib/serverClock.ts` reads the offset off the `Date` header of responses the page already makes, so it costs no endpoint and no round-trip), which is what keeps the armed window the length the screen names and the warning honest about when the runtime actually stops; the arming gap absorbs what that leaves, namely the header's one-second resolution and whatever the machine drifts while the editor stays open. The reader (`readObservabilityConfig`) resolves it per turn against the turn's own instant, and `storableObservability` is what every writer goes through, because `fullDetail` is derived and persisting it would let a bag and the code disagree.

The two switches are deliberately **not** merged, and neither is the tenant's `langfuse.sendContent`: they answer the customer's PII, database size, and destination respectively. Merging the first two would make "did my attribute block get injected?" start storing CPFs; merging in the third would make a local debug toggle ship customer content to a third party. What IS shared is the warning — `readDebugModes` (`src/modules/flowlog/debug-mode.ts`) is the single condition behind the console's indicator on the editor's Logs section and the `debugModes` block on the MCP agent read, so an operator has one place that says something is recording more than the default, and which.

**A call the SCHEMA refused leaves a line too, and it used to leave nothing at all** (issue #667). LangChain validates a tool's arguments inside `StructuredTool.call`, **before** the callback manager is configured, so `ToolFlowLogger` receives neither `handleToolStart` nor `handleToolError` for a refused call: not a handler it was missing, a callback that does not exist yet. The model does see the refusal (LangGraph's `ToolNode` answers the call with the parse error) and usually tries again, so a turn where the agent tried three times to hand a conversation to a human and never managed to was byte for byte identical, in this table, to a turn where it tried nothing. `logSchemaRefusals` (`src/graph/tools/refusal-log.ts`) wraps the assembled toolset at the one seam every source meets (`buildToolset`, which is also where `applyToolPreconditions` wraps), so the reactive turn, the follow-up, the observation and the playground are covered once instead of four times, and rethrows the refusal untouched: what the model reads, and whether the turn ends, is unchanged. The line is `stage: tool`, `status: skipped` (the tool never ran, so there is no result and no `detail.output`), `level: info` and `detail.phase = "schema_refusal"`, the same field the side-effect and precondition lines discriminate on, so **counting** the refusals of one `turn_id` answers "how many attempts did it spend" without opening any error text. `detail.refused` names the declared parameters the refusal was about (`{ params: ["customerMessage"], issues: ["customerMessage: missing"] }`), and `detail.args` carries what arrived under the same `describeShape` rule an executed call follows. `info` is the level for the same reason the precondition refusal is `info`: the frequency of a schema refusal is decided by the MODEL, so a warn would turn one badly-typed argument into a burst of alerts, while the failure alert of a tool that broke (`warn`) is untouched. The reason is rebuilt from the tool's own declaration rather than forwarded from LangChain: `ToolInputParsingException.output` is `JSON.stringify(arg)`, the arguments verbatim, and a zod `unrecognized_keys` message quotes the key the model invented, both of which are exactly what the argument side of a tool line refuses to write.

**The `skip_reply` line carries one thing no other tool line does** (issue #726): `detail.turnDelivered`, whether the TURN had already put something in front of the customer when the agent decided to stay quiet. It exists because that line is the only one whose operator-facing label asserts something — a silence — and nothing downstream can check the assertion: the tool's name answers both ways (a transfer with a closing line and a transfer that declared it had nothing to say are the same name), and `detail.args` is reduced to a shape. `turnDeliveredToCustomer` (`graph/tools/native.ts`) answers it from the turn's own state — a slow-tool acknowledgement that already left, the handoff's recorded line, or an attachment queued or reserved, asked in that order because it is the order of irreversibility: the ack is on the customer's phone, and the declared silence that drops the other two cannot un-send it — and the runtime hands the SAME reader to `ToolFlowLogger` and to `AgentStatusReporter`, because the live indicator labels the same call with no trail to read. It is stamped at `handleToolEnd` and not at the start, since a model may emit the decision alongside the tool that speaks and `ToolNode` runs a batch concurrently; such a batch does not end the turn (`onlySkipped`), so a turn can hold two of these lines and the trail projection takes the LAST one. **But no stamp can be the final word**, and issue #639 is why: a LONE `skip_reply` does not end the turn either, so the batch after the decision still runs, and a transfer with a closing line delivers a message after the only line that stamped anything. So the runtime writes the turn's own answer when the turn ENDS — a `generate` line carrying `detail.turnDelivered` with what actually went out (`turnReachedTheCustomer`: a balloon, an attachment that landed, or a slow-tool ack, counted in three different units because that is how the three roads to a customer are measured), emitted only on turns where the silence tool asked, since this table is high-write and a turn with no silence marker has nothing to label. The trail prefers that line and falls back to the stamps, which is what a turn written before this shipped has. The two are not the same question asked twice: the stamp is what the turn had COMMITTED to at that instant, which is all the live indicator can ever have, and the closing line is what REACHED the customer. Absent is unknown, never "no": a path with no turn to ask (playground, the observe runner) leaves it off and the screen keeps the plain label.

A side effect that fails **inside a tool that still returns success** (orphan Asaas correlation ref, missing PIX copy-and-paste code, handoff assignment/customer-message failure, attribute mirror write-through, kanban outbound emit, appointment-reminder arm/cancel) is surfaced as its **own** `tool`-stage `warn` line: the toolset builder (`prepare.ts`) binds `onSideEffectError` on `ToolpackCtx`/`ToolCtx` to `emitFlowEvent`, with `detail.tool` naming the tool and `detail.phase` discriminating the side effect. The tool's own line (and the model-facing return) stays `ok` — the call genuinely succeeded. Absent a flow context (playground), these failures stay stdout-only.

## Adding a provider integration

**Read this before writing the first request.** Anything a provider's server authored may be the customer's own content coming back: these requests carry the conversation, the message under review, the audio, the image, the question being embedded, and a refusal quoting the offending field is the ordinary way an API says no. Four operator-facing stores read the `.message` of whatever was thrown — `execution_logs.errorMessage`, `alert_deliveries.summary` (POSTed to a channel the operator configured, so it leaves the installation), `conversations.last_error`, and the private note a failed turn writes into the customer's Chatwoot conversation. `sanitizeErrorMessage` does not save you: it redacts substrings shaped like SECRETS, and a name, a phone number and a case number are not.

One question decides it, and it is **who chose the value**, never what the value looks like. A shape test rescues nothing, because a bare token is exactly the shape of a phone number, a CPF and a first name.

Two ways to discharge it, and a new boundary must pick one:

- **Throw your own error type**, built from a status and a constant, like `SttError` / `VisionError` / `ChatwootApiError`. The status is admissible because the client parsed it out of the status line into a number, and a number cannot carry a transcript.
- **Wrap the call in `throughProvider`** (`src/lib/provider-failure.ts`), which does the same reduction to a closed vocabulary (`timeout`, `HTTP <nnn>`, `provider error`), keeps the original as `cause`, and logs it — the vendor's words belong in the process log, which makes no PII promise and is exported by no product surface.

Model calls need neither: every one goes through `runModelCall`, which reduces what escapes it.

**This is checked, not trusted.** `tests/lib/provider-boundary-sweep.test.ts` finds every file that authenticates to a configured endpoint and issues a request, and fails until that file is listed with the answer it gives. The rule was already written beside nine call sites when the tenth was born without it (issue found by measurement, not by review), which is the whole reason the check exists: prose reaches the module you are editing, and a failing test reaches the module that does not exist yet.

## Alerting (`alerts.ts`, `alert-worker.ts`)

- `dispatchAlertsForEvent` is called fire-and-forget from `emitFlowEvent` for `warn`/`error` events **on `source==="inbox"` only** (a playground error must not page). It matches channels by `minLevel` + stage allowlist and **coalesces**: a pending delivery for the same `(channel, stage, level)` is bumped (`count++`) instead of inserting a new row. The **body** (`summary`, built by `alertSummary`) is `[stage via provider]` plus the event's `errorMessage` when there is one, and otherwise its `status` followed by why `detail` says the line was raised (issue #610): the first cause among `skipped`, `failed`, `outcome`, `state` and `reason` (never `reason` on `observe`, where it names the trigger), then `fallbackUnavailable`, `fallbackReason`, `phase`, `action`, `direction` and `strandedOn` as `key=value`, then the flags `toolLimitHit`, `retriedEmptyResponse`, `silenceTokenSuppressed`, `silenceTokenInReply` and `retry` by name. So `[delivery] error: stranded strandedOn=PROCESSING` instead of `[delivery] error`. It reads **only those keys**, because the alert receives the event before the row is redacted and a tool line's `detail` can carry the call's `args` and `output`; each listed key holds a closed vocabulary at every site that sets it, and a value that does not look like one (a slug with no spaces, 64 characters at most; `fallbackReason` alone may be the provider-failure classifier's short phrase, such as `HTTP 503`) is dropped. A coalesced row keeps the body of the first event of its window.
- **`alert-send.ts` is the one place that turns an alert into an HTTP request** (issue #605): decrypt the channel URL, SSRF guard, resolve the signing secret, build the body, `outboundHeaders`, POST with `redirect: "error"` and a 10s timeout. Two callers, the worker and the test route, and the split is deliberate: the send says WHAT happened (`stoppedAt` is `url` / `secret` / `request` / `response`, where the first two mean nothing left the process) and each caller decides what that means — a row transition for the worker, a sentence for a person for the test. The alternative is the shape next door in `webhooks/outbound/test.ts`, which re-states the outbound worker's rules in its own words and has to be kept in step by hand; a test button that exercises a different path from the real send approves channels whose alerts never arrive, which is the failure it exists to prevent, one level up.
- `alert-worker.ts` copies the outbound-webhook worker (single-leader `globalThis` singleton + reentrancy guard, `FOR UPDATE SKIP LOCKED`, full-jitter retry, `DEAD`, SSRF re-check, `.unref()`). A **coalesce window** (`ALERT_COALESCE_WINDOW_MS`, default 30s) holds fresh rows so the burst count accumulates before the single POST; retries (with `next_attempt_at`) are claimed when due. Discord gets `{ content }` markdown with the `count` and a link back to the console (issue #665): a single event links to `/logs?turnId=…`, plus `/conversations/<id>` when the event had one, and a burst (`count > 1`) links to `/logs?stage=…&level=…` instead, because its members may be unrelated conversations and the ids only name the first. Every link carries `switchTenant`, like the MCP console links, so it opens on the alert's tenant. The generic webhook gets the same two ids as `turnId`/`conversationId` fields in a versioned envelope, HMAC-signed when `secretRef` resolves. **When it does not resolve the alert still goes out, UNSIGNED, and the row says so** (issue #724): a signing secret is a vault reference, and it can stop resolving after the channel was saved — the entry is deleted, or it is created and never filled. Holding the alert back would be the worse trade, because for this bus not arriving is the damage itself and a receiver that does not verify is unaffected. So the delivery row carries `unsigned_reason`, a sentence naming WHICH of the two problems it is, written on every terminal write including `DELIVERED` — the one nothing else marks, and the one a verifying receiver silently threw away. `null` means either it signed or no secret was ever configured. The channel list answers the same question as `signingState` on the DTO, which needs the vault and not just the row: `none`, `ignored` (a secret on a Discord channel), `signed`, `unreadable` (a pre-#126 value naming no entry), `missing`, `pending`. Gated by `ALERT_WORKER_ENABLED` (off on extra replicas — see `docs/deploy.md`).

## Retention (`retention.ts`)

A per-tenant `FLOWLOG_SWEEP` scheduler job, armed at boot for every tenant and self-rearming every 24h, deletes `execution_logs` (and terminal `alert_deliveries`) older than `FLOWLOG_RETENTION_DAYS` (default 30) in RLS-scoped batches.

## Read / UI

- `GET /v1/logs` (`read.ts` + `logs.controller.ts`, TENANT_ADMIN): **keyset** pagination by `id desc` (high-write table), filters `since/until/level/stage/agentId/conversationId/source/ turnId/search`, `source` default `inbox`.
- `GET/POST/PATCH/DELETE /v1/alert-channels` (`channels.ts` + `alert-channels.controller.ts`), plus **`POST /v1/alert-channels/:id/test`** (`channel-test.ts`, issue #605): posts one sample alert through `sendAlert` and returns `{ok, status, error, signed, enabled, durationMs, warning}` synchronously. It **works on a disabled channel** and returns `enabled: false`, because testing before enabling is the normal order and refusing would force the operator to enable an untested channel. It writes **nothing**: no `AlertDelivery` (the sharp one — a PENDING row of the same `(channel, stage, level)` would swallow the next real alert's body through the coalescing bump), no `warn`/`error` flow-log line (`dispatchAlertsForEvent` routes exactly those, so the test would alert about itself), no audit row (the trail records changes). `warning` covers the one case a 2xx does not answer: the channel names a signing secret that no longer resolves, so the sample went out UNSIGNED and a verifying receiver will reject the real alert. The same call is `alert_channel_test` on MCP.
- Frontend: `/logs` (`LogsPage.tsx`, grouped by turn into collapsible cards, keyset Prev/Next) + the **Alert channels** section on the Webhooks page (`AlertChannelsSection.tsx`), with a per-channel **Test** button beside the webhook one.

## Export

`export.ts` is the shared core for a bulk, filtered dump — all three transports project over the one `exportExecutionLogs`. It reuses `buildLogWhere` / `mapExecutionLogRow` from `read.ts` (so an export matches exactly what the list shows), returns rows newest-first up to `MAX_LOG_EXPORT_ROWS` (10000; `maxRows` clamps under it), and serializes to **CSV** (spreadsheet-friendly; the `detail` object lands as one JSON-string cell, RFC 4180 quoting) or **JSON** (structured, lossless). Result carries `content` / `filename` / `contentType` / `count` / `truncated` (never a silent cap — the newest `count` win). Core/additive, like the rest of the logs feature.

- `GET /v1/logs/export` (`logs.controller.ts`, TENANT_ADMIN): same filter surface as the list (minus pagination) + `format` (`csv` default | `json`) + `maxRows`; returns the JSON wrapper (the browser turns `content` into a Blob, like the agent export).
- Frontend: an **Export** button + `LogsExportModal` on the Logs page (picks a time range — presets or a custom window, default last 7 days — and the format, applies the active on-page filters, toasts on truncation / empty).
- MCP: the `logs_export` read tool (`mcp/read.ts` `logsExport` → `server.ts`), same filters + `format` + `max_rows` (default 1000 for MCP, hard cap 10000).

Read before touching anything under `src/modules/flowlog/`, the seam wiring, or the Logs page.
