# Dashboard

The operator's dashboard (`src/client/pages/DashboardPage.tsx`, blocks under `src/client/pages/dashboard/`) is organised by the question an operator brings, not by the table the data lives in: is the agent doing its job, why does it hand over and what are people asking, what does it cost, is it healthy, and what else does it do on its own. This page maps every block to the query behind it, so the next change does not reintroduce a second source.

**Every figure comes from this app's own records.** Money is `llm_usage.cost_usd`, priced when the call was written and re-priceable after (`scripts/reprice-usage.ts`). No figure is read from Langfuse: it samples traces on the client, prices only at ingestion and delivers best-effort, so its sum is not a total. Langfuse appears only as the "Open in Langfuse" link (`DashboardCosts.langfuse`), and the page renders the same numbers with it unreachable; on the stream, its configuration is read on a budget of its own, so a request that spent its budget on the days it computed still gets the link.

## The one filter

Period, agent, inbox and source live in the URL (`?range=7d|30d|90d|12m|all|custom&from=&to=&agent=&inbox=&source=&audience=`, `src/client/pages/dashboard/filters.ts`). `audience` (`identified` | `anonymous`) refines the client source only: it is read, shown and sent under `source=client` and dropped under any other, and every block applies it (`audienceSql`, from the `anonymous` column each turn writes on its usage rows and flow lines). A value at its default is left out, a value that does not parse falls back to its default, and an agent or inbox id this account does not have is dropped from the URL rather than shown as an empty view. What the agent and inbox selects offer comes from `GET /v1/metrics/filter-options` (`src/modules/analytics/options.ts`): every agent and inbox, whole rather than paged, readable by anyone who can read the dashboard. An inbox whose name another inbox of the tenant also has (two connected Chatwoot accounts with a "SAC WhatsApp" each) carries `account: {id, name}`; this page's inbox select and the Dashboards panel editor's inbox filter read it as "SAC WhatsApp · <account>" ("Account 7" while the name has not synced, `inboxOptionLabel` in `src/client/lib/inboxOption.ts`), as the Dashboards panels' rows do. A link's ids are checked against that list only once it has arrived; an unreadable list keeps them. The window is half-open `[since, until)` in the browser's own days (`docs/ui.md`, "A day is defined by the viewer's browser timezone"), and the previous period is the same number of days ending where this one starts; "all" has none.

Every route takes the same query (`dashboardFilterQuery`, `src/api/v1/dashboard.controller.ts`) and every service builds on the fragments of `src/modules/analytics/filter.ts`:

| fragment | means |
|---|---|
| `cohortWhereSql` | **the view's conversations**: created in the window (`conversations.created_at`, when the conversation reached us), in the filtered inbox, and under an agent filter, the ones whose inbox is bound to that agent or that the agent ran on |
| `agentRanSql` | **the agent ran on it**: a real-traffic ledger row that is an agent turn (`node` null or not in `NON_AGENT_TURN_NODES`), by the filtered agent when there is one |
| `outcomeSql` | `classifyOutcome` in SQL (handoff, resolved by the agent, resolved before tracking, resolved by someone else, unresolved); fenced against the TypeScript rule by `tests/modules/analytics-outcome-sql.test.ts` |
| `usageWhereSql` | **the view's ledger rows**: billed in the window, in the source and audience, by the agent, in the inbox |
| `logWhereSql` | the same for `execution_logs`, which carries the same columns; under an inbox filter a line that names its conversation and no inbox (a takeover is logged from the webhook) is its conversation's inbox's. The Logs page reads the same rule (`inboxLogLineIds`, `src/modules/flowlog/read.ts`, bounded by the page size) |

**Every route reads through the metrics pool and answers within a bound** (`src/modules/analytics/budget.ts`, issue #1277). The reads, and the authentication of the `/api/v1/metrics` routes, run on a pool of their own (`METRICS_POOL_MAX`, default 3), so a page load queues there and never takes the connections turns need. Each request has one budget, `METRICS_TIMEOUT_MS` (default 15000), counted from its arrival and shared by the wait for a connection and the run of its reads; past it, or past the lock timeout, it answers 503 (`MetricsTooSlowError`, "try a shorter period, or again in a moment") and Postgres has already stopped the query. A block that gets that 503 says so in its slot, with its retry; any other failure keeps "Could not load metrics." The MCP `metrics_get` and `metrics_timeseries` return the same sentence. Sizes and the budget: `docs/deploy.md`, "Connection budget".

**What a page load costs the database.** The metrics pool runs with `jit=off` whatever the server says (`src/api/lib/pool-options.ts`): these reads are a few large aggregates, and compiling each one on every request cost more than it saved. The flow-log figures (handoffs by cause, silences, where the transfers went, follow-ups) reach their lines through the partial index `execution_logs_dashboard_lines_idx` on `(tenant_id, stage, created_at)`; a new figure over those lines writes a predicate that implies one of the index's arms, or it reads every line of the window, `generate` lines and their stored prompts included. A conversation's outcome and whether the agent ran on it are worked out once per conversation (`outcomeCountsSql`, the labels), not once per figure. The console sends each distinct request once per load: the cost block and the breakdown table share the agent breakdown (`askBreakdown`).

Conversation figures are real traffic by construction (a playground turn has no conversation). Ledger figures follow the source toggle.

## Kept days

A window that starts and ends on local midnights of its zone, which is every window the console asks for, is answered from **kept days**: per-day totals kept in `dashboard_days`, one row per tenant, filter (`source|agentId|inboxId`), zone, local day and section, computed the first time a request needs that day (`src/modules/analytics/rollup/`, issue #1383). Any other window (a hand-written `since` in the middle of a day) goes to the live readers above. Both answer with the same figures, to the last digit, and that equality is what `tests/modules/analytics-kept-days.test.ts` asserts block by block, across windows, zones and filters.

**What a day keeps.** Every section runs the live reader's own query for its figure, narrowed to a range of days and grouped by local day (`sections.ts`), so a window's figure is a merge of its days (`merge.ts`). Three kinds of figure do not add up by summing, and each keeps something that does:

| figure | kept as | merged as |
|---|---|---|
| distinct conversations across days (cost per conversation, a breakdown row's conversations, conversations per handoff cause and target, follow-up conversations, problem conversations) | per day and key, how many of that day's conversations were last seen on each earlier day (`prev`), and for a conversation already seen before the part, the last day it was | the conversations whose `prev` is before the window's first day: each one once, on its first day in the window |
| percentiles (first response median and p90, latency p50 and p90 per model) | a coarse histogram per day, and per bucket every value with its count (sections `conv.fr.<b>`, `ledger.lat.<b>`) | `percentile_cont`: the two order statistics around `p·(n−1)`, read from their bucket, interpolated with the server's own floating-point steps (`lerp.ts` asks the server once whether its build fuses the multiply-add) |
| figures that read a conversation's current state (resolved by the agent, came back after a follow-up) | evaluated when the day is computed | summed; a later change to the conversation drops the day (below) |

Money sums are decimal end to end, and text keys (labels, models, nodes, reasons) are ordered by the database's collation where the live reader orders them.

**Which days are computed.** Today and yesterday are never kept: every request computes them, side by side with its read of the kept days (as it does the flow log's day the retention cutoff falls in), so a view already kept is whole at its first snapshot (the cutoff's day is read as kept for the other families), and so does any day that ended less than 24 hours ago (the day before yesterday, in the first hour after the clocks move forward), since the triggers below queue nothing younger than that. Every other missing day is computed in parts of at most 30 days (15 for the ledger, the widest family), the most recent first, each in its own transaction on the metrics pool within `METRICS_TIMEOUT_MS`; a part that does not fit is split in half and retried, down to one day, and a single day that does not fit is the usual 503. A part is kept as it finishes, so a request that stops halfway leaves its parts for the next one, and a change of period reads every day another period already computed. Two requests for the same view take turns on an advisory lock per tenant, filter, zone and family, and the second reads the first one's days. A day before the tenant's first record (the oldest of its rows, or of the days kept for the view, whose rows the flow-log sweep may have removed) is empty without a query, except a flow-log day past retention, which is no data; such days are counted, not listed, so a window that starts centuries back costs no more than one that starts at the first record. A release that changes any section's query changes the version hash (`rollupVersion`) the rows are keyed by, so rows from an older release are simply not read.

**When a kept day is recomputed.** Triggers queue every late change in `dashboard_dirty` (migration `20261013170000_dashboard_days`): a conversation whose outcome or owner moves (status, `resolved_by`, assignee, inbox, labels, `last_inbound_at`, the first-reply clocks, a first reply found to be the platform's) or that is created or deleted with an old `created_at`, or backdated into an older day, a ledger row written, repriced or deleted, a fresh billed call written on, deleted from or moved off a conversation older than that, or changed in its agent, source, node or turn (whether the agent ran on it is read over its whole ledger, so its creation day moves, and whether a person taking over counts is read on its flow-log days; migrations `20261013170300_dashboard_dirty_fresh_turns`, `20261013170600_dashboard_dirty_fresh_turn_changes` and `20261013170900_dashboard_dirty_backdate_and_turns`), a flow-log line, a knowledge suggestion, a conversation deleted or moved to another thread (which queues the instants of its old thread's suggestions while that thread is still known, and on a move those of the new thread's too, migrations `20261013170400_dashboard_dirty_conversation_thread` and `20261013170500_dashboard_dirty_conversation_new_thread`), and an inbox bound to another agent (which drops every conversation day). Only rows older than 24 hours are queued: newer ones fall in days that are never kept. This covers every writer, the Chatwoot webhook's mirror included, since the trigger sits on the table. The next request settles the whole queue before it reads (`settleDirty`, in batches until none is left, each batch its own transaction on its own budget; a batch that does not fit is cut to a quarter and tried again, so the queue moves whatever its length, and the request waits for it rather than reading a stale day; a batch waits for rows another request is settling rather than skipping them, so nothing is read before their days are dropped). A batch turns its rows into the local days they reach, per family and kept zone, and drops those through the `(tenant, tz, day)` index: a repricing of a whole day (twenty thousand rows) or a restore of a hundred thousand old flow-log lines settles in seconds. A ledger line whose change stays within its own day (a repricing: cost, tokens, duration; not its conversation, day, agent, inbox, source, node, model or turn) is queued without its conversation, since its other days do not move (migrations `20261013170700_dashboard_settle_by_day` and `20261013170800_dashboard_dirty_reprice_inbox`). Settling drops every kept day, of every filter and zone, that the change reaches: for a changed conversation its creation day plus every day it has ledger lines, flow-log lines or suggestions on; for a ledger line the conversation's ledger days, its creation day and its flow-log days (a person taking over counts only after an agent turn); for a flow-log line the conversation's flow-log days. A part keeps none of the days reached by a change its snapshot may not have seen (`changedSince`: rows still in the queue when it checks, however long ago their writer began, and rows a batch settled since it began, which the batch stamps by the database's clock), so a stale part is never kept; a change settled before the part began was committed before it and is in its figures, so the part keeps the days that change reaches, and on a tenant whose old conversations change every few minutes a reload computes only the days a change reached since (issue #1545); and since a change can commit just after that check, a part holds a per-tenant advisory lock shared from the check until it commits, which every settling batch takes alone: a batch that consumes such a change waits for the part's rows and drops them. A percentile's value cells are read after its histogram, so a request checks that the cells come from the same computation as the histogram it already holds (`computed_at` of the histogram's own section and day, since two requests for different blocks compute the same family's days separately); a day dropped or recomputed in between is computed again in memory, whole, and the figures are merged again. A deleted tenant leaves nothing in the queue: its rows go with it, and the rows its cascade would queue are dropped as they are written, since no request could settle them (migration `20261013171000_dashboard_dirty_tenant_gone`). There is no periodic job.

**What "no data" means.** The flow log keeps `FLOWLOG_RETENTION_DAYS`. A flow-log day kept before the sweep reached it keeps its figures for good: nothing recomputes it, and a change to it is ignored. A day older than retention that was never kept has no figures to give, and the console says so on the blocks that read the flow log (handoffs, silences, follow-ups, problems: "no data for N days") rather than showing it as zero. A block with nothing to show over a window with such days does not say there was none in the period: handoffs and silences draw their chart with the "no data" band, and problems say there were none on the days with data (`hasNoData` in `Provisional.tsx`). The day the retention cutoff falls in is computed as the live reader reads it and never kept, since the sweep is still emptying it. A transfer the sweep removes changes the cause of its conversation's later takeovers (a takeover is a person's handoff only when no transfer precedes it), so its deletion queues the conversation and the days of those takeovers still within retention are computed again (migration `20261013171100_dashboard_dirty_swept_transfer`); no other line the sweep removes is read by a later day. One count is approximate past retention: a conversation counted under a cause (or a follow-up, or a problem) on a kept day whose lines were then swept, and counted again under the same one more than the retention period later, reads as two conversations in a window spanning both days, because the line that would say it was seen before is gone and a kept day records how many conversations, not which. The approximation errs that way on purpose: a kept day whose occurrence was seen before on a day of the window that was never kept, and is no data now, counts the conversation there, since that day adds nothing (`firstOf` in `merge.ts`).

**How the console fills.** `GET /v1/metrics/stream` sends the figures of every requested block as server-sent events: a `waiting` event every few seconds while the queue settles and the window's days are looked up, a `snapshot` with what is already kept, then one after every part, each with the coverage per family (days in, days out of the window, flow-log days with no data), a `computing` event naming the days about to be computed (repeated every few seconds while a part runs or a snapshot is merged, which keeps idle-timeouts from closing a long one), and a last snapshot with `done: true`. The page opens one stream for its window and one for the previous period (KPIs, funnel trend, costs), every block reads its figures from them, shows "partial · N of M days" while its families fill and nothing once they are in, and a line under the filter says how many days are ready and which ones are being computed. None of this appears for a view that completes within 1.5 s of the stream opening (`streamGrace`): a warm opening reads its kept days at once and computes today, yesterday and the cutoff's day about a second later, and its figures show as final from the start, with no badge, pulse, bar, band or progress line in between. While a figure does not cover its window, it reads as provisional where it is shown: its value is fainter and pulses slowly (0.55 to 0.85 opacity over 1.6 s, every card on the same clock, and held still under reduced motion), the "partial · N of M days" badge sits by it, and a static bar inside the card fills with its days; a stream that failed or was refused stops the pulse, and once the figure covers the window all of it fades out (`Provisional.tsx`). A chart with days on its axis draws the whole window from the first snapshot (the server names the window's first day, `Progress.first`, so a whole-history axis does not move as older parts arrive): a day still loading holds its place under a hatched band, "loading", and a day with no data for good (`Coverage.none`) under a dotted one, "no data", each with its own tooltip and a legend under the chart; the vertical scale only grows, on round steps, while the window fills. A block's chip and blank days follow the coverage its figures were merged at, from the last snapshot: a `computing` event moves only the line under the filter, since the days it reports are not in the figures yet. A comparison with the previous period appears only once the days of the same families are all in, in both periods: part of a period compared with a whole one would read as a change that is not there. While a family fills, a block that counts each conversation once (costs, the usage breakdown, handoffs, follow-ups, problems) is merged over the run of days in that ends on the window's last day, which is where parts start, since which day a conversation was first seen on cannot be told across a missing day; when what is in is not such a run (days kept by an earlier view, with today missing after them) the block waits for the rest. Latency is covered by the ledger's days and problems by the flow log's, each with its own chip and its own failure. A single day of a family that does not fit the budget stops that family only: its blocks say the period took too long, with the retry, and the other families go on to the end (the REST routes and `metrics_get` answer with that refusal for a block of the family). Each family's coverage names its days with no figures yet, or none for good, and a block's chart and table leave those days blank rather than zero. A flow-log block (handoffs, follow-ups, problems) reads the coverage of its own section (`Progress.sections`), and is merged over its own section's days, so a block already in is whole while a sibling section still fills: a day past retention may have been kept for one of them before the sweep and not for another, and the one kept shows it. The funnel tiles open their list of conversations only once every day of the period is in, since the list is the whole period's. A stream that closes before its last snapshot or a refusal reads as failed, with the retry; an error on the server that is no refusal (the database out of connections) ends the stream on a refusal with status 500 rather than cutting it mid-chunk. A refusal for a tenant a SUPER_ADMIN had selected and that no longer exists names it in the event, and the page drops the selection as it does for any other refused request. A viewer who leaves stops the request at the next part, or at the next settling batch or computation of today while it is still preparing: a part already running finishes and is kept, and one waiting for another request's part stops waiting. The REST routes and the MCP `metrics_get` answer the same figures in one response, computing whatever is missing first, within the request's one `METRICS_TIMEOUT_MS`, counted from its arrival as on every metrics route and shared by its parts and the merge after them (the Langfuse link of the costs is read first, on the same budget), rather than one per part (`WindowLoad.complete`, `figuresOf`, `fromKeptDays`): they send nothing until every part is in, so a cold window that takes longer would outlive the server's idle timeout. Past that deadline the request is the usual 503 naming `since`, the parts computed before it stay kept, and the same request again goes on from them, so a cold long period may need a retry or two; a caller that goes away (the request's signal, the MCP call's) stops it at the next part, and a part cut in halves for the budget starts no half once its caller has gone. The console never meets that ceiling, since it reads the stream.

## The blocks

The filter and the section index sit in one band across the top of the page, which stays on screen while the page scrolls (from the `lg` breakpoint). The index is a row, not a column beside the blocks: at a laptop's width a column took a quarter of the room the blocks need. Each section's title carries the icon its entry carries in the index.

The funnel's five tiles are laid out by the width the page has (a container query on their row, `KPI_GRID` in `PerformanceSection.tsx`), not by the window's, since the app's sidebar takes a share a window breakpoint cannot see: five across from 70rem, three and two below it, two by two below that with the last tile across the row. No width leaves a tile alone beside a gap.

Clicking an agent or inbox row applies it as the page's filter |

Two windows coexist on purpose: conversation figures count conversations **created** in the window, ledger figures count calls **billed** in it. A conversation that started last week and was answered today is in today's cost and in last week's funnel.

## Export and accessibility

Each block exports what it shows as CSV (`src/client/pages/dashboard/csv.ts`): raw numbers, a header row, the same rows the screen shows. A text cell that starts like a formula (`=`, `+`, `-`, `@`) is written behind an apostrophe, since agent, inbox and label names come from outside. A chart is hidden from the accessibility tree and a table with the same figures stands in its place (`Block`, `src/client/pages/dashboard/Block.tsx`); while a block's figures are loading it offers neither, since its table does not hold them yet; figures shown beside a chart that are not in its table (the handoff block's period totals and silences) go in the block's `footer`, which stays readable; the CSV and that table are built from one `BlockTable`, so they cannot disagree. Chart colors are read from the theme's CSS variables and re-read when the theme flips (`useChartPalette`).

Each block loads on its own (`useBlock`). A new filter takes the previous view's figures off the block at once, so nothing of the old view stays on screen or clickable while the new one loads; a refresh of the same view (the ceiling's poll, a retry) keeps them until the new ones arrive. A block whose request fails says so, with a retry, and offers no CSV: an empty result and a failed one never look alike.
