# Debounce (inbound message coalescing)

WhatsApp customers send several quick balloons ("oi", "tudo bem?", "queria saber…"). Answering each one is the #1 amateur tell and duplicates replies. Debounce waits for the customer to stop, then answers the **whole burst in one turn**. This is feature parity with the n8n workflows (which used a durable Postgres queue + a fixed Wait + supersede), reimplemented on our durable scheduler with the guards n8n lacked. It is **on by default** per agent.

## Flow

```
incoming message (gate=act)                 fast worker tick (~2.5s)
        │                                            │
   webhook (processChatwootDelivery)          claimDueDebounceJobs (FOR UPDATE SKIP LOCKED)
        │  resolveDebounceConfig → enabled?          │
        ├─ yes → armDebounce (re-arm runAt)    flushDebounceJob
        └─ no  → runAgentTurn (direct, as before)    │ re-fetch messages → coalesce past watermark
                                                      │ run one turn (coalesced text)
                                                      │ shouldPost: re-fetch → superseded? → CAS reply claim
                                                      └ post once via the bot token
```

- **Arming** (`armDebounce`, `src/modules/debounce/service.ts`): one live `SchedulerJob` (`kind = DEBOUNCE`, `dedupeKey = debounce:<threadId>`) per thread. Each new message bumps `runAt = min(now + windowSeconds, burstStartedAt + maxWindowSeconds)` via upsert — the durable, crash-safe equivalent of n8n's supersede, with an anti-starvation cap n8n didn't have. Serialized per thread by an advisory lock so concurrent deliveries can't lose the burst-start stamp. The payload is JSON-safe (no bigint): `instanceId`/`conversationId` are recovered from `threadId`.
- **Dedicated fast worker** (`src/modules/debounce/worker.ts`, `DEBOUNCE_WORKER_INTERVAL_MS`, default 2500ms): drains **only** `DEBOUNCE` (`claimDueDebounceJobs`), in **slots, not batches** (issue #807): at most `AGENT_MODEL_CONCURRENCY` jobs in flight, and each tick claims only into the slots that are free and returns once its jobs have STARTED, so no job waits for an unrelated one to finish. It used to await its whole batch before the next claim, and one model call of 5 min 36 s held every tenant's due flushes for as long. The rows in flight are kept out of the claim itself (`excludeIds`), because a message arriving during a flush re-arms the SAME row back to PENDING, and so does the reaper for a run longer than its stale window. When the lane is full, each tick also asks which due rows are still unclaimed, and a row that has waited past `AGENT_CAPACITY_WAIT_ALERT_MS` (default 30s) gets one `capacity` warn on its own conversation, while it is still waiting (issue #812, [`logs.md`](logs.md)). The wait counts from the later of its `run_at` and the moment the lane filled, so time a row spent overdue through a restart is not blamed on capacity. The main scheduler tick (15s) claims the kinds the lane table assigns to it (`claimDueJobs` → `laneFilter("shared")`, derived from `JOB_LANE` in `src/modules/scheduler/lanes.ts`), so the window is honored without ticking the reaper/sweep that fast. That file also carries the rule for when a lane is warranted at all: **cadence or budget, never duration**. Debounce is the cadence case (this one); attendance compaction is the budget case. A kind that is merely slow needs no lane, because the shared tick drains its batch concurrently (issue #165). The scheduler's reaper still re-pends a stranded `CLAIMED` debounce job.
- **Flush** (`flushDebounceJob`, `src/modules/debounce/handler.ts`): re-fetch the thread (admin token), coalesce the incoming messages past `Conversation.lastHandledMessageId` (the **watermark**), cap at `maxMessagesPerBurst` (keep the most recent), feed the joined text to `runLoadedTurn`.
- **`coalesceAndRunTurn`** (same file, exported) is the reusable "re-fetch → select a burst → coalesce → answer once" core. It takes a `selectPending` strategy: the flush passes `pendingIncoming(_, watermark)`; the **manual re-engage** (item 6, `src/modules/conversations/reengage.ts`) passes "incoming after the last outgoing" to re-answer the unanswered tail without a new inbound. Both share the same supersede + reply-claim at-most-once guards below; a failed turn stamps `Conversation.lastError` (cleared on a successful post) so the operator sees an error badge + a re-engage button.

## Watermark + supersede (why no duplicate / no incomplete reply)

The re-fetch decision (not a durable buffer) keeps us aligned with the anti-PII rule (we never mirror message bodies). Correctness rests on two guards in `shouldPost`, evaluated AFTER the LLM call and BEFORE the post:

1. **Post-response supersede**: re-fetch and ask whether this reply is still wanted. The question is asked BY IDENTITY, not by the arithmetic of the page (issue #698): "is there an OPEN message above what I am about to answer" (`selectOpenMessages`, below) and "did somebody else already answer what I am holding" (`foreignReplyBoundary`). It used to be `maxIncomingId > targetWatermark`, which reads every id above the target as a customer still waiting — including one another turn has already claimed, which made the retry defer forever. Re-fetch failure is non-fatal (reply rather than drop; the re-armed flush covers any miss). This gate also runs for EMPTY replies (since the deferred-resolve change), and any deferred resolve intent is discarded with the reply.

   **The gate reports what it SAW, and the turn's outcome says what that MEANS** (issue #703), because the two refusals it produces have opposite bookkeeping and only the gate knows which is which:

   | the gate saw | outcome | watermark, dispensal, ledger |
   | --- | --- | --- |
   | `newer-message` — a customer message arrived mid-turn | `superseded` | left where they were: the re-armed flush answers the FULL burst, so closing anything here would declare handled what nobody read |
   | `answered-by-other` — a person (or another AgentBot) answered this burst | `answered-elsewhere` | advanced and settled as `consumed`: nobody is coming, the conversation WAS attended, and a burst left open here keeps its stranded deliveries in the loss list — where the delivery recovery replays them, spending a model call and its tools on a conversation a person already handled |

   Read one word for both questions and the second row inherits the first row's silence, which is the whole of issue #703. The outcome list in `coalesceAndRunTurn` is read BY EXCLUSION — a word that is not named there advances the watermark and settles the ledger — so `answered-elsewhere` needs no entry, and `superseded`, `stale`, `thread-busy` and `agent-unavailable` are the four that do.
2. **Monotonic reply claim, under the row's own lock**: `runLoadedTurn` takes it, in `Conversation.lastRepliedMessageId`, and it answers TWO questions in one transaction — "is anybody else answering this right now" (the claim itself, monotonic) and "has the handled watermark moved past what this caller may answer over" (`maxHandledAllowed`, read off the mark under the same lock). The loser suppresses, so a burst is answered **at most once** through ONE column for every posting path (the direct turn, the flush, its retry and the manual re-engage), which is what makes them contend instead of each sending (issue #452). It cannot be the watermark: that one is advanced by deliberate SKIPS as well as by answers, so after a human-owned stretch it stands ahead of the tail the re-engage answers, and a CAS there loses forever while reporting a race that never happened. The ceiling is what separates the callers rather than a flag: the direct turn and the flush answer ABOVE the mark and pass `target - 1`; the re-engage answers a tail the mark already covers and passes the mark it read on the way IN, so a skip landing while its model runs still refuses it — and a null reading is that ceiling too ("no mark was there"), never the absence of one, so any mark that appears under a running model refuses the claim. **The claim is taken before the send and never given back** — the same trade the watermark's CAS made before: a send that fails leaves the burst marked and nothing re-answers it, because a reply the customer already has cannot be taken back. The watermark advance happens after the turn, on every consumed outcome, and the flush's burst selection floors on the max of the two so a lost watermark write cannot cost a second reply.

   Alongside the advance, a consumed burst also **retires the ledger rows** of the messages it contained (`retireCoveredDeliveries`, issue #228), keyed by account + conversation + message and restricted to rows already `PROCESSING` (or `DEAD`, which it corrects). The gate exits state the burst as the range their watermark advance covers — bounded at BOTH ends, since open at the bottom it reaches back over a strand an earlier message left behind and closes a real loss for good. Three of the four decide before any fetch and have nothing to enumerate; the spend-ceiling refusal DID read the page (to find out whether there was a burst to refuse at all), so it names its members instead, on the dispensal and on the ledger alike. A range there would cover everything BETWEEN the oldest member and the newest, including what the selection deliberately left out — a message some other turn claimed and died holding, whose delivery is a genuine loss the sweep still has to report. A burst re-read from Chatwoot can carry a message whose own webhook delivery died mid-processing, and that is the one case where re-reading the thread rescues something the ledger still shows as unfinished. The watermark cannot record it — it is a per-conversation high-water mark and this is a per-message fact — so the turn writes it where it belongs. The messages `maxMessagesPerBurst` takes OUT of the burst are retired too, always as `consumed`: the watermark advances past the whole burst either way, so leaving them open would report as lost a message the product looked at and deliberately dropped. `PENDING` is left alone because a burst also legitimately contains messages whose deliveries have not started yet, and consuming those would skip their mirror writes. A gate exit taken because **another AgentBot** now owns the conversation retires nothing at all: Chatwoot fans a message to up to two routes (`agent_bots_for`), so the owner's own delivery for a message in that range may be `PROCESSING` right now, and a range write would turn it `PROCESSED` — the one state the sweep never revisits. A **human** taking over is the opposite (they answer the message whichever route carried it) and so is a refusal by the contact-authorization gate (the conversation is still ours), and both keep the wide range. Best-effort: a miss costs a line in the stranded-delivery list, never a reply.

`runLoadedTurn` (`src/graph/runtime.ts`) is the shared tail of both the direct path and the flush: build → invoke → re-check the live assignee (human takeover aborts) → `shouldPost` → post. The assignee re-check comes FIRST, so any path that moves the conversation out of the bot's hands ends as `taken-over` and never reaches the gate above; `answered-elsewhere` is the case where somebody answered WITHOUT the assignment moving.

**And on the direct path the same question is asked BEFORE the invoke as well** (issue #688). That path waits out a turn already on the thread (`waitForThreadTurn`, up to `TURN_LEASE_SECONDS + 5`), and the webhook's ownership gate ran before that wait: a person can take the conversation over inside it. The re-check above suppresses the SEND and nothing else, so everything the invoke does on the way there — a ticket opened, a label written, an outgoing HTTP call — has already happened over the person. So the turn reads ownership once more right after it acquires the thread, and standing down there is `taken-over-unread`, a word of its own rather than `taken-over`: there the invoke ran and the customer's message is in the agent's memory, here nothing read it. The receiver treats that outcome the way it treats an observer's stand-down — the watermark does not advance, the delivery is not settled, and continuous ingestion keeps the message — so the words the turn never read are still folded into the thread the person hands back. It writes the same `handoff` line the other three gates write, for the reason `docs/chatwoot.md` gives: an operator filtering the log for one outcome has to get every gate that closes on this question.

**The gate does not act on a message that is still going to receive more content** (issue #688, review rounds 7 and 8), which today is exactly one: a voice note waiting on STT. Standing the turn down means handing the message to continuous ingestion, and the ingestion records the message id in the thread's dedupe window — so the transcription that arrives later, on the same message id, is discarded as a duplicate. The two outcomes for an audio are therefore losing what it already carries or losing the transcription. **The question is not whether the message already has words**, and that distinction cost two review rounds: a caption, or an email subject, ARE words, and the transcription still comes. What decides is whether more is coming. The third way out — teaching the ingestion to ENRICH a message it already folded in — touches the shared dedupe window and is an issue of its own; until then a voice note behaves exactly as it did before this change, and the fix covers everything else, which is the issue's population. The predicate is `awaitsTranscription` in `src/modules/chatwoot/normalize.ts`, extracted from `hasPendingInboundMediaUpdate`, whose question it already was for one event.

**The read that FAILS lets the turn go on**, which is the opposite of `botOwnsItNow` in the same file. That one is fail-closed because both of its uses are skippable (a hand-back note, a read receipt); here what is at stake is the customer's reply, and a `false` from a database that blinked would abandon every turn that waited. Carrying on costs the window that already exists today, and the post-generation re-check still holds the send. A fail-closed version of exactly this gate is what got reverted once already, in fazer-ai/agents#684 (`1ec96449`, undone in `9dce80e2` — shas in the PUBLIC repo, which the mirror regenerates, so they are not in this history).

## Which messages a burst contains (issue #698)

The burst is not "everything above a number". Above `conversations.reply_claim_floor_message_id` — the per-message era, opened by issue #690 — the absence of a row IS evidence, because every decision taken up there writes one: a `message_reply_claims` row saying `CLAIMED` (a turn took this message) or `DISPENSED` (something deliberately closed it), or a `reply_dispensals` range for a gate exit that could not enumerate its members. Below that floor the scalars still decide (`max(last_handled, last_replied)`), because down there no row was ever written and none ever will be. **That last clause is a rule for WRITERS, not a description** (issue #725): the era is opened by the first decision that writes a row, which is a winning claim (`claimReplyBurst`) or a standalone dispensal (`dispenseMessagesFromReply`, the refusal a gate records without moving the watermark), and both open it at the same `max` of the two scalars, because a message closed by either one is closed. A writer that skips this leaves a row the selection cannot see and the claim's unique index can: the burst carrying that message is refused WHOLE as `partial`, the flush reschedules, and the re-read finds the same state — the customer's newer message unanswered in a loop. For the same reason nothing is ever written at or below the floor: down there the decision has already been taken by the scalars.

`selectOpenMessages` (`src/modules/debounce/watermark.ts`) is that one question, and FOUR gates ask it: the burst the flush answers, the supersede gate of that flush, the supersede gate of the direct path, and the observer's ingestion. It takes a `purpose`, because "may I REPLY to this?" and "should I REMEMBER this?" have opposite answers twice over: a reply somebody else wrote closes the first and not the second (the observer's memory is what the CUSTOMER said), and so does a dispensal (a refusal to reply is a decision about the reply). A claim closes both, and so does `/reset`, whose whole point is that the memory it cleared must not be rebuilt.

Four fences the scalar used to carry for free, by the accident of being one number that only moved forward, are now explicit:

- **the rows** — claims and dispensals, per message;
- **a reply somebody else wrote** (`foreignReplyBoundary`) — a `user`, an AgentBot that is not this tenant's (matched by id), or an attendant typing on the phone paired to the inbox's number. That last one is stored sender-less and marked only by `content_attributes.external_sender_name`, so it counts ONLY where the WhatsApp provider reserves its send ids (`providerReservesEchoIds`); everywhere else our own reply comes back wearing the same shape when the send response is lost. The boundary moves on NAMED evidence and never on silence: an unattributed outgoing message read as somebody else's would silence a customer nobody answered, permanently, on the delivery-recovery path. A reaction is not a reply, a private note is not a reply, and a row the history importer backfilled is not a reply to anything live — it carries today's id and last year's conversation;
- **`/reset`** (`resetAtMessageId`), for both purposes;
- **the spend ceiling**, which names every member of the burst it refused.

**A reaction the page cannot carry (issue #746).** The flush selects from the fork's default page, and that page is built from the last twenty messages that are not reactions plus only the reactions whose `in_reply_to` points at one of them, resolved inside the same conversation. A customer reacting to an older message, or to a message of an earlier conversation (the reaction then opens a new one), sends a reaction no default page carries, and the flush found nothing above the mark: no turn, and a conversation left `pending`. The direct path never had this, because it renders from the webhook. The arm now records `reactionArmed` on the burst (sticky across its arms, like `lastMessageId`), and when the burst holds a reaction, or the page lacks the message that armed the flush, `readBurstPage` asks the fork's catch-up read (`?after=<mark>`, by id, with no reaction window) and merges what it adds. Without a mark (a conversation the agent never answered) the read starts at the burst's earliest reaction, which the arm records as `reactionFrom`, and not at the message that armed the flush last, which may be a text typed after it. That read answers at most a hundred rows, so it is repeated until it runs dry: stopping where it meets the page would leave a reaction above the page unread, and merging a partial read would hand the reply selectors a history with a hole where a reply may sit. A read that has not run dry after five batches adds nothing, and the page alone answers. The common flush pays nothing more. An operator's reaction the read brings in is not a reply, on the re-engage tail as everywhere else. The observation walk on a flip to monitoring, the manual re-engage (always, one read per click, from the mark it read on the way in) and the stranded-delivery recovery (when the anchored page lacks the message) ask the same read.

## Configuration

Per-agent, in `agent.settings.debounce` (free-form bag, validated/clamped by `readDebounceConfig` in `src/modules/debounce/settings.ts` — a bad value can never break the flush). Surfaced in the agent editor's **Behavior** tab and writable over REST (`PATCH /v1/agents/:id`) and MCP (`agent_settings_get`/`agent_settings_set`, the `debounce` block), per "one core, three transports".

| Setting               | Default | Range    | Meaning                                                      |
| --------------------- | ------- | -------- | ----------------------------------------------------------- |
| `enabled`             | `true`  | bool     | Off → the direct (balloon-by-balloon) path, unchanged.      |
| `windowSeconds`       | `15`    | 3–120    | Idle time after the last message before flushing.           |
| `maxMessagesPerBurst` | `20`    | 1–50     | Context/cost cap; the most recent N are kept.               |
| `maxWindowSeconds`    | `60`    | ≥ window | Anti-starvation: reply at most this long after burst start. |

Operational (env, NOT per-agent): `DEBOUNCE_WORKER_ENABLED`, `DEBOUNCE_WORKER_INTERVAL_MS` (keep it below the smallest window, 3s).

## Known limits (single-replica MVP)

- A transient LLM/Chatwoot error after a partial graph invoke can re-append the coalesced `HumanMessage` to the checkpointer on retry (a duplicated user line in context). Low-harm; rare.
- The supersede micro-race (a message arriving between the `shouldPost` re-fetch and the post) is irreducible without a transaction spanning the network. The window is one DB CAS + one POST.
- Concurrent flushes of one thread cannot happen inside one process: the thread is one row, and the drain's in-flight set keeps that row out of every claim until its run settles, even after the reaper re-pends it. A second replica running this worker would not share the set, which is one more reason for the single-replica rule; the watermark CAS still bounds it to one post.

Read before touching `src/modules/debounce/*`, the scheduler claim split, or the webhook → runtime seam.
