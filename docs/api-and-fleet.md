# Read API, instance identity & outbound webhooks

The substrate for the "one core, three transports" rule: every feature lives in a transport-agnostic service (`src/modules/*/service.ts`, takes `ScopedDb`/`TenantContext` by parameter, no HTTP types); REST v1, the MCP server, and outbound webhooks are thin projections on top. This doc covers the read API, instance identity, and the **outbound** webhook half. The inbound receptor + integration catalog live in [`integrations.md`](integrations.md).

## Read API (`/api/v1/*`)

Versioned, mounted under the `/api` group (so paths are `/api/v1/...`). The same surface serves the React UI and a future fleet dashboard. It goes through `tenancyPlugin` + `requireAuth`; `tenantContext` is derived from the JWT (`X-Tenant-Id` is honored only for `SUPER_ADMIN`, ignored-and-flagged for everyone else — see [`tenancy.md`](tenancy.md)).

Current endpoints: `GET /api/v1/meta`, `GET /api/v1/tenants`, `GET /api/v1/tenants/:id`. Conversations/metrics/funnel projections arrive in their phases.

### API keys: per-tenant, and fleet-scoped

A Bearer API key (`fazerai_…`, minted at `/api-keys`; only its SHA-256 hash is stored) authenticates the REST v1 API and the MCP transport in place of the cookie session, in one of two scopes. The two are the same `api_keys` row, and the shape is the one `users` already gives a SUPER_ADMIN (`api_keys_role_tenant_check`: `SUPER_ADMIN ⟺ tenant_id IS NULL`):

| | tenant key | fleet key (#308) |
| --- | --- | --- |
| row | `tenant_id = <tenant>`, `role = TENANT_ADMIN` | `tenant_id NULL`, `role = SUPER_ADMIN` |
| principal it resolves to | the tenant, implicit on every request | a SUPER_ADMIN with no home tenant: selects one per request with `X-Tenant-Id` (REST) or the `tenant` argument (MCP), exactly like a SUPER_ADMIN session |
| reaches | the tenant's routes | every route a SUPER_ADMIN session reaches, `POST/DELETE /v1/tenants` included |
| routes | `GET/POST /v1/api-keys`, `DELETE /v1/api-keys/:id` (TENANT_ADMIN, RLS-fenced) | `GET/POST /v1/api-keys/fleet`, `DELETE /v1/api-keys/fleet/:id` (SUPER_ADMIN) |
| listed | under its tenant only | under the fleet list only: `tenant_id = <guc>` is never TRUE for NULL, so no tenant scope ever lists or revokes it |
| audit trail | the tenant's | fleet-level (`tenant_id NULL`), like `tenant.create` |
| minted by | a TENANT_ADMIN **session**, confirmed with the current password | a SUPER_ADMIN **session**, confirmed with the current password |

Neither scope carries per-operation permissions: a fleet key is the whole SUPER_ADMIN authority, and an installation that needs less than that does not mint one. Fine-grained scopes are a separate feature.

**A key never mints a credential that outlives it.** Revoking a key has to end everything the key could do, so every route that mints a credential refuses an API-key principal outright (`requireSession`, 403 `errors.apiKeyRequiresSession`): `POST /v1/api-keys` and `POST /v1/api-keys/fleet` (a tenant key minted by a fleet key under `X-Tenant-Id`, or by another tenant key, would keep working after the minter is revoked), and the MCP OAuth `/authorize` and `/consent/:req` (a key is an authenticated principal there too; a first-party client skips consent, and the pending record is bound to the key's creator id, which the key carries). A credential comes from the console, where a person is. Invitations are not in this set: an invite ends in a person choosing a password, and issuing the first TENANT_ADMIN invite with the tenant (`POST /v1/tenants` + `adminEmail`) is the provisioning flow a fleet key exists for.

**Step-up is a property of the session, and a Bearer key answers it by itself.** The six password-gated routes (`POST /v1/api-keys`, `DELETE /v1/tenants/:id`, `DELETE /v1/agents/:id`, `DELETE /v1/chatwoot/deployment`, `POST /v1/chatwoot/instances/:id/remove`, `DELETE /admin/users/:id`) go through `confirmStepUp` (`src/api/lib/step-up.ts`): a session sends `password` (omitted → 400 `errors.passwordRequired`, wrong → 403 `errors.invalidPassword`), an API-key principal minted under the rule omits it and is not asked (on the two minting routes it is refused before that, see above). They used to verify the password against the row `ctx.userId` names, which for a key is its CREATOR, so an automation could only pass by holding a person's password as well — the coupling #308 reports as fragile, and one that proved nothing the key had not already proved: it is presented on every request, and it was minted under a step-up. That last half is what makes minting a key one of the six: a seven-day session that could mint a key without a password would carry the key past the rule on every destructive route (review round 1 on #308). **"Minted under a step-up" is what the row carries, not what the kind implies**: the mint stamps `api_keys.step_up_at`, and a key that predates the rule (`step_up_at NULL`, which is every key minted before this shipped) was minted with no password anywhere, so it keeps answering the six routes the way it always did, with its creator's password, until the operator rotates it (mint a new key, revoke the old one). The migration does not backfill the column: a step-up that never happened is not invented after the fact (review round 3). The console marks such a key in the list, and the API exposes it as `stepUpAt` on the key. The name confirmation (`confirmName`/`confirmDomain`) stays for every principal: it is about the target, not the actor. `tests/api/lib/step-up.test.ts` holds every `verifyPassword(` call in `src/api` to the login route and the helper.

**A query filter is used or refused, never dropped.** Every read surface parses its filters through `src/api/lib/query-filters.ts` (`parseQueryInstant` / `parseQueryId` / `parseQueryCount`), and a value the server cannot use is answered **400 naming the parameter** (`{ error, field }`, key `errors.invalidQueryParam`). The lenient spellings this replaced each had their own wrong answer: `agentId=abc` dropped the filter and returned the tenant's whole table, `cursor=abc` restarted pagination so a client following `nextCursor` never terminated, `since=2026-02-30T00:00:00Z` normalised to March 2 and queried a window nobody asked for, and `limit=abc` reached Prisma as `take: NaN` — a 500 for a caller's typo. Empty is a value, not an absence: `?agentId=` is what a form submits when its input is blank, and reading it as "no filter" is the same widening. The RANGE of a count lives in the SERVICE (`assertUsableCount` in `src/lib/query-param.ts`), not in the parser, so MCP and the console's own service calls are held to it too. An instant filter takes an ISO 8601 instant with an offset; a date alone is refused. Issues #305 / #361 settled this for the delivery ledger and #372 applied it to the rest.

**A mutation records itself, and the record names what changed and not which door.** `auditMutation` (`src/modules/audit/service.ts`) appends the `AuditLog` row from INSIDE the service performing the write, in the same transaction: `await auditMutation(db, ctx, { action, target, before, after })`. It exists because the trail used to be written by the MCP transport, after the service it called had already committed, which cost both halves of what an audit is for. It covered one door of three, so the console (REST) left no row at all; and its second transaction could fail on its own, landing a change with nothing saying who made it. Because the row now comes from the shared core, the action is `<entity>.<verb>` and the transport is carried by `TenantContext.actorType` (`user` for a cookie session, `api_key` for a Bearer key, `mcp` behind an MCP token, `system` for a mutation no request asked for). The projection is bounded by the seam, so a call site cannot forget; what goes IN it is still the caller's allowlist, never a secret and, for every family but one, never a message body. Rows written under the old `mcp.<tool>` names stay as they are. A row is appended only when something CHANGED: the console PATCHes a whole editor tab per save, so recording every apply would fill the trail with saves that moved nothing. Where several tools reach one service function — `agent_update`, `prompt_set` and `agent_settings_set` all call `updateAgent` — the diff picks the action, because the field a caller named says nothing about what the operator did. #392 built the seam and moved business hours, #393 the agent family, #394 the tenant/branding one, #397 outbound webhooks and alert channels, #399 the five configuration families (tool definitions, MCP connections, integration instances, experiments, document templates), #398 conversation control, #395 channel management and #444 the vault; the remaining families are sub-issues of #306.

**Every mutable column is in one half of the projection or the other.** The audited services split a row in two: what is PROJECTED is identity, policy and shape, safe to keep in a row that is append-only and outlives the record; everything else is named in that module's `UNDISCLOSED` list, which the update path COMPARES without carrying (`undisclosedMoved` in `src/modules/audit/projection.ts`). The split is what makes the trail honest, and being in NEITHER half is the failure mode — a column changes, the projection does not, `projectionMoved` sees nothing, and the edit writes no row at all. Review found five such columns at once on #399's first pass (a tool's headers and schemas, an integration's config VALUES under unchanged keys, an experiment's variant prompts), and each was the ordinary edit its family gets. A column shown through a TRANSFORM is not covered by that alone: a URL projected as its origin, a stdio command as its launcher, a host allowlist reduced to its COUNT (no test on a string separates a hostname an operator meant from a token they pasted: `ghp_0123` and a dotted JWT both parse as hosts), a field as `{name, type}` all report less than the column holds, so the whole value is listed as well. **What the row keeps of that half is one boolean**, `undisclosedChanged: true` on both sides — never a value and never a fingerprint of one, because an unsalted digest of a low-entropy secret is an offline verifier for it and these rows outlive the record they describe. Same answer #394 reached for the settings bag (`unreadConfigChanged`). `tests/modules/audit-config-families.test.ts` reads the columns out of `prisma/schema.prisma` and fails while one is in neither half, so the next column added to those models has to be placed rather than forgotten. #399.

**A URL an operator typed is redacted to its origin, wherever it appears.** `redactEndpoint` was written for the outbound subscription and the alert channel (#397), and the reasoning is not specific to them: the schema accepts any destination, a token in userinfo/path/query is how these are actually written, and the row outlives every correction. It therefore also covers a tool's `urlTemplate` and an MCP connection's `url`; a stdio `command` is projected as its launcher (`bunx`/`uvx`) for the same reason, because an argument is where a self-hosted server's key goes. Where a value is STORED says nothing about whether it is a secret.

**A stored credential reference contributes a pair, not a value.** `readableVaultRef` shows a `credentialRef`/`secretRef` column only where it IS a `vault:<id>` reference (#438), so a column holding anything else reads as null on the way out. In a projection that redaction has a second effect nobody asks for: clearing such a value looks identical on both sides of the change, so `projectionMoved` sees nothing and the one save that REMOVED a credential writes no row at all. `refForAudit` (`src/modules/audit/projection.ts`) returns `{ref, opaque}` for that reason, and the three columns that need it spell both halves onto the row (`credentialRef` + `credentialRefOpaque`). Same shape as the outbound subscription's `secretRefOpaque` (#397), which is where the problem was first measured.

**Which trail a row joins is the row that changed, not the principal that changed it.** `auditMutation` keys on `ctx.tenantId`, which is right for a tenant operating on itself and wrong for two shapes that answer to `auditMutationOn(db, ctx, tenantId, entry)` instead. A **fleet-level** change belongs to no tenant (`null`): branding is the whole deployment's identity, and a SUPER_ADMIN usually has a tenant selected in the console, so keyed on the context a change to everyone's login page would be filed under whichever tenant that header named. And a SUPER_ADMIN may write a tenant OTHER than the selected one: `PATCH /v1/tenants/7` succeeds under `X-Tenant-Id: 5`, because the update runs `asSuperAdmin` and never consults the context. `null` also carries a second meaning that is not stylistic: `audit_logs.tenant_id` is `ON DELETE CASCADE`, so a `tenant.delete` recorded against the tenant it deletes is erased by the same statement, in the same transaction. `tenant.create` and `tenant.delete` are therefore fleet-level and `tenant.update` is keyed on its target. #394.

**A mutation in somebody else's system records itself AFTER the effect, and every apply of it counts.** Conversation control (`reply`, `handoff`, `return`, `status`, `reengage`) changes state inside Chatwoot, so the seam's "same transaction" is unavailable and the ordering has to be chosen: the call goes first and the row follows it (`src/modules/conversations/audit.ts`). Both halves of that are the opposite of what the configuration families do, and for the same reason in reverse. A row written first would claim a message the customer never got every time Chatwoot refuses one, on the family whose actions are explicitly not reversible; and "a row only when something changed" exists because the console PATCHes a whole tab per save, while here every apply is an operator reaching into a live conversation, so setting a status Chatwoot already held is still recorded. The single exception is `conversation.reengage`, which runs a model before it decides: it records when the turn REACHED the customer (`posted`/`posted-partial`) and not when the button declined to act, which the flow log already narrates. **A partial effect gets a partial row**: a targeted handoff is two Chatwoot requests and the assignment can land while the toggle fails, so the row is written (with `partial: true`) before the error propagates, rather than leaving a person holding a conversation with nothing saying who put them there. **And a row that cannot be WRITTEN is lost rather than raised**, which is the inverse of every other family and the same reasoning again: the change is Chatwoot's, an error after the customer already has the message does not undo it, and the caller's retry sends it twice. The same fact decides where the row is written from: once the external call returns, everything after it is our own bookkeeping (the mirror, its fallback write, the broadcast, the ownership read that names the outcome), so the row goes in a `finally` and carries the reconciled state when the mirror got there and the state Chatwoot accepted when it did not. `conversation.reply` is also the one projection in the repo that keeps a message body, because there the text IS the mutation and a row saying only that somebody replied cannot answer what the family exists for; nothing the CUSTOMER wrote is ever recorded. #398.

**A command typed into a conversation has an action, never an actor.** `/reset` erases an episode (memory, audio preference, labels, conversation attributes, the kanban card) and hands the conversation back, and it is recognized only on an INCOMING message, so whoever typed it is the contact, who has no row in `users` and is no principal of this system. The rows it produces are `system`, and what the person did is carried by the action and the projection instead: `conversation.reset` names the steps that failed and the hand-back's outcome, alongside the `conversation.return` the service records for the hand-back itself. Two rows for one command, and they cover disjoint effects: the return is the state change a console button also performs, the reset is the erase that has no button at all. #398.

**A family moves down as a whole, and what is a READ falls out of it on the way.** #395 moved the channel trail into `src/modules/chatwoot/management.ts`, and three of its eleven console routes had no MCP twin at all, so `deployment.disconnect`, `instance.reconnect` and `instance.remove` are named there for the first time: before it, disconnecting a whole deployment (which cascades every account, inbox, bot and conversation of the tenant, and deletes its contacts by hand first) left nothing anywhere. The row for that one counts what it is about to destroy, inside the same transaction and before the delete. Connecting one is recorded in ITS OWN transaction (`instance.connect`, the name the disconnect side already had in the other direction), because `set_accounts` connects and syncs one account per iteration and a crash between two of them would otherwise leave an account handled with nothing saying so. Moving the family also settled what does NOT move: `inbox.reconcile` was audited by the MCP transport and `reconcileInboxBots` writes nothing on either side (its REST twin is a `GET`), so the row recorded a read, and pushing it down would have spread it to two more doors. It joins `webhook_test` and `mcp_connection_discover` in recording nothing. The deployment admin token stays out of every projection on both paths, which a fence over the whole family's rows measures rather than assumes. The same question caught a row that was not a read but might as well have been: the Channels page auto-syncs every active account when it OPENS, so `instance.sync_inboxes` recording unconditionally put one row per account into an append-only table on every visit. It now records only when the reconcile created an inbox, changed one, or renamed the account, decided by comparing the mirrored columns rather than by counting the inboxes that happened to already exist. The whole reconcile takes the ACCOUNT row's lock to decide that, which is the one lock that covers an inbox not yet mirrored: `FOR UPDATE` on a row that does not exist locks nothing, so two first-time syncs would each read it as absent and each claim the creation. The disconnect answers the same question on its other half: clearing a binding is a mutation whether or not the timestamp moved, so a retry that only finishes an unbind still records, with `stamped: false` saying which half it was. And it detaches the bots in Chatwoot AFTER its own transaction commits, not before: the local unbind, the stamp and the row are one atomic write, so a row that cannot be written takes the whole disconnect with it, and doing somebody else's write first would leave an account connected and bound here while Chatwoot had already stopped delivering to it. Detaching last fails into the outcome the function already accepts for an unreachable deployment, where the account is disconnected locally and the webhook ignores whatever still arrives. The route-token cache goes the moment that commit lands and not after the detach, because the detach is best-effort and can take as long as an unreachable Chatwoot takes to time out, and every warm entry keeps admitting webhooks for the disconnected account for that whole span. And a bind takes the ACCOUNT lock before it persists, re-asking the question its first read already asked: that read predates its own Chatwoot calls, so a disconnect fits entirely inside the window, and without the lock the binding lands just after the unbind and the disconnect's detach then pulls the bot the bind had just attached, leaving an inbox bound here with no bot upstream on an account that reconnects looking healthy. The detach loop itself is fenced on the same fact, re-asked before each call: it runs outside every lock and one unreachable inbox holds it for a whole network timeout, so an operator can reconnect and re-bind while it is still walking. The binding is what the fence asks about, not the disconnected flag, because a bot is on an inbox only because something bound it. Neither closes the window (no transaction of ours spans Chatwoot); both stop us issuing a write our own committed state no longer authorizes. Every row lock in the module is `FOR NO KEY UPDATE` and not `FOR UPDATE`, which is a property of the module rather than of any one path: an INSERT of a row whose foreign key points at a locked row takes `KEY SHARE` on it and `FOR UPDATE` conflicts with that, so the webhook mirror (which holds an inbox and then inserts a conversation keyed to the account) waits for the account while a sync waits for the inbox, and Postgres aborts one of them over a key nobody was changing. `NO KEY UPDATE` still excludes another of itself and any ordinary `UPDATE`, which is all these paths serialise for; a source fence keeps the mode uniform, because a deadlock has no green test. And one more thing follows from naming the CHANGE rather than the door: re-submitting the connect form against the deployment already connected replaces exactly one column, the admin token, so it records `deployment.rotate_token` with the rotation's own projection, not `deployment.connect` with an account count nothing moved. #395.

**A credential's row shows what it is for and never what it is.** #444 moved the vault trail into `src/modules/vault/service.ts`, where creating a credential was the only audited act and only over MCP: replacing the value behind a live reference and deleting an entry had no action name on any transport, so every consumer of a reference could start authenticating with something else and nothing said so. `credential.update` and `credential.delete` are named there. The projection carries identity, `kind`, `status` and the two fields that say how the credential is used, with `baseUrl` reduced to its origin like every operator-typed URL; the `secret` and the whole `baseUrl` are compared and never carried, so a rotation shows up as `undisclosedChanged` on both sides and a change living in a URL's path is still a change. The write is gated on that comparison rather than on the projection, because the save whose ONLY change is the credential itself moves nothing a reader can see. And the agent import emits one row per reference-only entry it creates, under the operator who ran it: those entries are wired into the imported agent, and the import's own row projects the agent, so they used to appear in the vault with nothing naming their origin. #444.

**Isolation-preserving projection.** Fleet-facing surfaces (read API, outbound webhooks, MCP read resources, SUPER_ADMIN cross-tenant) expose metrics + state + control by default, never message bodies or PII. A per-instance toggle opts a tenant into raw detail.

## Instance identity

`instanceIdentity` (`src/lib/instance.ts`) = `{ instanceId, name, version }`, stamped on every read-API response and outbound webhook payload so a fleet can attribute events to the emitting instance. `instanceId` is `INSTANCE_ID` (pinned across restarts/replicas) or a per-process random UUID for the single-replica MVP.

## Outbound webhooks (`src/modules/webhooks/outbound/`)

Three parts: the **closed event set + envelope** (`events.ts`), the deterministic **emit** side (called inline by domain code), the background **delivery worker**, and a **REST CRUD** for the subscription targets.

### Event set & envelope — `events.ts`

`OUTBOUND_EVENTS` is the single closed set; `OutboundEvent` is its union (emit is typed to it, the REST CRUD validates each subscribed event against it, the UI lists it via `GET .../webhooks/events`). The canonical events and their sanitized `data` projections (ids/status/counters/money only — never message bodies, contact PII, tokens, or raw entities):

| event                          | seam                                              | `data`                                                                                  |
| ------------------------------ | ------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `conversation.created`         | `chatwoot/mirror.ts` (Conversation create)        | `conversation_id, inbox_id, status, assignee_type`                                       |
| `conversation.status_changed`  | `chatwoot/mirror.ts` (status differs)             | `conversation_id, inbox_id, status, previous_status, assignee_type`                      |
| `conversation.handoff`         | `chatwoot/mirror.ts` (assignee → `User`)          | `conversation_id, inbox_id`                                                              |
| `kanban.card_moved`            | `graph/tools/native.ts` (`kanban_move_card`)      | `card_id, to_step, conversation_id`                                                      |
| `llm.usage`                    | `graph/usage.ts` (`defaultUsagePersist`)          | `agent_id, conversation_id, model, node, prompt_tokens, completion_tokens`               |
| `tenant.created`               | `api/v1/tenants.service.ts` (`createTenant`)      | `tenant_id, slug`                                                                        |
| `heartbeat`                    | `webhooks/outbound/heartbeat.ts` (periodic)       | `at, version`                                                                            |

Every emission is wrapped by `buildOutboundEnvelope(tenantId, event, data)` into a **versioned envelope** stored verbatim as the delivery payload and POSTed as-is by the worker:

```json
{ "version": 1, "instance_id": "…", "event": "conversation.created",
  "occurred_at": "2026-…Z", "tenant_id": "42", "data": { … } }
```

`occurred_at` is stamped at emit time (when the event happened), not at delivery. The delivery id (retry dedupe key) is NOT in the envelope — it travels in the `x-fazerai-delivery` header.

**Emit is best-effort for the domain.** Each seam wraps `emitOutbound` in a try/catch and logs on failure: enqueueing a fan-out row must never break the primary effect (the mirror write, the usage row, the tenant create). When viable the emit runs inside the same scoped tx as that effect.

`heartbeat` is a periodic liveness ping. It rides the scheduler (not a wall-clock cron) via a single self-re-arming `HEARTBEAT` `SchedulerJob` **per tenant** (`webhooks/outbound/heartbeat.ts`): the `dedupeKey` is constant, so `unique(tenant, kind, dedupeKey)` guarantees **at most one job per tenant** no matter how many heartbeat subscriptions exist (0 subs → no job, 1..N → 1 job). It is armed **lazily** — `syncTenantHeartbeat` runs after every subscription mutation and arms the job when an enabled `heartbeat` subscription exists, or cancels it when the last one is gone; the handler also self-terminates (`emitOutbound` returns 0 matched subs → the job ends) as a backstop. Each tick emits `{ at, version }` and re-arms `config.heartbeat.intervalMs` later (`HEARTBEAT_INTERVAL_MS`, default 1 min). Like every emitter, deliveries only go to subscriptions that list `heartbeat`.

### Emit — `emitOutbound(db, tenantId, event, data)`

Called inside the caller's scoped transaction. Wraps `data` in the envelope (above) and inserts one `OutboundWebhookDelivery` (status `PENDING`) per enabled `WebhookSubscription` that lists the event. `data` MUST be the allowlist-sanitized projection. Returns the number of deliveries enqueued.

### REST CRUD — `/api/v1/webhooks/*` (`webhooks.controller.ts` + `subscriptions.ts`)

TENANT_ADMIN. RLS fences every read/write to the active tenant; the secret value never crosses the surface — `secretRef` is a NAME into the tenant vault.

- `GET /webhooks/events` — the closed `OUTBOUND_EVENTS` set (for the UI multiselect).
- `GET /webhooks/subscriptions` — list this tenant's subscriptions.
- `POST /webhooks/subscriptions` — create (`url`, `events[]`, optional `secretRef`, `enabled`).
- `PATCH /webhooks/subscriptions/:id` — update any of those (`secretRef: null` clears it).
- `DELETE /webhooks/subscriptions/:id` — delete (clears its deliveries first, in the same scoped transaction).

Validation: each `event` ∈ `OUTBOUND_EVENTS` (unknown → 400 `errors.unknownWebhookEvent`); `url` passes `assertSafeOutboundUrl` (anti-SSRF, https-only) on create/update. A foreign/missing id under RLS yields 404, never a cross-tenant write. UI: the `/webhooks` page (top-level nav, admin-gated).

### Delivery ledger — `/api/v1/webhooks/deliveries*` (`deliveries.ts`)

TENANT_ADMIN, RLS-scoped, keyset paginated by id desc (same shape as `/v1/logs`). Added by issue #305: before it there was no delivery-facing route at all, so watching for events that never arrived meant reading `outbound_webhook_deliveries` in Postgres — a table whose columns the worker owns and changes without a deprecation window.

- `GET /webhooks/deliveries` — filters `status` (`PENDING|SENDING|DELIVERED|DEAD`, unknown → 400), `subscriptionId`, `event`, `since`/`until`, `limit` (default 50, max 200), `cursor`. `status=DEAD` is the dead-letter view.
- `GET /webhooks/deliveries/:id` — one delivery.
- `POST /webhooks/deliveries/:id/requeue` — put a **DEAD** delivery back in the worker's queue.

**The payload never crosses this surface.** It is the tenant's own data, it does not go through the PII scrub `execution_logs` rows get at write, and the subscriber already receives it at their endpoint — the ledger answers whether the event arrived, not what was in it. Same call as the dead-delivery alert line (#325).

**Requeue semantics.** `status` → `PENDING`, `attempts` → **0**, `nextAttemptAt` → null, `lastError` kept. The reset is what makes it a requeue: `finalizeFailure` gives up at `attempts + 1 >= MAX_ATTEMPTS`, so a row put back at 8 dies on its first post while the same row at 0 earns the full ladder. The count it died at survives in the `webhook` flow-log line. Only `DEAD` is accepted, and the guard is the `status: "DEAD"` in the update's own `where` rather than a branch above it: `SENDING` means a POST is in flight and a second claim would deliver it twice, `PENDING` is already queued, and replaying a `DELIVERED` event is a different promise. Any other status is refused with 409 naming it. The requeue writes one `info` `webhook` flow-log line (`action: "requeued"`, `attemptsBefore`, `subscriptionEnabled`) — `info` never pages, since `dispatchAlertsForEvent` only routes `warn`/`error`.

`subscriptionEnabled` rides on every delivery DTO because the claim joins `enabled = true`: a delivery on a disabled subscription sits at `PENDING` untouched, and without that field a correct requeue is indistinguishable from one that did nothing.

MCP: `webhook_delivery_list`, `webhook_delivery_get` (`mcp:read`), `webhook_delivery_requeue` (`mcp:write`, dry-run by default and audited on apply).

### Delivery worker — `src/modules/webhooks/outbound/worker.ts`

A single-replica tick (`WEBHOOK_WORKER_ENABLED`, `WEBHOOK_WORKER_INTERVAL_MS`) that:

1. **Reaps** stale `SENDING` rows (a crash between claim and outcome would strand them) back to `PENDING` — cross-tenant via `asSuperAdmin`; `attempts` untouched (the claim never bumped it).
2. **Claims** due `PENDING` deliveries cross-tenant (`asSuperAdmin`, the worker has no tenant) with `UPDATE ... FROM (SELECT ... FOR UPDATE OF d SKIP LOCKED LIMIT n) ...` flipping them to `SENDING`. The `enabled = true` join leaves a disabled subscription's deliveries `PENDING` (it does not kill them).
3. For each, **outside any transaction**: `assertSafeOutboundUrl` (anti-SSRF, https-only, no redirects), resolves the per-tenant signing secret via a **tenant-scoped** read (`runScopedOn`, RLS active — least privilege, not the cross-tenant bypass), signs, and POSTs with a timeout.
4. **Records the outcome** scoped to the row's tenant: `DELIVERED` (2xx); back to `PENDING` with `nextAttemptAt` from full-jitter backoff (`nextBackoffMs`); or `DEAD` after `MAX_ATTEMPTS`. An SSRF-blocked URL goes straight to `DEAD` (it can never succeed).

Headers: `x-fazerai-delivery` (the delivery id — a **stable dedupe key**, so at-least-once retries are safe for receivers), and when a secret is configured `x-fazerai-signature` (`sha256=` + HMAC-SHA256 over `"{timestamp}.{rawBody}"`, hex) + `x-fazerai-timestamp` (unix seconds). Receivers verify the timestamp window (anti-replay) and recompute over the raw body. See `signing.ts` (`signOutbound`/`verifyOutboundSignature`); every emit site builds its headers through `outboundHeaders`.

> **Compatibility window.** These headers were named `x-secretaria-*` before the brand rename. Both sets go out on every delivery, carrying identical values, so a receiver configured against either name keeps working. The legacy trio is dropped at `2.0` — point your receivers at `x-fazerai-*` before then.

**Single-replica invariant.** The worker holds a reentrancy guard (`running`) and an interval on `globalThis` (so `bun --hot` does not stack phantom timers); `stopOutboundWorker` runs on `SIGTERM`/`SIGINT`. `FOR UPDATE SKIP LOCKED` already future-proofs the claim, but scaling the app beyond one replica needs a leader election or durable claim before the worker is enabled on every instance. The delivery FK is `ON DELETE CASCADE` at the database (`20260727000000_init`), so what keeps a subscription delete from silently dropping rows the worker is mid-delivery is the service, not the constraint: `deleteWebhookSubscription` clears the deliveries explicitly inside the same RLS-scoped transaction, and that delete is operator-initiated.
