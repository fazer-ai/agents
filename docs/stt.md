# STT (voice-note transcription) + inbound message rendering

WhatsApp customers send voice notes constantly. STT transcribes them so the agent can read and answer; the same pass also shapes every inbound message (audio/image/file markers, quoted-message context) into the text the agent sees, mirroring the n8n "Extrair mensagem" node. On by default per agent (effective only once a provider credential is configured).

## Flow (eager, at message arrival)

```
incoming message with an audio attachment (gate=act)
        │  webhook (processChatwootDelivery)
        ▼
   resolveSttConfig → enabled?  ── no ─→ audio renders as "<…não audível; peça texto>" marker
        │ yes
        ▼
   transcribeInboundAudio:
     download data_url (client.downloadAttachment, anti-SSRF, 404-retry) →
     provider.transcribe (key from vault; withholds a transcription the model was unsure of) →
     cleanTranscription (drop Whisper's Amara.org silence hallucination) →
     client.updateAttachmentMeta { transcribed_text }   ← write-back (no body mirrored in OUR DB)
        │  also stashed on the in-memory event (n.message.transcribedText) for the direct path
        │  AND in the in-process annotation store (chatwoot/annotations.ts) for the flush
        ▼
   arm debounce / direct turn  (the flush re-fetch reads transcribed_text back, overlaying the store)
```

STT runs **before** arming/answering so the debounce re-fetch (and the direct path) get text instead of an empty audio message. On an agent with the contact authorization gate on, it runs **after** the gate instead, and only on the gate's yes for that message; where no gate is asked (a conversation a person holds, a late attachment, an observer's route) the pass asks the gate itself before paying a provider. Same for vision. See [`docs/contact-auth.md`](contact-auth.md#media-waits-for-the-gate-issue-890). The transcription lives only in Chatwoot (attachment meta) plus a TTL-bound in-process cache, never in our DB — consistent with the anti-PII no-body-mirror rule. Best-effort: any STT failure leaves the audio to render as a "please send text" marker and never strands the delivery.

**One read per file, whatever the number of deliveries.** Chatwoot delivers a voice note as a `message_created` and two `message_updated` within ~150 ms, and an update carrying an untranscribed audio counts as late media, so each delivery runs the media pass (on both bot routes and on an observer's). A delivery that finds the transcription in the annotation store reuses it, and one that finds the same file being read waits for that read (`shareInFlight` in `src/lib/locks.ts`, keyed by message and attachment); vision does the same per file, and keeps each file's successful read in the annotation store, under the same 15-minute TTL and active sweep (a failed read is not kept), so a later delivery aggregates exactly the files it carries without paying for the ones already read. The measured cost before this was about 2.5 provider calls per voice note on one production deployment (issue #893). The coalescing is in process: two replicas can still each read a file once.

**The meta write-back is a fork route, not a requirement.** `updateAttachmentMeta` PATCHes a route that only exists on the fazer.ai Chatwoot fork; on upstream Chatwoot it 404s (logged as an `stt`/`vision` warn line, `detail.step = "write_back"`). The transcription still reaches the agent on both paths: the direct turn uses the returned value, and the debounce flush overlays the in-process annotation store (`src/modules/chatwoot/annotations.ts`, stash-at-transcription + overlay-at-re-fetch, 15-minute TTL) over whatever the attachment meta is missing. What the fork ADDS is persistence and visibility: human agents see the transcription in the Chatwoot UI, and it survives an app restart within the debounce window. The same contract covers the vision write-back (`image_description` / `extracted_text`).

**A transient vision failure is asked again, inside the budget one call used to have.** A 503 from the provider used to end the attachment permanently: `extract` was called once, and the "couldn't extract" marker is what entered the conversation history, so no later turn could recover the content (issue #319 — measured at 12 failures in 45 extractions on one tenant, nine of them 503, with the next turn succeeding 16s later on the same credential and model). `src/modules/vision/retry.ts` owns both halves of the answer: **which** failures are worth repeating (`408/429/500/502/503/504/529` and a timeout — never a 4xx about what we sent, and never a connection that would not open, which is as often a base URL that will never resolve), and **how long** each attempt may take. Two attempts with a jittered 500ms backoff, all of it inside `VISION_TOTAL_BUDGET_MS` (60s, the value the single call already carried), so no turn can get slower than it already could. **A ceiling only applies where a measurement backs it.** A non-final attempt on an image at the vendor's own endpoint is capped at 20s (measured live at 2.0-4.4s through gpt-4o, including a 3000x3000 one), which is what funds a second attempt inside the same total. The two unmeasured cases keep the whole budget instead: a **document** (up to 25MB and ~100 pages of provider work) and a **custom `baseURL`** (the operator pointed us at their own hardware — a self-hosted Qwen-VL, a proxy, a regional gateway — which our numbers say nothing about; the provider name does not answer this, since `openai` with a `baseURL` is not the endpoint that was measured). Both still gain a retry whenever the failure leaves room, which an overload usually does. The **last** attempt is never capped by the ceiling either: the ceiling exists to leave room for a next attempt, and after the last one there is none. That is also why there are two attempts and not three — a third would come out of the same total, and what it costs is the length of the last one. Measured live: with the vendor endpoint, a first attempt aborted at 20s and the second answered at 23.4s; with a `baseURL` set, the single attempt kept the full 60s exactly as before this change. `stt` has the same gap and is NOT covered by this: no retry of a provider call exists anywhere else in the codebase.

**The download races Chatwoot's own storage write.** `message_created` carries the attachment's `data_url` but is dispatched *before* ActiveStorage finishes writing the file, so the eager download (it fires ~70ms after the webhook) can hit the storage service ahead of the bytes and get a **404** — the voice note then goes untranscribed and the customer is asked to "send text" for an audio that is perfectly fine. `downloadAttachment` therefore takes `retryOnMissing`, retrying **404 only** on a bounded backoff (250/750/1500ms, ~3 extra seconds worst case, inside a typical debounce window); every other status still fails immediately. The eager STT/vision path opts in; the interactive media proxy (`getConversationMedia`) does **not**, because there a 404 means the file is genuinely gone and the operator must not wait out the backoff. A download failure now also emits its own `stt`/`vision` line (warn + `status: error`, `detail.step = "download"`): it sits outside the `withFlowStage` span, so before this it left **no** trace on the Logs page at all.

## Generic provider abstraction (`src/modules/stt/providers.ts`)

The OpenAI `/audio/transcriptions` multipart shape is a de-facto standard, so `openai` and `openai-compatible` (Groq, self-hosted faster-whisper, …) share one adapter (baseURL switch). Gemini (inline base64 → `generateContent`, key in `x-goog-api-key`) and ElevenLabs (`/speech-to-text`, `xi-api-key` + `model_id`) get thin adapters. **Adding a provider = one function + one registry entry**; a future generic/declarative provider slots behind the same `SttProvider` interface without touching callers. `SttError` never captures the response body (PII). Provider is selectable per agent; the API key is a **vault** entry referenced by a stable `vault:<id>` ref (renaming the secret never breaks the agent).

| Provider            | Default model       | Endpoint                                   | Auth             |
| ------------------- | ------------------- | ------------------------------------------ | ---------------- |
| `openai`            | `gpt-4o-transcribe` | `…/v1/audio/transcriptions`                | `Bearer`         |
| `openai-compatible` | `whisper-1`         | `{baseURL}/audio/transcriptions`           | `Bearer`         |
| `gemini`            | `gemini-3.5-flash`  | `…/models/{model}:generateContent`         | `x-goog-api-key` |
| `elevenlabs`        | `scribe_v2`         | `…/v1/speech-to-text`                       | `xi-api-key`     |

### A transcription the model was unsure of is withheld (issue #1014)

On silence, noise or speech buried under noise the models do not return nothing: they return fluent text, in any language and script. On one production deployment, 3 of 678 voice notes in 7 days came back as Greek, Cyrillic or Hangul with `language: pt`, and the agent answered them. The script is not the signal: the same measurement below shows `gpt-4o-transcribe` inventing "Das ist gut." and "The sky is blue." and Whisper inventing Portuguese ("Legendas pela comunidade Amara.org", "Tchau!", "e aí"). What separates them from speech is the confidence the provider reports, so that is what decides.

- **gpt-4o transcription models** (`gpt-4o-transcribe`, `gpt-4o-mini-transcribe`) are asked for `include[]=logprobs`. A mean token logprob below -1.0 withholds the whole text.
- **Whisper models** (any model id containing `whisper`, through `openai` or `openai-compatible`) are asked for `verbose_json`. A segment with `no_speech_prob` above 0.7 or `avg_logprob` below -1.0 is dropped, which is how Whisper itself skips a stretch with no speech; when no segment is left, the text is withheld.
- **ElevenLabs Scribe** (issue #1021) is asked with `tag_audio_events=false`, and any audio event that still comes is dropped from the words: by default Scribe writes `[silêncio]`, `[ruído]`, `[ruído branco]` or `[música suave]` into the transcript when there is no speech, and the adapter used to hand that to the agent as if the customer had said it. The mean word logprob (entries of type `word` only) withholds the text under the same -1.0 floor.
- **Any other model, Gemini and OpenRouter** are asked exactly as before and nothing is withheld: a compatible server may not know either parameter, and the other APIs report no confidence through these adapters. A compatible server that answers `400` to the confidence request is asked again without it.

A withheld transcription reaches the agent as the inaudible-audio marker, is never written back to Chatwoot, and is logged on the `stt` line as numbers only (`withheld: "low_confidence"` beside the signal and its value). Every transcription that reports a confidence logs it the same way, withheld or not, so the real scores the threshold faces stay visible; an empty one logs `empty: true`, which is how a provider that heard no speech (Scribe, `gpt-4o-mini-transcribe`) is told apart from a withheld one, and the playground writes the same line under `source=playground`. The empty result is kept in the annotation store like a transcription, so the other deliveries of the same voice note do not draw a new sample, which could be a hallucination the model happened to be sure of.

Measured live in 2026-10 against the OpenAI API, on synthetic voice notes (pt-BR speech from macOS voices, alone, with leading noise, with trailing silence and buried under noise; silence and white, pink and brown noise from 1 to 8 s): on `gpt-4o-transcribe` every silence and noise sample was transcribed as text, with a mean token logprob between -1.76 and -7.0, speech buried under noise between -1.39 and -3.54, and clear speech between -0.001 and -0.16. On `whisper-1`, silence and noise segments reported `no_speech_prob` of 0.82 or more and speech 0.69 or less. `gpt-4o-mini-transcribe` returned empty text on silence and noise. On ElevenLabs `scribe_v2`, silence, noise and breathing came back empty or as an audio-event tag alone (empty with `tag_audio_events=false`), never as invented speech; clear speech averaged a word logprob of -0.65 or higher, and speech buried under heavy noise came back as fluent Portuguese that was never said ("A inflação vai continuar a pressionar...", "Em janeiro de 2015...") averaging -0.46 to -1.19, so on Scribe the floor withholds only part of that case (3 of 8 runs). The cost of the threshold is a one-word note the model was unsure of ("Tá" came back as "다" or "が"): it is withheld, and the agent asks the customer to repeat.

## Inbound rendering (`src/modules/chatwoot/render.ts`)

`renderInboundMessage` turns one message into agent-facing text, shared by the direct path (`runAgentTurn`) and the debounce flush so both behave identically:

- **text** → as-is.
- **audio** → `<mensagem-de-audio>{transcription}</mensagem-de-audio>`, or a "não audível; peça texto" marker when transcription is empty/failed.
- **image/document with a vision extraction** → `<imagem>{description}</imagem>` / `<documento>{text}</documento>` (from `image_description` / `extracted_text`, meta or in-process overlay). **Both blocks when a message carries both**: it used to be an `else if`, so a photo plus a PDF rendered the photo and the document vanished without a trace (issue #691).
- **image without an extraction** (vision off/failed) → marker asking the customer to send text/audio.
- **location** (a WhatsApp pin) → `<localização latitude="…" longitude="…" titulo="…">` — coordinates + place title from the attachment (`coordinates_lat`/`coordinates_long`/`fallback_title`); the model forwards them as ordinary tool args. `(0,0)` is the column default, treated as "no coordinates"; a pin with neither coordinates nor title falls back to the generic marker.
- **other file** → `<usuário enviou um arquivo do tipo '{type}'>`.
- **quoted/replied-to** (`content_attributes.in_reply_to`) → prefixed with the referenced snippet, resolved from the re-fetched page (flush) — omitted on the direct path (no page).

**EVERY attachment is analyzed, not the first (issue #691).** The eager pass took `firstVisualAttachment`, which did what its name said: a customer who attaches the receipt, the ID and a screenshot in one message had one of the three described, and the reply asked for what was in the other two. Nothing reported it — the `vision` stage wrote one `ok` line per turn, because from the pipeline's point of view nothing had been skipped. Measured on one production mailbox over 30 days, **50.6% of the conversations that arrive with an attachment carry more than one** (3,667 conversations, mean 1.98, max 70). The extractions run in PARALLEL, because the per-file budget is 20s for an image and 60s for a document and five of those in series is a turn nobody waits for; a cap of **8 per message** bounds the album case. What the pass did not read — over the cap, or attempted and failed — is NAMED to the model as `<anexos-nao-lidos quantidade="N">` rather than dropped, since a model told nothing answers as if the message had those files fewer. It is a COUNT on the message (`attachmentsUnread`), phrased by the renderer, because it has to cross the debounce re-fetch like every other marker; and it appears only ALONGSIDE something that was read, because when nothing was, the "send it as text" marker already asks for the same thing. `parseChatwootMessages` reads the meta of every attachment and labels each part with its file name when there is more than one, so two receipts read as two orders instead of one document contradicting itself; a single attachment keeps the bare text, byte for byte. One unreadable file never costs the others, and it is counted rather than hidden: a readable neighbour used to bypass the unreadable-file marker and the failure vanished. The in-process annotation store is written ONCE per message, after the loop, with the aggregate — it is keyed by message, so a per-extraction write is a singleton wearing the aggregate's clothes, and a flush landing mid-flight would overlay it over the complete meta. For the two vision fields that stash WINS over the fetched page, because the meta write-back is best-effort per attachment and a partial page must not suppress the complete aggregate; absent or past its TTL, the meta answers as before. That rule is only sound because the aggregate is complete BY CONSTRUCTION: an attachment that already carries an extraction is reused rather than paid for again, so a delivery recovery — which re-runs the pass from scratch — cannot publish an aggregate poorer than the metadata it overrides. Reusing it is also what makes recovery cheap. `firstAudioAttachment` still has this shape and is NOT covered: several audio attachments in one message transcribe one.

**An image attached after its message is read by the flush (issue #952).** Some transports create the message first and attach the file seconds later (the Chatwoot fork's UAZAPI inbox fetches the media in a job), so the eager pass on `message_created` finds nothing to read and the update that carries the file never drives vision (see `hasPendingInboundMediaUpdate`). The debounce flush re-reads the thread before the turn, and there it extracts what is still unread and was never TRIED (`fillMissingMedia: "untried"`): the eager pass marks a message it tried with its count of unread files in the stash, so a file that failed on arrival is not paid for a second time on the flush. The re-engage opens everything unread (`"all"`), a failure included, because a person asked for that tail. The flush's job deadline reaches every paid call it starts: past it no message, batch or provider attempt begins, a message the deadline cut before anything was read is left unmarked so the job's retry reads it, and one read in part keeps its reading and names the files that were cut. Three limits: a restart between arrival and flush empties the stash, so that flush retries a failed file once; a file cut by the deadline beside a sibling that was read is named as unread and not read again; and a file that lands after the flush, or on a conversation without debounce, is still not read, since nothing after the creation drives a turn for it.

**An image kept inside an email body is read too (issue #864).** Chatwoot's mailbox does not make an inline image an attachment: with an HTML body that references it by `cid:`, the reference becomes the blob URL in `content_attributes.email.html_content.full`; with no HTML at all (Apple Mail on iPhone sends the photo as a bare inline part), `<img src="<blob url>">` is appended to `text_content.full`. The message carries no attachment, and on one production mailbox that was 2,397 of the 4,197 email messages that declared one in 14 days. Both readers of a message (`visualAttachments` on the delivered event, `parseChatwootMessages` on the REST page) now add the Chatwoot blob URLs of the body (`emailBodyImageUrlsFrom`) to its visuals (the `src` of each `<img>`, its attributes tokenized as HTML does, so a bare value counts and a `data-src` does not: an absolute URL, or a path starting at `/rails/active_storage/`, which is relative to the Chatwoot host and is resolved against the instance's base URL before the host check, as the dashboard renders it; in both, the parsed and normalized pathname must stay under `/rails/active_storage/`, since the downloader sends the admin token to its own host and a query or a `../` must not reach an API route, and an `http:` image is refused for an `https:` instance for the same reason; among the URLs that pass, one per signed blob id is kept), AFTER the real attachments (a body image naming a blob that is also attached is dropped, by signed id, so the file is read once, as the attachment), with no attachment id: nothing is written back, since there is no attachment to write to. They share the cap of 8 with the attachments and get what the attachments left, in batches: an ornament is only known after its download, and it gives its slot back to the next batch. What is left past the cap is downloaded only to tell an ornament apart, in batches no larger than the cap and never sent to the provider, so only what is not an ornament is counted as unread. No more than three caps' worth of body images (`BODY_IMAGE_MAX_DOWNLOADS`, 24) are downloaded per message across both passes, and whatever is left unlooked-at counts as unread, since it cannot be called an ornament; a body image that 404s is not retried as a freshly posted attachment is, because the mailbox stored the blob before the message existed. Their count (`bodyImages`) makes a message whose only content is a body image answerable, and a body image that fails is named in `<anexos-nao-lidos>` beside the text, an audio note or a pin, since no attachment marker carries it; the notice is left out only where a branch already said a file could not be read. An email with no text whose body images were all ornaments (or with vision off) renders as an email with nothing readable, not as a file to ask for again. Body images leave no meta, so a pass that went through them says so in the stash (`bodyRead`, also on the delivered event), even when all of them were ornaments: on the turn's re-read a message with body images is extracted again only without it, and attachment meta alone never counts as covering them; the pass then reuses what the meta already has. Two kinds of body image are not the customer's and are neither read nor counted as unread: a URL whose host is not this Chatwoot's (dropped against the instance's base URL before the cap, so it takes no slot and is never counted as overflow; when that URL cannot be read, no body image is), and an ornament (`isDecorativeImage`: at most 160px on both sides, or at most 160px on one and at least three times as long on the other, read from the PNG/GIF/WebP/JPEG header; an image whose size cannot be read, like HEIC, is kept; a type vision cannot read, like SVG, is not an ornament and is counted as unread). Measured on the same mailbox, 4,663 body images: that rule drops 2,437, among them one store logo quoted 1,490 times (908x140) and ~900 icons (144x144), and only 15 of the 1,429 images that appear once, all icons and banners.

The flush's `pendingIncoming` now includes voice notes (empty content + an attachment), not just text. `parseChatwootMessages` reads `attachments[].meta.transcribed_text` (REST list) so the re-fetch surfaces the write-back; `overlayMediaAnnotations` then fills anything the meta is missing from the in-process store (upstream Chatwoot, where the write-back route does not exist).

## Configuration

Per-agent, in `agent.settings.stt` (free-form bag, validated by `readSttConfig`): `enabled` (default `true`), `provider` (default `openai`), `model` (`""` → provider default), `language` (ISO, default `pt`), `credentialRef` (a `vault:<id>` ref), `baseURL` (openai-compatible). Surfaced in the agent editor's **Behavior** tab and writable over REST (`PATCH /v1/agents/:id`) + MCP (`agent_settings_get`/`agent_settings_set`, the `stt` block; the MCP transport translates the `vault:<id>` ref to/from the entry **name** at its boundary — agent-friendly — never the secret). No env vars — the credential is a per-tenant vault secret.

## Known limits

- Images/documents without a vision extraction (vision off or failed) become a "send text/audio" marker; the eager vision pass, when enabled, fills `image_description`/`extracted_text` under the same write-back + overlay contract as STT.
- Attachment download follows storage redirects (S3) without re-validating the redirect target (TOCTOU); the data_url comes from the HMAC-authenticated webhook of the tenant's own Chatwoot.
- **A flush waits for a voice note still being transcribed** (issue #1026). The flush armed by one message re-reads the thread while a later voice note's own delivery is still transcribing it, and that note would render as the "not audible" marker, so the model asks the customer to resend words that land a moment later; nothing takes that reply back. The eager pass announces each transcription it runs (`openTranscription` in `chatwoot/annotations.ts`, opened before the config is read and closed when the provider answers or the pass gives up), and `selectAnswerableBurst` waits for the announced ones of its burst, once for the whole burst, at most `FLUSH_TRANSCRIPTION_WAIT_MS` (8 s) and never past the job's deadline. A message's wait ends as soon as its words (or an empty result) are stashed, so the Chatwoot meta write-back that follows is not waited for. The annotations are overlaid again before rendering whether or not anything was waited for, since a transcription can settle between the thread read and the wait. Past the bound the marker stays, as before. What it does not cover: a delivery that has not yet reached the eager pass when the flush re-reads (the window between the webhook and `runEagerMedia`), media held back for the contact authorization gate, and a flush in another process (single-replica, `docs/deploy.md`).
- The in-process annotation store is per-process memory: an app restart inside the debounce window loses the overlay on upstream Chatwoot (the fork's meta write-back survives restarts). Bounded by the single-replica deploy invariant (`docs/deploy.md`). Expiry is **active**, not lazy: a rescheduled (unref'd) sweeper deletes annotations past the TTL even when no new voice note arrives, so an idle process does not keep customer speech in memory until restart; a size cap bounds bursts as a second limit.

Read before touching `src/modules/stt/*`, `chatwoot/render.ts`, the message parser, or the eager-STT seam in the webhook.

## Bun derives a multipart file's MIME from the filename extension

In Bun's `multipart/form-data` round trip (`request.formData()`), the `File.type` the server sees comes from the **filename extension**, ignoring the `type` the browser set on the `File`/`Blob`. Measured on Bun 1.3.14: a file sent as `recording.webm` with `type: "audio/webm;codecs=opus"` arrives as `type: "video/webm"`, because the mime DB maps `.webm` to the video container even for pure audio. Also `.ogg`→`audio/ogg`, `.m4a`→`audio/x-m4a`, `.bin`→`application/octet-stream`, and no extension→`""`.

This reaches every multipart endpoint (playground STT, branding image upload, RAG documents): never validate an audio or image by `file.type.startsWith("audio/")` alone — a MediaRecorder voice note would be rejected. Accept `video/webm` and normalize it to `audio/webm` before anything downstream, and on the frontend name the file with the real container extension (Chrome→webm, Firefox→ogg, Safari→m4a) so the derived mime matches. Fixed once in `src/modules/playground/service.ts`, with a NOTE in the code.
