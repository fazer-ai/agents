# Dashboards

Pro edition. Panels an admin arranges over the account's conversations and AI usage, each dashboard at its own address (`/dashboards/<slug>`). Not to be confused with the operator dashboard at `/` ([`dashboard.md`](dashboard.md)), whose blocks are fixed.

## Model

- `dashboards`: `name`, `slug` (unique per tenant), `default_range` (`24h`, `today`, `yesterday`, `7d`, `30d`), `refresh_seconds` (`60`, the default, or `300`: every period is relative, so there is no off; a dashboard saved at `0` before this moved to `60`), and the TV mode's `tv_rotation` (dashboard ids, in order) and `tv_seconds` (10 to 600, default 30).
- `dashboard_panels`: `position`, `width` (`third`, `half`, `two_thirds`, `full` of a six-column grid; one column on a phone), `title`, `description`, `visualization` (`number`, `timeseries`, `bars`, `table`) and `query` (JSON).
- `viewer_emails` and `viewer_domains` on `dashboards`: who may open it at its public address (below). `dashboard_viewers` (one row per address per tenant), `dashboard_viewer_sessions`, `dashboard_viewer_visits` (last access per dashboard) and `dashboard_viewer_codes` hold the sign-ins.
- `dashboard_data_sources`: the account's HTTP sources (below): `name` (unique per tenant), `url`, `method`, `headers`, `body`, `credential_ref`, `cache_seconds`.
- Every table carries the RLS policy pair and cascade from the tenant and the dashboard. **The schema is identical in Free**: only the code is dropped by the derivation, so a Free database upgraded to Pro needs no migration and the two never diverge.

## The query

`query` is validated by `panelQuerySchema` (`src/modules/dashboards/query-schema.ts`), a closed vocabulary rather than SQL, so a panel can only ask what the module knows how to answer under the tenant's RLS and the metrics budget.

- `source: "conversations"`: counts the mirrored `conversations` created in the window, or with `scope: "unresolved"` the ones open, pending or snoozed right now, whenever they began: the period does not change that panel, a number has no previous period (`previous: null`, "Not resolved right now" under it), a grouping says `now: true` and its column reads "Not resolved now", and neither a time grouping nor `compare` is accepted. `groupBy` is `none`, `time` (`hour`/`day`, buckets filled in the viewer's timezone), `attribute` (a Chatwoot custom attribute key), `label`, `inbox`, `status` or `outcome` (the operator dashboard's: `outcomeSql()` among the conversations the agent ran on, `agentRanSql()`, and `agent_not_involved` for the rest, so the categories add up to every conversation and "resolved by the agent" and "handed off" equal `GET /v1/metrics/kpis` for the same window). Filters: inboxes, one label (case-insensitive), one attribute equal to a value.
- An `attribute` grouping takes two options. `multiple: true` reads the value as a comma-separated list (`"55340,55945"`): each value is a row, a conversation counts once in each of its values (`"1, 1"` is one), and the rows can add up to more than the conversations, as labels do. `labelKey` names each row by another attribute, its most common value among the row's conversations (ties by the value): an attribute that holds an id shown by the name another one holds. The row then shows that name with its own value beside it, so two rows of one name stay apart; a row none of whose conversations has the name shows its value.
- `link` (conversations grouped by `attribute` or `label`): an http(s) address with `{value}`, which each row opens in a new tab with its value URL-encoded in place of the placeholder (`GroupRow.href`). For example, an attribute that lists the ids of the events a conversation asked about, with `multiple`, named by the attribute that holds the event's name, opens each event's page at `https://tickets.example/evento_{value}`.
- An `inbox` grouping (conversations or usage) names a row by its inbox. When another row of the same grouping has an inbox of the same name (two connected Chatwoot accounts with a "SAC WhatsApp" each), both rows also carry `account: {id, name}` and read "SAC WhatsApp · <account>" ("Account 7" while the account's name has not synced), in the console, at the viewer address and on a TV. Every row of the grouping counts, the ones the limit folds into `other` included; a name no other row has stays alone, and the key stays the inbox id.
- `source: "usage"`: `measure` is `cost` (`llm_usage.cost_usd`, the same ledger and the same total as the operator dashboard's cost by model), `cost_per_conversation`, `calls` or `tokens`, grouped by `none`, `time`, `model`, `agent` or `inbox`. A number with nothing in the period nor in the previous one shows the empty state ("nothing matches"), as a grouping with no rows does: a removed inbox or a value no conversation has would otherwise read as a bare 0. A cost result carries how many calls have a price and how many do not, for the window and for each value, group and bucket (`priced`, `unpriced`): a cost sums the priced calls only, so a value, group or bucket whose calls are all unpriced shows "No price" instead of zero, a chart leaves that bucket as a gap, and a bucket of free-model calls is a zero with calls behind it, which keeps the panel from reading as empty. `cost_per_conversation` is the operator dashboard's "Cost per conversation": the priced cost over the distinct conversations with a model call in the window, bucket or group (a conversation created before the window counts when a call of it falls inside; one with no model call never counts), with the same `priced` and `unpriced` counts. It is a ratio, so its `value` is `null` where there is no figure (no priced call, which shows "No price", or no conversation, which shows "No conversations", and a window with neither in both periods is the empty state), never a zero; its groups do not add up, so `other` is 0 and `total` is the window's own figure. It is drawn as money with up to four decimals, as on the operator dashboard.
- `compare: { threshold }` (conversations, categorical groupings only): each group also gets its daily average over the 7 days before `since` (`usualDaily`), the ratio of the period to that average (`ratio`, null when the group has no history) and `hot` when the ratio reaches the threshold. The ratio compares rates: the period's count is divided by its length in days, so "today" at 10:00 is compared as a pace per day. When the period is still running and is not a whole number of days, `compare.projected` is true and the panel says under it that the ratio is projected; a closed period ("yesterday") or a full 24 hours is not projected and shows no note. This is the "which event is getting more contacts than usual" panel a high-volume customer-service team asked for.
- Categorical groupings return the top `limit` rows (max 50) and the remainder as `other`.
- `source: "http"`: `sourceId` (one of the account's HTTP sources) and `map`, which reads its JSON by path. `{kind: "value", value, previous?}` draws a number; `{kind: "series", items, time, value}` a time series (or a table), each item's instant as the source gave it, an ISO instant with its offset on a real calendar day (`bucket: "instant"`; one without an offset, or off the calendar, is a mapping problem); `{kind: "rows", items, name, value, key?, link?}` bars or a table, in the source's order, with `limit` and `other` as a grouping's. See "HTTP sources".

`queryFitsVisualization` decides which visualization can draw which grouping (a number needs `none`, a series needs `time`, bars need a category, a table takes anything but `none`), and refuses the options that need a kind of grouping (a comparison or what is not resolved now over time, a link over an inbox or a status). The API refuses a mismatch with 422, and the editor only offers what fits.

A stored query that no longer parses (written by another version) is returned as `query: null`, and its data route answers `{ broken: true }`: the panel says so and asks to be edited, instead of failing the whole dashboard.

## HTTP sources

For figures that do not live in the agents database: an event's whole record, counts an account keeps in its own system. An admin registers a source (`/dashboards/_sources` in the console, `GET`/`POST /sources`, `GET`/`PATCH`/`DELETE /sources/:sourceId` and `POST /sources/:sourceId/test` over REST, the `dashboard_source_*` tools over MCP): a name, an `https` URL, `GET` or `POST`, headers, a body for a `POST`, a vault credential and a cache time from 0 to 300 seconds. `{since}` and `{until}` (ISO instants) and `{tz}` (IANA zone) in the URL (URL-encoded) and in the body (as written) become the panel's window. The code is `src/modules/dashboards/data-sources.ts` (the rows) and `http-source.ts` (the request and the mapping).

- **The request runs on the server**, after the metrics transaction that read the panel and its source, so a slow source holds no metrics connection: the console, a viewer and MCP all read through it, and a viewer gets the mapped figures only, never the URL, the headers or the body. The destination rules are the HTTP tools' (`assertSafeOutboundUrl`): https, no private, loopback, link-local or metadata address, checked after DNS, and on every redirect (at most 3, followed by hand; a redirect to another origin drops the credential and every header but `Accept` and `Content-Type`, since any header an admin wrote may authenticate). The answer is capped at 1 MB and the request at 8 s or what is left of the metrics budget, whichever comes first; past either, the panel shows its own error and the others render.
- **The credential** is a vault reference, sent the way its type says (`Authorization: Bearer` for a bearer token, its header or query parameter otherwise), or as `{{secret}}` written in a header's value. Header values are shown to the account's admins and logged by name only in the audit trail. The vault's "where is this used" lists the sources that reference an entry.
- **Mapping.** Paths are dot keys with `[n]` (or `.n`) for array items, read inside each item when the item is an array's; `$` alone is the whole answer, for a source that answers with a bare array or value. A number accepts a JSON number or a numeric string. What the mapping cannot read is reported in `problems` as data, by path, issue and the count of items it failed in (`{path: "data.items[].total", issue: "notNumber", rows: 3}`, `{path: "data.total", issue: "missing"}`; the issues are `missing`, `notArray`, `notNumber`, `notInstant`, `notName` and `notLink`), worded on the panel in the viewer's language, and those items are left out: never drawn as zero. A row's `key` is unique within the answer: a repeated name or key takes the first free `#n`. A link that is not `https` is reported and the row is not a link.
- **Cache.** Within a source's cache time, one request per source, window and definition serves every panel and viewer; a request in flight is shared, and a failed answer is not kept. Editing a source starts afresh. The test action is never cached.
- **Removal** is refused with 409 naming the panels that read the source; a panel write refuses a source that is not the account's (422), under the same lock a removal takes. The console page is `/dashboards/_sources`: `_` is never in a slug, so no dashboard's address can be it.

## Routes

All under `/api/v1/dashboards`, `TENANT_ADMIN`, in `src/api/v1/dashboards.controller.ts`. `GET`/`PUT /:id/viewers` read and replace the viewer list (with the public address and who has opened it), and `POST /:id/viewers/:viewerId/revoke` ends that person's sessions. `GET /:id` takes the id and `GET /slug/:slug` the address's slug; a slug is never read as an id, so a slug made only of digits still opens its own dashboard. Each panel reads its own data (`GET /:id/panels/:panelId/data?since&until&tz`), so a panel past `METRICS_TIMEOUT_MS` shows its own 503 and the others still render. `POST /query` runs an unsaved query, which is the editor's live preview. Every write is audited (`dashboard.*`, `dashboard_panel.*`).

The window is cut by the client in the viewer's timezone (`src/client/pages/dashboards/period.ts`), once per period choice and per refresh, so every panel of a screen reads the same instants. The server refuses windows longer than 92 days or with `until <= since`.

A time series drawn as a chart is `SeriesChart.tsx`, loaded with `lazyWithReload`: the dashboards route is a static import of the app, so a static import of Recharts there would load it on every screen. `biome-plugins/no-static-chart-import.grit` refuses a static import of `recharts` or of `pages/dashboard/charts` outside the chart modules. Every panel write on the dashboard screen (order, width, the editor's save and a removal) goes through one queue, in the order the admin made them, so a write still queued cannot land after a later one and undo it.

## TV mode

A dashboard on a screen across a room: `/dashboards/<slug>/tv` in the console (the TV mode action on the dashboard, outside the console's layout, with its session) and `/d/<account>/<slug>/tv` at the public address (a viewer's session; a member is sent to the console's TV address). `TvDashboard.tsx` draws both.

- **No chrome.** No sidebar, header, editing, settings or sharing. The way out ("Exit TV mode", to the dashboard's page in the console, or its public page at `/d/`) shows while the pointer moves and hides 3 seconds after, and Escape leaves too; the name, the period (the dashboard's default), how long ago the last read that worked was ("Updated less than a minute ago", then in minutes, so the text changes only when something stalled) and a wall clock without seconds whose separator blinks once a second, which is what shows a frozen page, are always on screen. The status dot sends out a ripple each time a read works, so a screen still being fed shows it without anything blinking all the time; with reduced motion neither animates. Panels keep the dashboard's layout and widths, with larger type (`TvModeContext`), sized by the viewport so 1366x768, 1080p and 4K all fit without a horizontal scroll.
- **Refresh** on the dashboard's interval (every 60 seconds for a row still read at `0` before its migration), whether or not the tab is visible; the definition is read again with it, so a panel added in the console reaches the screen.
- **Offline.** A read that fails keeps the last figures. When every read of the screen's round (a refresh, or a change of stop) fails, the header says so once, in its own line ("Offline since 14:02"), and each card keeps the time its own figures are from ("Figures from 14:01"), since a stop the rotation came back to may hold older ones; when one panel fails among live ones, that panel says it under its title ("Offline since 14:02. These figures are from 14:01."). The next read that works clears both, with no reload. A panel whose first read fails has no figures to keep and says it waits for the next refresh; a stop the rotation comes back to is not a first read, and shows the figures it last read there (for the panel's same version) until a read works. A TV never shows the error a console panel does.
- **Deleted.** A failed read is not a deletion: only a 404 on the dashboard's definition is. The console's TV whose own dashboard is deleted reloads, and lands on "Dashboard not found"; another stop of the rotation deleted while on screen leaves it on the next refresh, paused too. The public address reloads on any 404.
- **Rotation.** The dashboard's settings list the dashboards a screen alternates and the seconds each stays (`tvRotation`, `tvSeconds` over REST and `tv_rotation`, `tv_seconds` on `dashboard_update`). A dashboard read returns `tvSequence`: the saved ids that still exist, in order, and at the public address only those whose list admits the viewer. The screen starts on its own dashboard (put first when the list does not name it) and skips one it cannot read, so a removed or closed dashboard is never shown as an error. A rotation that names another account's dashboard is refused (422). On screen, the header shows the brand logo and names the rotation's dashboards with the current one marked, and its rule fills over the stop's seconds until the next one, so a change never comes as a surprise. Clicking a name or the arrow keys change the dashboard and start its time over; the pause button or the space bar stop the rotation, and a paused screen says "Paused" in the header instead of showing the bar, so a screen someone left paused is visible from the room. The next dashboard reads its panels in a hidden layer and fades in over half a second once they have answered (or after 4 seconds), so a change never shows loading placeholders; with reduced motion the change is immediate.
- **Sessions.** The console's TV stays as long as the console's session; a viewer's stays as long as theirs, and when the account revokes it the next read takes the screen to the address's sign-in, which returns to the TV address. The screen asks the browser to keep it on (Wake Lock) where allowed, and asks again when the page shows after being hidden, since the browser releases the lock then. The rotation is read from the dashboard the screen was opened on each time it is read again, so a rotation changed in the console reaches a running screen.

## Viewer access

A dashboard opens at `/d/<account slug>/<dashboard slug>` to people outside the account, without a console login. The account lists who may: e-mail addresses, and domains matched whole (`parceiro.com` admits `ana@parceiro.com`, never `ana@outroparceiro.com` nor `ana@parceiro.com.evil.com`). The list is edited in the dashboard's settings and in its Share button, and over REST and MCP.

- **Sign-in.** A 6-digit code sent by e-mail (15 minutes, one use, 5 wrong guesses charged to every live code of the address, 50 s between two codes and 10 a day per address and account), or Google (`GOOGLE_CLIENT_ID`, a verified address; the first sign-in binds the Google subject to the address). The code route answers the same whether or not a code went out, and answers before any of the work behind it (the admission, the cooldown and cap, the insert, the mail), so neither its body nor its time says who is on a list. With no mail provider the code is not offered, with no `GOOGLE_CLIENT_ID` Google is not, and with neither the screen says there is no way in. Both routes are in the credential rate-limit bucket.
- **The session is not a user.** A viewer is a `dashboard_viewers` row, never a `users` row or a membership. Its cookie (`fazerai_dashboard_viewer`, an opaque token whose sha256 is stored, 30 days) has the path `/api/d/<account slug>`, so the browser sends it nowhere else, and nothing outside `src/api/features/dashboard-viewer` reads it: every console route, the API and the WebSocket see no session. Its reads run under the dashboard's tenant with RLS, and the list is checked on every read, in the same transaction as the figures, so removing an address cuts a live session on its next request. A dashboard the list does not admit answers 404, the same as one that does not exist; an account slug that does not exist answers like "not signed in". A panel's figures are read entirely on the metrics pool, the account's address included, under the request's metrics budget.
- **Members.** An admin of the account (or a SUPER_ADMIN) opening the address with the console's session is taken to the dashboard in the console, with its sidebar, its breadcrumb and its editing. The read carries the account's id for a member only, and the redirect carries it as `?switchTenant`, so a console with another account selected opens this dashboard and not one of the same slug there.
- **Audit.** `dashboard_viewer.sign_in` (actor type `dashboard_viewer`, the viewer row's id), `dashboard.viewers_update` with both lists, `dashboard_viewer.revoke`. A save that moves nothing (the same list, settings, panel or order) writes no row, as everywhere in the trail.
- **Revoking** ends every open session of that person in the account. The list is untouched: taking the address off it is what keeps them out.

Mail goes through `src/api/lib/mail` (from bunfire): `MAIL_PROVIDER` (`resend`, `smtp`, `console`, `none`), `MAIL_FROM`, `MAIL_REPLY_TO`, `RESEND_API_KEY`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_SECURE`/`SMTP_USER`/`SMTP_PASSWORD`. Without a provider, production sends nothing and dev logs the message; the suite uses an in-memory outbox. The three deploy composes forward all of them, empty for the default.

## MCP

Every route above has a tool: `dashboard_list`, `dashboard_get` (by id or slug), `dashboard_create`, `dashboard_update`, `dashboard_delete`, `dashboard_panel_add`, `dashboard_panel_update`, `dashboard_panel_remove`, `dashboard_panels_reorder`, `dashboard_panel_data`, `dashboard_query_preview`, `dashboard_viewers_get`, `dashboard_viewers_set`, `dashboard_viewer_revoke`, `dashboard_source_list`, `dashboard_source_get`, `dashboard_source_test`, `dashboard_source_create`, `dashboard_source_update` and `dashboard_source_delete` (`src/modules/mcp/write-dashboards.ts`). `dashboard_query_schema` serves a panel query's JSON Schema, generated from the schema a write parses with, and which grouping each visualization draws; it is listed to read and write tokens alike, and the panel tools publish `query` as an open object instead of inlining the union. Their windows are ISO instants with an offset, parsed as REST parses them. A token of an AGENT is refused, as the console refuses that role. A write previews by default, and the preview runs the same service call in a transaction that is rolled back (`previewBase`), so it refuses exactly what the apply would and shows the row the apply would leave.

## Free edition

`DashboardsRoutes.tsx` is paired with `DashboardsRoutes.free.tsx`, which shows the feature with `<ProGate feature="dashboards"/>`. The sidebar item stays in Free. The module, the controller, the pages and the tests are Free-only drops in `tooling/derivation/manifest.ts`; the controller's mount and the audit actions are `@full-only`. The catalogs are JSON, which carries no markers, so the Free derivation prunes the `dashboards` namespace (`pruneLocaleNamespaces` in the manifest, `tooling/derivation/locales.ts`): every key of it with no literal call left in the Free sources goes, as `i18n:extract` would remove it there, and the title and upgrade copy stay.

The viewer controller, its page's route (`PublicDashboardRoute`, a redirect home in Free), the MCP module and their tests are Free drops too, and the MCP registration is `@full-only`, so the Free `tools/list` has no dashboard tool. The mail library and the viewer tables stay in Free, unused, so the schema is the same.

In the console the list and each dashboard are in the header's breadcrumb (`Dashboards > <name>`), the name registered by the screen once it loads, and the sidebar item sits right before Channels.
