# Routing — BrowserRouter + the `serve.routes` carve-out

Why deep-link refreshes work and why `/api/*` is not served as HTML. Four pieces of plumbing are load-bearing, and three of them exist because of a Bun runtime behaviour that has no opt-out. Includes the smoke test to run on every Elysia upgrade.

The template uses `BrowserRouter` (in `src/client/App.tsx`) so URLs are canonical (`/settings/profile`, not `/#/settings/profile`). To make refreshes on deep routes work, `src/app.ts` registers a catch-all `.get("/*", indexHandler)` that serves `index.html` for any non-API, non-asset request.

Four pieces of plumbing are load-bearing:

1. **`serve.routes` carve-out** on the root Elysia constructor:
   ```ts
   new Elysia({ serve: { routes: { "/api": false, "/api/*": false } } })
   ```
   Bun's native routes table is consulted before Elysia's `fetch` handler. When `.get("/*", htmlBundle)` is registered as a static handler, Bun stores the `HTMLBundle` directly in that table, and any `/api/*` request would be served as HTML before Elysia could route it. The `false` entries disable Bun's interception so `/api` paths fall through to Elysia. The bare `/api` carve-out covers requests without a trailing slash (Bun treats `/api` and `/api/` as separate keys). Asset paths under `/assets/*` and hashed bundle files at the root do **not** need carve-outs because `staticPlugin` registers them as more-specific entries in the same table and Bun picks the more specific match.

2. **GET 404 guards for `/api` and `/api/*`** registered between the API group and the catch-all:
   ```ts
   .get("/api", ({ set }) => { set.status = 404; return { error: "Not Found" } })
   .get("/api/*", ({ set }) => { set.status = 404; return { error: "Not Found" } })
   .get("/*", indexHandler)
   ```
   Once Bun delegates to Elysia, the catch-all `/*` *would* swallow GETs for missing API paths and serve `index.html` (prod) or `{}` (dev — because the HTMLBundle, returned from a dynamic Elysia handler, is JSON-serialized). The explicit GET guards make missing API paths return JSON 404 instead. `.all()` doesn't work here — Elysia's trie gives `.get()` wildcards higher priority than `.all()` wildcards. Non-GET methods on missing API paths are caught by the `onError` NOT_FOUND handler (the GET-only catch-all never matches them). WebSocket upgrades for `/api/realtime/*` are also unaffected because `.ws()` registrations outrank `.get` wildcards.

3. **Dev vs prod `indexHandler`**. In prod the catch-all serves the pre-built `dist/index.html` (`productionIndexHandler` in `src/api/lib/static-cache.ts`, see the cache policy below). In dev the document is the `HTMLBundle` from `public/index.html` (the conditional `await import("@/public/index.html")` only runs in dev), so Bun's bundler resolves the `<script>` reference and HMR keeps working on deep routes, **and since Elysia 1.4.30 it is registered straight on Bun's routes table, not through `.get("/*")`.** That release makes `createNativeStaticHandler` bail out on any route with hooks *before* checking for an HTMLBundle, and every route here inherits helmet and the locale middleware, so through `.get("/*")` the bundle never reaches Bun's native router and Elysia serializes it as JSON: every SPA path answers `{}`. `devSpaRoutes` in `src/app.ts` puts `{ GET: indexHandler }` under `serve.routes["/*"]`, with a `false` carve-out for `/api`, `/api/*`, `/.well-known/*` (the OAuth discovery documents, which MCP clients reject as HTML) and every entry of `public/` (derived from the directory at boot, so `favicon-*.png` and `/assets/*` keep reaching `staticPlugin` as their real media types). GET only, so other methods still fall through to Elysia's 404. What a carve-out hands back with no file behind it, like a missing `/assets/` file, reaches Elysia's own `/*`, which in dev is `developmentIndexHandler`: a static-asset path gets the same 404 `no-store` as production instead of the bundle serialized as a 200 under the asset's day of cache. The dev document is served natively and carries no helmet headers; API responses and the production document keep them.

4. **`publicPath: "/"` in `build.ts`**. Without it, Bun emits relative asset paths (`./index-abc.js`) in `dist/index.html`. A browser at `/settings/profile` would resolve those against the current pathname (`/settings/index-abc.js`), 404 → SPA catch-all returns `index.html` → `<script type="module">` chokes on HTML. Absolute paths from the document root sidestep this. When `BUN_PUBLIC_CDN_URL` is set the CDN URL takes over (same effect, different origin). The dev server already emits absolute `/_bun/...` paths automatically, so this only matters for the prod build.

**Cache policy of the document and the assets** lives in `src/api/lib/static-cache.ts`, and three things about it are load-bearing. The production catch-all sets `no-cache` on the document itself, because a deep route matches no suffix rule and would otherwise go out with no `cache-control`, letting a browser keep a shell that points at bundles the next deploy removed. A GET whose last segment carries a static-asset extension (a list, not "any dot", so `/users/jane.doe` still reaches the SPA) and that is not a real file answers **404 `no-store`**: `staticPlugin` with `alwaysStatic` registers only files that exist, and anything else would get the shell stamped with the asset's policy by the path's shape, `immutable` for a year on HTML under a removed bundle's `.js` URL. And the `onAfterHandle` writes the policy **onto the `Response`**, not into `set.headers`, and only for a 200 or 304: `staticPlugin` answers with its own `Response` carrying `public, max-age=86400`, and Elysia fills in only the `set.headers` keys a returned `Response` lacks, so through `set.headers` a hashed bundle never becomes immutable. `immutable` is withheld from anything under `/assets/`, which `build.ts` copies verbatim from `public/assets/` (`inter-variable.woff2` has the shape of a hashed name without being one), and `/api/*` is left to its own handlers. The CDN worker applies the same rule, and `tests/workers/cdn.test.ts` runs its real `fetch` against the app's `cacheControlFor`.

**A tab older than the server.** The document is `no-cache`, but a tab opened before a deploy keeps running the bundle it loaded until it reloads, and nothing in that bundle changes on its own. So every response names the build the server serves: `build.ts` gives each build an id (`scripts/lib/build-id.ts`: the version plus a hash of what the bundle is built from, `src/`, `public/`, the lockfile and the public build env, so a release rebuilt from changed sources is another build, while the CDN upload and each image architecture, which CI builds separately from one tree, inline the same id), inlines it into the bundle as `BUN_PUBLIC_BUILD_ID` and writes it to `dist/build.json`; the production server reads that file at boot and sends `x-app-build` and `x-app-version` on every response (`src/api/lib/served-build.ts`; a `dist/` without the file sends neither, and dev sends neither). The console's API client hands every response to `client/lib/staleBuild.ts`, which compares the header with its own id, and window focus asks `/api/health` (at most every 15s) so an idle tab finds out too. While they differ, the shell shows a banner with Reload and the sidebar's version line, which keeps showing the tab's own version, offers the same reload behind a reload icon (never the dot, which belongs to the newer-release link that it replaces while the tab is stale); the next change of screen (the pathname: a filter, a search or an anchor rewrites only the query or the hash and never counts) with nothing unsaved (no page guard, no dirty modal, no modal whose save is in flight (`busy`) and no held draft, `hasUnsavedChanges()` in `unsavedGuard.ts`; a composer whose unsent input no guard covers, like the playground's typed text or a recording running or paused, holds it with `useHeldDraft` while it is on screen, every write through the console's API client (POST, PUT, PATCH or DELETE) holds it from the request until its answer has been read (`holdingWrites`, the client's `fetcher`, so it holds whichever screen started it and outlives that screen: a reload aborts the request and drops the answer, which for a password change is the cookie of the replacement session), and what the server does not have yet between two requests (a file or a recording read into its multipart body, a recording stopped by the operator or by leaving the editor before the browser hands it over) holds itself with `holdWhile`/`holdInFlight` until it settles; a read holds nothing; none of these arms a prompt, they only stop the reloads the console starts by itself) reloads by itself. This is separate from the release check in `UpdatesContext`, which compares the installed server with the newest release and goes quiet right after a deploy, which is exactly when the tab is behind. A dynamic import that fails goes through `importWithReload`/`lazyWithReload`, which reload once per build (a `sessionStorage` key holding the build that already reloaded) and surface the error after that, so a chunk that keeps failing cannot loop. `biome-plugins/require-reload-on-dynamic-import.grit` refuses a dynamic import in `src/client` outside those two.

**Two smokes probe all of this against a booted server**, because no unit test sees the routing table as Bun builds it. `bun dev:smoke` boots the development server and checks the document, a deep route, a favicon, an `/assets/` file, the OAuth discovery documents and the API's JSON answers; `bun smoke:prod` (after `bun run build`) boots the production server, adds the cache policy to each probe, and checks that the build `/api/health` names is the one `dist/build.json` records and the served bundle inlines. Both boot with the workers off, so they never claim jobs from the database in `.env`. CI runs both in `build-check.yml`.

The root cause lives in the Bun runtime (the static `routes` table has unconditional priority over `fetch` and there is no opt-out for HTML bundles): see [oven-sh/bun#17595](https://github.com/oven-sh/bun/issues/17595), [#17363](https://github.com/oven-sh/bun/issues/17363), [#23999](https://github.com/oven-sh/bun/issues/23999). The Elysia-side discussion and the carve-out pattern are tracked in [elysiajs/elysia#1515](https://github.com/elysiajs/elysia/issues/1515) (root-cause analysis by @a-rebets, 2025-11-11) and [#1347](https://github.com/elysiajs/elysia/issues/1347). Confirmed working on Elysia 1.4.28.

**On every Elysia upgrade**, run `bun dev:smoke` and `bun smoke:prod`, and re-run the smoke test below before bumping in `main`:

1. In a temp dir, install the upgraded Elysia version
2. Register a static `.get("/*", htmlBundle)` plus a `.get("/api/health", () => ({ ok: true }))` (no carve-out)
3. Fetch `/api/health`: if it returns HTML, the bug is still present and the carve-out is still needed; if it returns JSON, the bug is fixed

If the bug is fixed, simplify `src/app.ts` by removing the `serve.routes` carve-out, drop this section, and add a regression test. Issue/PR status is not a reliable gate, only the runtime check is.
